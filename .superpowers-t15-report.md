## Red proofs

Every new test was shown red before it was accepted:

- Scenarios 1–5: the fake `git` was made to skip `.mcp.json` / `.claude/commands/hello.md` and stop
  printing "Cloning into", the loopback server answered `Version: "0.0.0"`, the fake `gh` dropped the

  failed (the seventh, scenario 2 sandbox, asserts the device's limits rather than the fixture, and is
  pinned by `mode: sandbox` / `network.kind: allowlist`). Restored byte-for-byte afterwards.
- Scenario 6: the scripted `sudo …` was replaced with `echo hi` and the outside write with a
  workspace write; both scheduled-task tests failed on the deny assertions.
- Review-before-launch in scenario 3 is pinned by the denied `rm -rf /` launch (no
  "Started background task", `review.decision: deny`) and by the successful launch's
  `review.rule: allow.git`. Review was deliberately not disabled for that test: the fake sandbox
  would then execute the command on the host.

## Fix round 1 (review `.superpowers-t15-review.md`)

### 1 (HIGH, safety) the background `rm -rf /` is safe by construction and the assertion is real

`packages/kernel/test/sandbox/review-acceptance.test.ts`:
- writes a no-op `rm` (`FAKE_RM`) at `<root>/bin/rm`, beside the fake `git` / `gh`. That directory is
  first on every fake-sandbox exec `PATH`, so if a launch-then-deny regression ever executes
  `rm -rf /`, it deletes nothing. The review is textual, so `deny.root-delete` still fires and the
  test still pins the intended rule.
- asserts the deny left **no `capybara.background_tasks` row** for the conversation (the row is
  inserted by `markStarted` as soon as a launch starts) and **no `exec`** for the conversation in
  the fixture's `ops.log` (an exec's log line is written before its result resolves, so it is
  present by the time the call's terminal event is). The "Started background task" text absence is
  kept, but it is no longer the only proof. A later assertion shows the allowed launch's exec under
  the same conversation, so the empty check cannot be vacuous.

Red proof: a launch-then-deny regression necessarily writes the launch row and then the exec log;
both assertions fail on it, without depending on any text.

### 2 (HIGH, safety) no destructive command on the owner's machine

Checklist section 3: the local-device held-command step is now `sudo true` (non-destructive; an
approval card or a hold, no task started). `rm -rf /` appears only under "the **cloud Docker device
only** (a disposable container, never the local machine)".

### 3 (MEDIUM) the socket proxy actually starts

Checklist section 2 now uses `docker compose -f docker/compose.dev.yaml --profile sandbox up -d
sandbox-proxy`; the service is behind `profiles: ["sandbox"]`, so `127.0.0.1:2375` is published.

### 4 (MEDIUM) the dual-replica tests pin the executing replica

`review.dual.test.ts` `openAskScene` now starts `[["api","worker","gateway"],["api"]]`: replica 0
is the only worker and gateway, replica 1 serves the API only. The first message goes to replica 0,
so the run, the ask and the resume all execute on replica 0's worker; the decision is posted to
replica 1. The session-grant test posts its second message to replica 0 (the reviewing worker), so
the grant must be read from PG. A per-process cache regression now fails deterministically.

### 5 (LOW) the `approvals` table is checked

`review-pipeline.test.ts`: `fireScheduled` returns `{ terminal, conversationId }`;
`expectUnattendedDeny` is async, takes the conversation id and asserts `capybara.approvals` has no
row for it. The inline "unattended run asks no one" test checks the table too.

### 6 (LOW) the vacuous token regex is gone

`review-acceptance.test.ts` scenario 5 no longer asserts `/gh[pousr]_…/`: the fake `gh` prints only
the device prompt, and the kernel copies raw exec output into the result by design, so that regex
could never fail. The real `loginCode`-absence guard stays, with a comment saying why.

### 7 (LOW) the corpus carries the loopback command

`review/corpus/acceptance-2026-11-13.jsonl`: added `curl http://127.0.0.1:2375/version` with
`outcome: allow`, `rules: ["allow.network"]`.

### 8 (LOW) checklist coverage and nits

- sections 1 and 2 gained cloud-device repeat steps; the Results table has cloud rows for both
  variants of scenarios 1 and 2;
- the table now has OS and Model columns (as line 15 promises), plus a note that scenarios 5 and 6
  are cloud-only by design;
- the unattended deny quote is the product's exact "do the work another way or leave it for the
  person.";
- section 9 quotes the real `capybara-device mode sandbox` output and states separately that every
  command is still reviewed.
