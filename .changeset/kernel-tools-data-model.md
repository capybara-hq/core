新增工具相关数据表（迁移 `0010_tools.sql`：`apps`、`app_tools`、`tool_grants`、`conversation_tool_grants`、`approvals`、`questions`、`tool_outputs`，`runs.status` 增加 `waiting`，`orgs.settings`）、`tools` 配置段与 `http.publicUrl`；组织动作新增 `apps.manage`（admin）、`apps.use`（guest）、`approvals.decide`（guest），均仅限用户主体；错误码 `app.*`、`approval.*`、`question.*`、`tool_output.not_found`、`credential.missing`。

应用凭据（`Credentials`）：信封加密存入 `capybara.secrets`（命名空间 `kernel`，键前缀 `credentials:app:`），支持 bearer / api_key / basic / headers 静态认证注入，读出的值登记日志打码，缺凭据抛 `CredentialMissing`（`credential.missing`）。

应用管理与工具注册表：新增 `/api/v1/orgs/:orgId/apps`（`GET` 列表 / 详情用 `apps.use`；安装、`PATCH`、软删、`POST /:appId/refresh`、`PUT /:appId/credentials/org` 用 `apps.manage`；`PUT|DELETE /:appId/credentials/me` 用 `apps.use`，只动本人的个人凭据）。安装时可带 `credential`，先用它（不落库）连接连接器并 `listTools` 拍快照，连接失败返回 502 `app.connect_failed`（消息只含上游错误类名）且不写任何数据，成功后应用、工具快照、凭据与审计在同一事务写入；工具默认策略按注解推导（只读 → allow，其余 → ask），`spec_hash` 为规范化 JSON 的 sha256 前 16 位；slug 由名称推导或显式给出（`^[a-z][a-z0-9_]{0,23}$`，不含连续 / 结尾下划线），冲突 409 `app.slug_taken`；工具 key（`<slug>__<tool>`）超过 64 字符或含非法字符时该工具停用并在响应 `issues` 与工具的 `issue` 中给出原因，不截断。`ToolRegistry.forAgent` 解析内置 / 插件 / 应用工具，过滤停用、待复核、已删除、插件未在本组织启用等情况并返回 `unavailable` 原因；`connector(kind)` 按 `Connector.kind` 查找连接器。`Kernel.tools` 暴露注册表与凭据服务。

Agent 定义可引用工具：`tools` 接受内置（`{kind:"builtin",name}`）/ 插件（`{kind:"plugin",plugin,name}`）/ 应用（`{kind:"app",appId,tools:"all"|string[]}`）引用（M2 保存的 `tools: []` 仍合法），新增 `toolPolicies`（按工具 key 只能收紧为 `ask` / `deny`）；创建时省略 `tools` 默认带 `ask_user`、`read_tool_output`，修改不注入默认值。保存时校验引用存在（内置按 `BUILTIN_TOOL_NAMES`，插件须已注册，应用须属本组织且未删除、点名工具须存在）、key 不冲突、`toolPolicies` 的键属于该 agent，否则 400 `validation_failed`（path `tools.<i>` / `toolPolicies.<key>`）。运行时每步经 `ToolRegistry.forAgent` 解析工具，按 key 排序放进 `ModelRequest.tools`（收尾调用不带工具），`model_call.request.tools` 记录 `{key, specHash}`，token 估算计入工具定义；有不可用工具时写英文 `reminder`（`The following tools are unavailable in this run: …`，同一 run 内内容不变不重复写），运行不失败。新增事件 `tool_call_started`、`tool_result`，构建请求时 `tool_result` 还原为紧随其 assistant 消息的 user 消息（同一步合并、按调用顺序）。`ModelStepDeps` 新增 `tools`，`ModelStepInput` / `LoopContext` 新增 `orgId`。

工具执行管线（`ToolPipeline`，LangGraphLoop 的 `tools` 节点）：按顺序处理本步 assistant 消息里的每个 `tool_call`——解析参数中的 `{"$output": "<id>"}` 引用（不存在 / 过期 / 跨组织 → 错误结果）→ ajv（JSON Schema 2020-12）校验参数（错误含全部路径与完整 inputSchema）→ 策略判定（`decidePolicy` 可注入）→ 写 `tool_call_started`（幂等键 `tool_started:<runId>:<callId>`）后执行（`tools.timeoutMs` 超时与 run 中止信号合并传给处理函数 / 连接器；应用工具每次调用打开并关闭连接器会话；应用级熔断器 `capk:breaker:<orgId>:<appId>`，连续失败 `tools.breakerFailures` 次后打开 `tools.breakerOpenSeconds` 秒，计数与打开状态都带 TTL）→ 渲染结果（文本拼接，图片 / 资源链接给出类型说明，畸形结果给出说明）→ 超过 `tools.outputSpillChars` 的结果存为输出存档（`tool_outputs`，保留 `tools.outputRetentionDays` 天），模型只见预览与存档 id → 写 `tool_result`（幂等键 `tool_result:<runId>:<callId>`）并在同一事务写审计 `tool.called`（detail 只有 toolKey、isError、durationMs）。续跑时已有结果的调用跳过，「有开始无结果」的调用记为结果未知、不再执行；未知 / 不可用工具返回明确错误（启用 `tool_search` 时提示用它加载）。新增事件 `connection_required`（发起人未连接个人凭据的应用；组织凭据缺失只返回错误说明）。`LoopContext` 新增 `agentId`、`triggerAccountId`，loop 依赖改为 `LoopDeps`（`ModelStepDeps` + `toolPipeline`），`Kernel.tools` 暴露 `outputs` 与 `pipeline`，`ToolRegistry.handler(source)` 返回内置 / 插件工具的处理函数。

工具策略与审批：`ToolPipeline` 默认改用 `createDecidePolicy`（`tools/policy.ts`），在执行那一刻实时判定（R5）——重读 `app_tools.default_policy` / 状态（应用或工具已不可用 → `unavailable`，见下）、agent 当前版本的 `toolPolicies`（与运行版本取更严者，缺字段视为空）与授权表；纯函数 `decide` 取组织默认、agent 收紧、R3 固定询问（`R3_FIXED_ASK_TOOL_KEYS`，M3 为空，及 `annotations.requiresUserInteraction`）中最严者，记住的授权只能把 `ask` 放行为 `allow`、`spec_hash` 不一致即失效，不越过 `deny`、对固定询问无效。`ResolvedTool` 新增可选 `requiredRole`（R1）：发起人实时角色不足时转为按角色升级的审批（`approverRole` = 所需角色、`requestedFor` = null），非成员拒绝。迁移 `0011_approvals_spec.sql`：`approvals` 增加 `spec_hash`、`app_id`。新增 `ApprovalsService`（`Kernel.tools.approvals`）：`request` 建 pending 审批（`expires_at` = 现在 + `tools.approvalTimeoutHours`，按 (run, call) 幂等）并写 `approval_requested`；`/api/v1/orgs/:orgId/approvals`（`approvals.decide`）：`GET ?status=` 列出当前用户能处理的审批（`requested_for` = 本人，或按角色升级且本人角色足够、不是该运行发起人——R2），`GET /:id` 详情（工具名、应用、参数、agent、会话路径、过期时间），`POST /:id/decision {decision, scope?, note?}` 在事务内锁审批行，非 pending / 已过期 → 409 `approval.already_decided`，看不到 → 404 `approval.not_found`，按角色升级的审批只能 `once`（否则 400），同一事务写状态、授权（`session` → `conversation_tool_grants`，`always` → `tool_grants`）、`approval_decided` 事件（幂等键 `approval_decided:<id>`）与审计 `approval.decided`，提交后调用可注入的 `onDecided`；`GET /api/v1/orgs/:orgId/me/tool-grants` 与 `DELETE …/me/tool-grants/:agentId/:toolKey` 查看 / 撤销本人的「以后都允许」授权（审计 `tool_grant.revoked`）。新增事件 `approval_requested`、`approval_decided`。

运行等待人处理时暂停并从快照续跑：`LoopOutcome` 新增 `{ kind: "suspended", waitingFor: { kind: "approval" | "input", id, expiresAt } }`，`ToolPipeline.runStep` 返回 `{ kind: "done" } | { kind: "suspended", waitingFor }`（新依赖 `approvals`、`questions`）。策略为 `ask` 时 tools 节点建审批（按 (run, call) 幂等）、写 `approval_requested` 后暂停（不写 `tool_call_started`），LangGraph checkpoint 停在 tools 节点之前；处理函数返回 `input_required` 时校验表单（`validateInputForm`，不合规 → 工具错误）与 state（≤ 16 KB），建输入请求（新 `QuestionsService`，`Kernel.tools.questions`）并写 `question_asked {step, callId, questionId, form, expiresAt}` 后暂停；同一调用最多连续请求输入 3 次（第 4 次 → `Tool requested user input too many times.`），再次调用照常写 `tool_call_started`（第 n ≥ 2 次的幂等键带 `:<n>` 后缀）并传 `ctx.resume = {state, answer}`（超时 / 取消时 `answer` 为 null）。worker 收到 `suspended` 后释放会话锁与组织配额、条件更新 `running → waiting`、保留 checkpoint，并在维护队列 `cap-kernel-maintenance` 投递延迟到 `expiresAt` 的 `wait-timeout-<waitId>` 任务（只在 worker 角色处理）；续跑 `Waits.resume` 是条件更新 `waiting → queued`（且已无 pending 等待），只有一个调用方成功并投递 jobId 为 `run-<conversationId>-resume-<waitId>` 的运行任务，人工决定（`onDecided` / `onAnswered`）、超时任务与暂停后的复查竞争时恰好续跑一次。续跑时审批结果：`approved` → 执行；`denied` / `expired` / `cancelled` → `The user denied this tool call.` / `Approval timed out after <h>h; treated as denied.` / `The run was stopped while waiting for approval.`。`POST .../abort` 对 waiting 的运行直接取消等待（`approval_decided{cancelled}` / `question_answered{cancelled}`、取消说明的 `tool_result`）、写 `run_aborted` 并删除 checkpoint；暂停到置 waiting 之间到达的中止经中止标记补查（`RunAbort.requested`）。等待期间的新消息不新建运行，续跑后作为插话吸收；`ensureRun` / 孤儿判定（waiting 不是孤儿，续跑任务按 `runs.job_id` 查、宽限期从 `queued_at` 起算）/ stalled 处理（任务失败时运行已是 waiting 则不标记失败）都认得 `waiting`。等待时长不计入 `runtime.maxRunSeconds`。迁移 `0012_run_waits.sql`：`runs` 增加 `waiting_since`、`waited_ms`、`job_id`、`queued_at`，`questions` 增加 `attempt`（唯一键改为 (run_id, call_id, attempt)）。`QuestionsService.answer(questionId, accountId, answer, orgId?)`：只有运行发起人（否则 404 `question.not_found`），非 pending / 已到期 → 409 `question.already_answered`，答案不符合表单（`validateAnswer`）→ 400 `validation_failed`，写 `question_answered {questionId, callId, answer, byAccountId, outcome}` 后续跑（HTTP 接口在后续版本）。策略判定新增 `{ unavailable: 原因 }`：调用时应用 / 工具已不存在、停用、删除或待审核，返回 `Tool "<key>" is unavailable: <原因>.`，不再说成策略拒绝。`GET /approvals?status=pending` 不再列出已到期的审批。新增事件 `question_asked`、`question_answered`；`Kernel.runs.waits` 暴露等待服务。
