## What was built

- Pure parser `parseDeviceCode` recognises only `gh auth login --web`'s fixed output: the
  `! First copy your one-time code: XXXX-XXXX` line (upper-case letters / digits) plus the
  `https://github.com/login/device` token. Anything else returns `null` (P-D13).
- `Bash` sets a kernel-internal `loginCode` field on its result. That field never enters the
  written `tool_result` or any model request (proved in the pipeline test).
- The pipeline appends one `device_code { step, callId, url, code }` event before the call's
  result, idempotent under the deterministic id `device_code:<runId>:<callId>`.
- Request building skips `device_code` explicitly (display-only), matching `network_blocked`.
- Web: the timeline puts a `device-code` entry under the command's group, and the thread draws
  `DeviceCodeCard`: the URL as an open link, the code in mono (`<kbd>`), a copy button (two-second
  `Copied`, manual-copy fallback), localized zh/en (en `chat.deviceCode.*`).
- No changeset added: the branch already carries `.changeset/kernel-auto-mode.md` (and the
  matching SDK/device changesets).

## How the brief's traps are answered

- **`loginCode` leaking to the model:** it lives only on the in-process `BuiltinResult`; the pipeline
  reads it into the `device_code` event and never copies it into the `tool_result` payload. The
  pipeline test asserts the result has no `loginCode` property, and that a `buildModelRequest` over
  the real run's events equals the same request with the `device_code` event removed.
- **Written twice under a retry / resumed run:** the append carries
  `idemKey = device_code:<runId>:<callId>`; the test re-appends the same event with that key and the
  log keeps exactly one.
- **Over-matching (P-D13):** the parser is output-only and requires both the anchored gh sentence
  with a well-formed code and the exact GitHub device URL; negative fixtures cover `az login`'s
  device flow, a URL without the code, a code without the URL, malformed codes, a similar sentence
  from another program, and a `…/device-help` lookalike URL. The pipeline additionally re-checks
  the URL against `GITHUB_DEVICE_LOGIN_URL`.
- **Parser purity / fixtures:** pure function, English comments, recorded `gh auth login --web`
  output inline (gh 2.63, GitHub.com, 2026-11-14).

## Fix round 2 (scoped re-review follow-ups N1, N2)

**N1 — a prompt split across `TaskOutput` reads never matched.** `task-output.ts` parsed only the
new slice after the read offset advanced, so a non-blocking read landing between `gh`'s code line
and its URL line (or a read cap splitting them) saw one half and no later read saw both.
`readWindow(offset, cap)` (exported, `READ_TAIL_BYTES = 4096`) now starts every read up to 4 KiB
before the offset and reports `skip` (the already-delivered prefix); the tool displays/advances by
`data.subarray(skip)` only and parses the whole window (`data`), so a pattern spanning the boundary
matches. The buffer is `cap + 4 KiB` at most, independent of the task's output size; per-call local
state only (nothing persisted, no cross-request state). Deterministic ids and the per-code dedupe are
unchanged; `loginCode` stays kernel-internal and display-only, and is only produced when a read
delivered new bytes.

**N2 — `Bash` pointed at `Read` for background output.** The description now says "Read the output
with TaskOutput", with no mention of `gh` or logins (neutral, same for every background task).

**Tests added.**
- `packages/kernel/test/tools/sandbox/task-output.test.ts` (new): read 1 ends mid-prompt and read 2
  carries the rest (the new bytes alone do not match; the window does), the code line and URL line in
