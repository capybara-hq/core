# Writing plugins

Terms: a **plugin** is the install and distribution unit: a bundle of at most one **extension** (in-process code, `.agents/skills/writing-extensions`), skills, connector templates and agent templates (`agents/<name>.md`, sub-agents a parent agent can dispatch), possibly depending on other plugins. The **catalog** is what a deployment has imported for its orgs to install; it holds one kind of item, the plugin. A **marketplace** is a `marketplace.json` listing importable plugins.

Spec: `docs/superpowers/specs/2026-10-22-package-ecosystem-design.md` §4, §5.2, §6, §10.

This skill covers what core owns: the plugin format as the SDK parsers and the kernel readers enforce it, the `capybara-plugin` toolchain (`packages/plugin-tools`), the catalog (readers, network rules and git access of marketplaces, enterprise import and review, the CLI, Claude Code translation, bootstrap plugins, org install, upgrade and uninstall). **Writing, packing, versioning and releasing a plugin** is in [writing-plugins in capybara-hq/plugins](https://github.com/capybara-hq/plugins/tree/main/.agents/skills/writing-plugins); the official plugins live in that repository (the official marketplace `https://github.com/capybara-hq/plugins.git`). Core's only plugin is `plugins/model-fake`; the fake extensions under `packages/testing/fixtures/extensions/*` use the same layout.

## Layout

A plugin is a directory, packed into an npm-pack tgz:

```
<plugin>/
  .capybara-plugin/plugin.json   the plugin manifest (required in the source; the packer adds `extension`)
  package.json                   npm metadata; `version` equals plugin.json `version`
  skills/<name>/SKILL.md …       skills (scanned unless plugin.json lists them)
  connectors/<id>.json           connector templates (scanned unless plugin.json lists them)
  agents/<name>.md               agent templates for sub-agents (scanned unless plugin.json lists them)
  src/index.ts                   extension source (optional; bundled into dist/index.mjs)
  migrations/*.sql, ui/**        extension migrations and UI files (optional)
  README.md, LICENSE, NOTICE
```

`pnpm pack-plugin <dir> [--out <dir>]` (`capybara-plugin pack` of the published `@capybara-hq/plugin-tools`, `packages/plugin-tools`; outside this repository `npx capybara-plugin pack <dir>`, and `capybara-plugin check` runs the plugin checks) packs it: it validates the source `plugin.json`, bundles `src/index.ts` when it exists (a plugin without one is **declarative**: no esbuild runs and the package has no `peerDependencies`), ships `skills/**`, `connectors/*.json`, `agents/*.md`, the listed paths and icons, writes `package.json` (no `capybara` section) and the final `.capybara-plugin/plugin.json` with `extension = { entry: "./dist/index.mjs", manifest: <static extension manifest>, migrations?: "./migrations", ui?: "./ui" }`, and produces a reproducible tgz. The packer fails early on a missing listed path, a skill directory without `SKILL.md`, an invalid `connectors/*.json` or `agents/*.md` and an empty plugin (`a plugin must contain an extension, a skill, a connector template or an agent template`).

The format and its validation are pure functions in the SDK: `packages/plugin-sdk/src/plugin-manifest.ts` (`parsePluginManifest`, `parseConnectorTemplateFile`, `PLUGIN_MANIFEST_LIMITS`), `plugin-package.ts` (`validatePluginPackageJsonFor`, `validateConnectorTemplate`), `marketplace.ts` (`parseMarketplaceManifest`, `marketplaceEntryVersion`). The kernel reads a plugin in `packages/kernel/src/catalog/plugin-package.ts`: `readPluginPackage` unpacks a tgz and hands its files to `readPluginFiles(files, opts)`, which a git tree goes through too, so tgz and git share every check. The plugin is always hostile input, every problem is collected, and nothing is written until all checks pass.

- **From git, `package.json` is optional** (spec §4.1 needs it only for npm): the package name is then null and the item is identified by its git source (host, repo, path), so an unrelated repo with the same plugin name never adds versions to it. A plugin **with an extension** still needs `package.json` (its `peerDependencies` ranges are checked), and its whole folder is packed into a deterministic tgz (`packPackageTgz`) and read like an upload. A folder without `plugin.json` but with `skills/` is a **skills-only plugin**: named after the marketplace entry (a direct import: the last segment of `path`, else of the repo URL without `.git`), versioned per spec §5.3, published by the marketplace's `owner.name` (else `<host>/<owner>` of the repo). An archive without `plugin.json` is a skills-only plugin the same way.
- **Content digest** (`contentDigest`, computed for every import, stored on the version): sha256 hex over the sorted file list, one line `path + "\0" + sha256(content) + "\n"` per file, so a tgz and a git tree of the same files have the same digest whatever the archive bytes.
- **Versions** (`versions.ts`, spec §5.3): `plugin.json` version, else the entry's `version`, else `0.0.0-git.g<sha12>` (git) / `0.0.0-sha256.h<12>` (archive). Re-importing an imported release with **another** digest records `<version>+git.<sha12>` (git) or `<version>+sha256.<12>` (archive, npm, upload) and never overwrites the imported version; the same digest is `catalog.version_exists` ("already imported"). Ordering is semver ignoring build metadata, ties by import time; ranges ignore build metadata.

**JSON Schemas**: `packages/plugin-sdk/schemas/plugin.v1.schema.json`, `connector-template.v1.schema.json` and `marketplace.v1.schema.json` are generated from the zod schemas by `pnpm gen:package-schemas` and drift-checked by `check:package-schemas`; regenerate them after changing a schema. Files may set `$schema` to `https://capybarahq.com/schemas/<file>`. Rules JSON Schema cannot express (path safety and nesting, uniqueness, no self-dependency, the extension's name and version equal to the plugin's, template static rules, unique `(name, version)` in a marketplace) are decided only by the parsers, so external CI must run them too.

## Toolchain (`capybara-plugin`, `@capybara-hq/plugin-tools`)

The published package `@capybara-hq/plugin-tools` (`packages/plugin-tools`) is the one toolchain for official and third-party plugins; a plugin repository adds it as a devDependency. Every relative path resolves against the current directory; a root is either a repository with `plugins/*` or a single-plugin directory (its own `.capybara-plugin/plugin.json`).

| Command | What it does | In core |
|---|---|---|
| `capybara-plugin pack <dir>… [--all <root>] [--out <dir>]` | the packer described above; byte-reproducible, so the sha512 of a pack is known before publishing; `--bootstrap <bootstrap.json>` packs a kernel bootstrap manifest instead (below) | `pnpm pack-plugin <dir>` (any plugin directory you give it), `pnpm pack-plugins` (core's `plugins/*`: `model-fake`), `pnpm pack-bootstrap` |
| `capybara-plugin check [--root <dir>] [--plugins <glob>] [--base <ref>]` | every plugin-scoped check: the SDK boundary (`check:deps`), extension state (timers, module-level state), permissions (`perm-hooks` / `perm-ui` / `perm-storage`), plugin packing (`plugin-pack-dropped` etc.), the tool design rules, migrations; with `--base`, an edited applied migration fails | part of `pnpm check` (core runs the same code on `plugins/model-fake` and the fake extensions) |
| `capybara-plugin sync-versions [--root <dir>] [--plugins <glob>]` | copies each plugin's `package.json` version into its `plugin.json` and extension manifest (the packer requires them equal); run after `changeset version` | `pnpm sync:plugin-versions` (inside `pnpm version-packages`) |
| `capybara-plugin marketplace --write\|--check [--base <rev>] [--root <dir>] [--file <path>] [--plugins <glob>]` | keeps `.capybara-plugin/marketplace.json` listing one npm entry per public plugin version, with the sha512 of its reproducible pack; listed versions are left to the release gate, `--base` keeps published entries append-only and checks added ones against the packs (`marketplace-missing`, `marketplace-integrity`, `marketplace-append-only`, `marketplace-invalid`) | not used in core; the plugins repository's Version Packages PR and CI |
| `capybara-plugin release [--dry-run] [--provenance] [--auto] [--root <dir>] [--plugins <pattern>]... [--marketplace <file>]` | the npm half of the release: publish plan, dist tags, skips versions already on npm, plugins as their plugin tgz; `--plugins` limits the plugins, `--marketplace` (default the repository's `marketplace.json` when present) checks every plugin pack against its entry before the first publish (`release.integrity_mismatch`) | `pnpm release` |

## `plugin.json`

```json
{
  "$schema": "https://capybarahq.com/schemas/plugin.v1.schema.json",
  "schemaVersion": 1,
  "name": "crm",
  "version": "1.2.0",
  "publisher": "Acme",
  "description": "CRM tools for sales teams",
  "displayName": { "zh": "CRM", "en": "CRM" },
  "icon": "./icon.svg",
  "license": "Apache-2.0",
  "homepage": "https://acme.example/crm",
  "dependencies": [{ "name": "crm-core", "version": "^1.0.0" }],
  "skills": [{ "path": "./skills/crm-notes", "pinned": true }],
  "connectorTemplates": [{ "path": "./connectors/crm-mcp.json" }]
}
```

- Objects are strict: an unknown key is an error, not ignored (`$schema` is allowed). The text is at most 256K characters; errors come back as `path: message`, at most 50.
- `name`: the catalog item name, `^[a-z0-9][a-z0-9-]{0,63}$`. With an extension it must also be a valid extension name (`EXTENSION_NAME_RE`) and equal `extension.manifest.name`: the extension's PG schema `plugin_<name>`, storage prefix, tool keys and hook ownership stay keyed by that one name. The plugin name is independent of the npm name (`package.json` `name`, recorded as the item's package name; one catalog name belongs to one npm package: `catalog.name_conflict`).
- `version`: an exact semver version, equal to `package.json` `version` and to the extension manifest's `version`.
- `description` <= 1024 characters, `publisher` and `displayName` <= 100; `homepage` is https; `icon` is a `./…` `.svg` / `.png` (the kernel also checks the content is really svg / png, <= 64 KB; icons are served only through kernel routes with nosniff + CSP sandbox).
- Paths start with `./`, stay inside the plugin root (`isSafePackagePath`) and do not nest (no skill directory inside another).
- `skills` (<= 50): directories holding `SKILL.md`. Omitted = scan `skills/*/SKILL.md`. Each `SKILL.md` goes through `parseSkillMd` (YAML frontmatter, Agent Skills format) and skill names are unique. `pinned` (suggested as pinned) is accepted and stored, with no runtime effect yet (spec §9.1).
  - **Invocation keys** (phase D, Claude Code's names, checked by `parseSkillMd` / `skillInvocation`, `SKILL_INVOCATION_LIMITS`): `disable-model-invocation: true` makes the skill **manual-only** (never in the model's catalog or the pinned skills; only a person runs it with `/name args`), `user-invocable: false` hides it from the `/` menu (both together is refused), `context: fork` runs a person's invocation as a sub-agent (`agent:` picks the sub-agent type: `general-purpose`, `Explore`, `Plan` or one of the plugin's `agents/*.md`, as `<plugin>:<name>`; an unknown one runs as `general-purpose` with a warning), `argument-hint` is the `/` menu's placeholder (a YAML list such as `[issue-number]` reads back as text) and `arguments` names positional values. The body uses `$ARGUMENTS`, `$N`, `$ARGUMENTS[N]`, `$name`, `\$` and `${CLAUDE_SKILL_DIR}` (`/skills/<name>`); nothing is executed: `` !`cmd` `` lines stay text and the model is told to run them with `sandbox_bash` when it has it. Arguments are at most 10 000 characters and the rendered skill at most 200 000 (`renderedMaxChars`). A wrong type is refused at import (the strict `parseSkillMd`); only the Claude translation drops such a key with a warning.
- `connectorTemplates` (<= 20): `./…/<id>.json` files; the template id is the file's base name (`^[a-z0-9][a-z0-9-]{0,63}$`), unique in the plugin. Omitted = scan `connectors/*.json`.
- `dependencies` (<= 20): a plugin name and a semver range; no self-dependency, no duplicates. There is no integrity lock: each dependency was verified against its own source when it was imported.
- `agents` (<= 64, phase C, sub-agents spec §16): `./…/<name>.md` agent templates (`parseAgentTemplate`: frontmatter `name` (the template name rule), `description` (<= 4096), optional `tools` / `disallowedTools` (tool keys), `toolPolicies` (`ask` / `deny`), `model` (`inherit` / `fast` / `standard` / `capable`, a purpose tier, never a model id), `effort`, `maxSteps`, `skills` (<= 3 names, preloaded); the body (<= 100 000 characters) is the instructions). Omitted = scan `agents/*.md`. Names are unique in the plugin; an agent with the builtin `agent` tool that selects a template dispatches it as `<plugin>:<name>`. A plugin with only templates is valid and needs no extension or permission approval.
- Version ranges on official packages (`pluginVersion`, `dependencies`, the `sdk` range) are written `^0.1.0-rc.0` while they are release candidates: a plain `^0.1.0` does not accept `0.1.0-rc.N`.
- `extension`: **written by the packer, never by hand** (a source `plugin.json` that has it fails to pack). Its `manifest` is `staticManifestOf(manifest)`; its `sdk` range must have an upper bound and equals `package.json` `peerDependencies["@capybara-hq/plugin-sdk"]`.
- `package.json` in the tgz: an npm name, no install scripts, no `gypfile`, no dependency fields; `peerDependencies` only the host packages (`@capybara-hq/plugin-sdk`, `zod`) and only with an extension.

## Connector templates (`connectors/<id>.json`, C30)

```json
{
  "$schema": "https://capybarahq.com/schemas/connector-template.v1.schema.json",
  "displayName": { "zh": "Acme CRM", "en": "Acme CRM" },
  "description": "Acme CRM over MCP",
  "icon": "./icons/crm.svg",
  "template": {
    "plugin": "connector-mcp",
    "pluginVersion": "^0.1.0-rc.0",
    "connector": "mcp",
    "endpoint": { "url": "https://mcp.acme.example/mcp" },
    "editableEndpoint": ["url"],
    "auth": { "type": "bearer", "ownership": "org" },
    "defaultToolPolicies": { "search": "allow", "delete_record": "deny" }
  }
}
```

The file is strict; `template` is validated by `validateConnectorTemplate`, and values are never echoed in errors.

- `plugin` / `connector`: the connector extension's name and its `Connector.kind`. At import, when that connector is **loaded on the replica serving the request**, the endpoint is validated against its `endpointSchema`, every `editableEndpoint` path must be a field of that schema, and `pluginVersion` must be satisfied by the loaded version. When the connector is this plugin's own extension or comes from one of its dependencies, only the static checks run now (the review shows `endpointChecked: false`). Any other connector that is not loaded -> 422 `catalog.invalid_manifest`. At org install it is checked again against the connector loaded at that time (not loaded, or not at `pluginVersion` -> `catalog.not_deployed`).
- `endpoint`: the preset, visible to every org; **no credential-like keys at any level** (`token`, `apiKey`, `secret`, `password`, `authorization`, `cookie` and so on, ignoring case and `-` / `_`); headers, query and URL userinfo are checked by the connector install rules too.
- `editableEndpoint`: the dotted paths an org may change at install (letters, digits, `_`, `-`, <= 50, no duplicates, not credential-like). List only fields that really differ by org (the `url` of a self-hosted service, a tenant id). Changing another path -> 400 `validation_failed`; the merged endpoint is re-checked against the schema, the credential rules and the OAuth address policy.
- `auth`: the shape of the connector install API's auth methods (`none` / `bearer` / `basic` / `api_key` / `headers` / `oauth_code` / `oauth_client`), **without credentials** (extra fields are rejected). An org fills in only `credential` (static) or `client: { clientId, clientSecret? }` (OAuth). `ownership` defaults to `auth.ownership` and must match it when given; not allowed with `auth.type = none`.
- `defaultToolPolicies`: local tool name (without `<slug>__`) -> `allow` / `ask` / `deny`, recorded as `policy_source 'template'` (kept through drift review like an admin's setting). For an authorization-code connector it applies when the first member connects. When unsure, do not write `allow`.
- `icon` (file level): a safe path relative to the plugin root (a leading `./` is optional), `.svg` / `.png`, checked like the plugin icon.

## Marketplaces (`marketplace.json`)

```json
{
  "$schema": "https://capybarahq.com/schemas/marketplace.v1.schema.json",
  "schemaVersion": 1,
  "name": "Acme plugins",
  "owner": { "name": "Acme", "url": "https://acme.example" },
  "plugins": [
    {
      "name": "crm",
      "summary": { "en": "CRM tools" },
      "version": "1.2.0",
      "minKernel": "0.1.0",
      "permissions": { "keys": ["db"], "sensitive": [] },
      "source": { "npm": { "package": "@acme/plugin-crm", "version": "1.2.0", "integrity": "sha512-…" } }
    }
  ]
}
```

- Unknown fields are dropped (forward compatible). One entry is one version: `(name, version)` is unique, where the version is `version`, else `source.npm.version` (`marketplaceEntryVersion`); a marketplace that offers several versions lists the plugin once per version. When both are given they must be equal.
- `source` is exactly one of `{ npm: { package, version, integrity } }` (exact version, sha512 SRI), `{ archive: { url, integrity } }` (https, sha512 or sha256 SRI), `{ path }` or `{ git: { url, ref?, commit?, path? } }`. A `path` source is read from a git marketplace's own repository at its last refreshed commit (a git marketplace whose url or ref changed since that refresh returns 409 `conflict`: refresh first) (in an http marketplace it is listed with `reason: "path_needs_git_marketplace"` and importing returns 422 `marketplace.path_unsupported`); a `git` source is read at its pinned `commit`, else at its `ref`'s head at import time. Both are recorded with source `git` and `source_detail` (host, repo, path, ref, commit, followsBranch); a git / archive host outside `marketplaces.allowedHosts` is `reason: "host_not_allowed"` / 403 `marketplace.host_not_allowed`. A git marketplace (`owner/repo`, an https `.git` URL or `form: "git"`, optional `ref`; no mirrors) reads `.capybara-plugin/marketplace.json`, or a single-plugin repo (root `plugin.json` or `skills/`) as one entry; an unchanged commit skips the refresh (only `info/refs` is fetched). The refresh also resolves the branch head (and the plugin directory's tree oid) of imported entries that follow a branch, so an entry shows `contentChanged` ("content changed at the same version") when its directory moved on; a monorepo commit that leaves a plugin's directory alone does not flag it.
- **Git access** (`git-source.ts`, isomorphic-git, Decision 2): https smart HTTP only, depth 1, one commit, no tags, submodules never fetched (a submodule or symlink entry under the plugin's path is `marketplace.git_unsupported_entry`), LFS pointer files read as plain files; the pack <= `packages.maxBytes`, <= 5000 files, <= 4 x `packages.maxBytes` unpacked (else `marketplace.git_too_large`), 120 s per operation; files are read from the fetched pack, never checked out. Other failures are 502 `marketplace.git_failed`; a pinned commit the server will not serve says "pin a branch or tag tip". The marketplace token (`catalog-token:<id>`) is sent as Basic `x-access-token:<token>` only to the marketplace URL's origin, never to other repos or archive hosts.
- **Network rules** (`packages/kernel/src/net`, every marketplace, mirror, archive and git download): https only (`http` only to loopback with `marketplaces.allowInsecureLoopback`, testing), no redirects (`marketplace.redirect`), every resolved address must be public (`marketplace.private_address`; the ranges of the sandbox egress proxy, v4-mapped / NAT64 / 6to4 included) and the connection is pinned to the checked address. Exceptions: `marketplaces.allowPrivateHosts` (hostnames, or IPs / CIDRs that match **IP-literal URLs only**: an internal DNS name must be listed by name; link-local and metadata addresses are refused even then; prefixes shorter than /8 (IPv4) or /16 (IPv6) are refused) and the origin of `packages.npmRegistry`. `marketplaces.allowedHosts` (hostnames or IPs, no port; empty = unrestricted) limits the hosts entries may download git and archive sources from; it does not apply to a direct git import, which is the admin's own action. With `net.httpsProxy` set (`packages/kernel/src/net/proxy.ts`), https downloads tunnel through the proxy with `CONNECT` (Basic proxy auth from the URL userinfo, never in errors or logs; a non-2xx answer is `net.proxy_refused`) and the kernel does not resolve the target: SSRF protection for DNS names is then the proxy's job, while IP-literal private and link-local targets, `allowedHosts`, https-only and no redirects still apply; `net.noProxy` hosts (and loopback) go direct with local resolution and pinning. npm registry downloads (`packages.npmRegistry`, trusted by origin) do not use the proxy in this release. Without a proxy, a fake-IP DNS resolver (answers in `198.18.0.0/15`) makes every host look private: set `net.httpsProxy`, use real DNS for the kernel or list the hosts in `marketplaces.allowPrivateHosts`. The CLI git import (`git:<url>`) takes no token.
- Downloads are always verified against the marketplace's integrity, never npm metadata (`marketplace.integrity_mismatch`). npm sources are fetched from `packages.npmRegistry`; archive URLs are https only, no redirects, size-capped, and never get the marketplace token. `permissions` is display only: the review warns when it differs from the package (`permissionsMismatch`, kept with the staged import).
- `minKernel`: an entry needing a newer kernel is listed as incompatible (`marketplace.incompatible`).
- Tests: `startFakeMarketplace({ manifest })` from `@capybara-hq/testing` serves `/marketplace.json`.

## Enterprise import: one review (`/api/v1/admin/catalog/*`)

Every plugin, whatever it contains, goes through the same two steps (`packages/kernel/src/catalog/plugin-import.ts`).

- **Prepare** (200 `{ stagingId, review }`): `POST import/file` (the tgz as the raw body, `application/octet-stream`, <= `packages.maxBytes`), `POST import/npm { package, version? }` (version, dist-tag or range; verified by `dist.integrity`), `POST import/git { url, ref?, path? }` (a direct git import: an https URL or `owner/repo`, a branch / tag / 40-hex commit, default the remote HEAD, and the plugin's folder, default the root; no marketplace is created and no updates are tracked; a bad url or path is 400 `validation_failed`), or `POST /api/v1/admin/marketplaces/:id/entries/:name/import { version? }` (default: the newest compatible version; also returns `permissionsMismatch`). It reads the whole plugin (`readPluginPackage`), the extension's module graph and migrations, checks skills, templates, icons, name and version conflicts (`catalog.version_exists` when the release is already imported with the same content digest; other content at an imported version is recorded as `<version>+git.<sha12>` / `+sha256.<12>`, spec §5.3; `catalog.name_conflict`, config-declared extension names), the extension's deployment state (a downgrade to a version with unrun migrations -> `extension.downgrade_unsupported`) and resolves dependencies for display. Then the extension goes into the package store (source `catalog`), the skill / template / icon files into object storage, and a staging row is kept for 24 hours (audit `catalog.plugin_staged`).
- **Review** (`PluginReview`): name, version (and `pluginVersion` when build metadata was appended), `contentDigest`, npm package (null without `package.json`), publisher, license, homepage, source (`source.detail`: `{ host, repo, path, ref?, commit, followsBranch, tree? }` for git, `{ url }` for an archive, `{ registry }` for npm; stored on the version as `source_detail`); `provenance` (spec §5.5, display only: for npm sources the registry's attestation `<registry>/-/npm/v1/attestations/<name>@<version>` is parsed for "built from `repository`@`commit` by `workflow`"; signatures are not verified; no attestation, offline or unreadable -> `{ checked: false, reason }`, "provenance not checked", never a refusal) and `provenanceWarning: "repository_mismatch"` when a git marketplace's repository differs from the attested one; the extension (`action` `install` / `upgrade` / `keep`, permission groups with additions and removals against the current snapshot, migration warnings, sensitive items); every skill with its body; every connector template with endpoint, auth and editable paths; every agent template (`agentTemplates`: name, path, description, instructions, model tier and tool narrowing; covered by `reviewHash` only when there are any, so earlier digests are unchanged); every dependency with the version it resolves to (`resolved`, or null). An unresolved dependency **does not block the import**; orgs cannot install until a matching version is imported. Dependencies are never fetched.
- **Reopen**: `GET imports/:stagingId` returns `{ stagingId, review, permissionsMismatch? }` for a staged import (404 `plugin.staging_not_found` when expired or confirmed). The web's review page (`/admin/catalog/import?staging=<id>`) loads from it, so a review link can be shared or reopened.
- **Confirm**: `POST imports/:stagingId/confirm { reviewHash, deployExtension }` (201 `{ item, deploy }`). `reviewHash` must match, and the extension's deployment state is recomputed (installed / upgraded / swapped since the review -> 409 `plugin.review_stale`). It writes the extension's permission snapshot when this import installs it (audit `extension.permissions_approved` with the plugin), then creates the item or adds the version: `manifest` (the normalized `plugin.json`, with skills and templates listed explicitly), `extension_sha256`, the stored files.
  - `deployExtension: true`: after the commit the plugin's own extension is installed on the deployment and enabled (each replica reconciles, no restart); an `upgrade` also gets its snapshot. A failed deploy is returned in `deploy`, not thrown; the committed item stays, and an upgrade that was not installed gets its old snapshot back.
  - `deployExtension: false`: only the catalog changes. The extension is installed later with `POST /api/v1/admin/catalog/items/:id/install-deployment { version }` (409 `catalog.no_extension` for a version without one) or from the extensions page by sha256; until then org installs return `catalog.not_deployed`.
- Errors: a pre-0.1.0 package (a `capybara` section in `package.json`, or an app bundle, without `.capybara-plugin/plugin.json`) -> 422 `catalog.legacy_format` ("repack it as a plugin with .capybara-plugin/plugin.json (pnpm pack-plugin)"); any other invalid plugin -> 422 `catalog.invalid_manifest` with every problem in the details.
- Expired staging is cleaned by the maintenance job `app-staging-cleanup` (hourly; the job name is frozen). A stored extension package stays in the content-addressed store and, with no install record, is never loaded.
- Catalog item routes: `GET items` / `items/:id` / `items/:id/icon`, `PUT items/:id/policy` (`allow` / `needs_approval` / `disabled`), `DELETE items/:id`. There is no `kind` anywhere.

### CLI

`capybara plugins list` (name, latest version, components, policy) and `capybara plugins import <file.tgz | npm:<name>[@<version>] | git:<url>[#<ref>][:<path>]> [--deploy-extension] [--yes]` (`apps/capybara/src/commands/plugins.ts`, kernel `openCatalogCli`) run the same prepare / confirm against PG directly (`git:` is `CatalogService.importFromGit`, under the same `marketplaces.*` network rules; `:<path>` follows the ref, or without one the first colon in the URL's path, so a port is not a path; the printed review includes the git location and commit, the content digest and provenance), with the operator as the actor (null actor, snapshot source `cli`). The CLI loads no connector extensions, so templates of connectors the plugin does not bring get the static checks only. A plugin with files needs object storage: the CLI runs the object-store extension's `setup` with only `ctx.config` / `ctx.provide`, and only for a config-declared provider, or an enabled install record (e.g. the bootstrap object-store-s3) whose package is approved, migrated and configured; otherwise it refuses with `storage.unavailable` and the plugin is imported in the admin console (`.agents/skills/writing-object-store-providers`).

## Claude Code plugins (phase B, `packages/kernel/src/catalog/claude/`)

A Claude Code plugin is translated into an ordinary Capybara plugin on import, then follows the flow above (spec §8, "Phase B as built"). The reader is pure (`translate.ts`, `manifest.ts`, `mcp.ts`, `marketplace.ts`, `report.ts`) and treats the tree as hostile: every problem is a report item, never an exception.

- **Where from**: git only (a Claude marketplace entry, a single-plugin repo, `POST import/git`). An uploaded or npm tgz without `.capybara-plugin/plugin.json` stays `catalog.invalid_manifest`. **Detection** (`isClaudePluginTree`): no `.capybara-plugin/plugin.json` and one of `.claude-plugin/plugin.json`, `hooks/hooks.json`, `.mcp.json`, `commands/`, `agents/`, a root `SKILL.md`, or the entry comes from a Claude marketplace. A tree with only `skills/` stays the skills-only plugin. With both manifests the Capybara one wins and the review says so (`claudeManifestIgnored`).
- **Allowlist translation**: only the rows of spec §8.2 / §8.3 are translated. Skills (default `skills/`, `plugin.json` `skills` paths including `./`, a root `SKILL.md` moved under `skills/<name>/`) are stored byte for byte; a skill without `name` / `description` frontmatter is not imported; `disable-model-invocation: true` imports a manual-only skill (`skill_manual_only`), `context: fork` a forked one (`skill_forked`, `detail.agent`; `skill_agent_unknown` when `agent` is neither `general-purpose` / `Explore` / `Plan` nor an agent of the plugin); `allowed-tools` / `model` / …, Claude variables (skills and commands), `` !`cmd` `` shell injections (`skill_shell_injection`) and `@path` file references (`skill_file_reference`, they stay text) are warnings. Invocation keys the strict `parseSkillMd` checks refuse (a wrong type, an over-long `argument-hint` / `agent`, or both `disable-model-invocation: true` and `user-invocable: false`) are left out with `skill_invocation_key_ignored` (`detail.keys`, `detail.problem`) instead of refusing the skill or command, so a skill that imported before phase D still imports: the import reads a translated tree's SKILL.md files with `invocationKeys: false` (`readPluginFiles`, `checkContent`) and the install reads stored files leniently through `cleanInvocationKeys` (`skills/invocation-keys.ts`). A command's frontmatter that is not valid YAML is read again with its `argument-hint:` value quoted (Claude Code documents `argument-hint: [pr-number] [priority]`); a skill's SKILL.md is never rewritten, so invalid YAML there stays `skill_invalid`. **Commands** (phase D, `claude/commands.ts`; `commands/*.md` non-recursive, declared paths, or the object map with `source` / inline `content`) become ordinary skills (`command_imported`; model-invocable unless `disable-model-invocation: true`): each is generated as `.capybara-generated/commands/<name>/SKILL.md` (JSON frontmatter with `name`, `description` (else the first body line) and the command's invocation keys; body unchanged) and listed in `skills`; a name that is not a skill name, equals a skill of the plugin (the skill wins) or has no description is `command_invalid`. When the tree has a command, a manual-only or a forked skill, the translation's `translatorRevision` (`claude-translation-2`) is folded into `claudeContentDigest`, so re-importing a version imported before phase D is new content. `skill_manual_invocation`, `command_manual_invocation` and `skill_needs_subagents` are no longer emitted (kept for stored reports). Hooks are listed, never run (`hooks_not_run`; a `SessionStart` hook sets `sessionStart` and adds `session_start_pin_hint`). **Agents** (`agents/**/*.md` or the declared paths; phase C, `claude/agents.ts`, sub-agents spec §16.4) become agent templates: each is generated as `.capybara-generated/agents/<name>.md` (frontmatter translated, written as JSON; body copied unchanged; the source file is never rewritten) and listed in the synthesized `agents`. Tools go through the Claude tool-name table (`Bash` / `Read` / `Write` / `Edit` / `MultiEdit` / `Glob` / `Grep` -> `sandbox_*`, `Skill` -> `skill_load`, `TodoWrite` -> `todo__write`, `ToolSearch` -> `tool_search`; anything else, `Agent` / `Task` / `AskUserQuestion` and patterns such as `Bash(git:*)` in `tools` are dropped: `agent_tools_unmapped`; a pattern in `disallowedTools` disallows the whole tool), `model` aliases map to tiers (`haiku` -> `fast`, `sonnet` -> `standard`, `opus` / `fable` -> `capable`; a full id by its family, else `inherit`: `agent_model_mapped`), `maxTurns` -> `maxSteps`, `skills` (> 3 or invalid names cut: `agent_skills_truncated`), `effort`; `permissionMode` / `hooks` / `mcpServers` are `not_applicable`, other fields `agent_field_ignored`; a name outside the template name rule, a missing description, a duplicate or an unparsable file is `agent_invalid` (never renamed). `agent_needs_subagents` is no longer emitted (kept for stored phase B reports). Agents are collected recursively, but a template is named by its file name only: a nested `agents/sub/x.md` becomes `<plugin>:x` (Claude Code includes the subdirectory), and same-named files in two subdirectories are `agent_invalid` duplicates. `package.json` is left out of the translated tree (it still counts in the digest). Version: `plugin.json` first (Claude's rule; the entry's version is not enforced), then the entry's, else `0.0.0-git.g<sha12>`; publisher: `author.name`, else the marketplace owner. `displayName.zh` copies `en`. Refusals (`catalog.invalid_manifest`) only for: a name Capybara cannot use or an unreadable `plugin.json`, a `strict: false` entry declaring components that `plugin.json` also declares, a plugin with no importable skill, no agent and no template, and a synthesized manifest that fails `parsePluginManifest` (a guard).
- **Remote MCP servers** (`.mcp.json` in either shape, or `mcpServers`) of type `http` / `streamable-http` become templates `.capybara-generated/connectors/<id>.json` for `connector-mcp`: `Authorization: Bearer ${X}` -> `bearer`, one other `${X}` header -> `api_key`, several -> `headers` (all `ownership: "personal"`, so the installer passes their own credential in `connectors.<id>.credential`; without it org install and upgrade planning answer 400 at that path before any write, and the web wizard asks for it), `oauth` -> `oauth_code` with MCP discovery and DCR, none -> `auth: none` plus `mcp_auth_none`, `${X}` in the URL -> an editable endpoint. Literal credential-like headers, `headersHelper`, user info or credential-like query parameters are `mcp_invalid`; `sse`, `ws`, stdio, `.mcpb` / `.dxt` are `mcp_unsupported_transport`. When `connector-mcp` is not loaded the templates get the static checks (`endpointChecked: false`) and a `connector_not_loaded` warning instead of the refusal of an unknown connector; org install still checks against the loaded connector.
- **Translation report** (`TranslationReport`): `format: "claude-code"`, `manifestPath`, `sessionStart`, `items` in five groups (`imported`, `converted`, `needsInput`, `ignored`, `warnings`) with a `code` and `detail`, sorted, at most 500 items (then one `{ more }` item; hook items 100 per kind); names, paths and details pass through `printable` (no control or bidi characters). Each component key takes at most 100 distinct declared paths (repeats skipped, the rest one `too many paths` item) and each JSON file is parsed once, so a hostile manifest cannot stall the event loop. A root `SKILL.md` takes every file not excluded, so a large repository can exceed the skill package limits and refuse the import. It is part of the review (`format`, `translation`, `repository` (display only, not hashed), `licenseText` (the root LICENSE of any plugin, ≤ 64 KiB, else `licenseTruncated`), `skills[].suggestPinned`), covered by `reviewHash`, and stored on the version (`source_format`, `translation`, `license_text`, `license_truncated`; the version API returns `licenseTruncated`). `capybara plugins import` prints it.
- **Claude marketplaces**: a git marketplace without `.capybara-plugin/marketplace.json` reads `.claude-plugin/marketplace.json`. Sources: a relative path (`metadata.pluginRoot` applies to bare names only), `github`, `url` (https), `git-subdir`; entries Capybara cannot store are listed in `marketplaces.skipped` (`{ name, reason }`, replaced on every refresh, shown on the marketplaces page): `claude_npm_unpinned` (npm, no integrity), `claude_source_unsupported` (`archive` zips, `command`, non-https URLs), `invalid_name`, `invalid_entry` (also one row for entries past 5000). Each entry keeps an overlay (`marketplace_entries.claude`: `strict`, its component fields, publisher); with no `plugin.json` the entry is the manifest. The content digest is over the files as read, plus the overlay's canonical JSON when the entry has components, so an entry-only change re-imports as new content (`+git.<sha12>`, or `+sha256.<12>` when that build is taken).
- **Pinned suggestion** (any plugin): `.capybara-plugin/plugin.json` `skills[].pinned`; at confirm the admin may send `pinnedSuggestions: [<skill name>]` (unknown names -> `validation_failed`; omitted keeps the plugin's own; not part of `reviewHash`). Org installs and upgrades copy it to `skill_versions.suggest_pinned` with `source_format` (an upgrade that leaves a skill unchanged sets the flag on its current version); the skills APIs return `plugin`, `sourceFormat`, `suggestPinned`, `entryBytes`, `tokenEstimate`. Agents pin with `skills.pinned` (`.agents/skills/writing-tools`).
- Tests: `packages/kernel/test/catalog/claude-*.test.ts` (translate, marketplace, git-marketplaces, import, install), `plugin-review-hash.test.ts`, the fixtures `test/catalog/fixtures/claude/` (`superpowers` from obra/superpowers 7.0.1, `mixed`, `root-skill`), the acceptance `claude-superpowers.e2e.test.ts`, the live `claude-live.test.ts` (only with `CAPYBARA_TEST_CLAUDE_SUPERPOWERS=1`; behind a proxy add `CAPYBARA_TEST_HTTPS_PROXY=<url>`, which becomes `net.httpsProxy`). A translated bearer template against the real `connector-mcp` is tested in capybara-hq/plugins.

## Bootstrap plugins (`packages/kernel/bootstrap.json`)

The plugins every deployment installs (spec §7; today `openai-compatible` and `object-store-s3`, both required) are pinned in `packages/kernel/bootstrap.json` (v1, schema `packages/plugin-sdk/schemas/bootstrap.v1.schema.json`, parsed by the SDK's `parseBootstrapManifest`; strict: unknown keys are errors). Since phase A3b every entry is `{ name, version, integrity, required, "source": "npm", "npm": "<package>" }`, with a top-level `marketplace: { url, commit }`: the official marketplace (`https://github.com/capybara-hq/plugins.git`) at the commit the pins were checked against. The SDK still accepts `"source": "workspace", "path": "plugins/<dir>"` entries (the sha512 of the `packages/plugin-tools` pack, byte-reproducible across hosts), but core no longer has any.

- The image build downloads every npm entry (`pnpm pack-bootstrap --registry <url>`, default `CAPYBARA_PACKAGES__NPM_REGISTRY` or the public registry) and refuses a tarball whose sha512 differs from the pin; it writes `/app/bootstrap/<name>-<version>.tgz`, and `capybara bootstrap` (compose `init`, after `migrate`) installs from there, offline. Only the build needs the network. The extension side (lock, `bootstrap_runs`, the rules per entry, `required`) is in `.agents/skills/writing-extensions` ("Bootstrap plugins").
- Each entry goes through the same import as any plugin (`PluginImport.prepare` / `confirm`): a catalog version with source `bootstrap` and `source_ref` `bootstrap:<name>@<version>`, the package with source `bootstrap` (kept in PG), the install record with source `bootstrap`; a declarative entry (no extension) is only imported into the catalog. Afterwards the plugin is managed like any other catalog item (org installs, upgrades), except that a required one cannot be disabled or uninstalled (409 `extension.required`).
- `pnpm check:bootstrap` (full on PRs, part of `pnpm check`) parses the manifest (`bootstrap-invalid`) and checks that every remote build context of `docker/compose.yaml` and `docker/compose.dev.yaml` is exactly the official repository at `marketplace.commit` (`bootstrap-compose-ref`: today `https://github.com/capybara-hq/plugins.git#<commit>:plugins/sandbox-docker/image` and `…/egress-proxy`; a fork, an scp-style or scheme-less URL, a branch, `?ref=` or a missing directory fails); its workspace-entry rules (`bootstrap-stale`, `bootstrap-name`, `bootstrap-pack`) have nothing to check today. `pnpm check:bootstrap --network` (by diff on PRs when `bootstrap.json` or the check's own code changes; `docker/**` runs everything; always on `main` and before publishing) checks each npm entry against the registry (published, `dist.integrity` and tarball sha512 equal to the pin: `bootstrap-npm`), against the official marketplace's `.capybara-plugin/marketplace.json` at `marketplace.commit` (same version, package and integrity: `bootstrap-marketplace`), and that the `sandbox-docker` test copy of the socket proxy config at that commit equals core's `docker/sandbox-proxy/haproxy.cfg` (`bootstrap-haproxy`), that each compose build context has its `Dockerfile` there (`bootstrap-compose-ref`), and that `marketplace.url` is the official one (`bootstrap-marketplace-url`).
- **Moving a pin**: once capybara-hq/plugins has published the new versions and listed them in its marketplace, update the entries' `version` / `integrity` and `marketplace.commit` together (the compose git contexts follow the same commit), then run `pnpm check:bootstrap --network`. One `marketplace.commit` pins three things: the bootstrap entries, the compose sandbox build contexts and the plugin's copy of `docker/sandbox-proxy/haproxy.cfg` (`bootstrap-haproxy`); a haproxy-only change lands in capybara-hq/plugins first, then a core PR changes the file and moves `marketplace.commit` and the contexts to that commit.

## Org install and uninstall (`/api/v1/orgs/:orgId/catalog/:itemId/install`, `plugin-installs`)

Code: `org-catalog.service.ts` (policy, requests) and `plugin-install.ts` (`PluginInstaller`).

- **Body**: `{ version?, connectors?: { <template id>: { name?, slug?, endpoint?, credential?, client? } }, extensionConfig?: { … } }` (strict). `endpoint` is limited to `editableEndpoint`; `extensionConfig` is the org config of the plugin's own extension, validated against its `config.org` schema and used only when this install enables it (an extension already enabled in the org is recorded as pre-existing and its config is untouched). Unknown template ids, or `extensionConfig` for a plugin without an extension -> 400 `validation_failed`. Bad template input (credential shape, endpoint, OAuth client, slug) is a 4xx before anything is written, with the path prefix `connectors.<id>.`.
- **Permissions**: the actions of every plugin the install brings in (extension -> `org.extensions.manage`, templates -> `connectors.manage`, skills -> `skills.manage`, agent templates -> `agents.manage`), re-checked under the org row lock.
- **Policy** follows the installed plugin only (upgrades too): `disabled` -> 403 `catalog.item_disabled`; `needs_approval` without a grant for this org -> 202 and a request for the enterprise admin; otherwise 201 `{ installed: { itemId, version, pluginInstallId }, install: <PluginInstallView> }`. Dependencies are not approved separately (a `needs_approval` dependency installs under the root's grant). **Exception (Ruling M-5)**: a plugin item set to `disabled` is a master switch for its extension: no path (direct enabling, its own item, another plugin depending on it) newly enables it in an org.
- **Dependencies** (resolved before any request or row exists): each range resolves to the highest imported, non-deleted version satisfying it (prereleases included). No such item or version -> 409 `catalog.dependency_unresolved` (details `{ dependency, range }`); a disabled dependency anywhere in the tree -> 409 `catalog.dependency_disabled` naming it; a cycle by name, or nesting deeper than 10 levels -> 409 `catalog.dependency_cycle`. A dependency already installed in the org at a version outside the range is unresolved too (upgrade it first). Dependencies take no install input: one whose templates need a credential or an OAuth client must be installed on its own first (400 saying so, with the path `dependencies.<name>.connectors.<id>.…`), and a dependency's extension is enabled without org config.
- **Steps**, depth first: `dependencies` (each one not yet in the org gets its own nested `plugin_installs` row through the same installer, recorded as a `plugin` component with `ref` = its install id and `created: true`; one already in the org, including one an earlier sibling just brought in, is recorded `created: false`) -> `extension` (enable in this org; not loaded on the deployment -> `catalog.not_deployed`) -> `connectors` (from the templates, through `ConnectorsService.create`) -> `agent_templates` (an org template per plugin and name, `agents/templates.ts`, component kind `agent_template`; names are scoped by plugin, so two plugins never conflict; the org's live template of the same plugin and name gets a new version when it differs, recorded as pre-existing with the version) -> `skills` (an org skill of the same name from the same catalog item, a reinstall, gets a new version, recorded as pre-existing with the version number; one of other provenance, the org's own skill or another plugin's, refuses the install while planning, before anything is written: 409 `plugin.skill_conflict`, one message line per skill, `details: [{ skill, source: { kind: "org" } | { kind: "plugin", name, version } }]`, spec §9.2). Each component is recorded in `plugin_install_components` as soon as it exists. Audit `plugin.org_installed` / `plugin.org_install_failed` per install, nested ones with `dependencyOf`.
- **Failure**: everything this install created is undone in reverse order, nested dependency installs included, the row is marked `failed` and the root returns 502 `plugin.install_failed` with `{ step, code, dependency?: "a > b", message, rolledBack }`.
- **Uninstall** (`DELETE plugin-installs/:installId`, the plugin's component actions re-checked under the lock) removes, in one transaction, skills -> connectors -> extensions (reverse requires) -> dependency installs, **only components this install created and nothing else uses**. Kept ones are reported with a reason: `pre_existing`, `used_by_agents` (a skill selected by an agent, a connector referenced by one, an agent template in an agent's `subagents.templates`: dispatches of it keep working until the agent drops it), `used_by_other_install` (another install in this org uses it; ownership passes to it), `used_by_connectors`, `used_by_plugins` (another enabled extension requires it). A dependency install is removed with the last install that uses it; deleting a dependency install that another live install still uses returns 200 with nothing removed and `kept: [{ kind: "plugin", reason: "used_by_other_install" }]`. A `failed` install, or one still `installing` after `catalog.staleInstallMinutes` (default 30), is cleaned up as a rollback; one still installing -> `plugin.install_in_progress`.
- **Org upgrade** (spec §10, `plugin-upgrade.ts`): `POST /orgs/:orgId/plugin-installs/:installId/upgrade/preview { version }` -> `{ from, to, diffHash, components: { kind, ref, change: added | changed | removed | unchanged, detail? }[], inputs: { connectors, credentialsChanged, extensionConfig } }`, then `POST …/upgrade { version, diffHash, connectors?, extensionConfig? }` -> 200 `{ install }` (202 `{ request }` for needs_approval without a grant; disabled -> `catalog.item_disabled`; another diff -> 409 `plugin.upgrade_stale`). A plugin with an extension can move only to the catalog version carrying the deployment's extension package (by sha256, newest import on ties; else 409 `plugin.upgrade_target_invalid`); a declarative one to any imported version (rollback). Skills and agent templates get a new version (agents keep them by id; sub-agents already started keep the definition frozen in their `subagent_started`; a rollback writes the previous definition as a new version); a changed template's connector gets only template-owned fields (endpoint preset with the org's editable values, auth preset, default policies of tools not set by the org: `template` and `derived` rows take the new template's policy, an unnamed `template` row returns to `derived`), credentials kept unless the auth's credential shape changes (`credentialsChanged`, input required); removals follow the uninstall rules (a skill or connector an agent still uses stays in the ledger marked `dropped`, "no longer in the plugin"). Status `upgrading` under the org lock (uninstall / a second upgrade -> `plugin.install_in_progress`); each step is journaled in `plugin_installs.upgrade` and undone on failure (502 `plugin.upgrade_failed`, the install stays `installed` at the old version with `error`), or by the next preview / upgrade / uninstall once older than `catalog.staleInstallMinutes`. The views carry `upgradeAvailable` and `deploymentPending`. Connector components record `template_id` (migration 0049). Tests: `packages/kernel/test/catalog/plugin-upgrade.test.ts`.
