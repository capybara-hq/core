# Writing plugins

Terms: a **plugin** is the install and distribution unit: a bundle of at most one **extension** (in-process code, `.agents/skills/writing-extensions`), skills, connector templates and agent templates (`agents/<name>.md`, sub-agents a parent agent can dispatch), possibly depending on other plugins. The **catalog** is what a deployment has imported for its orgs to install; it holds one kind of item, the plugin. A **marketplace** is a `marketplace.json` listing importable plugins.

Spec: `docs/superpowers/specs/2026-10-22-package-ecosystem-design.md` §4, §5.2, §6, §10, amended by `2026-11-05-plugin-component-management-design.md` (scope replaces policy, grants and the install-deployment step).

This skill covers what core owns: the plugin format as the SDK parsers and the kernel readers enforce it, the `capybara-plugin` toolchain (`packages/plugin-tools`), the catalog (readers, network rules and git access of marketplaces, platform import and review, the CLI, Claude Code translation, bootstrap plugins, org install, upgrade and uninstall). **Writing, packing, versioning and releasing a plugin** is in [writing-plugins in capybara-hq/plugins](https://github.com/capybara-hq/plugins/tree/main/.agents/skills/writing-plugins); the official plugins live in that repository (the official marketplace `https://github.com/capybara-hq/plugins.git`). Core's only plugin is `plugins/model-fake`; the fake extensions under `packages/testing/fixtures/extensions/*` use the same layout. Core's writing skills cover the kernel side; a contract change needs a PR in core first, then the plugins follow.

**The official marketplace** is a git marketplace, on by default (`marketplaces.official.enabled`; `marketplaces.official.url` defaults to `https://github.com/capybara-hq/plugins.git`). Offline deployments set it to `false`, and every test kernel config, the e2e stack and the docker smoke tests turn it off unless the test is about it (checked by `packages/kernel/test/offline-configs.test.ts`).

## Layout

A plugin is a directory, packed into an npm-pack tgz:

```
<plugin>/
  .capybara-plugin/plugin.json   the plugin manifest (required in the source; the packer adds `extension`)
  package.json                   npm metadata; `version` equals plugin.json `version`
  skills/<name>/SKILL.md …       skills (scanned unless plugin.json lists them)
  connectors/<id>.json           connector templates (scanned unless plugin.json lists them)
  agents/<name>.md               agent templates for sub-agents (scanned unless plugin.json lists them)
  src/index.ts                   extension source (optional; bundled into dist/index.mjs)
  migrations/*.sql, ui/**        extension migrations and UI files (optional)
  src/client.tsx (or .ts)        browser entry of the extension (optional; bundled into dist/client/client.mjs)
  client/styles/*.css            plugin CSS (optional; each file wrapped in `@layer extensions`)
  client/assets/**               files plugin CSS and code refer to (optional)
  README.md, LICENSE, NOTICE
```

`pnpm pack-plugin <dir> [--out <dir>]` (`capybara-plugin pack` of the published `@capybara-hq/plugin-tools`, `packages/plugin-tools`; outside this repository `npx capybara-plugin pack <dir>`, and `capybara-plugin check` runs the plugin checks) packs it: it validates the source `plugin.json`, bundles `src/index.ts` when it exists (a plugin without one is **declarative**: no esbuild runs and the package has no `peerDependencies`), ships `skills/**`, `connectors/*.json`, `agents/*.md`, the listed paths and icons, writes `package.json` (no `capybara` section) and the final `.capybara-plugin/plugin.json` with `extension = { entry: "./dist/index.mjs", manifest: <static extension manifest>, migrations?: "./migrations", ui?: "./ui", configSchemas?: { deployment?, org? } }`, and produces a reproducible tgz. `configSchemas` are the extension's config schemas as form JSON Schemas (the SDK's `configJsonSchema`, with the `x-ui` hints of `ui()`; each ≤ 96 KiB), so a replica that has not loaded the extension still draws its form (extension config forms spec §4.5); the packer refuses hints with problems (`validateConfigUi` at the level, or `options` / `presets` on a secret, which the JSON Schema would drop). The packer fails early on a missing listed path, a skill directory without `SKILL.md`, an invalid `connectors/*.json` or `agents/*.md` and an empty plugin (`a plugin must contain an extension, a skill, a connector template or an agent template`).

The format and its validation are pure functions in the SDK: `packages/plugin-sdk/src/plugin-manifest.ts` (`parsePluginManifest`, `parseConnectorTemplateFile`, `PLUGIN_MANIFEST_LIMITS`), `plugin-package.ts` (`validatePluginPackageJsonFor`, `validateConnectorTemplate`), `marketplace.ts` (`parseMarketplaceManifest`, `marketplaceEntryVersion`). The kernel reads a plugin in `packages/kernel/src/catalog/plugin-package.ts`: `readPluginPackage` unpacks a tgz and hands its files to `readPluginFiles(files, opts)`, which a git tree goes through too, so tgz and git share every check. The plugin is always hostile input, every problem is collected, and nothing is written until all checks pass.

- **From git, `package.json` is optional** (spec §4.1 needs it only for npm): the package name is then null and the item is identified by its git source (host, repo, path), so an unrelated repo with the same plugin name never adds versions to it. A plugin **with an extension** still needs `package.json` (its `peerDependencies` ranges are checked), and its whole folder is packed into a deterministic tgz (`packPackageTgz`) and read like an upload. A folder without `plugin.json` but with `skills/` is a **skills-only plugin**: named after the marketplace entry (a direct import: the last segment of `path`, else of the repo URL without `.git`), versioned per spec §5.3, published by the marketplace's `owner.name` (else `<host>/<owner>` of the repo). An archive without `plugin.json` is a skills-only plugin the same way.
- **Content digest** (`contentDigest`, computed for every import, stored on the version): sha256 hex over the sorted file list, one line `path + "\0" + sha256(content) + "\n"` per file, so a tgz and a git tree of the same files have the same digest whatever the archive bytes.
- **Versions** (`versions.ts`, spec §5.3): `plugin.json` version, else the entry's `version`, else `0.0.0-git.g<sha12>` (git) / `0.0.0-sha256.h<12>` (archive). Re-importing an imported release with **another** digest records `<version>+git.<sha12>` (git) or `<version>+sha256.<12>` (archive, npm, upload) and never overwrites the imported version; the same digest is `catalog.version_exists` ("already imported"). Ordering is semver ignoring build metadata, ties by import time; ranges ignore build metadata.

**JSON Schemas**: `packages/plugin-sdk/schemas/plugin.v1.schema.json`, `connector-template.v1.schema.json` and `marketplace.v1.schema.json` are generated from the zod schemas by `pnpm gen:package-schemas` and drift-checked by `check:package-schemas`; regenerate them after changing a schema. Files may set `$schema` to `https://capybarahq.com/schemas/<file>`. Rules JSON Schema cannot express (path safety and nesting, uniqueness, no self-dependency, the extension's name and version equal to the plugin's, template static rules, unique `(name, version)` in a marketplace) are decided only by the parsers, so external CI must run them too.

## Toolchain (`capybara-plugin`, `@capybara-hq/plugin-tools`)

The published package `@capybara-hq/plugin-tools` (`packages/plugin-tools`) is the one toolchain for official and third-party plugins; a plugin repository adds it as a devDependency. Every relative path resolves against the current directory; a root is either a repository with `plugins/*` or a single-plugin directory (its own `.capybara-plugin/plugin.json`).

| Command | What it does | In core |
|---|---|---|
| `capybara-plugin pack <dir>… [--all <root>] [--out <dir>]` | the packer described above; byte-reproducible, so the sha512 of a pack is known before publishing | `pnpm pack-plugin <dir>` (any plugin directory you give it), `pnpm pack-plugins` (core's `plugins/*`: `model-fake`) |
| `capybara-plugin check [--root <dir>] [--plugins <glob>] [--base <ref>]` | every plugin-scoped check: the SDK boundary (`check:deps`), extension state (timers, module-level state), permissions (`perm-hooks` / `perm-ui` / `perm-storage`), plugin packing (`plugin-pack-dropped` etc.), config forms (`plugin-config-ui`: invalid hints; `plugin-config-labels`: a published plugin's rendered config field without a zh + en label, secret records drawn per item skipped), release metadata (`plugin-release-metadata`, `release-display-name`: a published plugin's `plugin.json` needs `displayName`), the tool design rules, migrations; with `--base`, an edited applied migration fails | part of `pnpm check` (core runs the same code on `plugins/model-fake` and the fake extensions) |
| `capybara-plugin sync-versions [--root <dir>] [--plugins <glob>]` | copies each plugin's `package.json` version into its `plugin.json` and extension manifest (the packer requires them equal); run after `changeset version` | `pnpm sync:plugin-versions` (inside `pnpm version-packages`) |
| `capybara-plugin marketplace --write\|--check [--base <rev>] [--root <dir>] [--file <path>] [--plugins <glob>]` | keeps `.capybara-plugin/marketplace.json` listing one npm entry per public plugin, its current version, with the sha512 of its reproducible pack, `summary` from the `plugin.json` `description` (`{ en, zh? }`, a string being `en`), `displayName` from `plugin.json` and `icon`, the repository path of the `plugin.json` `icon` (`./plugins/<dir>/<icon>`); `--write` replaces a plugin's entry when its version moves, drops its other versions (entries of plugins not in the tree stay) and refreshes a listed entry's `summary` / `displayName` / `icon` from `plugin.json` (`marketplace-display-stale` in `--check`; source, integrity and a hand-set `deprecated` untouched); listed versions are left to the release gate; `--base` lets a plugin's version only increase, also against a base listing several versions (`marketplace-version-decrease`), keeps a published version's integrity and checks added entries against the packs (`marketplace-integrity`); also `marketplace-missing`, `marketplace-invalid` | not used in core; the plugins repository's Version Packages PR and CI |
| `capybara-plugin release [--dry-run] [--provenance] [--auto] [--root <dir>] [--plugins <pattern>]... [--marketplace <file>]` | the npm half of the release: publish plan, dist tags, skips versions already on npm, plugins as their plugin tgz; `--plugins` limits the plugins, `--marketplace` (default the repository's `marketplace.json` when present) checks every plugin pack against its entry before the first publish (`release.integrity_mismatch`) | `pnpm release` |

## `plugin.json`

```json
{
  "$schema": "https://capybarahq.com/schemas/plugin.v1.schema.json",
  "schemaVersion": 1,
  "name": "crm",
  "version": "1.2.0",
  "publisher": "Acme",
  "description": "CRM tools for sales teams",
  "displayName": { "zh": "CRM", "en": "CRM" },
  "icon": "./icon.svg",
  "license": "Apache-2.0",
  "homepage": "https://acme.example/crm",
  "dependencies": [{ "name": "crm-core", "version": "^1.0.0" }],
  "skills": [{ "path": "./skills/crm-notes" }],
  "connectorTemplates": [{ "path": "./connectors/crm-mcp.json" }]
}
```

- Objects are strict: an unknown key is an error, not ignored (`$schema` is allowed). The text is at most 256K characters; errors come back as `path: message`, at most 50.
- `name`: the catalog item name, `^[a-z0-9][a-z0-9-]{0,63}$`. With an extension it must also be a valid extension name (`EXTENSION_NAME_RE`) and equal `extension.manifest.name`: the extension's PG schema `plugin_<name>`, storage prefix, tool keys and hook ownership stay keyed by that one name. The plugin name is independent of the npm name (`package.json` `name`, recorded as the item's package name; one catalog name belongs to one npm package: `catalog.name_conflict`).
- `version`: an exact semver version, equal to `package.json` `version` and to the extension manifest's `version`.
- `description` <= 1024 characters, `publisher` and `displayName` <= 100; `homepage` is https; `icon` is a `./…` `.svg` / `.png` (the kernel also checks the content is really svg / png, <= 64 KB; icons are served only through kernel routes with nosniff + CSP sandbox).
- Paths start with `./`, stay inside the plugin root (`isSafePackagePath`) and do not nest (no skill directory inside another).
- `skills` (<= 50): directories holding `SKILL.md`. Omitted = scan `skills/*/SKILL.md`. Each `SKILL.md` goes through `parseSkillMd` (YAML frontmatter, Agent Skills format) and skill names are unique. Every skill is on in every agent of an org where it is on (skills default-on spec); there is no pinning: `skills[].pinned` is gone from the SDK type and the schema, and the kernel strips it from a stored package's `plugin.json` before parsing (`plugin-package.ts`), so packages imported before still read.
  - **Invocation keys** (phase D, Claude Code's names, checked by `parseSkillMd` / `skillInvocation`, `SKILL_INVOCATION_LIMITS`): `disable-model-invocation: true` makes the skill **manual-only** (never in the model's catalog; only a person runs it with `/name args`), `user-invocable: false` hides it from the `/` menu (both together is refused), `context: fork` runs a person's invocation as a sub-agent (`agent:` picks the sub-agent type: `general-purpose`, `Explore`, `Plan` or one of the plugin's `agents/*.md`, as `<plugin>:<name>`; an unknown one runs as `general-purpose` with a warning), `argument-hint` is the `/` menu's placeholder (a YAML list such as `[issue-number]` reads back as text) and `arguments` names positional values. The body uses `$ARGUMENTS`, `$N`, `$ARGUMENTS[N]`, `$name`, `\$` and `${CLAUDE_SKILL_DIR}` (`/skills/<name>`); nothing is executed: `` !`cmd` `` lines stay text and the model is told to run them with `Bash` when it has it. Arguments are at most 10 000 characters and the rendered skill at most 200 000 (`renderedMaxChars`). A wrong type is refused at import (the strict `parseSkillMd`); only the Claude translation drops such a key with a warning.
- `connectorTemplates` (<= 20): `./…/<id>.json` files; the template id is the file's base name (`^[a-z0-9][a-z0-9-]{0,63}$`), unique in the plugin. Omitted = scan `connectors/*.json`.
- `dependencies` (<= 20): a plugin name and a semver range; no self-dependency, no duplicates. There is no integrity lock: each dependency was verified against its own source when it was imported.
- `agents` (<= 64, phase C, sub-agents spec §16): `./…/<name>.md` agent templates (`parseAgentTemplate`: frontmatter `name` (the template name rule), `description` (<= 4096), optional `tools` / `disallowedTools` (tool keys), `toolPolicies` (`ask` / `deny`), `model` (`inherit` / `fast` / `standard` / `capable`, a purpose tier, never a model id), `effort`, `maxSteps`, `skills` (<= 3 names: a sub-agent of the template is told to load them with `Skill` first, never pinned); the body (<= 100 000 characters) is the instructions). Omitted = scan `agents/*.md`. Names are unique in the plugin; an agent with the builtin `Agent` tool that selects a template dispatches it as `<plugin>:<name>`. A plugin with only templates is valid and needs no extension or permission approval. Phase 4 (spec §15, rulings P4-1, P4-2) adds optional fields, so existing files stay valid and unknown keys stay ignored: `disallowedSkills` (<= 64 skills an agent made from it turns off, every other skill on in the org staying on: `<plugin>:<name>`, `<plugin>:*` for the whole plugin including skills it gains later, or a bare `<name>` for an org skill without a plugin; `isDisallowedSkillRef`; it replaced `selectedSkills`), `connectors` (<= 16 entries, each `{ template: "<connector template id | plugin:id>", tools?, policies? }` or `{ needs: { protocol: "mcp" | "openapi", endpoint, tools, label }, tools?, policies? }`; `policies` maps a tool name to `ask` / `deny`), `subagents` (`{ general?, types?, inline? }`, `types` + `inline` <= 16; an inline entry's `tools` absent = all of the agent's tools, `[]` = none), `modelRef` (`provider/model`), `quickActions` and `instructionFiles`. As a sub-agent type the template ignores the new fields except `disallowedSkills`, which narrows the child's skills (the parent's `disabledSkills` plus these; builtin skills stay on).
- Version ranges on official packages (`pluginVersion`, `dependencies`, the `sdk` range) are written `^0.1.0-rc.0` while they are release candidates: a plain `^0.1.0` does not accept `0.1.0-rc.N`.
- `extension`: **written by the packer, never by hand** (a source `plugin.json` that has it fails to pack). Its `manifest` is `staticManifestOf(manifest)`; its `sdk` range must have an upper bound and equals `package.json` `peerDependencies["@capybara-hq/plugin-sdk"]`.
- `package.json` in the tgz: an npm name, no install scripts, no `gypfile`, no dependency fields; `peerDependencies` only the host packages (`@capybara-hq/plugin-sdk`, `zod`) and only with an extension.

## Client code (`extension.client`, `suggestedAppearance`; spec `2026-11-09-client-extensions-design.md`)

Behaviour and delivery: [writing-extension-ui](../writing-extension-ui/SKILL.md) (client code section). The format and the packer:

- **`extension.client`** (`PluginClientSection`, SDK `client-section.ts`; written by the packer, never by hand): `{ entry?: "./dist/client/client.mjs", styles?: ["./dist/client/styles/<name>.css"], assets?: ["./dist/client/assets/<path>"], integrity: { <path>: "sha384-<base64>" }, apiVersion }`. It needs an entry or one style file; `validateClientSection` checks it (`parsePluginManifest`, pack and the kernel's import use it). `CLIENT_LIMITS`: entry 1 048 576 bytes, 8 style files of at most 262 144, 64 assets of at most 2 097 152, 8 388 608 in all. Asset types: `.png .webp .svg .woff2 .mp3 .ogg .wav`. Every segment of a client file path is `[A-Za-z0-9._-]` (style names start with a letter or digit).
- **`permissions.client: true`** is declared exactly when the package has a client section (`client-undeclared` from the packer in both directions; the kernel's import refuses a mismatch, `client.undeclared`). Components also need `permissions.ui.components`. Both keys are sensitive and block loading (writing-extensions).
- **Pack** (`packages/plugin-tools/src/pack/client.ts`): esbuild (`platform: "browser"`, `format: "esm"`, `target: "es2022"`, minified, one file, automatic JSX) of `src/client.tsx|ts`; externals are only `react`, `react-dom`, `react/jsx-runtime` and `@capybara-hq/plugin-client` (the host provides them through an import map); anything else is bundled. `client-import-forbidden` for an unresolved bare import, a Node builtin, `react-dom/server`, a dynamic `import()` of a non-relative URL, or any `@capybara-hq/*` other than `plugin-client`. `client-size` for a limit. CSS: each file is wrapped in `@layer extensions { … }`; `client-css-remote` for `@import`, a `url()` that is not `../assets/<own asset>`, `data:` or `#fragment`, the functions `image-set`, `-webkit-image-set`, `cross-fade`, `-webkit-cross-fade`, `element`, `-moz-element`, `paint`, `src`, `image`, and invisible characters (non-ASCII whitespace, zero-width, U+FEFF); the rule is one pure module in the SDK (`clientCssProblem` / `wrapClientCss`, `packages/plugin-sdk/src/client-css.ts`) that the packer and the kernel both import (the pack toolchain never imports the kernel), and the kernel re-checks stored bytes with its tokenizer (`client.invalid`). The full rules are in writing-extension-ui.
- **Check** (`capybara-plugin check`, `check/client.ts`, `check/deps.ts`): errors `client-import-forbidden`, `client-css-remote`, `client-size`, `client-api-version` (the packed section was built for a client API other than the toolchain's `CLIENT_API_VERSION`), `client-undeclared`, `appearance-invalid`; warnings `client-css-selector` (a selector not built from `[data-cap-part]`, `[data-cap-state]` or `cx-<plugin>-` classes, or a `:root` custom property not named `--cx-<plugin>-*`) and `ui-part-unknown` (a `data-cap-part` value not in `UI_PARTS`). The plugin dependency boundary allows `@capybara-hq/plugin-client` (dev and peer) next to `plugin-sdk`.
- **`@capybara-hq/plugin-client`** is a published package: `CLIENT_API_VERSION` is pinned equal to the SDK's (`check:plugin-client-api` and an SDK test); a bundle with a newer `apiVersion` than the kernel supports is refused at import (`client.api_unsupported`) and never listed or delivered; the kernel's gate is authoritative (the host stamps its own version into the import map, so the bundle's `apiVersion` is a repeated check in the web).
- **`suggestedAppearance`** (top level of `plugin.json`; JSON Schema regenerated by `pnpm gen:package-schemas`): `{ theme?: "<theme file id>", replacements?: { "<slot ref>": "<component contribution id>" } }`. At least one of the two; `theme` names a theme the plugin carries; `replacements` needs an extension, has at most 8 entries (`PLUGIN_MANIFEST_LIMITS.appearanceReplacements`), each key a slot ref (`parseSlotRef`) and each value a contribution id. For a slot the SDK knows it must be `cardinality: "single"` and the value a `component` contribution of the manifest in that slot (`appearance-invalid` otherwise); an unknown slot is accepted and skipped when applied. Nothing applies on install; an admin applies it (writing-extension-ui: results in the order the author wrote the keys, at the org level `from` is the value in effect with `followsPlatform`, and a plugin with client code reloads the page after the apply). Two refs to one slot (`shell.brand` and `shell.brand@1`) are refused by the parser. Authors of overlay components mark decorative text beside their interactive elements `aria-hidden` themselves (the decoration layer hides only whole elements). There is no `decorations` field: decoration is on wherever the plugin is on and scopes itself with the `theme=` state token.
- **Bootstrap rule**: a bootstrap plugin may not carry client code: client files are kept in and delivered from object storage, which a bootstrap run may not have (the object store may be a bootstrap plugin itself). The kernel's bootstrap import refuses such a package (`client.invalid`, naming the plugin; a required entry then stops the start), and `check:bootstrap` reports it first (rule `bootstrap-client-code`: workspace entries from their pack, npm entries from the tarball in the network mode).
- Org uploads with client code follow the extension branch (`awaiting_confirmation`, the permission snapshot needs approval); nothing is delivered before both.

## Setup guides (`setupGuides`, spec `2026-11-09-setup-guides-v2-design.md`)

A guide is a Markdown document a plugin ships, rendered where a person sets up what it brings, with
live check rows. v2 replaced v1's steps and files directly (pre-0.1.0, no compatibility layer; spec
§15).

- **Declaration** (§4.1, SDK `setup-guide.ts`): `plugin.json` `setupGuides` (≤ 8) of `{ id, place,
  template? }`. `id` `^[a-z0-9][a-z0-9-]{0,63}$`; the documents sit at the fixed paths
  `guides/<id>.md` (English, required) and `guides/<id>.zh.md` (optional; `setupGuideDocPath`).
  `place` is one of `SETUP_GUIDE_PLACES`: `channel-connection` (the extension must provide
  `channel@1`; at most one per plugin) or `connector-template` (`template` required: one of the
  plugin's own `connectors/<template>.json`, at most one guide per template). The title is the
  document's `#` heading; there is no title, steps or files field.
- **The document** (§4.2): CommonMark + GFM with exactly one leading `# Title` (no further `#`),
  `{{name}}` variables, sections (a column-0 line `::: mode <mode>` or `::: audience <audience>`
  opens one, `:::` closes it; one `mode` section may nest inside an `audience` section, nothing
  else nests), check lines (`::check <id> <label>`: a plugin check id `^[a-z0-9][a-z0-9-]{0,47}$`
  or a kernel `capybara:<id>`, label ≤ 80 plain characters) and code fences `<language>
  [title="<text>"]`. Directive lines and fence info strings never hold variables; indented code
  blocks are refused. Limits are `SETUP_GUIDE_LIMITS` (64 KiB per document without NUL or
  U+E000–U+E0FF, 24 code blocks, 16 checks, 16 sections, 100-character titles and headings).
- **Places** (`SETUP_GUIDE_PLACE_INFO`, §9.1): each defines its modes, audiences (and the org action
  each needs), typed variables (`url` / `text` / `token`) and whether it records drift.
  `channel-connection`: modes `long_connection` / `webhook`, audience admin (`channels.manage`).
  `connector-template`: no modes, audiences admin (`connectors.manage`) and member
  (`connectors.use`). No variable is ever a secret, a config value or a client id (§6.3).
- **Languages** (§4.3): the zh document carries the same sections in the same order, the same check
  ids and byte-equal code blocks (titles aside); pack, check and import refuse a difference and
  name the block and the first differing line. Drift hashes only the English document.
- **Rendering** (§6, §7, `renderSetupGuide` in `setup-guide-render.ts`): parse first, substitute into
  the tree, escape per node (JSON escapes in `yaml` / `json` fences, so put the variable inside
  double quotes), sanitize (no raw HTML, no images, author links https only, no autolinks from
  text) and cut into blocks `markdown` / `code` / `check`. Deterministic.
- **Validation** (§4.5): `validateSetupGuide` is the one validator. `capybara-plugin pack` / `check`
  fail on its errors (and on a plugin check id missing from the extension's
  `permissions.setupChecks`, or any plugin check in a plugin without an extension) and print its
  warnings (e.g. a `text` variable outside double quotes in a `yaml` fence; never fatal). The kernel's
  `readPluginFiles` runs it at import with `allowUnknownVariables` (a newer variable stays as
  written) and fails the import with `catalog.invalid_manifest` naming the guide. An unknown
  `capybara:` check renders as `unknown`.
- **`capybara-plugin guide <id> [--locale en|zh] [--mode m] [--audience a] [--var name=value]…`**
  (`packages/plugin-tools/src/guide/cli.ts`) prints the guide rendered as the kernel would, then
  the unresolved variables: what an admin will see.
- **Storage and rendering in the kernel**: the documents are kept with the version like the icon
  (`catalog_files`, paths in `catalog_item_versions.files`). `PluginGuides`
  (`packages/kernel/src/extensions/plugin-guides.ts`) renders `GET
  /api/v1/orgs/:orgId/catalog/:itemId/guides/:guideId?mode=&audience=&locale=&connectionId=&name=&connectorId=`
  with the catalog visibility (`orgVisibleItems`), then the place and audience action, then the
  target (a live connection on the plugin, a connector made from the template; else
  `channel.not_found` / `connector.not_found`); `resolvePlace` (`guide-places.ts`) fills the
  variables and the `unresolved` reasons. A stored v1-shaped entry is skipped and logged, not a
  crash. The super admin's preview `GET /api/v1/admin/catalog/:itemId/guides/:guideId` renders with
  no org and no target.
- **Drift** (§11, `setupGuideHash`): sha256 over the code blocks and check lines of the English
  document after section selection (prose, headings and labels never count). Channel connections
  and connectors made from a template record `guide_ack` (writing-channels, writing-connectors).
- **Checks** run by the plugin's extension (`ctx.setup.check`, writing-extensions) or by the kernel
  (`capybara:*`); agents read guides through the Platform `setup` domain (writing-kernel-api).

## Connector templates (`connectors/<id>.json`, C30)

```json
{
  "$schema": "https://capybarahq.com/schemas/connector-template.v1.schema.json",
  "displayName": { "zh": "Acme CRM", "en": "Acme CRM" },
  "description": "Acme CRM over MCP",
  "icon": "./icons/crm.svg",
  "template": {
    "plugin": "connector-mcp",
    "pluginVersion": "^0.1.0-rc.0",
    "connector": "mcp",
    "endpoint": { "url": "https://mcp.acme.example/mcp" },
    "editableEndpoint": ["url"],
    "auth": { "type": "bearer", "ownership": "org" },
    "defaultToolPolicies": { "search": "allow", "delete_record": "deny" }
  }
}
```

The file is strict; `template` is validated by `validateConnectorTemplate`, and values are never echoed in errors.

- `plugin` / `connector`: the connector extension's name and its `Connector.kind`. At import, when that connector is **loaded on the replica serving the request**, the endpoint is validated against its `endpointSchema`, every `editableEndpoint` path must be a field of that schema, and `pluginVersion` must be satisfied by the loaded version. When the connector is this plugin's own extension or comes from one of its dependencies, only the static checks run now (the review shows `endpointChecked: false`). Any other connector that is not loaded -> 422 `catalog.invalid_manifest`. At org install it is checked again against the connector loaded at that time (not loaded, or not at `pluginVersion` -> `catalog.not_deployed`).
- `endpoint`: the preset, visible to every org; **no credential-like keys at any level** (`token`, `apiKey`, `secret`, `password`, `authorization`, `cookie` and so on, ignoring case and `-` / `_`); headers, query and URL userinfo are checked by the connector install rules too.
- `editableEndpoint`: the dotted paths an org may change at install (letters, digits, `_`, `-`, <= 50, no duplicates, not credential-like). List only fields that really differ by org (the `url` of a self-hosted service, a tenant id). Changing another path -> 400 `validation_failed`; the merged endpoint is re-checked against the schema, the credential rules and the OAuth address policy.
- `auth`: the shape of the connector install API's auth methods (`none` / `bearer` / `basic` / `api_key` / `headers` / `oauth_code` / `oauth_client`), **without credentials** (extra fields are rejected). An org fills in only `credential` (static) or `client: { clientId, clientSecret? }` (OAuth). `ownership` defaults to `auth.ownership` and must match it when given; not allowed with `auth.type = none`.
- `defaultToolPolicies`: local tool name (without `<slug>__`) -> `allow` / `ask` / `deny`, recorded as `policy_source 'template'` (kept through drift review like an admin's setting). For an authorization-code connector it applies when the first member connects. When unsure, do not write `allow`.
- `icon` (file level): a safe path relative to the plugin root (a leading `./` is optional), `.svg` / `.png`, checked like the plugin icon.
- `defaultEnabled` (file level, optional boolean, default `true`): `false` ships the template switched off. While it follows its plugin it is off in every org, even where the plugin is on, until an org admin switches it on (`PUT /orgs/:orgId/components/connector_template/:id/switch { enabled: true }`); while off it creates no connector at install and needs no org input (no `needs_config`). Read from the platform row's `file` (`loadComponents` -> `defaultOff`, `componentOn`); ignored for a builtin plugin and for a template the super admin gave its own scope. Previews count it: moving it from its own scope back to follow lists the orgs it turns off in; a platform update takes an added template's value from the target's file (shipped off: no `needsConfig`), and one that flips it lists each org without a switch under `needsConfig` (now on) or `turnedOff` (now off; agents using it, connectors kept). Use it for a template most orgs that turn the plugin on do not want (Slack's personal connector next to its bot).

## Marketplaces (`marketplace.json`)

```json
{
  "$schema": "https://capybarahq.com/schemas/marketplace.v1.schema.json",
  "schemaVersion": 1,
  "name": "Acme plugins",
  "owner": { "name": "Acme", "url": "https://acme.example" },
  "plugins": [
    {
      "name": "crm",
      "summary": { "en": "CRM tools", "zh": "客户管理工具" },
      "displayName": { "zh": "客户管理", "en": "CRM" },
      "version": "1.2.0",
      "minKernel": "0.1.0",
      "permissions": { "keys": ["db"], "sensitive": [] },
      "source": { "npm": { "package": "@acme/plugin-crm", "version": "1.2.0", "integrity": "sha512-…" } }
    }
  ]
}
```

- Unknown fields are dropped (forward compatible). One entry is one version: `(name, version)` is unique, where the version is `version`, else `source.npm.version` (`marketplaceEntryVersion`). When both are given they must be equal. `capybara-plugin marketplace --write` lists **one entry per plugin**, its current version (spec `2026-11-05-plugin-component-management-design.md` §13.2, following Claude Code's marketplaces; older versions stay importable by direct npm import, imported versions stay in the catalog); readers still accept several versions of a plugin (custom marketplaces in the older form), and the web groups them per plugin. An entry may carry `deprecated: true | { reason? }` (`marketplaceEntryDeprecation`), set by hand by the maintainer on a published version's entry (never in `plugin.json`: that would change the pack) and kept by `--write`; the kernel never offers it as newer or as the default version and refuses importing or requesting it (409 `marketplace.entry_deprecated`); the web lists it under 其他版本 as 已废弃 with the reason. The web's row shows the newest stable importable version, prereleases folding into 其他版本 unless no stable version can be imported.
- `summary: { en, zh? }` (≤ 280 characters each; `--write` takes it from the `plugin.json` `description`, which is a string (`en`) or `{ en, zh? }`; read it with the SDK's `pluginDescription`) and an optional `displayName: { zh, en }` (copied from `plugin.json`): the market lists show `displayName` in the UI language, else the name, and the `zh` summary in Chinese (`GET …/marketplaces/entries` returns `displayName` or null and searches it). `capybara-plugin check` warns (`release-description-zh`, never failing) when a public plugin's description has no `zh`. Catalog item views (admin and org, list and detail) and the import review carry `description` (the `en` text, the item's column) and `descriptionZh` (the `zh` text of the latest version's stored manifest, or null; no column), and the web shows the one of the UI language (`descriptionOf`).
- `icon` (optional, display only; spec `2026-11-05-plugin-component-management-design.md` §16): the plugin's icon in the market list before it is imported (an imported plugin shows its catalog icon instead, also on a newer entry). An absolute `https://` URL whose path ends in `.svg` / `.png` (a query allowed, no fragment), or `./<path>.svg|png` in a git marketplace's repository, read at the refreshed commit from the pack the refresh fetched anyway (ignored in an http marketplace; a single-plugin repo's entry takes its `plugin.json` `icon`). The refresh keeps icons in `marketplace_icons` (migration 0101; `catalog/marketplace-icons.ts`): a URL is downloaded through `packages/kernel/src/net` under the marketplace network rules and `marketplaces.allowedHosts`, never with the token, 10 s, <= 64 KiB, only when not stored yet (a URL's content counts as fixed: a new icon needs a new URL), at most 100 per refresh, never-tried URLs first, a failed one retried after 6 hours (`marketplace_icon_failures`); a path is read again at each new commit, and a commit whose icons were not stored (`marketplaces.icons_commit`) is read again; the bytes must really be svg / png (`iconProblem`). A bad icon is logged and skipped, never failing the refresh; icons no entry names are deleted. `GET …/marketplaces/entries` (admin) gives `icon` (the item's icon URL, else `/api/v1/admin/marketplaces/:id/icons/:sha256`, else null), served from PG with the plugin icon headers (`sendCatalogIcon`); the org browse (`GET /api/v1/orgs/:orgId/marketplaces/entries`) gives the item's org icon route when the org's catalog shows the item (share gate), else `/api/v1/orgs/:orgId/marketplaces/:id/icons/:sha256` (`catalog.decide`, browsing on, the marketplace enabled, else 404); both icon routes are Platform exclusions.
- `source` is exactly one of `{ npm: { package, version, integrity } }` (exact version, sha512 SRI), `{ archive: { url, integrity } }` (https, sha512 or sha256 SRI), `{ path }` or `{ git: { url, ref?, commit?, path? } }`. A `path` source is read from a git marketplace's own repository at its last refreshed commit (a git marketplace whose url or ref changed since that refresh returns 409 `conflict`: refresh first) (in an http marketplace it is listed with `reason: "path_needs_git_marketplace"` and importing returns 422 `marketplace.path_unsupported`); a `git` source is read at its pinned `commit`, else at its `ref`'s head at import time; the imported version stays pinned to the commit recorded at import. Both are recorded with source `git` and `source_detail` (host, repo, path, ref, commit, followsBranch); a git / archive host outside `marketplaces.allowedHosts` is `reason: "host_not_allowed"` / 403 `marketplace.host_not_allowed`. A git marketplace (`owner/repo`, an https `.git` URL or `form: "git"`, optional `ref`; no mirrors) reads `.capybara-plugin/marketplace.json`, or a single-plugin repo (root `plugin.json` or `skills/`) as one entry; an unchanged commit skips the refresh (only `info/refs` is fetched). The refresh also resolves the branch head (and the plugin directory's tree oid) of imported entries that follow a branch, so an entry shows `contentChanged` ("content changed at the same version") when its directory moved on; a monorepo commit that leaves a plugin's directory alone does not flag it.
- **Git access** (`git-source.ts`, isomorphic-git, Decision 2): https smart HTTP only, depth 1, one commit, no tags, submodules never fetched (a submodule or symlink entry under the plugin's path is `marketplace.git_unsupported_entry`), LFS pointer files read as plain files; the pack <= `packages.maxBytes`, <= 5000 files, <= 4 x `packages.maxBytes` unpacked (else `marketplace.git_too_large`), 120 s per operation; files are read from the fetched pack, never checked out. Other failures are 502 `marketplace.git_failed`; a pinned commit the server will not serve says "pin a branch or tag tip". The marketplace token (`catalog-token:<id>`) is sent as Basic `x-access-token:<token>` only to the marketplace URL's origin, never to other repos or archive hosts.
- **Network rules** (`packages/kernel/src/net`, every marketplace, mirror, archive and git download): https only (`http` only to loopback with `marketplaces.allowInsecureLoopback`, testing), no redirects (`marketplace.redirect`), every resolved address must be public (`marketplace.private_address`; the ranges of the sandbox egress proxy, v4-mapped / NAT64 / 6to4 included) and the connection is pinned to the checked address. Exceptions: `marketplaces.allowPrivateHosts` (hostnames, or IPs / CIDRs that match **IP-literal URLs only**: an internal DNS name must be listed by name; link-local and metadata addresses are refused even then; prefixes shorter than /8 (IPv4) or /16 (IPv6) are refused) and the origin of `packages.npmRegistry`. `marketplaces.allowedHosts` (hostnames or IPs, no port; empty = unrestricted) limits the hosts entries may download git and archive sources from; it does not apply to a direct git import, which is the admin's own action. With `net.httpsProxy` set (`packages/kernel/src/net/proxy.ts`), https downloads tunnel through the proxy with `CONNECT` (Basic proxy auth from the URL userinfo, never in errors or logs; a non-2xx answer is `net.proxy_refused`) and the kernel does not resolve the target: SSRF protection for DNS names is then the proxy's job, while IP-literal private and link-local targets, `allowedHosts`, https-only and no redirects still apply; `net.noProxy` hosts (and loopback) go direct with local resolution and pinning. npm registry downloads (`packages.npmRegistry`, trusted by origin) do not use the proxy in this release. Without a proxy, a fake-IP DNS resolver (answers in `198.18.0.0/15`) makes every host look private: set `net.httpsProxy`, use real DNS for the kernel or list the hosts in `marketplaces.allowPrivateHosts`. The CLI git import (`git:<url>`) takes no token.
- Downloads are always verified against the marketplace's integrity, never npm metadata (`marketplace.integrity_mismatch`). npm sources are fetched from `packages.npmRegistry`; archive URLs are https only, no redirects, size-capped, and never get the marketplace token. `permissions` is display only: the review warns when it differs from the package (`permissionsMismatch`, kept with the staged import).
- `minKernel`: an entry needing a newer kernel is listed as incompatible (`marketplace.incompatible`).
- Tests: `startFakeMarketplace({ manifest })` from `@capybara-hq/testing` serves `/marketplace.json`.

## Platform import: one review (`/api/v1/admin/catalog/*`)

Every plugin, whatever it contains, goes through the same two steps (`packages/kernel/src/catalog/plugin-import.ts`).

- **Prepare** (200 `{ stagingId, review }`): `POST import/file` (the tgz as the raw body, `application/octet-stream`, <= `packages.maxBytes`), `POST import/npm { package, version? }` (version, dist-tag or range; verified by `dist.integrity`), `POST import/git { url, ref?, path? }` (a direct git import: an https URL or `owner/repo`, a branch / tag / 40-hex commit, default the remote HEAD, and the plugin's folder, default the root; no marketplace is created and no updates are tracked; a bad url or path is 400 `validation_failed`), or `POST /api/v1/admin/marketplaces/:id/entries/:name/import { version? }` (default: the newest compatible version; also returns `permissionsMismatch`). It reads the whole plugin (`readPluginPackage`), the extension's module graph and migrations, checks skills, templates, icons, name and version conflicts (`catalog.version_exists` when the release is already imported with the same content digest; other content at an imported version is recorded as `<version>+git.<sha12>` / `+sha256.<12>`, spec §5.3; `catalog.name_conflict`, config-declared extension names), the extension's deployment state (a downgrade to a version with unrun migrations -> `extension.downgrade_unsupported`) and resolves dependencies for display. Then the extension goes into the package store (source `catalog`), the skill / connector template / agent template files into object storage under the staging prefix, the display files (the plugin icon, connector template icons, setup guide files) into PG, and a staging row is kept for 24 hours (audit `catalog.plugin_staged`). **Display files live in PG, never object storage** (`catalog/catalog-files.ts`, table `catalog_files`, migration 0100): content-addressed by sha256 (one row shared by every version listing it; a reader asks only for the sha256 its version row records and re-checks it), written in the staging row's transaction (`ON CONFLICT` renews `touched_at`), read only from PG by `readCatalogDisplayFiles` (the icon routes, `PluginGuides`; no object-storage fallback, a listed file missing from PG is `internal`). So a deployment without an object store still imports and shows icons and guides, and a bootstrap plugin's icon (object-store-s3's own included) is stored before any object store runs. The staging cleanup job sweeps rows no version or staging lists once older than the staging TTL. A display file inside a skill directory or at a template's path is also stored under the object prefix (each reader looks in one place). Object storage is asserted only when the plugin ships skills or templates.
- **Review** (`PluginReview`): name, version (and `pluginVersion` when build metadata was appended), `contentDigest`, npm package (null without `package.json`), publisher, license, homepage, source (`source.detail`: `{ host, repo, path, ref?, commit, followsBranch, tree? }` for git, `{ url }` for an archive, `{ registry }` for npm; stored on the version as `source_detail`); `provenance` (spec §5.5, display only: for npm sources the registry's attestation `<registry>/-/npm/v1/attestations/<name>@<version>` is parsed for "built from `repository`@`commit` by `workflow`"; signatures are not verified; no attestation, offline or unreadable -> `{ checked: false, reason }`, "provenance not checked", never a refusal) and `provenanceWarning: "repository_mismatch"` when a git marketplace's repository differs from the attested one; the extension (`action` `install` / `upgrade` / `keep`, permission groups with additions and removals against the current snapshot, migration warnings, sensitive items); every skill with its body; every connector template with endpoint, auth and editable paths; every agent template (`agentTemplates`: name, path, description, instructions, model tier and tool narrowing; covered by `reviewHash` only when there are any, so earlier digests are unchanged); every dependency with the version it resolves to (`resolved`, or null). An unresolved dependency **does not block the import**; orgs cannot install until a matching version is imported. Dependencies are never fetched.
- **Reopen**: `GET imports/:stagingId` returns `{ stagingId, review, permissionsMismatch? }` for a staged import (404 `plugin.staging_not_found` when expired or confirmed). The web's review page (`/admin/plugins/import?staging=<id>`) loads from it, so a review link can be shared or reopened.
- **Confirm**: `POST imports/:stagingId/confirm { reviewHash, scope?, orgs? }` (201 `{ item, deploy }`; the removed `deployExtension` and `pinnedSuggestions` are unknown keys, 400). `reviewHash` must match, and the extension's deployment state is recomputed (installed / upgraded / swapped since the review -> 409 `plugin.review_stale`). It writes the extension's permission snapshot when this import installs it (audit `extension.permissions_approved` with the plugin), then creates the item or adds the version: `manifest` (the normalized `plugin.json`, with skills and templates listed explicitly), `extension_sha256`, the stored files.
  - Confirming **always installs and enables the plugin's extension** on the deployment (each replica reconciles, no restart); an `upgrade` also gets its snapshot. A failed deploy is returned in `deploy`, not thrown; the committed item stays (retry with `POST items/:id/confirm`, or from the extensions page by sha256). A version older than the deployed extension is **catalog-only** (review action `keep` with `olderThanDeployed`): the deployment stays.
  - `scope` (`all` / `optional` / `named`) and `orgs` apply to a **new** item only (default `optional`; `named` needs at least one org, else 400); a new version of an existing item never rewrites its scope and an import never downgrades it. A newly imported dependency takes the dependent's scope (spec §5 rule 9). A request-driven import (kind `import`) defaults to `named` = the requesting org and resolves the request in the confirm's transaction.
- Errors: a pre-0.1.0 package (a `capybara` section in `package.json`, or an app bundle, without `.capybara-plugin/plugin.json`) -> 422 `catalog.legacy_format` ("repack it as a plugin with .capybara-plugin/plugin.json (pnpm pack-plugin)"); any other invalid plugin -> 422 `catalog.invalid_manifest` with every problem in the details.
- Expired staging is cleaned by the hourly `@LockedCron` job `app-staging-cleanup` (`CatalogJobs`, once per hour across replicas; the job name is frozen). A stored extension package stays in the content-addressed store and, with no install record, is never loaded.
- Catalog item routes: `GET items` (`?pending=true` lists the 待确认 ones) / `items/:id` / `items/:id/icon`, `POST items/:id/scope/preview` and `PUT items/:id/scope` (`{ scope, orgs?, scopeHash }`), `PUT items/:id/disabled`, `PUT items/:id/shown` (对其他组织显示, audited `catalog.shown_changed`), `POST items/:id/confirm` (approves the permission set the item still lacks and installs a never-deployed extension), `DELETE items/:id` (a platform item whose extension is enabled on the deployment -> 409 `catalog.extension_enabled`, details `[{ extension, displayName }]`, like an uninstall: disable it first; a disabled extension keeps its install record, uninstalled on the Extensions page). There is no `kind` anywhere and no `policy` or `install-deployment` route (migration 0075 backfilled scope from policy, grants, installs and required bootstrap plugins).

### Scope (`catalog/scope.ts`, `catalog-scope.service.ts`, `scope-sync.ts`)

- Each item has `scope` (`all`: on in every org, an org admin may switch it off (the choice is kept in the switch row, also when the scope changes); only builtin items cannot be switched; `optional`: off until an org admin switches it on; `named`: on in the listed orgs, which may switch it off, invisible to others unless `shown_to_others`), `builtin` (a required bootstrap plugin: `all`, scope not changeable, 409 `plugin.builtin`), `disabled` (a deployment-wide stop; the scope is kept) and `scope_version`. The pure functions `wantedOn` / `visibleTo` / `switchable` / `requestable` decide the effective org state (`on` / `off` / `needs_config` / `unavailable` / `not_offered`); tables `catalog_item_scope_orgs` and `catalog_item_org_switches`.
- A scope or disabled change first **previews its impact** (orgs and agents that lose the plugin, orgs that would need config) and is confirmed with the preview's `scopeHash` (409 `plugin.scope_stale` when it changed meanwhile); each change bumps `scope_version`, audits `catalog.scope_changed` and owes the sync in the same transaction (an outbox row).
- **Sync**: `PluginScopeSync` on queue `cap-kernel-plugin-scope` (consumer only under `WorkerModule`, `PluginScopeWorkersModule`) converges each (item, org) to `wantedOn` (or a live install depends on it): wanted on and not installed -> installs as the kernel (null actor, audit actor `scope`, no switch row); the org needing input -> `needs_config`, never attempted; wanted off -> uninstall. Job ids `scope-item-<itemId>-<scope_version>` and `scope-org-<orgId>` (owed by the org's creation), both outbox jobs (`PluginScopeSync.enqueueItem` / `enqueueOrg`, `propagation: "mandatory"`): every transaction that changes a scope, the disabled flag, a `named` list, the owner or the platform version owes the item's job, and a confirmation whose last write (the extension's deploy) is not the scope service's owes it in a transaction of its own after it; its commit (the import's, an org upload's first version, or a transaction before a permissions confirm's deploy) also owes a backstop `scope-item-backstop` (`scopeBackstopJobId`, `runAt` 5 min) that throws, so BullMQ retries it (5 attempts, 1 min doubling), while the extension is not enabled on the deployment, never recording `catalog.not_deployed`. The CLI's import owes its sync the same way (`OutboxService` in the CLI context). No start-time resync: a migration that changes a scope inserts the outbox rows itself (writing-migrations). Pairs of one org serialize on a Redis lock; a failure is logged, audited `plugin.scope_sync_failed` and kept in `plugin_scope_sync_failures` (the super admin's inbox), no retry until the next sync of the item. The installer re-checks scope, list and switch under the org row lock (`ScopeNoLongerWanted`).

### Platform components (phase 2, `catalog/platform-components.ts`, `component-state.ts`, `component-scope.service.ts`)

Spec `2026-11-05-plugin-component-management-design.md` §6-§8 and its rulings §13.6 (A2-F2, P2-n).

- **Tables** (migration 0081): `platform_skills` / `platform_skill_versions`, `platform_agent_templates` / `platform_agent_template_versions`, `platform_connector_templates`; files under `deployment/platform/{skills,agent-templates,themes}/` (never `kernel/<orgId>/`: orgs are purged by prefix): a plugin sync's under `sha256-<digest>/` of their content (`contentPrefix`), an upload's or promotion's under `<id>/<version>-<uuid>/`. Invariant: nothing deletes a content-addressed platform object (versions with the same content share it, and an import that rolled back leaves objects a later one reuses); any future garbage collection must count the version rows referencing a prefix before deleting it. A plugin's components are planned and their files copied before the transaction (`prepareImport` for a confirm, `prepareSync` for the platform update and the confirmation of an org upload's first version), and their rows written in it (`applySyncIn`): the import confirm that makes an item's first usable version, the super admin's confirmation of an org upload's first version and the platform update each write them in their own transaction, so a failure rolls the whole step back and a retry copies nothing again (no job heals an item later; transactional outbox spec §8.1). Unchanged components keep their version. A super admin may upload a version on its own: `POST /admin/components/skill/:id/versions` (zip as the raw body) and `…/agent_template/:id/versions { content }` (the name may not change; 409 `component.version_stale`; the version is `updated_on_own`, which the next update preview marks).
- **On in an org** (read at every resolution, never copied): the component is live and not disabled, its plugin is not deleted or disabled, and either it follows the plugin (`scope_mode: follow`: a live install in the org or builtin, and no `component_org_switches` row off) or it has its own scope (`own`: `wantedOn` over `component_scope_orgs` and the switch). Skills: `skills/usable.ts` (`usableSkills`, `skillVersionsById`); agent templates: `agents/templates.ts` (`loadTemplates`, `usableTemplates`). An org's own skill or template of the same name wins (rule 10, logged). A skill on in the org reaches every agent unless the agent's `disabledSkills` turns it off (`agentSkills`); the skills of builtin items (platform-owned `catalog_items.builtin`, e.g. `skills-core`'s `skill-guide`; `builtinSkillIds`) cannot be turned off (the agent's own skill of the same name wins; the library list marks them `builtin: true`).
- **Routes**: `GET /admin/components?kind=` (platform components plus org-owned skills and templates, read-only, P2-11), `…/:kind/:id/versions`, `POST …/:kind/:id/scope/preview` (`{ scope, orgs? } | { disabled: true } | { follow: true }` -> `{ affected, conflicts, scopeHash }`), `PUT …/scope`, `…/disabled`, `…/shown` (409 `plugin.scope_stale` / `plugin.skill_conflict` / `plugin.builtin`; audits `component.scope_changed` / `component.shown_changed`); `GET /orgs/:orgId/components?kind=&itemId=` (members; `switchable`, `locked`, `pluginOn`) and `PUT /orgs/:orgId/components/:kind/:id/switch { enabled, confirm? }` (org admins through the kind's manage action; not offered -> 404, `all` -> 409 `plugin.scope_locked`, off answers `{ preview: { agents }, confirm }` first, 409 `plugin.switch_stale`; on refuses a same-name own skill and a disabled component). A plugin scope change resets components with their own scope to `follow` after its preview lists them (`replaced`).
- **Linked org copies** (ruling B2): skills and templates that installs copied before phase 2 link to their platform component (`skills.platform_skill_id`, `agent_templates.platform_template_id`) and keep their ids, so agent definitions and logs are never rewritten. Without `pinned_version` a copy serves the platform's current version under its own id; with one it serves its own stored version (the copy changed in the org, or an org upload to its name pinned it, P2-4) until a platform update clears the pin where the component is on (P2-8). A pinned copy still follows its component's availability (ruling P2-18: deployment disable, org switch-off, scope removal, uninstall hide it; the pin fixes the version only), except after a platform update removed the component (P2-7: it then stays the org's own), and `referenceIds` counts it, so the disable, scope and uninstall previews list its agents. Connectors follow their template through `connectors.platform_template_id` (ruling E2). An org's own skill or upload named like a platform skill offered to it is refused (409 `plugin.skill_conflict`, P2-3).
- **Platform inbox** (`inbox/platform-inbox.service.ts`): `GET /admin/inbox` (super admins, `{ items, truncated }`, at most 100) and `…/count`: `catalog_request`, `permission_confirmation`, `scope_sync_failed` (`plugin_scope_sync_failures`, migration 0083: one row per plugin and org, written with the `plugin.scope_sync_failed` audit and deleted by the next attempt of the pair that does not fail, P2-12). No actions; the web links each to its page.

### Org uploads and owner mode (phase 3, `catalog/org-plugin-uploads*.ts`, `ownership.ts`, `owned-items*.ts`)

Spec §14 (rulings P3-1…P3-52; migration 0084). Every reader of an org-owned item must keep these.

- **Owner and share gate**: `owner_org_id` (null = platform) and `shareable` on `catalog_items` and the `platform_*` component rows (an org plugin's flag is copied to its components in the same transaction). The gate `owner_org_id IS NULL OR shareable` is checked on the row written by `requestable()`, `PUT …/shown` true, `addScopeOrg` and widening to `optional` / `all` (409 `catalog.not_shareable`; import confirm fails closed, P3-26). Turning 可共享 off narrows an `optional` / `all` item, or a component's own `all`, to `named` = owner + the orgs where it is on (P3-25). The owner org cannot change scope or drop itself (409 `catalog.owner_required`); only what the org created is shareable (409 `catalog.not_owned`: copies, plugin skills and, until phase 4, agent templates, P3-46).
- **Routes** (org admin, `catalog.upload`, checked before the body is read, P3-29): `POST /orgs/:orgId/catalog/uploads/file` (tgz only; `{ stagingId, review, update }`) -> `GET …/uploads/:stagingId` -> `POST …/uploads/:stagingId/confirm { reviewHash }`; `PUT /orgs/:orgId/owned-plugins/:id/shareable`, `POST …/:id/delete/preview` -> `POST …/:id/delete`, `DELETE …/:id/pending` (withdraw). Staging rows carry `org_id`: org routes see only their org's, admin routes only the platform's (P3-8). The commit goes through `PluginImport` in owner mode: the item is owned by the org, scope `named: [owner]`.
- **Pending (P3-9…P3-11, P3-31…P3-38)**: an upload with an extension stores the package and claims the extension name (before the plugin-name check, P3-33) and nothing else: no snapshot, no install, no components, no sync. `awaiting_confirmation` marks a first version, `pending_version` / `pending_by` / `pending_at` a later one. The super admin's `POST /admin/catalog/items/:id/confirm` takes the digest of the package's sha256 and `reviewHash` (`pendingDigest`), runs every step under the item's lock, and answers 409 `extension.approval_stale` for a replaced upload, `extension.name_conflict` for an install of the name that is not this item's (another package, or the same package name left by another owner's item: org code never inherits another item's config, P3-36, P3-51), `catalog.item_removed` when the item went away meanwhile (the cleanup takes the extension out, P3-21). The order differs by version (P3-37): a first version is installed, approved, enabled and only then marked confirmed (a confirmation that did not win takes its install out); a later version is applied first (`updateToPendingLocked`) and approved after, and a failed approval puts the pending state back so it shows in 待确认 again. `POST …/reject { reason? }` deletes a first version (name claim released, under the per-name install lock) or clears a later one, and marks the version `rejected_at`. A pending or rejected version never becomes `latest_version`, and the scope sync, org switch, dependency resolution and generic update read only applied versions (P3-34); a version row's `applied_at` (set on apply / confirm; an org upload writes null) and `rejected_at` keep that true after a transfer to the platform (P3-52). The scope sync of a just-confirmed extension that its replica has not loaded yet re-enqueues itself (`scope-item-<id>-<v>-r<n>`, P3-38).
- **Versions without an extension (P3-12, P3-12', P3-30, P3-32)** apply at once through the platform updater acting for the owner org (one hash covers the review and the update preview, whose `orgNames` names the other orgs it mentions); dropping the extension or moving to a lower version is allowed; an awaiting item that gets one takes it as its first version.
- **Names (P3-14, P3-28, P3-51)**: a plugin name live for another owner -> 409 `plugin.name_taken` with `details[0].owner`; so is an org upload whose npm package another owner holds (`assertPackageFree`: a package name is an identity within one owner only, and the cleanup's `referenced` compares item and owner, never the package alone); a bootstrap pin whose name an org holds fails with a warning naming the org; the same `owner` on `extension.name_conflict`; an org upload of a name in the bundled bootstrap manifest or any marketplace entry the deployment has read -> 409 `plugin.name_reserved` (bootstrap takes no name over either). Dependencies must resolve to confirmed, enabled items the org can use (409 `plugin.dependency_unavailable`, P3-13). `customSkills` deny refuses packages with skills or agent templates, `customConnectors` deny those with connector templates (403 `catalog.custom_disabled`, P3-15').
- **Delete, transfer, org deletion (P3-19…P3-21, P3-39…P3-41)**: an item on in another org (P3-18) is transferred (owner null, owner removed from its list, a component's own `all` narrowed to its users, `optional` stays optional, platform notice `ownership_transferred`), else removed (an owned plugin uninstalled in the owner org first). `OwnedItems.onOrgDeleted` does the same inside the org deletion's transaction; extension cleanup is the job `owned-plugin-cleanup-<itemId>`, owed in the removal's transaction (no sweep). Lock order (P3-50): org rows (sorted) -> the item -> its components; `PlatformPluginUpdater.commit` locks the connector orgs and the owner org before the item.
- **Promote on share (P3-3, P3-42…P3-48)**: an org skill stays an org row until the super admin shows or associates it (`admin/components/:kind/:id/*` accept the org row id and answer with the platform id, P3-23); promotion writes a platform row with `origin_org_id`, copies the files to a unique prefix under `deployment/platform/…` (P3-45) keeping the version number, and links the org row. The owner's later versions go to the platform row; the super admin cannot upload one (P3-48). Promoted rows are never plugin-installed or uninstalled (P3-47).
- **新建技能** (P3-24): `POST /orgs/:orgId/skills { name, description, body, shareable? }` writes `SKILL.md` and runs the upload's checks (409 `skill.name_exists`); a leading frontmatter in `body` is dropped except the invocation keys.
- **Notices**: org `item_shared`, `shared_item_updated`, `upload_confirmed`, `upload_rejected`; platform `ownership_transferred` (`POST /admin/inbox/notices/:id/dismiss`) and the inbox kind `org_upload_pending`.

## Agent templates as agent blueprints (phase 4, spec §15, `packages/kernel/src/agents/from-template.ts`, `org-templates.ts`)

Any member creates a private agent from a usable template (`POST agents/from-template`, an org admin may pick another 可见范围); `…/preview` resolves what carries over (instructions, tools usable in the org, skills by name, connectors, sub-agents into the roster) as 带入 / 待配置 / 不可用 with a `previewHash` that the create must repeat (409 `agent.template_preview_stale` when the template version or the org's state moved: never a half-resolved agent). A template that is not usable in the org (its plugin turned off there, another org's unshared template) answers 404 `component.not_found`, at the preview and at the create. A bare sub-agent type of a plugin's template resolves to that plugin's own template first (`<plugin>:<name>`, as a forked skill's `agent` does), then the exact bare type, then a unique `<plugin>:<name>`. The agent is a copy: it records its provenance (`created_from_template_id` / `_version` / `_name`, migration 0085) and is never linked back. A `{ template }` connector entry counts only a platform connector template the org may see (on or offered there, owned by it, or one it made connectors from; any other is `template_not_found`, named by the entry's reference only) and binds the org's oldest connector made from it (several: listed); a missing connector, or any `needs` entry, becomes a model-invisible entry of `definition.pendingConnectors` and the agent still runs. A `needs` endpoint loses userinfo, query and fragment on every path into a pending entry, a plugin's template included; one that is no http(s) URL is `invalid_endpoint`. Resolving one is `POST agents/:agentId/pending-connectors/:key/bind { connectorId }` (the agent's owner or an org admin; an unauthorised OAuth connector is refused with reason `not_synced`), after which a new agent version adds the connector's tools. Whoever cannot configure connectors gets one org inbox request per agent (`catalog_requests` kind `connector_setup`, with `agent_id` and the keys; created at create, again on `POST …/pending-connectors/request`); an admin configures it from the inbox dialog or rejects it with a reason, and it closes when the last key is bound or the agent is deleted. 另存为模板 (`POST agents/:agentId/save-as-template`, org admins) writes an **org** template row (`plugin_name` null, a bare name that must not clash with a type usable in the org, version 1, shareable under the P3 rules): a platform connector becomes `{ template }`, any other connector a `needs` entry whose endpoint has userinfo, query and fragment removed (a `PUT` that sends them is refused 400), never credentials, headers or OAuth data. Whatever a template cannot hold is listed in the answer's `omitted`, never dropped silently and never a 400: org agents in the roster, the agent's own skills, model parameters other than `effort`, the fallback model, an inline sub-agent's fields and skills past 3, blank inline texts and quick actions. Skills (skills default-on spec §6.2): the new agent has every skill on in the org; each name in the template's `skills` (and an inline sub-agent's) is reported `carried` or unavailable `not_found` and narrows nothing, and each `disallowedSkills` entry that resolves becomes a `disabledSkills` entry, reported `carried` with reason `disallowed` (one that names nothing the org has, or a builtin plugin or skill, is dropped). 另存为模板 writes the agent's `disabledSkills` as `disallowedSkills` (`<plugin>:*`, `<plugin>:<name>`, a bare name; what no longer resolves or is past 64 goes to `omitted`). Org templates are edited with the agent editor's sections on the template page and each save is a new version.

## Claude Code plugins (phase B, `packages/kernel/src/catalog/claude/`)

A Claude Code plugin is translated into an ordinary Capybara plugin on import (never with an extension: only skills, agent templates and `connector-mcp` templates), then follows the flow above (spec §8, "Phase B as built"). The reader is pure (`translate.ts`, `manifest.ts`, `mcp.ts`, `marketplace.ts`, `report.ts`) and treats the tree as hostile: every problem is a report item, never an exception.

- **Where from**: git only (a Claude marketplace entry, a single-plugin repo, `POST import/git`). An uploaded or npm tgz without `.capybara-plugin/plugin.json` stays `catalog.invalid_manifest`. **Detection** (`isClaudePluginTree`): no `.capybara-plugin/plugin.json` and one of `.claude-plugin/plugin.json`, `hooks/hooks.json`, `.mcp.json`, `commands/`, `agents/`, a root `SKILL.md`, or the entry comes from a Claude marketplace. A tree with only `skills/` stays the skills-only plugin. With both manifests the Capybara one wins and the review says so (`claudeManifestIgnored`).
- **Allowlist translation**: only the rows of spec §8.2 / §8.3 are translated. Skills (default `skills/`, `plugin.json` `skills` paths including `./`, a root `SKILL.md` moved under `skills/<name>/`) are stored byte for byte; a skill without `name` / `description` frontmatter is not imported; `disable-model-invocation: true` imports a manual-only skill (`skill_manual_only`), `context: fork` a forked one (`skill_forked`, `detail.agent`; `skill_agent_unknown` when `agent` is neither `general-purpose` / `Explore` / `Plan` nor an agent of the plugin); `allowed-tools` / `model` / …, Claude variables (skills and commands), `` !`cmd` `` shell injections (`skill_shell_injection`) and `@path` file references (`skill_file_reference`, they stay text) are warnings. Invocation keys the strict `parseSkillMd` checks refuse (a wrong type, an over-long `argument-hint` / `agent`, or both `disable-model-invocation: true` and `user-invocable: false`) are left out with `skill_invocation_key_ignored` (`detail.keys`, `detail.problem`) instead of refusing the skill or command, so a skill that imported before phase D still imports: the import reads a translated tree's SKILL.md files with `invocationKeys: false` (`readPluginFiles`, `checkContent`) and the install reads stored files leniently through `cleanInvocationKeys` (`skills/invocation-keys.ts`). A command's frontmatter that is not valid YAML is read again with its `argument-hint:` value quoted (Claude Code documents `argument-hint: [pr-number] [priority]`); a skill's SKILL.md is never rewritten, so invalid YAML there stays `skill_invalid`. **Commands** (phase D, `claude/commands.ts`; `commands/*.md` non-recursive, declared paths, or the object map with `source` / inline `content`) become ordinary skills (`command_imported`; model-invocable unless `disable-model-invocation: true`): each is generated as `.capybara-generated/commands/<name>/SKILL.md` (JSON frontmatter with `name`, `description` (else the first body line) and the command's invocation keys; body unchanged) and listed in `skills`; a name that is not a skill name, equals a skill of the plugin (the skill wins) or has no description is `command_invalid`. When the tree has a command, a manual-only or a forked skill, the translation's `translatorRevision` (`claude-translation-2`) is folded into `claudeContentDigest`, so re-importing a version imported before phase D is new content. `skill_manual_invocation`, `command_manual_invocation` and `skill_needs_subagents` are no longer emitted (kept for stored reports). Hooks are listed, never run (`hooks_not_run`; a `SessionStart` hook sets `sessionStart` and adds the warning `session_start_hook`: put the gist of what the hook adds in the agent's instructions; the older `session_start_pin_hint` is no longer emitted, kept for stored reports). **Agents** (`agents/**/*.md` or the declared paths; phase C, `claude/agents.ts`, sub-agents spec §16.4) become agent templates: each is generated as `.capybara-generated/agents/<name>.md` (frontmatter translated, written as JSON; body copied unchanged; the source file is never rewritten) and listed in the synthesized `agents`. Tools go through the Claude tool-name table (the names shared with Capybara map to themselves: `Bash` / `Read` / `Write` / `Edit` / `Glob` / `Grep` / `Skill` / `AskUserQuestion` / `ToolSearch` / `Agent`; `MultiEdit` -> `Edit`, `Task` -> `Agent`, `TodoWrite` -> `plugin__todo__write`; anything else, `mcp__*` entries and patterns such as `Bash(git:*)` in `tools` are dropped and reported: `agent_tools_unmapped`; a pattern in `disallowedTools` disallows the whole tool), `model` aliases map to tiers (`haiku` -> `fast`, `sonnet` -> `standard`, `opus` / `fable` -> `capable`; a full id by its family, else `inherit`: `agent_model_mapped`), `maxTurns` -> `maxSteps`, `skills` (> 3 or invalid names cut: `agent_skills_truncated`), `effort`; `permissionMode` / `hooks` / `mcpServers` are `not_applicable`, other fields `agent_field_ignored`; a name outside the template name rule, a missing description, a duplicate or an unparsable file is `agent_invalid` (never renamed). `agent_needs_subagents` is no longer emitted (kept for stored phase B reports). Agents are collected recursively, but a template is named by its file name only: a nested `agents/sub/x.md` becomes `<plugin>:x` (Claude Code includes the subdirectory), and same-named files in two subdirectories are `agent_invalid` duplicates. `package.json` is left out of the translated tree (it still counts in the digest). Version: `plugin.json` first (Claude's rule; the entry's version is not enforced), then the entry's, else `0.0.0-git.g<sha12>`; publisher: `author.name`, else the marketplace owner. `displayName.zh` copies `en`. Refusals (`catalog.invalid_manifest`) only for: a name Capybara cannot use or an unreadable `plugin.json`, a `strict: false` entry declaring components that `plugin.json` also declares, a plugin with no importable skill, no agent and no template, and a synthesized manifest that fails `parsePluginManifest` (a guard).
- **Remote MCP servers** (`.mcp.json` in either shape, or `mcpServers`) of type `http` / `streamable-http` become templates `.capybara-generated/connectors/<id>.json` for `connector-mcp`: `Authorization: Bearer ${X}` -> `bearer`, one other `${X}` header -> `api_key`, several -> `headers` (all `ownership: "personal"`, so the installer passes their own credential in `connectors.<id>.credential`; without it org install and upgrade planning answer 400 at that path before any write, and the web wizard asks for it), `oauth` -> `oauth_code` with MCP discovery and DCR, none -> `auth: none` plus `mcp_auth_none`, `${X}` in the URL -> an editable endpoint. Literal credential-like headers, `headersHelper`, user info or credential-like query parameters are `mcp_invalid`; `sse`, `ws`, stdio, `.mcpb` / `.dxt` are `mcp_unsupported_transport`. When `connector-mcp` is not loaded the templates get the static checks (`endpointChecked: false`) and a `connector_not_loaded` warning instead of the refusal of an unknown connector; org install still checks against the loaded connector.
- **Translation report** (`TranslationReport`): `format: "claude-code"`, `manifestPath`, `sessionStart`, `items` in five groups (`imported`, `converted`, `needsInput`, `ignored`, `warnings`) with a `code` and `detail`, sorted, at most 500 items (then one `{ more }` item; hook items 100 per kind); names, paths and details pass through `printable` (no control or bidi characters). Each component key takes at most 100 distinct declared paths (repeats skipped, the rest one `too many paths` item) and each JSON file is parsed once, so a hostile manifest cannot stall the event loop. A root `SKILL.md` takes every file not excluded, so a large repository can exceed the skill package limits and refuse the import. It is part of the review (`format`, `translation`, `repository` (display only, not hashed), `licenseText` (the root LICENSE of any plugin, ≤ 64 KiB, else `licenseTruncated`)), covered by `reviewHash`, and stored on the version (`source_format`, `translation`, `license_text`, `license_truncated`; the version API returns `licenseTruncated`). `capybara plugins import` prints it.
- **Claude marketplaces**: a git marketplace without `.capybara-plugin/marketplace.json` reads `.claude-plugin/marketplace.json`. Sources: a relative path (`metadata.pluginRoot` applies to bare names only), `github`, `url` (https), `git-subdir`; entries Capybara cannot store are listed in `marketplaces.skipped` (`{ name, reason }`, replaced on every refresh, shown on the marketplaces page): `claude_npm_unpinned` (npm, no integrity), `claude_source_unsupported` (`archive` zips, `command`, non-https URLs), `invalid_name`, `invalid_entry` (also one row for entries past 5000). Each entry keeps an overlay (`marketplace_entries.claude`: `strict`, its component fields, publisher); with no `plugin.json` the entry is the manifest. The content digest is over the files as read, plus the overlay's canonical JSON when the entry has components, so an entry-only change re-imports as new content (`+git.<sha12>`, or `+sha256.<12>` when that build is taken).
- **Skills APIs**: the platform component sync records each platform skill version's `source_format`; the skills APIs return `plugin`, `sourceFormat` and, on the skill library list, `builtin` (a skill of a builtin plugin, which no agent can turn off). The pinned suggestion is gone (no `pinnedSuggestions`, `suggestPinned`, `entryBytes` or `tokenEstimate`; the `suggest_pinned` column stays at its default). Agents turn skills off with `disabledSkills` (`.agents/skills/writing-tools`).
- Tests: `packages/kernel/test/catalog/claude-*.test.ts` (translate, marketplace, git-marketplaces, import, install), `plugin-review-hash.test.ts`, the fixtures `test/catalog/fixtures/claude/` (`superpowers` from obra/superpowers 7.0.1, `mixed`, `root-skill`), the acceptance `claude-superpowers.e2e.test.ts`, the live `claude-live.test.ts` (only with `CAPYBARA_TEST_CLAUDE_SUPERPOWERS=1`; behind a proxy add `CAPYBARA_TEST_HTTPS_PROXY=<url>`, which becomes `net.httpsProxy`). A translated bearer template against the real `connector-mcp` is tested in capybara-hq/plugins.

## Bootstrap plugins (`packages/kernel/bootstrap.json`)

The plugins every deployment installs (spec §7; today `openai-compatible` and `object-store-s3`, both required, the builtin `skills-core` (`builtin: true`, below), plus the optional preinstalls `anthropic`, `openai`, `connector-mcp`, `connector-openapi`, `jina`, `sandbox-docker` and `todo`: installed and enabled on the deployment, catalog scope `optional`, so off in each org until an org admin switches them on, and a super admin may disable or uninstall them) are pinned in `packages/kernel/bootstrap.json` (v1, schema `packages/plugin-sdk/schemas/bootstrap.v1.schema.json`, parsed by the SDK's `parseBootstrapManifest`; strict: unknown keys are errors). Since phase A3b every entry is `{ name, version, integrity, required, "source": "npm", "npm": "<package>" }` (plus the optional `builtin`, below), with a top-level `marketplace: { url, commit }`: the official marketplace (`https://github.com/capybara-hq/plugins.git`) at the commit the pins were checked against. The SDK still accepts `"source": "workspace", "path": "plugins/<dir>"` entries (the sha512 of the `packages/plugin-tools` pack, byte-reproducible across hosts), but core no longer has any.

- The image carries no packages. The bootstrap step (`capybara bootstrap`, compose `init` after `migrate`, or any `capybara start`) obtains each entry when the run is not done: a `*.tgz` of the offline directory `bootstrap.dir` (`./bootstrap`, `/app/bootstrap` in the image; any file name, matched by sha512), else the npm download from `packages.npmRegistry` verified against the pin only (`resolveBootstrapPackages` in `packages/kernel/src/extensions/bootstrap.ts`; `bootstrap.download_failed` / `bootstrap.integrity_mismatch`; a workspace entry without a matching file is `bootstrap.missing_file`). Only that first run needs the network. The extension side (lock, `bootstrap_runs`, the rules per entry, `required`) is in `.agents/skills/writing-extensions` ("Bootstrap plugins").
- Each entry goes through the same import as any plugin (`PluginImport.prepare` / `confirm`): a catalog version with source `bootstrap` and `source_ref` `bootstrap:<name>@<version>`, the package with source `bootstrap` (kept in PG), the install record with source `bootstrap`; a declarative entry (no extension) is only imported into the catalog. No object store runs during the first bootstrap pass (object-store-s3 is itself a bootstrap plugin, and even an installed one is not serving yet): an entry's icon and setup guide files go to PG and need none, but skills, connector templates and agent templates do, so an entry shipping them fails that pass (`storage.unavailable`, naming the plugin); an optional one is retried after the extensions loaded, a required one stops the start. Keep required bootstrap plugins free of skills and templates; a plugin that must be builtin and ships them is a `builtin: true` entry (never together with `required: true`, a parse error): the first pass skips it (not a failure), the pass after the extensions loaded imports it, its catalog item is builtin (scope `all`, not disabled, no org switch), a failure is logged like an optional entry and retried on the next start, and it is put back when missing (a declarative one whose item a super admin deleted is imported again by the next run). Example: `skills-core` (`skill-guide`). Afterwards the plugin is managed like any other catalog item (org installs, upgrades), except that a required one cannot be disabled or uninstalled (409 `extension.required`).
- `pnpm check:bootstrap` (full on PRs, part of `pnpm check`) parses the manifest (`bootstrap-invalid`) and checks that every remote build context of `docker/compose.yaml` and `docker/compose.dev.yaml` is exactly the official repository at `marketplace.commit` (`bootstrap-compose-ref`: today `https://github.com/capybara-hq/plugins.git#<commit>:plugins/sandbox-docker/image` and `…/egress-proxy`; a fork, an scp-style or scheme-less URL, a branch, `?ref=` or a missing directory fails); its workspace-entry rules (`bootstrap-stale`, `bootstrap-name`, `bootstrap-pack`) have nothing to check today. `pnpm check:bootstrap --network` (by diff on PRs when `bootstrap.json` or the check's own code changes; `docker/**` runs everything; always on `main` and before publishing) checks each npm entry against the registry (published, `dist.integrity` and tarball sha512 equal to the pin: `bootstrap-npm`), against the official marketplace's `.capybara-plugin/marketplace.json` at `marketplace.commit` (same version, package and integrity: `bootstrap-marketplace`), and that the `sandbox-docker` test copy of the socket proxy config at that commit equals core's `docker/sandbox-proxy/haproxy.cfg` (`bootstrap-haproxy`), that each compose build context has its `Dockerfile` there (`bootstrap-compose-ref`), and that `marketplace.url` is the official one (`bootstrap-marketplace-url`).
- **Moving a pin**: the official marketplace lists one version per plugin, so every pin of one manifest is the version current at `marketplace.commit`. Once capybara-hq/plugins has published the new versions and listed them in its marketplace, update the entries' `version` / `integrity` and `marketplace.commit` together (the compose git contexts follow the same commit), then run `pnpm check:bootstrap --network`. One `marketplace.commit` pins three things: the bootstrap entries, the compose sandbox build contexts and the plugin's copy of `docker/sandbox-proxy/haproxy.cfg` (`bootstrap-haproxy`); a haproxy-only change lands in capybara-hq/plugins first, then a core PR changes the file and moves `marketplace.commit` and the contexts to that commit.

## Org switch, install and uninstall (`PUT /api/v1/orgs/:orgId/catalog/:itemId/switch`, `plugin-installs`)

Code: `org-catalog.service.ts` (switch, requests) and `plugin-install.ts` (`PluginInstaller`). `PUT catalog/:itemId/switch { enabled: true, inputs? }` installs (and records the org's switch), `{ enabled: false }` answers `{ preview, confirm }` and uninstalls once `confirm` carries the hash; only builtin items are 409 `plugin.scope_locked`. Switching off a dependency an on plugin needs is recorded and the dependency stays on (no 409). `POST catalog/:itemId/install` stays as an alias of switching on and no longer creates requests. Neither body takes a `version` (400 `validation_failed`): an org installs the platform version (`platform_synced_version`, one per deployment, ruling P2-17), and an install marked installed records the platform version current at its commit.

- **Body**: `{ version?, connectors?: { <template id>: { name?, slug?, endpoint?, credential?, client? } }, extensionConfig?: { … } }` (strict). `endpoint` is limited to `editableEndpoint`; `extensionConfig` is the org config of the plugin's own extension, validated against its `config.org` schema and used only when this install enables it (an extension already enabled in the org is recorded as pre-existing and its config is untouched). Unknown template ids, or `extensionConfig` for a plugin without an extension -> 400 `validation_failed`. Bad template input (credential shape, endpoint, OAuth client, slug) is a 4xx before anything is written, with the path prefix `connectors.<id>.`.
- **Permissions**: the actions of every plugin the install brings in (extension -> `org.extensions.manage`, templates -> `connectors.manage`, skills -> `skills.manage`, agent templates -> `agents.manage`), re-checked under the org row lock.
- **Scope, not policy**: a `disabled` item is refused (409 `plugin.disabled`); an item the org cannot see or that is not offered to it is refused (a `named` item outside the list; `optional` and `named` need the switch, `all` is on until the org switches it off, builtin is never switched by the org); success is 201 `{ installed: { itemId, version, pluginInstallId }, install: <PluginInstallView> }`. Dependencies are installed whatever their own scope says (the dependent's switch brings them) but a disabled dependency anywhere in the tree refuses. **Exception (Ruling M-5)**: a `disabled` item is a master switch for its extension: no path (direct enabling, its own item, another plugin depending on it) newly enables it in an org.
- **Requests** (`requests.service.ts`, `request-rules.ts`; migration 0077): `POST catalog/:itemId/requests` and `POST marketplace-requests`, decided with `catalog-requests/:id/decide` (rejection with an optional reason) and dismissed with `…/dismiss`. Kinds: `access` (org admin -> super admin, a `named` item shown to others; approving adds the org to the list and enqueues the sync), `import` (org admin -> super admin, a marketplace entry; only while the deployment setting `orgMarketplaceBrowse` is on, else its error; approving prepares the import and its confirm resolves the request), `enable` (member -> org admin, an item that is off; approving switches it on). One pending request per (org, kind, item or entry). An item hidden from the org (not `shown_to_others`) is unknown to it.
- **Dependencies** (resolved before any request or row exists): each range resolves to the dependency's platform version (ruling P2-17), which must satisfy it; only while the dependency has none yet (its first sync failed), the highest imported version satisfying it that its marketplace does not deprecate, a stable one before a prerelease. No such item or version, or a platform version outside the range (the super admin updates the dependency first) -> 409 `catalog.dependency_unresolved` (details `{ dependency, range }`); a disabled dependency anywhere in the tree -> 409 `catalog.dependency_disabled` naming it; a cycle by name, or nesting deeper than 10 levels -> 409 `catalog.dependency_cycle`. A dependency already installed in the org at a version outside the range is unresolved too (upgrade it first). Dependencies take no install input: one whose templates need a credential or an OAuth client must be installed on its own first (400 saying so, with the path `dependencies.<name>.connectors.<id>.…`), and a dependency's extension is enabled without org config.
- **Steps**, depth first: `dependencies` (each one not yet in the org gets its own nested `plugin_installs` row through the same installer, recorded as a `plugin` component with `ref` = its install id and `created: true`; one already in the org, including one an earlier sibling just brought in, is recorded `created: false`) -> `extension` (enable in this org; not loaded on the deployment -> `catalog.not_deployed`) -> `connectors` (from the templates on in the org, through `ConnectorsService.create`, storing `platform_template_id`; ruling P2-6). Skills and agent templates are platform components (below): an install writes no org rows for them, but a skill name the org already uses (its own skill, another plugin's, or a name two plugins of the plan both bring) refuses the install while planning, before anything is written: 409 `plugin.skill_conflict`, one message line per skill, `details: [{ skill, source: { kind: "org" } | { kind: "plugin", name, version } }]`, spec §9.2. Each component is recorded in `plugin_install_components` as soon as it exists. Audit `plugin.org_installed` / `plugin.org_install_failed` per install, nested ones with `dependencyOf`.
- **Failure**: everything this install created is undone in reverse order, nested dependency installs included, the row is marked `failed` and the root returns 502 `plugin.install_failed` with `{ step, code, dependency?: "a > b", message, rolledBack }`.
- **Uninstall** (`DELETE plugin-installs/:installId`, the plugin's component actions re-checked under the lock) removes, in one transaction, skills -> connectors -> extensions (reverse requires) -> dependency installs, **only components this install created and nothing else uses**. Kept ones are reported with a reason: `pre_existing`, `used_by_agents` (a skill selected by an agent, a connector referenced by one, an agent template in an agent's `subagents.templates`: dispatches of it keep working until the agent drops it), `used_by_other_install` (another install in this org uses it; ownership passes to it), `used_by_connectors`, `used_by_plugins` (another enabled extension requires it). A dependency install is removed with the last install that uses it; deleting a dependency install that another live install still uses returns 200 with nothing removed and `kept: [{ kind: "plugin", reason: "used_by_other_install" }]`. A `failed` install, or one still `installing` after `catalog.staleInstallMinutes` (default 30), is cleaned up as a rollback and writes no org switch row (it was never on, so an item its scope wants is installed again by the scope sync); removing a live install of a catalog plugin writes the switch off; one still installing -> `plugin.install_in_progress`.
- **Platform plugin update** (plugin and component management spec §7, `plugin-upgrade.ts`, `PlatformPluginUpdater`; the per-org upgrade routes are retired, ruling F2, and install views always carry `upgradeAvailable: null`, `deploymentPending: false`): `POST /admin/catalog/items/:id/update/preview { version }` -> `{ itemId, name, from, to, components: { kind: skill | agent_template | connector_template, id, name, change: added | removed | upgrade | downgrade | same, from, to, updatedOnOwn, ownScope, pinnedOrgs, kept? }[], extension: { from, to, orgs, needsApproval } | null, connectorOrgs: { orgId, connectors: { id, name, templateId, credentialsReset }[], needsConfig }[], diffHash }`, then `PUT …/update { version, diffHash }` (super admins). `from` is `catalog_items.platform_synced_version`. Refused: the same version, a target without the extension the deployment runs or moving a config-declared one, a template moving to another connector, a plugin another platform plugin depends on outside its range (409 `plugin.upgrade_target_invalid`), an added skill named like one in use where the plugin is on (409 `plugin.skill_conflict`, rule 10). The confirm runs under a Redis lock per item (409 `plugin.install_in_progress`): the extension first (`ExtensionAdminOps.install`; added permissions wait for approval like any extension upgrade), then one transaction under the item lock that recomputes the diff (409 `plugin.upgrade_stale`), writes the platform versions (`syncFromVersion`, also the pinned suggestions of unchanged skills), soft-deletes removed components no agent uses (unpinned linked copies go with them; one agents use stays and is listed in `kept`; removed connector templates leave their connectors to the orgs), clears the pins of linked copies where the component is on, fans changed templates out to every connector with that `platform_template_id` (`applyTemplateIn` under each org's lock; credentials cleared only when their shape changed), moves every live org install (installing, installed, legacy upgrading) to the version and audits `plugin.platform_updated`; the scope sync of the item and its dependencies is owed in that transaction. Added templates create no connector (they need the org's input: `needsConfig`); the installed plugin shows `needs_config` in the org until an org admin creates them with `POST /orgs/:orgId/catalog/:itemId/connectors { inputs: { connectors } }` (install input checks, recorded on the install; ruling P2-10). A target that adds a dependency gets it installed where the plugin is installed by the scope sync (`addMissingDependencies`, rule 9). Storage is read and platform files copied before the transaction (`prepareSync` / `applySyncIn`); a crash after the extension step is completed by a new preview (the extension then shows unchanged). A failure undoes everything and puts the extension back (502 `plugin.upgrade_failed`, audit `plugin.platform_update_failed`). Tests: `packages/kernel/test/catalog/platform-update.test.ts`.
