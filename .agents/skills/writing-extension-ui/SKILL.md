# Extension UI: the kernel and web host side

This skill covers what core owns: the web host (`ExtensionSlot` and the slots it renders, the "Extensions" menu, the `/plugin-ui` proxy and CSP, the message bridge's host side), the kernel's `ctx.ui` registry and routes, embed token issuing and `verifyEmbedToken`, view validation and `UI_LIMITS`, file previewers, and the tests on the `fake-tools-ui` and `fake-embed` extensions of `@capybara-hq/testing`. **Adding UI to a plugin** (writing views and embed pages, its tests) is in [writing-extension-ui in capybara-hq/plugins](https://github.com/capybara-hq/plugins/tree/main/.agents/skills/writing-extension-ui); the rules below are the contract both sides follow.

For the extension host (manifest, permission approval, ctx, multi-replica prohibitions, dual-replica tests) see `.agents/skills/writing-extensions`, and for tools themselves see `.agents/skills/writing-tools`. The design basis is `docs/superpowers/specs/2026-10-21-chat-panel-plugin-ui-design.md`. Implementations:

- Core fakes: `fake-tools-ui` (tool `write`, conversation view `tasks`) and `fake-embed` (embeds `panel` on an org page and `panel-conv` in a conversation, static `/ui/panel.js`, token-checked routes, SSE over `ctx.bus`; `apps/web/e2e/embed-panel.spec.ts`), plus the kernel fixtures `packages/kernel/test/fixtures/plugins/ui-*` and `preview-fake`.
- Tier 1 (rendered schema view) in the official [`todo`](https://github.com/capybara-hq/plugins/tree/main/plugins/todo) plugin (capybara-hq/plugins): views `tasks-panel` / `tasks-section` / `tasks-card` (and the alias `tasks`; still on the deprecated `place` until step B); `todo__write` returns `card` and calls `invalidate` after writing.
- Tier 2 (embed) in the official [`example-board`](https://github.com/capybara-hq/plugins/tree/main/plugins/example-board) plugin: org page `board` and conversation panel `board-conv` (still declared with the deprecated `place`; step B of the slot migration moves them to `slot`), icon `layout-grid`, with live SSE refresh.

## How to choose between the two tiers

| | Tier 1: rendered schema (`kind: "view"`) | Tier 2: embed (`kind: "embed"`) |
|---|---|---|
| What the extension provides | `render()` returns a `UiView` (a list of blocks), drawn by the web app with design system components | A full page of HTML / JS served by extension routes, placed in a sandboxed iframe |
| Styles and code | The extension cannot write styles or run code | The page is responsible for itself and can use the `--cb-*` design tokens sent by the outer page |
| Interaction | Buttons and forms call back into `ctx.ui.action` | Anything (drag and drop, multi-user collaboration, complex forms) |
| Refresh | `ctx.ui.invalidate` -> the web app re-fetches the view | The extension opens its own SSE / long polling |
| Approval | Recorded in the snapshot, **does not block loading** | **Blocks loading**, needs approval, a sensitive item |

**Use tier 1 whenever you can**: lists, progress, key-values, tables, simple charts, a few buttons or one form are all covered, and there is no new security surface. Only things the blocks cannot draw (kanban drag and drop, real-time multi-user editing, workflow canvases) should use an embed.

Both tiers go in the same positions: the **slots** of the catalog below. A contribution appears only in **orgs where this extension is enabled** (a `platform.page` contribution only needs the extension running); kind view also requires that the extension actually registered a render with `ctx.ui.view`.

**Roles (Ruling A38, now per slot)**: every slot has a `minRole` and a scope rule (below). `org.page` is given only to org roles **member and above**, `org.settings.section` to admin and above, `platform.page` only to super admins. A caller below the slot's role does not see the contribution in the lists, and when they fetch its view, run its actions, mint an embed token or connect to the org-level refresh stream, the answer is always 404 `ui.not_found` (the same as if it did not exist). Conversation and agent slots go to any role that can read the conversation or the agent (a guest also uses shared agents). The extension can read `role` (`owner` / `admin` / `member` / `guest`, `superAdmin` on the platform scope) in `UiRenderArgs` / `UiActionArgs` / `EmbedClaims` and can tighten further on it (for example, only member and above may change data); but it does not need to block lower roles from a slot itself, the kernel already does.

## The slot catalog

Where extension UI goes is a **slot**: a named, versioned position in the web, rendered by exactly one web file, with a typed contract. The catalog is `UI_SLOTS` in `packages/plugin-sdk/src/ui-slots.ts` (types `UiSlotSpec`, `UiSlotId`; `uiSlot(id)`, `parseSlotRef`); the table of every slot (scope, accepted kinds, minimum role, args, density, anchors, owning web file) is generated into [docs/guide/ui-slots.md](../../../docs/guide/ui-slots.md) and the web's `apps/web/src/lib/ui-slots.generated.ts` by `pnpm gen:ui-slots`: never edit either by hand (`check:ui-slots` fails on drift). Design: `docs/superpowers/specs/2026-11-08-ui-slots-design.md`. Agents read the same catalog through `GET /api/v1/ui/slots` and the `ui.slots` Platform operation.

| Slot | Scope | Where | Min role |
|---|---|---|---|
| `conversation.panel` | conversation | Right panel opened from the extension's icon in the conversation title bar (full height, one at a time) | guest |
| `conversation.properties.section` | conversation | A section of the properties panel, `dense`; `after` picks the anchor `context` / `files` / `background` | guest |
| `conversation.tool-result.card` | conversation | An inline card hanging off a tool result (`ToolResult.card`) | guest |
| `org.page` | org | A page in the org's extension pages, route `/p/<plugin>/<id>` | member |
| `file.preview` | file | An embed previewer of `file-preview@1` (below), embed only | guest |
| `agent.detail.section` | agent | A section on an agent's detail page (receives `agentId`) | guest |
| `org.settings.section` | org | A section on the org settings page | admin |
| `platform.page` | platform | A page in the admin console, route `/admin/p/<plugin>/<id>` | superAdmin |
| `shell.brand` | org | Replaceable: the sidebar brand row, component only | guest |
| `shell.overlay` | org | List (4): a full-viewport decoration layer, component only | guest |
| `conversation.empty` | org | Replaceable: the new-conversation hero, component only | guest |
| `conversation.composer.frame` | org | Replaceable: the frame around the composer, component only | guest |

**Declaring a slot.** A contribution sets exactly one of `slot` (`"<id>"`, or `"<id>@<n>"` for a version; version 1 when omitted) and the **deprecated** `place`. `place` is step A of a three-step migration: it still works and is mapped through `PLACE_SLOTS` (`panel` and `conversation` to `conversation.panel`, `section` to `conversation.properties.section`, `inline` to `conversation.tool-result.card`, `page` to `org.page`, `file-preview` to `file.preview`), and `capybara-plugin check` warns `ui-place-deprecated`. Step B moves the official plugins (`todo`, `example-board`) to `slot` in capybara-hq/plugins; step C (core, after the next rc pinned by `bootstrap.json`) removes `place` for good: `UiContribution.place`, `PLACE_SLOTS`, the `place` branches of `validateUiContributions` / `resolveUiSlots` / `slotRefOf`, the `ui-place-deprecated` rule and its fixture. Write new code with `slot`. `after` names one of the slot's `anchors` to sit after; omitted or not an anchor (`unknownAnchors`; `capybara-plugin check` reports `ui-slot-anchor` as an error) means the slot's first anchor.

**Split validation.** Structure is checked by `validateUiContributions` and fails the extension (bad id, both or neither of `slot` / `place`, an `embed` in a slot that accepts only views, a malformed slot ref, ...). Whether the slot exists is not structure: `resolveUiSlots` runs when the kernel loads the instance, and an **unknown slot or unsupported version drops that contribution** (reason `unknown-slot` / `unsupported-version`; an alias whose target is dropped is dropped with the target's reason) with one warning per extension, while the extension still loads. A newer plugin on an older kernel therefore degrades instead of failing. The dropped list is `uiDropped` on `GET /api/v1/admin/extensions/:name` and is shown as 未生效的界面 on the extension detail page. A dropped contribution is not listed and its routes answer 404 `ui.not_found`.

**The gate (kernel, `packages/kernel/src/ui/views.ts`).** Every view, action and embed-token route checks, in this order: the slot of the contribution it names, the slot's `minRole`, then the scope rule (conversation: whoever can read the conversation; agent: whoever can read the agent, in the org of the route; org: org membership; platform: an active super admin, a person, never a service token). Failing any of them is 404 `ui.not_found`. The org routes `/api/v1/orgs/:orgId/ui/*` serve every slot but `platform.page`; the platform routes `/api/v1/admin/ui/*` (`contributions`, `arrangement`, `views`, `actions`, `embeds/.../token`, `stream`) serve only `platform.page`, with no org: a platform contribution needs its extension running (no org enablement applies), is given the platform's deployment config, and its render args are `scope: "platform"`, `role: "superAdmin"`, no `orgId`. A contribution in the wrong family of routes is 404.

**Render args and claims are unions on `scope`.** `UiRenderArgs` is `{ scope: "conversation" | "agent" | "org" | "file", orgId: string, ... } | { scope: "platform", orgId?: undefined, ... }` (also `slot: UiSlotId`); narrow on `scope` before using `orgId`. `agentId` is set for `agent.detail.section`, `conversationId` for conversation slots and `file.preview`. `EmbedClaims` and `EmbedInitContext` (the `context` of the bridge's `init`) are unions on `scope` the same way: an org-scope token carries `orgId` (and `conversationId?` / `agentId?` / `fileId?`), a platform-scope token (`scope: "platform"`, `role: "superAdmin"`) carries none and `verifyEmbedToken` accepts it only for a `platform.page` contribution while the account is still an active super admin.

**`ctx.ui.invalidate` and the platform.** `orgId` is required except for a `platform.page` contribution, where it must be omitted (the hint goes to the platform topic, and the platform refresh SSE `GET /api/v1/admin/ui/stream` receives it); naming an `orgId` or `conversationId` for a platform contribution, or omitting `orgId` for any other, throws.

**Arrangement: hidden = not listed.** Org admins (for their org) and the super admin (the platform default) arrange every arrangeable slot (`UI_ARRANGEABLE_SLOTS`: all but `file.preview`, whose order is the previewer setting) on the 界面位置 page: hide a contribution or reorder. `GET /api/v1/orgs/:orgId/ui/arrangement` (and `/api/v1/admin/ui/arrangement`) returns `{ slots: { slot, source, items }[] }` in effective order with `hidden` marked; the contributions list leaves hidden ones out. **Hidden is only "not listed", never "not served"**: the view, action and embed routes ignore the arrangement (the gate above is the only access control), so a hidden `org.page` or `platform.page` still opens by its direct link (the page reads the arrangement listing to find it and the slot gets `args.direct`); in every other slot a hidden contribution simply does not show, there is no link to it. The arrangement is display only and is never an authorization input. An org follows the platform arrangement until it saves its own.

**`ExtensionSlot` (web).** `apps/web/src/components/extension-ui/ExtensionSlot.tsx` is the one renderer: a page writes `<ExtensionSlot slot="agent.detail.section" args={{ orgId, agentId }} host={...} select? />`, and the component reads the contributions, applies order and anchors, draws each through `ExtensionPanel` / `ExtensionSection` / `ExtensionCard` / `ExtensionViewTab` / `EmbedTab`, and isolates each in a `BlockBoundary` (a failing block shows "Failed to load · Retry" in that block only). The args type is per slot (`SlotArgs`), the per-call-site props are `SlotHost`. Never render those pieces directly outside `components/extension-ui` (`web-ui-extension-slot`). A new slot is: an entry in `SLOT_DATA`, `pnpm gen:ui-slots`, kernel scope handling when the scope is new, an `ExtensionSlot` branch, a Platform / parity check as usual, the arrangement label in `messages/{zh,en}.json`, and a changeset (`pnpm gen:sdk-api`, `@capybara-hq/plugin-sdk`).

**The two checks.** `check:ui-slots` (in `pnpm check`): the generated web copy and `docs/guide/ui-slots.md` equal what `pnpm gen:ui-slots` renders (`ui-slots-stale`), and every `<ExtensionSlot slot=...>` in `apps/web/src` has a literal, catalogued id, every catalog slot is rendered, in its `owner` file, exactly once. `web-ui-extension-slot` (a rule of `check:web-ui`): `ExtensionPanel`, `ExtensionSection`, `ExtensionCard`, `ExtensionViewTab` and `EmbedTab` appear in JSX only inside `components/extension-ui`; pages go through `<ExtensionSlot>`. Both are described in `tools/checks/README.md`.

### Conversation slots

The conversation page (design spec §5.4, §6.16; UI refresh spec §5.3) has three extension slots.

- **`conversation.panel`**: full-height right panel, one at a time, opened from the contribution's icon in the title bar.
- **`conversation.properties.section`**: rendered `dense`; a `badge` shows as the section's value (todo's "1 / 3"); `after` is `context` (default), `files` or `background`.
- **`conversation.tool-result.card`**: **hangs off a tool result**: the tool returns `card: { view: "<card view id>", key? }` in its `ToolResult` (display only, recorded as `tool_result.card: { plugin, view, key? }`, never in the model's context). An unknown view id is dropped with a warning and the result still succeeds. Extensions cannot write card events into the log themselves.
- **Icon**: a contribution may set `icon` from `UI_ICONS` (`list-checks`, `layout-grid`, `file`, `chart`, `calendar`, `users`, `bot`, `book`, `message-square`, `puzzle`); the default is `puzzle` (drawn as the design `extension` icon). The title-bar button uses it, so pick one per panel.
- **Open targets**: `UiOpen = { contribution, item? }`, where `contribution` is a `conversation.panel` of the same extension. A view may carry `open` (the arrow in a card's title row and the section header); checklist items and keyValue items may carry `open` and `id`; a table block carries a parallel `open?: (UiOpen | null)[]` (never a `_open` key in a row). Clicking opens that panel scrolled to the block or item whose `id` equals `item`; `render` receives it as `UiRenderArgs.item`, and a card's render receives `card: { callId, key? }`.
- **Access**: the conversation rule (anyone who can read the conversation, guests included).
- **Aliases**: `aliasOf: "<id>"` keeps a retired id answering as another contribution of the same extension and kind (it is not listed, has no `ctx.ui.view` of its own, but stays in `permissions.ui`). Refresh it too while it lives (todo invalidates `tasks` with the rest).
- **Kernel**: the contributions list carries `slot`, `after` (the resolved anchor, for a slot with anchors) and `icon`; aliases and `file.preview` embeds are not listed. The views route takes `?item=` (to `args.item`) and `?callId=&key=` (to `args.card`; `key` needs `callId`; served only for a `conversation.tool-result.card` view when a `tool_result` of that conversation recorded the same card, plugin, view or its alias target and key, else 404 `ui.not_found`). The pipeline keeps a plugin tool's `card` only when it names a card contribution of the same extension (`ToolPipelineDeps.inlineViews`).
- Reference: the official [`todo`](https://github.com/capybara-hq/plugins/tree/main/plugins/todo) plugin uses all three; [`example-board`](https://github.com/capybara-hq/plugins/tree/main/plugins/example-board) is an embed page and panel with icon `layout-grid`.

### File previewers (`file-preview@1`)

Previewing a file output in the right panel is the extension point `file-preview@1` (org scoped, several providers). A provider lists `previewers`, each with an `id` (`[a-z0-9-]{1,40}`), a bilingual `title`, `accepts: { mimeTypes?, extensions? }` (at least one; `image/*` allowed; extensions match case-insensitively), `maxBytes` (≤ `FILE_PREVIEW_MAX_BYTES`, 20 MB) and exactly one of `render(args) => UiView` or `embed: <id of a ui contribution { kind: "embed", place: "file-preview" }>`. The extension never gets a storage key or a URL: `render` reads the bytes through `args.read()`, a read grant for that one file in that conversation, valid only during the call; an embed gets them through the message bridge (`type: "file"` after `init`). An org admin orders and disables previewers; an accepting extension previewer wins over the built-in ones (image, text, Markdown, CSV / TSV), and the person can switch in the panel header. A slow or failing previewer affects only the panel and falls back to the file card with Download.

- **Validated at `ctx.provide`**: an invalid provider (`validateFilePreviewProvider`), or an `embed` that names no ui contribution `{ kind: "embed", place: "file-preview" }` of the same extension, fails `setup`.
- **Kernel routes** (`packages/kernel/src/files/previewers.controller.ts`): `GET /api/v1/orgs/:orgId/conversations/:id/files/:fileId/previewers` → `{ previewers: { plugin, id, title, kind }[] }` (the viewer must read the conversation); `GET …/files/:fileId/previews/:plugin/:previewerId?locale=` → `{ view }` (10 s → 504 `ui.timeout`, a throw, including a rejected `read()`, → 502 `ui.render_failed`, an invalid view → 502 `ui.invalid_view`); `GET | PUT /api/v1/orgs/:orgId/file-previewers` (`org.extensions.manage`) → `{ items }`, the org order (`capybara.file_previewers`: listed items first, the rest in provider order). The settings page section is `apps/web/src/components/FilePreviewersSection.tsx`.
- **Embed previewers**: the web asks the existing embed-token route with `{ conversationId, fileId }`; the kernel issues it only when an enabled previewer of that extension with `embed: <contribution>` takes that file, and the claims carry `fileId`. `createEmbedBridge({ file })` posts the file once after `init` (again only to a remounted document).
- **Tests**: `packages/plugin-sdk/test/file-preview.test.ts`, `packages/kernel/test/files/previewers.http.test.ts` (fake provider `test/fixtures/plugins/preview-fake`), `apps/web/test/previewers.test.tsx`.

## Manifest

The examples are the official `todo` and `example-board` plugins, written the way they will look after step B (today they still say `place`):

```ts
defineExtension({
  name: "todo",
  ui: [
    { id: "tasks-panel", title, slot: "conversation.panel", kind: "view", icon: "list-checks" },
    { id: "tasks-section", title, slot: "conversation.properties.section", after: "context", kind: "view", icon: "list-checks" },
    { id: "tasks-card", title, slot: "conversation.tool-result.card", kind: "view", icon: "list-checks" },
    { id: "tasks", title, slot: "conversation.panel", kind: "view", aliasOf: "tasks-panel" },
  ],
  permissions: {
    tools: ["write"],
    ui: { views: ["tasks-panel", "tasks-section", "tasks-card", "tasks"] },
  },
  // ...
});

defineExtension({
  name: "example-board",
  ui: [
    { id: "board", title: { zh: "看板", en: "Board" }, slot: "org.page", kind: "embed", path: "/ui/board" },
    { id: "board-conv", title: { zh: "看板", en: "Board" }, slot: "conversation.panel", kind: "embed", path: "/ui/board-conv" },
  ],
  permissions: {
    http: [{ method: "GET", path: "/ui/board" }, { method: "GET", path: "/ui/board-conv" }, /* data routes are also under /ui/ */],
    ui: { embeds: ["board", "board-conv"] },
  },
});
```

- A contribution `id` matches `^[a-z][a-z0-9-]{0,39}$` and is unique within the extension; both the zh and en parts of `title` must be non-empty and <= 100 characters.
- `path` is allowed only on embeds: it starts with `/ui/` and is declared as `GET <path>` in `permissions.http`. All routes an embed uses (page, scripts, data, SSE) must be under `/ui/`; the web proxy forwards only there.
- **Two-way cross-check** (`defineExtension` -> `validateUiContributions`, which the kernel also runs when loading): the id of a kind view must be listed in `permissions.ui.views`, and that of a kind embed in `permissions.ui.embeds`; conversely every id in `permissions.ui` must have a contribution of the same kind. The same id cannot be listed on both sides.
- **Approval**: the permission keys are `ui.view:<id>` and `ui.embed:<id>`.
  - `ui.view:*` is recorded in the snapshot and visible when admins review, but **never blocks loading**: when an extension upgrade adds only views it loads as usual and the kernel merges them into the snapshot (no audit entry, one info log `plugin ui views merged into the permission snapshot`); `capybara extensions approve` also answers "no approval needed" for such an upgrade. The reason is that a view only hands the extension's existing data to our components and adds no new extension point. Exception: a brand-new extension (no snapshot yet) needs approval even if it has only views.
  - `ui.embed:*` blocks loading like any other newly added permission, waits for `capybara extensions approve`, and is a **sensitive item**: `capybara extensions review` / `approve` mark it with `  (sensitive)` after it, and the `ui` group on the org enablement page is highlighted. There is only one definition of sensitive (`isSensitivePermissionKey` in `permission-view.ts`).
- **Static check `perm-ui`** (`pnpm check:extension-permissions`): the id of `ctx.ui.view(id)` / `ctx.ui.action(id)` must be in `permissions.ui.views` (action is also checked against views; embeds do not go through action). Write the id as a string literal or a same-file const; dynamic values and aliasing `ctx.ui` both report "Cannot statically confirm", and for ones truly only known at runtime use the exemption `// capybara:allow-dynamic-permission <reason>`; an outright undeclared id cannot be exempted. When passing `ctx.ui` to another function, pass a wrapper (`{ invalidate: (t) => ctx.ui.invalidate(t) }`) so the check can see the usage.
- **Setup guides are not extension UI** (spec `2026-11-09-setup-guides-v2-design.md` §7, §10): a plugin's setup guide is a Markdown document the kernel renders and the web draws with the design `GuideDocument` and `CheckRow` inside `SetupGuideSection` (channel and connector pages); no slot, view or embed is involved and the plugin ships no UI code for it. Its live rows come from `ctx.setup.check` (writing-extensions), declared in `permissions.setupChecks` and checked by `perm-setup-check`, the same scan, literal-id rule and `// capybara:allow-dynamic-permission <reason>` exemption as `perm-ui`; unlike an embed, a setup check never blocks loading.

## Tier 1: `ctx.ui`

```ts
setup(ctx) {
  ctx.ui.view("tasks", async ({ orgId, accountId, conversationId, locale, signal }) =>
    tasksView(conversationId === undefined ? [] : await readTodos(ctx.db, conversationId)),
  );
  ctx.ui.action("tasks", async ({ actionId, payload, answer, signal }) => {
    // ...
    return { toast: { zh: "已清空", en: "Cleared" } }; // or { view: newView }, or {}
  });
}
// when the data changes:
await ctx.ui.invalidate({ orgId, conversationId, contribution: "tasks" }).catch(() => {});
```

- `view` / `action` can be called only in `setup` (sealed when setup ends), and the id must be in `permissions.ui.views`, otherwise `ExtensionPermissionError` is thrown and an out-of-scope audit entry is written; registering the same id twice throws.
- The identities in the arguments (`orgId`, `accountId`, `role`, `conversationId`) are given by the kernel after authentication: a conversation view has already verified that the caller can access this conversation, and the extension never gets the user's session credentials. Slots outside the conversation are not passed `conversationId` (an agent section gets `agentId`, the platform scope has no `orgId`: narrow on `scope`). `locale` is the web app's current language (`zh` / `en`, default `en`), and text in the view is produced according to it.
- **5 second timeout; both `render` and `action` must respond to `signal`**: pass it to queries and external requests (`fetch(url, { signal })`) and give up as soon as it aborts. After a timeout the user sees a failure and may retry, so a write in an `action` in particular must not keep running to completion after the timeout.
- A failure affects only that one tab (it shows the error and "Retry"); the conversation keeps streaming as usual; the kernel logs a warning and writes nothing to the conversation log. Error codes:

  | Code | Status | When |
  |---|---|---|
  | `ui.not_found` | 404 | extension not enabled / not loaded, contribution does not exist, an embed fetched as a view, the view has no action, the conversation is not accessible (someone else's, nonexistent, another org's, id is not a UUID) |
  | `ui.render_failed` | 502 | `render` threw (the extension's exception message is not echoed) |
  | `ui.action_failed` | 502 | `action` threw |
  | `ui.invalid_view` | 502 | the returned view or toast is invalid |
  | `ui.timeout` | 504 | over 5 seconds (`signal` has been aborted) |
  | `validation_failed` | 400 | a conversation view lacks `conversationId`, an org page carries one, the action request body is over the limit |

- Action request body: `actionId` 1-200 characters; `payload` <= `UI_LIMITS.payloadBytes` in UTF-8 bytes of its JSON; the number of keys and the multi-select length of a form `answer` <= `UI_LIMITS.tableRows`, a single text <= `UI_LIMITS.textChars`. When `{ view }` is returned the web app replaces the view directly (the badge is updated together), and for `{ toast }` it shows `toast[locale]`.
- **`invalidate({ orgId?, conversationId?, contribution })`** (`orgId` required, except for a `platform.page` contribution, where it is omitted): `contribution` is an id in the manifest `ui` (view or embed both work), and `conversationId` must be a conversation UUID. With a conversation it is sent to the conversation topic, and the conversation SSE receives `event: ui` `{"plugin","contribution"}`; without one it is sent to the org topic, and the org-level SSE `GET /api/v1/orgs/:orgId/ui/stream` receives it; for a platform page it goes to the platform topic and `GET /api/v1/admin/ui/stream` receives it. It crosses replicas through the Redis bus, and the extension needs to do nothing. The kernel first checks the target with one query: this extension is enabled in `orgId`, and when a conversation is given it belongs to `orgId`; if not satisfied it is silently dropped (only a debug log, no error). It is only a "go fetch again" hint, and authorization happens when the view is fetched; a refresh failure should not affect business writes, hence `.catch(() => {})`.
- **Web refresh coalescing**: each view has at most one request in flight at a time; refreshes that arrive in flight, however many, produce just one re-fetch after it completes; the old view is kept during the re-fetch, with no flash back to loading; after the event stream reconnects, all views are re-fetched once (frames may have been missed during the disconnection). So you can call invalidate on every write without throttling yourself.

## Tier 1: `UiView` blocks and limits

The types and `validateUiView` are in `packages/plugin-sdk/src/ui.ts`; the kernel validates every `render` / `action` return one by one, and an invalid one is handled as `ui.invalid_view`.

| Block | Fields | How the web app draws it |
|---|---|---|
| `heading` | `text` (non-empty) | small heading |
| `text` | `markdown` | **Shown in M4 as plain text with line breaks** (Ruling A36): Markdown is not rendered, links are not clickable, raw HTML is treated as text. The field is still named `markdown` and validation still requires links to be absolute http(s) addresses (defense in depth); it will be upgraded when a Markdown component exists |
| `checklist` | `items[{ text, status: pending / in_progress / completed }]` | a checklist; the `in_progress` item is highlighted, `completed` is struck through |
| `keyValue` | `items[{ label, value }]` | key-value table |
| `table` | `columns[{ key, label }]`, `rows[Record<key, string>]` | data table. Column keys cannot repeat; a row cannot have undeclared columns, but may omit columns |
| `code` | `language?`, `text` | monospace code block |
| `image` | `url`, `alt` | **Absolute http(s) addresses only** (<= 2000 characters, Ruling A34); a relative address under the extension's own routes is rejected |
| `chart` | `kind: bar / line`, `series[{ label, value }]` | bar chart / line chart; `value` must be a finite number |
| `actions` | `buttons[{ actionId, label, payload?, danger? }]` (non-empty) | a group of buttons, calling back into `ctx.ui.action` |
| `form` | `form: InputForm`, `actionId`, `submitLabel` | reuses the form fields of `AskUserQuestion`; submitting goes through `action` (with `answer`); it does not submit while a required field is empty |

A view may carry a `badge` (<= 32 characters), shown on the tab, such as todo's "2/4".

- **Limits `UI_LIMITS`**: `blocks` 50; `tableRows` 200 (also the cap on the number of keyValue items, table columns, chart points and buttons); `checklistItems` 100; `textChars` 20000 (the total of all text in the whole view; a form counts by JSON length); `payloadBytes` 2000 (the JSON byte count of a single button `payload`; one that cannot be serialized is also an error). Going over makes the whole view invalid, so truncate yourself and give text such as "N more items".
- **`actionId` is unique across the whole view** (buttons and forms counted together); the action callback uses it to tell sources apart.
- **Danger buttons** `danger: true`: the web app first shows `DangerConfirm` and requires the user to type the button text before running. Mark every delete, clear and irreversible operation. Buttons in a view are never primary buttons (the only primary action on a page is "Send").
- **Use `Object.hasOwn(row, key)` for table cells**, not `row[key]` or `key in row`: a column key may be `constructor` or `toString` and would pick up values from the prototype chain. Follow the same rule when you write your own rendering (such as future IM cards).
- Text in a view is for people: produce Chinese or English according to `locale`. It does not enter the model context.

## The display summary for tool results, `ToolResult.display`

A tool (extension tools and builtin tools) can return in its result a sentence meant only for people, and the tool-call line in the conversation stream shows it instead of the raw input JSON:

```ts
return {
  content: [{ type: "text", text: renderTodos(todos) }],
  display: { summary: { zh: `更新任务清单（${n} 项）`, en: `Updated task list (${n} items)` } },
};
```

- Give both Chinese and English, each <= 200 code points (`validateToolDisplay`); an invalid one is dropped by the kernel with a warning logged, and the result is written as usual.
- The summary goes into the log with the `tool_result` event, so reloading the page restores it; it **does not enter the model context**, and neither rebuilding the model request nor generating compaction records uses it, so anything the model needs must be written in `content`.
- Without a summary (connector tools' are never trusted), the web app falls back to "tool name + the first two fields of the input". Details are in `.agents/skills/writing-tools`.

## Tier 2: embeds

The extension's own page is placed in the web app's sandboxed iframe (`sandbox="allow-scripts allow-forms"`, without `allow-same-origin`, so it has an opaque origin) and cannot read the outer page or cookies. `apps/web` renders the iframe only through the design system's `EmbedFrame` (the `web-ui-iframe` rule of `check:web-ui`).

### Embed tokens

- The web app calls `POST /api/v1/orgs/:orgId/ui/embeds/:plugin/:id/token` (a conversation embed carries `{ conversationId }`) and gets `{ token, src, expiresAt, expiresIn }`; `src` is `/plugin-ui/<plugin>/<path with the leading /ui/ removed>`, such as `/plugin-ui/example-board/board`. At signing time the kernel has already verified that the extension is enabled, the contribution is an embed, and the caller can access this conversation.
- A token is `base64url(claims).base64url(HMAC)`, **stateless** (not stored in the DB or Redis), verified by every replica with the same master key; valid for 300 seconds (`EMBED_TOKEN_TTL_SECONDS`, tolerating 30 seconds of clock skew); after a master key rotation, tokens signed by the previous key remain valid until they expire. The claims are `EmbedClaims`, a union on `scope`: `plugin`, `scope`, `accountId`, `role`, `contribution`, `exp`, and for `scope: "org"` also `orgId` and `conversationId?` / `agentId?` / `fileId?` (a `scope: "platform"` token, for `platform.page`, has no `orgId` and role `superAdmin`) (`role` is written at signing and checked at verification to be one of the four roles).
- **Every data route of the extension first does `await ctx.ui.verifyEmbedToken(token)`** and returns 401 if it returns null. It accepts only tokens signed for **this extension** (a token signed for another extension is always null), and each time uses one PG query to confirm that this extension is still enabled in `claims.orgId`, the org is not deleted, and the account is active and still a member of that org (Ruling A37, not cached): after an org disables the extension, a member leaves, or an account is disabled, already-issued tokens become invalid immediately, and after re-enabling the unexpired ones work again. The returned `role` is the role at verification time; an org-page token also returns null after the caller is demoted to guest. Take the org, account and conversation only from the returned claims, and trust no parameter in the request. A conversation token must scope data by `conversationId`; an org token (no conversation) must not see data inside conversations.
- **The kernel's `/api` does not accept embed tokens**: the auth guard treats a Bearer only as an API token (`cap_pat_` / `cap_svc_`) lookup, and an embed token is always 401 `auth.required`. The worst outcome of a leaked token is calling **this extension's** data routes as that user within 300 seconds.

### The `/plugin-ui` same-origin proxy

The web app's `/plugin-ui/<plugin>/<rest>` is forwarded to the kernel's `/plugins/<plugin>/ui/<rest>` (`apps/web/src/lib/plugin-ui-proxy.ts`):

- Only GET / POST pass (OPTIONS answers 204 for preflight); a non-conforming extension name or path segment (empty segment, `.` / `..`, containing `/`, `\` or control characters after decoding) is a 404 without forwarding. An undeclared route gets 404 from the kernel.
- **Request header allowlist**: `accept`, `accept-language`, `cache-control`, `content-type`, `if-modified-since`, `if-none-match`, `last-event-id`, plus the trusted `x-forwarded-for`. Cookies and the CSRF header are not forwarded. **`Authorization` is forwarded only as a Bearer in the embed-token shape** (`Bearer <base64url>.<base64url>`, not starting with `cap_`), so API tokens and Basic never reach the extension.
- **Response header allowlist**: `content-type`, `cache-control`, `etag`, `last-modified`, `expires`, `vary`, `content-language`, `x-accel-buffering`, `retry-after`; other headers such as `Set-Cookie`, `Clear-Site-Data`, HSTS, NEL and `Link` are dropped. A 3xx `Location` is kept only if it is still under `/plugin-ui/<this plugin>/` and unchanged after normalization.
- **Caching can only be private**: if this request forwarded a token it is always `no-store`; without a token, the extension's Cache-Control has `public` / `s-maxage` / `proxy-revalidate` removed and `private` prepended; if none is given it is `no-store`.
- Every response gets the same security headers: CSP (`default-src 'self'`, scripts and styles allow `'unsafe-inline'`, `connect-src 'self'`, `frame-ancestors 'self'`, `base-uri 'none'`, `object-src` / `frame-src` / `worker-src 'none'`, and the critical **`sandbox allow-scripts allow-forms`**: a page opened directly at top level is also an opaque origin and cannot call `/api` same-origin with the user's cookies), `nosniff`, `Referrer-Policy: no-referrer`, `Access-Control-Allow-Origin: *` (without `Allow-Credentials`).
- The request body limit is the same as `/api` (413 when exceeded), an unreachable upstream is 502, and the response body is streamed through (SSE works).
- So always use **relative addresses** in the page (`fetch("cards")`, `<script src="board.js">`); external resources are blocked by the CSP.

### The message bridge (`postMessage`, protocol `capybara-embed/1`)

- **Outer -> iframe**:
  - `init` (token, `locale`, `theme`, the `--cb-*` design tokens (at most 300, each value <= 200 characters), `context: { orgId, conversationId? }`) is **sent only on the iframe's first `load`**; if the token arrives late, wait until it arrives and then send.
  - `token`: renewal, scheduled after a token is obtained at `max(30 seconds, expiresIn - 60 seconds)` (not relative to the browser clock); on failure retry after 10 seconds and show a warning line in the tab.
  - `theme`: sent when the outer theme switches.
- **A second `load` of the iframe is taken as having left the extension page** (whole-page navigation, a navigation caused by a form submit, assigning to `location`): the outer page sends it no more messages and handles none of its messages, and remounts the iframe at the original `src`; at most 3 remounts within 10 seconds, beyond that it stops and shows an error until the user clicks "Retry". So:
  - **Use the History API for multiple pages** (`history.pushState` plus a front-end router), not whole-page navigation.
  - **The page must not navigate before `load`**: the outer page sees only the `load` event and cannot tell which document it is for, so `init` (with the token) goes to the first document that fires `load`. Do not redirect during loading, and do not use `location.replace` or `<meta http-equiv="refresh">`; route-level redirects may only stay under this extension's `/plugin-ui/<plugin>/`.
- **iframe -> outer**, using `window.parent.postMessage(msg, "*")` (an opaque origin cannot specify a targetOrigin); the outer page first checks that the source is this iframe, then validates with `parseEmbedChildMessage`, and ignores what it does not recognize:
  - `resize { height }`: 0-10000, which the outer page clamps to 120-4000 pixels.
  - `navigate { path }`: only an in-site path (such as `/chat/<id>`): a single leading `/`, no `//`, backslash or control characters anywhere; no `.` / `..` segments in the path part (including `%2e` encoding), no `%2f` / `%5c` / `%00`-`%1f` / `%7f`; identical to the original after URL normalization; <= 2000 characters. Non-ASCII characters are first passed through `encodeURIComponent`. The SDK and the web app validate verbatim identically, sharing the test vectors `tools/fixtures/embed-navigate-vectors.json`.
  - `toast { text }`: non-empty, <= 500 characters, shown as plain text.
- The outer implementation is in `apps/web/src/lib/embed-bridge.ts` and `components/chat-panel/EmbedTab.tsx`; extensions need not care about it and only follow the rules above.

### Pages and data

- **Static pages and scripts carry no data** and may skip token verification (an iframe navigating by `src` cannot carry an `Authorization` header, and the token is given only by `init`); data is given only through routes that verify the token. Do not put the token in the URL query string (it would enter logs and browser history).
- Build the DOM with `textContent`; data does not go through `innerHTML`. For styles use `var(--cb-*, fallback)`, written to `:root` on `init` / `theme`.
- **Real-time refresh goes through `ctx.bus`, subscribed per request**: in an SSE route `await ctx.bus.subscribe(topic, ...)`, and unsubscribe when `req.signal` aborts (the client disconnects) or in the `ReadableStream` `cancel`; end the stream proactively at the token's `exp`, and the page reconnects with the renewed token, so permissions expire with the token. Heartbeats use `AbortSignal.timeout` as a wait within this request, not a timer; do not keep a module-level subscription table. The page reads the stream with `fetch` (`EventSource` cannot carry an `Authorization` header). The writer calls `ctx.bus.publish` once and the streams on all other replicas receive it.
- `req.signal` aborts only if the client disconnects before the response has been fully written; it does not abort after a normal finish.

## Client code: components, replaceable slots and decoration (L2 / L3)

Spec: `docs/superpowers/specs/2026-11-09-client-extensions-design.md` (the code is the source of truth; §17 lists where the spec was adjusted). A plugin's extension may carry **client code** next to its server code: one browser ES module, CSS files and assets, built by `capybara-plugin pack`, reviewed with the extension, delivered only where the plugin is on. It runs in the page with full trust (approval is governance, not a sandbox). Four layers: L0 themes, L1 slots (views and embeds), L2 `component` contributions and replaceable slots, L3 decoration (parts, state tokens, overlay, events, plugin CSS). The browser SDK is `@capybara-hq/plugin-client` (`packages/plugin-client`, published; depends on `react` as a peer and on no `@capybara-hq/*`). Plugin authors: writing-extension-ui in capybara-hq/plugins.

### The `component` kind and permissions

- `UiContribution.kind: "component"`; `permissions.client: true` and `permissions.ui.components: [<id>...]` (the two-way cross-check of `validateUiContributions` covers components: an id in `components` has a `component` contribution and the reverse, an id is in only one of `views` / `embeds` / `components`, `path` is refused, the slot must accept `component`, `components` needs `client: true`).
- Both new keys are **sensitive and block loading** (`itemReason`: `client_code` for `client`, `ui_component` for `ui.component:<id>`; `blockingKeys` exempts only `ui.view:*`). An upgrade that changes only the client bytes loads like any server-code change (keys are reviewed, not bytes); one that adds a component or the `client` key waits for approval, and the old build keeps being served meanwhile (below).
- A component may have a server side: `ctx.ui.view(<component id>, render)` / `ctx.ui.action(...)` are allowed for ids in `ui.views` or `ui.components` (`perm-ui` accepts both). Its view is gated like a view of its slot (`minRole`, scope) and may carry `data` (a `JsonValue`, at most `UI_LIMITS.componentDataBytes` = 32768 bytes, else `ui.invalid_view`); the other kinds refuse `data`. A component's view may have no blocks. Props carry what the page already shows; anything the server must authorize goes through `useView` / `useAction`.
- `ToolResult.card` may name a `component` contribution of `conversation.tool-result.card`.
- Components in **list slots** are drawn inside the host's frame (the section, panel, card or form section views get: `ClientComponentBlock` takes a `frame`, the title comes from the manifest), so a plugin does not draw its own section, title or box. Components in single and overlay slots draw whatever they want. A `conversation.panel` component is always drawn in the host's panel frame (title, close), and the entry is not offered in safe mode or under the kill switch.
- **Component pages and sections have designed states** (`ClientComponentBody`): loading is a skeleton, a delivered build whose entry failed (or lacks the component) is a load-failed line with retry (a document reload), and a component that is not delivered (safe mode, kill switch, outside the document's set, crash budget, withdrawn) is an empty state. `org.page`, `platform.page` and `agent.detail.section` use it, and navigation hides entries that cannot render (`useOfferedContributions`; the admin console reads safe mode, the kill switch and its list itself).

### Replaceable single slots

`UiSlotSpec` has `cardinality: "list" | "single"`, `replaceable` and `builtin` (what the built-in is). A single slot accepts only `component`, has no anchors or limits, and always renders its built-in unless a winner is chosen. The three replaceable slots: `shell.brand` (the sidebar brand row; props `builtin`, `collapsed`, `panel`), `conversation.empty` (the new-conversation hero; `builtin`, `agentId`, `greeting`), `conversation.composer.frame` (`builtin` is the framed composer, `children` the composer inputs **without** the frame, `conversationId`, `runState`; `children` must render **exactly once, inside the frame**: none, two, or a portal out of the frame falls back to the built-in). The design `Sidebar` takes `brand` as a function of the panel it is drawn in (`{ collapsed, panel: "full" | "rail" | "drawer" }`, once per drawn panel), and the `shell.brand` props carry `panel` too. `shell.overlay` is a list slot (`maxShown: 4`).

- **Winner (`use`)**: the arrangement entry of a single slot is `{ use: "<extension>/<contribution>" | null }`. `use` on a list slot and `hidden` / `order` on a single slot are 400 `validation_failed`. Resolution: the org's entry, else the platform's, else the built-in; `use: null` or no entry is the built-in; a `use` naming something not available in the org (extension off, dropped, role below the slot's) is the built-in, never the other level's pick and never an error, and the stored key is kept. The contributions route lists at most the winner of a single slot; the web renders the built-in for an empty list. Enabling a plugin never picks a replacement by itself.
- **Fallback** (`ReplaceableSlot.tsx`, `ReplaceableFrame` of the design system): a winner that throws, fails to load, times out, or breaks the composer rule (after every commit and every DOM change in the slot the composer's textarea must be there exactly once; the host checks with a MutationObserver) is replaced by the built-in for that mount and reported once. While the module loads, the built-in sits in a `ReplaceableFrame` that is `visibility: hidden` for at most `CLIENT_LIMITS.pendingMs` = 1500 ms, then shown: the server renders the slot pending when the shell lists a delivered winner, and the frame's CSS alone reveals the built-in after 1500 ms, so scripts that never run never leave it blank. Safe mode and the kill switch show the built-in.

### Suggested appearance

`plugin.json` `suggestedAppearance: { theme?, replacements? }` (validated by `parsePluginManifest`; error `appearance-invalid`; details in writing-plugins). Nothing applies on install or enable. **Apply this plugin's appearance** (zh 应用此插件的外观) is one confirmed step: super admin `POST /api/v1/admin/catalog/items/:id/appearance` (platform default theme and platform arrangement `use`), org admin `POST /api/v1/orgs/:orgId/extensions/:extension/appearance` (org theme, keeping `personal`, and org arrangement `use`); body `{ dryRun? }`, answer `{ theme, replacements, skipped }` in the **author's order** (`skipped[].reason`: `unknown-slot` / `not-available` / `not-eligible`; the order is recorded at prepare in `catalog_item_versions.appearance_order`). At the org level `from` is the value **in effect** (the org's entry, else the platform's) with `followsPlatform: true` when it is the platform's; an org following a platform that already uses the suggestion gets nothing pinned. A plugin with client code **reloads the page after a successful apply** (the confirm dialog says so), because the document's client set is fixed at first render; a theme-only plugin does not. Code: `packages/kernel/src/catalog/appearance.service.ts`. The web calls with `dryRun: true` for the confirm dialog, then writes everything in one transaction. A theme that cannot be the default (the org route: not on in the org) is 400 `theme.not_available` and refuses the whole call; an unavailable replacement is skipped. A member gets 403 (and sees no action); availability is judged on the serving replica (`host.enabledPlugins`, the loaded extension), so a replica that has not loaded the extension yet skips its replacements as `not-available`. Platform operations: `plugins.platform-apply-appearance` (super admin) and `plugins.apply-appearance` (org admin), confirmed every time, never rememberable; `dryRun` is their card, not an input.

### Parts, state tokens, the overlay

- **Parts**: `UI_PARTS` (`packages/plugin-sdk/src/ui-parts.ts`) lists `{ name, version, owner, states, description }`; `owner` is a **list** of the files that render the element (one concept can be drawn by several components). Built-ins carry a literal `data-cap-part="<name>"` (several names allowed: `button button.primary`); plugin CSS selects with `[data-cap-part~="<name>"]`. `data-part` stays internal. `check:ui-parts` pins every literal to a catalog name in one of its owner files and the generated copies and [docs/guide/ui-parts.md](../../../docs/guide/ui-parts.md) (`pnpm gen:ui-parts`). Renaming or removing a part, or dropping a promised state, bumps its `version`. The `sidebar` and `section` parts promise no `aria-expanded` (the sidebar mode is the `sidebar=` token).
- **State tokens**: the shell element (`[data-cap-part~="shell"]`, not `<html>`) carries `data-cap-state`, space separated, in this order: `run=idle|running|waiting|failed`, `theme=<plugin>/<theme file id>` or `theme=builtin`, `motion=full|reduced` (after hydration), `sidebar=rail|full` (after hydration; the drawer below 960 px counts as `full`). Plugin CSS: `[data-cap-state~="run=running"] [data-cap-part~="properties-panel"]`. The server render writes `run=idle` and the theme; first-paint CSS should use `@media (prefers-reduced-motion: reduce)`.
- **Run state** comes from the conversation page (`ConversationView` publishes its phase into a context above `AppFrame`); `failed` holds until the next `run_started` or navigation; pages without a conversation are `idle`.
- **Overlay**: `shell.overlay` is drawn in the design `DecorationLayer` (fixed, above every layer, `pointer-events: none` except `[data-cap-interactive]`). The layer is not `aria-hidden` itself: it marks every element that neither is nor holds an interactive element, so interactive elements are never under `aria-hidden`, and **text directly beside an interactive element stays exposed unless the plugin wraps it in an `aria-hidden="true"` element itself** (the layer does not rewrite React-owned text); not rendered in safe mode, under the kill switch or on admin pages.
- **Client events** (`useCapybaraEvents`, `events` of `defineClientExtension`): derived **on the client** from the conversation log the page already reads (`apps/web/src/components/client-ext/events.ts`, the table of spec §7.5), never a new kernel stream and never written to the log. The history loaded when a page opens sets a baseline and **emits nothing**; every later list emits the events past the highest seq seen, once each, in order. A revisit's catch-up (events that arrived while the page was away, then read) therefore **emits them as live events**. Payloads carry no message text or tool input. Sub-agent conversations in the side panel emit nothing. A listener that throws counts toward the crash budget and does not stop other listeners. A **crash counts once per contribution per document** (`plugin, build, contribution, kind`); errors of no contribution (listeners, uncaught errors) count each time.
- **CSS layers**: the design stylesheet is `@layer design`, theme CSS `@layer theme`, plugin CSS `@layer extensions` (order declared `design, theme, extensions`), so plugin rules win without `!important`.

### Client CSS rules (packer, import check, delivery)

The packer wraps each `client/styles/*.css` in `@layer extensions { … }`; the kernel re-checks stored bytes with a CSS tokenizer; the rule is one pure module in the SDK (`packages/plugin-sdk/src/client-css.ts`: `clientCssProblem`, `wrapClientCss`) that the packer and the kernel both import, with shared vectors in `packages/plugin-sdk/test/fixtures/client-css-vectors.json`: the file must be exactly one such block. Violations are `client.invalid` (400) at import and `client-css-remote` in pack:

- `@import` is refused (a remote sheet is not integrity-pinned).
- A `url()` may name only `../assets/<file>` of the plugin's own assets (exact match), a `data:` URL or a `#fragment`; any other URL, relative ones included, is refused (the sheet is served from `/api/v1/client/<plugin>/<build>/styles/`, so a relative climb would reach kernel routes with the viewer's cookies).
- Functions refused outright, in any case or escape spelling: `image-set`, `-webkit-image-set`, `cross-fade`, `-webkit-cross-fade`, `element`, `-moz-element`, `paint`, `src`, `image` (they build URLs from strings or `var()`); write `url(../assets/x.png)` directly.
- Invisible characters are refused anywhere in the file (escaped or not): non-ASCII whitespace (NBSP, U+0085, U+1680, U+2000-U+200A, U+2028, U+2029, U+202F, U+205F, U+3000), zero-width characters (U+200B-U+200D, U+2060, U+180E) and U+FEFF. URLs are trimmed with CSS whitespace only.
- Selectors are advice only: `capybara-plugin check` warns `client-css-selector` (not built from `[data-cap-part]`, `[data-cap-state]`, `cx-<plugin>-` classes, `--cx-<plugin>-*` custom properties on `:root`) and `ui-part-unknown`.

### Delivery, access and the served build

- **Storage**: when a package with a `client` section is stored, the kernel checks the section (limits, types, CSS rule, every sha384 `integrity` recomputed: `client.integrity_mismatch`) and writes the files to object storage under `deployment/platform/client/<plugin>/<package sha256>/`; the `extension_client_builds` row (migration 0107) holds the integrity, never the object store. No object store: `storage.unavailable`. A section whose `apiVersion` is above the kernel's `CLIENT_API_VERSION` is refused with `client.api_unsupported` (400); the shell reads **and the delivery route** (404) also omit builds the running kernel does not support. The kernel's gate is authoritative: the web stamps its own `CLIENT_API_VERSION` into the import map, so a bundle's declared `apiVersion` is only a repeated check. A manifest and a section that disagree are `client.undeclared`. Bootstrap plugins may not carry client code: the kernel's bootstrap refuses such a package (`client.invalid`, naming the plugin) and `check:bootstrap` reports it (rule `bootstrap-client-code`: workspace entries offline, npm entries in the network mode).
- **Key charset**: every segment of a client file key and of a delivery path is `[A-Za-z0-9._-]` (not `.` or `..`); files are known only by their exact manifest key.
- **Route** `GET /api/v1/client/:plugin/:build/*` (`client-delivery.controller.ts`; the build id is the package sha256): the file is named from the **raw** request path, never decoded; the **kernel route never redirects** (no trailing-slash or case redirect), because the web's script CSP allows scripts from this path prefix only and a redirect would leave it. The web origin in front of it keeps Next's own 308 for a trailing or duplicated slash; that is accepted. Headers: `Cache-Control: private, max-age=31536000, immutable`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `text/css; charset=utf-8` for CSS, SVG assets also `Content-Security-Policy: default-src 'none'; sandbox`. Everything else (unknown file, build not served, kill switch, no access) is one 404 `client.not_found`.
- **The served build is the one a live replica runs** (`ClientAccess.served`: `extension_replica_status.serving_sha256` with a fresh heartbeat, an enabled install, and an approved snapshot covering `permissions.client` and the manifest's `ui.component:*`). So an upgrade pending approval, or one whose migration / setup / import failed, keeps the **old build served and listed**; the new one appears once a replica serves it; with no live replica nothing is served. An org upload awaiting the super admin has no install, so nothing of it is served. The caller must be a member (any role) of a live org where the extension is on, or a super admin for a build with a `platform.page` component. One PG query per request, nothing cached.
- **Shell reads**: `GET /api/v1/orgs/:orgId/ui/client` (`ui.use`) and `GET /api/v1/admin/ui/client?plugin=` (super admin; only `platform.page` components, no stylesheets; `?plugin=` narrows to one plugin, which `/admin/p/<plugin>/<id>` uses); both `no-store`.
- **Kill switch**: deployment setting `clientExtensions: { enabled, disabled: string[] }` (`PUT /api/v1/admin/settings`, platform operation `admin.update-settings`). `enabled: false` stops all client code, `disabled` stops listed plugins' client code only; the shell reads return `enabled: false` / omit them and delivery is 404. A corrupt stored value logs a warning and reads as the default.
- **Reports**: `POST /api/v1/orgs/:orgId/ui/client/reports` and `POST /api/v1/admin/ui/client/reports` (204, throttled `client-reports`, 20 per minute per account), body `{ plugin, build, contribution, kind: "load" | "render" | "event" | "api" | "budget", message }`; `message` over **500 characters is a 400**, not truncated (the web sends the error's message only). `contribution` is null or one of **the build's own component ids** (grammar `^[a-z][a-z0-9-]{0,39}$`: 400 when malformed, 404 `client.not_found` for an id the build lacks), so reports cannot grow without bound. 404 `client.not_found` also for an extension not on in the org or a build the caller cannot fetch. A row's `org_id` is not a foreign key: it may name an org deleted since (the admin page says so). Rows are upserted in `extension_client_reports` (count, first / last, last message); a `@LockedCron` job under `WorkerModule` prunes rows older than 30 days. The admin extension detail shows `client` (the build a live replica serves; files and sizes, also in the catalog item detail and the org extension view) and `clientReports` (at most 50 per extension, newest first, limited in SQL) with org names.

### Web host (`apps/web/src/components/client-ext/`)

- **CSP** (`apps/web/src/proxy.ts`, `lib/headers.ts`): every document gets a fresh nonce and `script-src <host>/_next/ <host>/api/v1/client/ <host>/_capybara/client-host/ 'nonce-…'` (no scheme, `'unsafe-eval'` only in dev), `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'self'`, `form-action 'self'`. The host is `X-Forwarded-Host` when present and nameable, else `Host`; a reverse proxy must forward the original `Host` (docs/deploy/README.md). `/api/*`, `/plugin-ui/*`, `/_next/*`, `/dev/ui/*` and `/icon.svg` skip the proxy. `style-src`, `connect-src`, `img-src` stay open (full trust).
- **Loading**: `ClientExtensionsHead` renders the import map (host shims for `react`, `react/jsx-runtime`, `react-dom`, `@capybara-hq/plugin-client`, plus the integrity of every entry and shim) and, per entry, a classic `preload` (not `modulepreload`; React sends it as a Flight hint that the client turns into a `<link>`, so it is not in the first server HTML); the plugin stylesheets with `precedence="extensions"` and integrity. `ClientHost` sets `globalThis.__CAPYBARA_CLIENT_HOST__` in its first layout effect and `import()`s each entry in plugin-name order. Load timeout `CLIENT_LIMITS.loadTimeoutMs` = 10000. The shims are generated by `pnpm gen:client-host` (`<webBuild>` = web version plus the shim hash; the Next build id is unknown before the build); the export list and `CLIENT_API_VERSION` copy is `pnpm gen:plugin-client` (`check:plugin-client-api`).
- **Where it runs**: workspace pages only (components in every component slot, plugin CSS, overlay, replacements). Admin pages run no org client code, plugin CSS, overlay or replacements; only `platform.page` components on their own page. A client navigation that crosses the boundary (workspace / admin, into or out of a client-bearing platform page, another org) becomes a document load. Auth pages, the org chooser, the setup frame and the root error pages load none.
- **Safe mode**: `?safe-ui=1` sets the session cookie `cap_safe_ui` in the proxy (`HttpOnly`, no max-age); safe mode then **lasts the browser session**, not just the document. Only `?safe-ui=0` ends it, and the banner's exit navigates there through the proxy (script cannot clear an `HttpOnly` cookie). The banner is a **row of the App Shell** (design `AppShell` / `SetupPage` take `banner`; the shell is a grid and carries `data-banner="true"`), not an element above it. In safe mode: no import map, preload, plugin stylesheet or overlay, the built-ins in replaceable slots, component contributions skipped (views and embeds still render), a banner while client code exists for the viewer; the error pages and the crash notice link to the current URL with `safe-ui=1`.
- **Crash budget**: errors are a boundary catch, a listener throw, a failed or timed-out load, an unsupported `apiVersion`, an uncaught `error` / `unhandledrejection` naming the build URL. At 3 in one document the build is disabled for the browser session (`sessionStorage` key `cap-client-disabled`, `<plugin>/<build>`; a new build is not covered): components unmount to the built-ins, sheets are disabled, listeners dropped, a notice with the safe-mode link shows. A client navigation that is not a click (router push, back / forward) across the workspace / admin boundary leaves plugin code first: every extension sheet is disabled and every plugin marked disabled before `navigate`.
- **Client set changes while a page is open**: the kill switch and a per-plugin disable reach an open page on its **next client-set read** (30 s freshness, reconnect, navigation, reload), not instantly; JavaScript that already ran cannot be unloaded. A live set that gains client code (entry or stylesheet) of a `plugin/build` the document lacks shows one "client set changed" notice with a reload action (never in safe mode; a withdrawal shows none).
- **Stylesheet policing**: React never removes a hoisted sheet, so `ClientHost` disables (`link.disabled`) every extension sheet not belonging to an active plugin of the document's set (safe mode: all), now and on each head mutation. Two consequences to know: (1) a **session-disabled plugin's CSS flashes** until hydration, because the server cannot see session storage; (2) when a plugin is withdrawn from an open page (switch, upgrade, kill switch) its components unmount and its linked sheets are disabled at once, but styles a component injected from JavaScript (a `<style>` it appended itself) **persist until the next document load**; plugins should remove what they add on unmount.
