# M7 发布与生态 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 Capybara 做成可以发布、可以部署的 0.1.0。本里程碑做两件事：

1. **发布与部署**：
   - 四个 ghcr 镜像（amd64 + arm64）；
   - compose 一条命令起全部服务，含 init 容器；
   - npm 发布流水线：SDK、内核、测试工具，以及官方插件的 npm-pack tgz；
   - gateway 角色接管渠道长连接，副本间公平分配，另加可选的 webhook 入站；
   - 部署与升级文档。
2. **生态**：
   - `ctx.hooks`：四个观察 / 拒绝型挂载点，外加 `usage.report` 计量；
   - 插件 SDK 公开 API 快照检查；
   - CLA。

**Architecture:**
- **镜像**：
  - 后端只有一个 Dockerfile（`docker/kernel.Dockerfile`），按默认 `CAPYBARA_ROLES` 出三个镜像 `capybara-api` / `capybara-worker` / `capybara-gateway`，内容是 `apps/capybara` 的生产构建、内核与两个内置插件；
  - `capybara-web` 跑 `node server.mjs`，不用 Next 的 standalone 输出。
- **官方插件**只发 npm：发布脚本先用 `pack-plugin` 打出 tgz，再 `npm publish <tgz>`。部署时按包名安装（`capybara plugins install npm:<name>` 或网页）。M7 不上线官方清单。
- **渠道长连接**由 `ChannelSupervisor` 在 gateway 角色上跑：
  - 每个 gateway 副本在 Redis 登记心跳，按「连接总数 ÷ 在线副本数 + 余量」认领连接，超出份额就逐个交还；
  - 租约语义不变：每条连接只有一个持有者，租约过期后由别的副本接管；
  - webhook 是每条连接可选的入站方式，由插件验签、处理 URL 校验，内核复用现有的入站去重与入队。
- **hooks** 只能观察或拒绝，不能改写：
  - 拒绝写进事件日志（`hook_denied`），模型请求仍然能由日志还原；
  - `usage.report` 经队列可靠投递。

**Tech Stack:** TypeScript、Node 24、pnpm、Docker Buildx（多架构）、GitHub Actions（ghcr、npm provenance）、changesets、`@microsoft/api-extractor`、CLA Assistant（`contributor-assistant/github-action`）、NestJS + Fastify、BullMQ、Redis、Vitest + Testcontainers。

## 计划层面的取舍（设计者的决定，执行中如被推翻，记入台账）

- **F1 官方清单默认关闭。** `catalogs.official.enabled` 的默认值由 `true` 改为 `false`，`url` 不变。
  - 关闭时内核从不拉取，后台显示「离线模式」，没有错误状态，也不打日志。
  - 理由：现状是开着时每 360 分钟拉一次占位地址。虽然只在状态变化时打一次 warn，但后台会一直显示官方来源 `error`。况且占位域名不归项目控制，默认向它拉取清单是供应链风险。官方市场上线时再把默认值改回来。
- **F2 发布集合。**
  - npm 普通包（`pnpm publish`）：`@capybara-hq/plugin-sdk`、`@capybara-hq/kernel`、`@capybara-hq/testing`。`testing` 供第三方插件写双副本测试用，它依赖 `kernel`。
  - npm 插件包（`pack-plugin` 打出 tgz 后 `npm publish <tgz>`）：`plugins/*` 里除 `example-counter` / `example-board` 之外的全部插件，包括 `model-fake`（README 的免密钥体验要用它）。两个 example 加 `"private": true`。
  - 不发布：`@capybara-hq/design` 改为 `"private": true`（只有 web 用）；`capybara`、`web`、`checks`、`pack-plugin` 本来就是私有的。
- **F3 首发版本 0.1.0。** 现有约 150 个待发布 changeset 记的是发布前的开发历史。它们若进 `changeset version` 会把版本推过 0.1.0，所以在首发前的最后一个任务（T21）里全部删除，`CHANGELOG.md` 写一条「0.1.0 初版」。此后照常用 changeset。M7 期间各任务照常附 changeset（工作流规则不变），T21 一并清理。
- **F4 插件包带上 npm 元数据。** pack 生成的 `package.json` 增加透传字段 `description`、`repository`、`homepage`、`keywords`（npm provenance 要求 `repository.url` 与 GitHub 仓库一致）。所有要发布的源 `package.json` 补上 `repository: {type:"git", url:"git+https://github.com/capybara-hq/core.git", directory:"<路径>"}`。
- **F5 生产 CLI 入口。** `apps/capybara/bin/capybara.mjs` 现在经 tsx 跑源码。改为：`../dist/cli.js` 存在时直接 import 它；不存在时退回 tsx（开发模式）。镜像只放 `tsc -b` 的产物，不带 tsx 加载器。
- **F6 init 幂等。** 新增 `capybara admin create --if-none`：已有任何一个活跃的企业管理员时，打印一行并以 0 退出。
  - init 容器依次执行 `capybara migrate`，再执行 `capybara admin create --if-none`。密码从文件 `CAPYBARA_INIT_ADMIN_PASSWORD_FILE` 读（compose secret），login / 显示名从环境变量读。
  - 没有提供密码文件时跳过建管理员，提示用网页 setup。
- **F7 gateway 心跳与份额。**
  - 心跳：ZSET `capk:gateway-replicas`，member 为副本 id，score 为毫秒时间戳。在线 = score > now − `channels.leaseTtlMs`。由续租循环每轮写一次。
  - 份额：`target = ceil(runnable / live) + channels.shareSlack`（默认 1），其中 `runnable` 是本轮扫描查到的可持有连接数。
  - 持有数 ≥ target 时不再认领。持有数 > target 时，每轮扫描只交还一条：选最近一次接上的那条，用 `releaseInBackground`。交还时写 `capk:channel-handoff:<connectionId>`（值为本副本 id，PX = 2 × `scanIntervalMs`），本副本在它过期前不再认领这条连接。
  - 停机时 `ZREM` 自己。
- **F8 webhook 契约**（SDK 新增，可选实现）：
  ```ts
  interface ChannelWebhookRequest { method: "POST"; headers: Readonly<Record<string, string>>; body: Uint8Array; receivedAt: number }
  interface ChannelWebhookResponse { status: number; headers?: Record<string, string>; body?: string }
  type ChannelWebhookResult =
    | { kind: "respond"; response: ChannelWebhookResponse }                        // URL 校验 challenge 等，直接回复
    | { kind: "events"; events: InboundEvent[]; ack: ChannelWebhookResponse }       // 内核逐个 onEvent 全部 resolve 后才回 ack
    | { kind: "reject"; status: 400 | 401 | 403 };
  interface Channel { /* … */ webhook?: { handle(args: { config: unknown; request: ChannelWebhookRequest; signal: AbortSignal }): Promise<ChannelWebhookResult> } }
  ```
  - 验签、解密、时间戳防重放都在插件里做，内核不懂平台格式。
  - 任一 `onEvent` reject 时内核回 503，让平台重投；去重沿用现有的 `messageDedupeKey` / `eventId`。
  - 只有声明了 `webhook` 的插件，其连接才能切到 webhook 模式。
- **F9 webhook 路由与地址。**
  - 路由：`POST /channels/webhook/:connectionId`，挂在 gateway 角色上（新 `GatewayModule`；`serveGateway = roles.includes("gateway")`）。不经内核鉴权，体积上限 1 MiB。
  - 连接不存在、不是 webhook 模式或已停用时，一律回 404 `channel.webhook_not_found`，不泄露连接是否存在。
  - 后台显示的回调地址 = `channels.webhookBaseUrl` + `/channels/webhook/<id>`。没配 `webhookBaseUrl` 时不能切到 webhook 模式，返回 409 `channel.webhook_unavailable`。
  - 切换模式后，内核广播 `channel.changed {reconnect:true}`，现持有者断开长连接；supervisor 只扫 `inbound_mode = 'long_connection'` 的连接。
- **F10 hooks 语义。**
  - 注册：`ctx.hooks.on(mount, handler, { mode: "observe" | "policy" })`，只能在 `setup` 期间调用，并且必须在 `permissions.hooks` 里声明。M7 可注册的挂载点只有 `model.request`、`model.response`、`tool.preExecute`、`tool.postExecute`、`usage.report`；`session.*`、`agent.preStep` 仍是预留项，注册时抛错。
  - **只读**：handler 拿到的载荷是深冻结的副本，返回值只认 `{ deny: string }`。
    - `observe` 的返回值被忽略。
    - 只有 `policy` 模式、且挂载点是 `model.request` 或 `tool.preExecute` 时，返回 `deny` 才生效；其他组合在注册时就抛错。
  - **出错与超时**（`hooks.timeoutMs`，默认 5000）：
    - `policy` 出错或超时，按拒绝处理，原因为 `hook_error`（策略类出错即拒绝，§2.4）；
    - `observe` 出错或超时，放行，并且每个插件、每个挂载点每分钟最多告警一次（Redis 计数，带 TTL）。
  - **范围**：只对组织已启用该插件的会话触发，判断用 `host.enabledPlugins(orgId)`。只在 `kind = 'chat'` 的对话上触发，评测回放不触发 model / tool hook。多个 handler 按插件名排序后串行执行，遇到第一个 deny 就停。
  - **拒绝的落点**：
    - `model.request` 被拒：不写 `model_call`，写 `hook_denied`，运行以 `run.hook_denied` 失败（不可重试，模型看不到任何东西）；
    - `tool.preExecute` 被拒：写 `hook_denied`，工具结果为英文错误 `Tool call blocked by the "<plugin>" policy hook: <reason>`（原因截断到 500 字符）。这条结果照常进 `tool_result`，回放时从日志读，所以不需要新的 `DriftReason`。
  - **载荷里不含**凭据、媒体字节和已打码的密钥。
- **F11 `usage.report` 可靠投递。**
  - 每写一条 `usage` 事件，就在同一个后续步骤里向队列 `cap-kernel-usage-report` 加任务。job id 为 `usage-<conversationId>-<seq>`，不含 `:`。
  - 任一 worker 副本执行：按插件名逐个调用 handler；某个插件失败时只重试这个插件，最多 5 次、指数退避，每次记在 job data 里。
  - handler 收到 `{ eventId: "<conversationId>/<seq>", orgId, accountId, agentId, conversationId, conversationKind, runId, provider, model, usage, occurredAt }`，须按 `eventId` 幂等。
  - 单步评测与评委的用量不进事件日志，M7 不上报（列入推迟项）。
- **F12 权限检查。** `check:plugin-permissions` 新增规则 `perm-hooks`：`ctx.hooks.on(mount, …)` 的 mount 必须是字面量，且在 `permissions.hooks` 里声明。hooks 仍按敏感项展示，已有展示不变。
- **F13 SDK 快照。**
  - 报告文件：`packages/plugin-sdk/api/plugin-sdk.api.md`；api-extractor 读 `packages/plugin-sdk/dist/index.d.ts`。
  - `pnpm check:sdk-api` 先 `tsc -b packages/plugin-sdk`，再以非 local 模式运行；报告不一致即失败，并提示运行 `pnpm gen:sdk-api`。
  - 另一项检查 `check:sdk-api-changeset`（只在 PR 上跑）：相对 base，`.api.md` 变了，而 diff 里没有提到 `"@capybara-hq/plugin-sdk"` 的 changeset，就失败。
- **F14 测试容器复用。**
  - Vitest `globalSetup` 每次运行只起一个 PG 17 和一个 Valkey，地址经环境变量 `CAPYBARA_TEST_PG_ADMIN_URL` / `CAPYBARA_TEST_REDIS_URL` 传给 worker。
  - `startTestPostgres()` 在共享模式下返回一个新建的随机数据库（`stop()` 用 `DROP DATABASE … WITH (FORCE)` 删掉），这对现有调用方透明。
  - Redis 默认**不**共享：bus 的频道 `cap:<namespace>:<topic>` 不分 DB，多个测试文件共用一个实例会串消息。所以 `startTestRedis()` 在共享模式下按文件分配 DB 编号（容器以 `--databases 1024` 启动，编号由 `INCR capybara-test:db` 分配），**只**给显式传 `{ shared: true }` 的调用方用。T1 先调查哪些测试文件不用 bus 或 BullMQ 事件，再把它们改成共享。
  - 双副本 harness 不传 `pgUrl` 时也走共享 PG。

## Global Constraints

- 依赖方向不变（见 `AGENTS.md`）。新增：`@capybara-hq/plugin-sdk` 以 devDependency 使用 `@microsoft/api-extractor`；新建私有包 `tools/release`（`@capybara-hq/release`），dev 依赖 `@capybara-hq/pack-plugin`。插件不得 import 内核；web 只经 `/api/*` 调内核。
- **事件日志是唯一事实源**：hooks 不改写请求或结果。改 `runtime/model-call.ts` 与 `tools/pipeline.ts` 的前后，都要跑零漂移夹具 `packages/kernel/test/evals/reconstruct.test.ts`、`packages/kernel/test/tools/rename-compat.test.ts`。
- **多副本纪律**：
  - gateway 心跳、交还标记、hook 告警计数都放在 Redis 并带 TTL；
  - 队列名 `cap-kernel-usage-report` 与 job id 不含 `:`；
  - `ctx` 不提供定时器。
- **迁移**：纯 SQL，按 `skills/writing-migrations` 写。本里程碑只有 `0038_channel_inbound_mode.sql`（T4）；事件类型由 zod 定义（`conversations/events.ts`），表上没有 CHECK，所以 `hook_denied` 不需要迁移。建表、删表都带 `IF NOT EXISTS` / `IF EXISTS`。
- **配置**（新键写进 `config/schema.ts`，重新生成 `docs/config.md`；`hot` 字段在 `HOT_APPLIERS` 登记）：

- **镜像**：基础镜像为 `node:24-bookworm-slim`，以非 root 用户 `capybara`（uid 10001）运行。镜像标签 = `ghcr.io/capybara-hq/<image>:<version>` 加 `:latest`，PR 上只构建不推送。镜像里不放源码 `.ts`（`server.mjs` 依赖的 `apps/web/src/lib/peer.ts` 除外）。

## Review Focus

1. **滚动升级或扩缩容时 gateway 副本数在变。** 新副本加入后，老副本每轮最多交还一条，不会一次全断；每条连接任一时刻最多一个持有者；一个副本被杀，它的连接在一个 `leaseTtlMs` 内被接管。由 T3 的双副本测试覆盖（第三个副本中途加入、再被 SIGKILL）。
2. **webhook 请求伪造或重放。** 签名错误、时间戳超出 5 分钟、连接不是 webhook 模式，都不入队，并分别回 401 / 401 / 404；同一事件重投只处理一次。由 T4（内核）和 T5（Slack / Lark 验签）的测试覆盖。
3. **policy hook 自身故障。** handler 抛错或超时，`tool.preExecute` 按拒绝处理，运行继续，模型收到英文错误；observe hook 故障不影响运行，告警被限流。插件停用后 hook 立即不再触发。由 T14、T15 的测试覆盖。
4. **在旧数据卷上 `docker compose up`（升级）。** init 再跑一次 migrate 是幂等的，`--if-none` 不会重复建管理员；init 失败（例如 PG 版本 < 15）时，内核服务不启动，因为它们 `depends_on: init: service_completed_successfully`。由 T8 的冒烟脚本覆盖（连续 up 两次、PG 14 失败用例）。
5. **发布流水线重跑。** 某个包的这个版本已经在 npm 上时跳过它，不报错；部分发布失败后重跑能补齐。插件 tgz 的 sha512 与 CI 产物一致。由 T9 的 `publish-plan` 单测覆盖。
