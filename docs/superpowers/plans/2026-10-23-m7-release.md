# M7 Release and Ecosystem Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Precondition:** execution starts after PR #13 merges and this branch is rebased on main.

**Goal:** Turn Capybara into a releasable, deployable 0.1.0. This milestone does two things:

1. **Release and deployment**:
   - four ghcr images (amd64 + arm64);
   - compose brings up every service with one command, including an init container;
   - an npm release pipeline: the SDK, the kernel, the testing helpers, and the official plugins as npm-pack tgz;
   - the gateway role takes over channel long connections, shared fairly across replicas, plus optional webhook inbound;
   - deployment and upgrade docs.
2. **Ecosystem**:
   - `ctx.hooks`: four observe / deny mount points, plus `usage.report` metering;
   - a public API snapshot check for the plugin SDK;
   - CLA.

**Architecture:**
- **Images**:
  - The backend has a single Dockerfile (`docker/kernel.Dockerfile`) that produces three images by default `CAPYBARA_ROLES`: `capybara-api` / `capybara-worker` / `capybara-gateway`, containing the production build of `apps/capybara`, the kernel and the two builtin plugins;
  - `capybara-web` runs `node server.mjs`, not Next's standalone output.
- **Official plugins** are published only to npm: the release script first packs a tgz with `pack-plugin`, then runs `npm publish <tgz>`. Deployments install by package name (`capybara plugins install npm:<name>` or the web UI). M7 does not launch the official catalog.
- **Channel long connections** are run by `ChannelSupervisor` on the gateway role:
  - each gateway replica registers a heartbeat in Redis and claims connections up to "total connections ÷ live replicas + slack", releasing extras one at a time when above its share;
  - lease semantics are unchanged: each connection has exactly one holder, and another replica takes over after the lease expires;
  - webhook is an optional per-connection inbound mode; the plugin verifies signatures and handles URL verification, and the kernel reuses the existing inbound dedupe and enqueueing.
- **hooks** can only observe or deny, never rewrite:
  - denials are written to the event log (`hook_denied`), so model requests can still be reconstructed from the log;
  - `usage.report` is delivered reliably through a queue.

**Tech Stack:** TypeScript, Node 24, pnpm, Docker Buildx (multi-arch), GitHub Actions (ghcr, npm provenance), changesets, `@microsoft/api-extractor`, CLA Assistant (`contributor-assistant/github-action`), NestJS + Fastify, BullMQ, Redis, Vitest + Testcontainers.

## Plan-level tradeoffs (the planner's decisions; if overturned during execution, record it in the ledger)

- **F1 The official catalog is off by default.** The default of `catalogs.official.enabled` changes from `true` to `false`; `url` is unchanged.
  - When off, the kernel never fetches, the admin console shows "offline mode", with no error state and no logs.
  - Rationale: today, when on, it fetches the placeholder URL every 360 minutes. Although it only warns once on state change, the admin console keeps showing the official source as `error`. The placeholder domain `catalog.capybarahq.com` belongs to the project (confirmed by the user), but no catalog is hosted there; the official marketplace is planned to be hosted on GitHub later (decided by the package-ecosystem project), and the url and default will change then.
- **F2 Release set.**
  - Regular npm packages (`pnpm publish`): `@capybara-hq/plugin-sdk`, `@capybara-hq/kernel`, `@capybara-hq/testing`. `testing` is for third-party plugins to write dual-replica tests; it depends on `kernel`.
  - npm plugin packages (`pack-plugin` packs a tgz, then `npm publish <tgz>`): every plugin in `plugins/*` except `example-counter` / `example-board`, including `model-fake` (the README's no-key trial uses it). The two examples get `"private": true`.
  - Not published: `@capybara-hq/design` becomes `"private": true` (only web uses it); `capybara`, `web`, `checks`, `pack-plugin` are already private.
- **F3 First release version 0.1.0.** The ~150 pending changesets record pre-release development history. If they went into `changeset version` they would push versions past 0.1.0, so they are all deleted in the last task before the first release (T22), and `CHANGELOG.md` gets one entry "0.1.0 initial release". Changesets are used normally afterwards. During M7, tasks still include changesets as usual (the workflow rule is unchanged), and T22 cleans them up together.
- **F4 Plugin packages carry npm metadata.** The `package.json` generated by pack gains the pass-through fields `description`, `repository`, `homepage`, `keywords` (npm provenance requires `repository.url` to match the GitHub repo). Every source `package.json` to be published gets `repository: {type:"git", url:"git+https://github.com/capybara-hq/core.git", directory:"<path>"}`.
- **F5 Production CLI entry.** `apps/capybara/bin/capybara.mjs` currently runs the sources through tsx. Change it to: import `../dist/cli.js` directly when it exists; fall back to tsx (dev mode) when it doesn't. The image contains only the `tsc -b` output, without the tsx loader.
- **F6 Idempotent init.** Add `capybara admin create --if-none`: when any active enterprise admin already exists, print one line and exit 0.
  - The init container runs `capybara migrate`, then `capybara admin create --if-none`. The password is read from the file `CAPYBARA_INIT_ADMIN_PASSWORD_FILE` (a compose secret); login / display name come from env vars.
  - Without a password file, admin creation is skipped with a hint to use the web setup.
- **F7 Gateway heartbeat and share.**
  - Heartbeat: ZSET `capk:gateway-replicas`, member = replica id, score = millisecond timestamp. Live = score > now − `channels.leaseTtlMs`. Written once per round by the lease-renewal loop.
  - Share: `target = ceil(runnable / live) + channels.shareSlack` (default 1), where `runnable` is the number of holdable connections found by this round's scan.
  - When held ≥ target, stop claiming. When held > target, release only one per scan round: pick the most recently connected one, using `releaseInBackground`. On release, write `capk:channel-handoff:<connectionId>` (value = this replica's id, PX = 2 × `scanIntervalMs`); this replica won't claim that connection again until it expires.
  - On shutdown, `ZREM` itself.
- **F8 Webhook contract** (new in the SDK, optional to implement):
  ```ts
  interface ChannelWebhookRequest { method: "POST"; headers: Readonly<Record<string, string>>; body: Uint8Array; receivedAt: number }
  interface ChannelWebhookResponse { status: number; headers?: Record<string, string>; body?: string }
  type ChannelWebhookResult =
    | { kind: "respond"; response: ChannelWebhookResponse }                        // URL verification challenge etc.; reply directly
    | { kind: "events"; events: InboundEvent[]; ack: ChannelWebhookResponse }       // kernel replies ack only after every onEvent resolves
    | { kind: "reject"; status: 400 | 401 | 403 };
  interface Channel { /* … */ webhook?: { handle(args: { config: unknown; request: ChannelWebhookRequest; signal: AbortSignal }): Promise<ChannelWebhookResult> } }
  ```
  - Signature verification, decryption and timestamp replay protection all happen in the plugin; the kernel knows no platform formats.
  - If any `onEvent` rejects, the kernel replies 503 so the platform redelivers; dedupe reuses the existing `messageDedupeKey` / `eventId`.
  - Only connections of plugins that declare `webhook` can switch to webhook mode.
- **F9 Webhook route and URL.**
  - Route: `POST /channels/webhook/:connectionId`, mounted on the gateway role (new `GatewayModule`; `serveGateway = roles.includes("gateway")`). No kernel auth; body limit 1 MiB.
  - When the connection doesn't exist, isn't in webhook mode or is disabled, always reply 404 `channel.webhook_not_found`, without leaking whether the connection exists.
  - The callback URL shown in the admin console = `channels.webhookBaseUrl` + `/channels/webhook/<id>`. Without `webhookBaseUrl` you can't switch to webhook mode; reply 409 `channel.webhook_unavailable`.
  - After switching modes, the kernel broadcasts `channel.changed {reconnect:true}` and the current holder drops the long connection; the supervisor only scans connections with `inbound_mode = 'long_connection'`.
- **F10 Hook semantics.**
  - Registration: `ctx.hooks.on(mount, handler, { mode: "observe" | "policy" })`, callable only during `setup`, and must be declared in `permissions.hooks`. The only mount points registrable in M7 are `model.request`, `model.response`, `tool.preExecute`, `tool.postExecute`, `usage.report`; `session.*` and `agent.preStep` remain reserved and throw on registration.
  - **Read-only**: the payload a handler receives is a deep-frozen copy, and the only recognized return value is `{ deny: string }`.
    - The return value of `observe` is ignored.
    - A returned `deny` takes effect only in `policy` mode on `model.request` or `tool.preExecute`; any other combination throws at registration.
  - **Errors and timeouts** (`hooks.timeoutMs`, default 5000):
    - a `policy` error or timeout counts as a denial with cause `hook_error` (policy hooks fail closed, §2.4);
    - an `observe` error or timeout lets the call through, with at most one warning per plugin per mount point per minute (Redis counter with TTL).
  - **Scope**: fires only for conversations of orgs that have enabled the plugin, checked with `host.enabledPlugins(orgId)`. Fires only on conversations with `kind = 'chat'`; eval replay doesn't fire model / tool hooks. Multiple handlers run serially, sorted by plugin name, stopping at the first deny.
  - **Where denials land**:
    - `model.request` denied: no `model_call` is written; `hook_denied` is written; the run fails with `run.hook_denied` (not retryable; the model sees nothing);
    - `tool.preExecute` denied: `hook_denied` is written; the tool result is the English error `Tool call blocked by the "<plugin>" policy hook: <reason>` (reason truncated to 500 characters). This result goes into `tool_result` as usual and replay reads it from the log, so no new `DriftReason` is needed.
  - **Payloads exclude** credentials, media bytes and redacted secrets.
- **F11 Reliable delivery of `usage.report`.**
  - For every `usage` event written, a job is added to queue `cap-kernel-usage-report` in the same follow-up step. The job id is `usage-<conversationId>-<seq>`, with no `:`.
  - Any worker replica executes it: calls the handlers one plugin at a time by plugin name; when a plugin fails, only that plugin is retried, up to 5 times with exponential backoff, each attempt recorded in the job data.
  - A handler receives `{ eventId: "<conversationId>/<seq>", orgId, accountId, agentId, conversationId, conversationKind, runId, provider, model, usage, occurredAt }` and must be idempotent by `eventId`.
  - Usage from single-step evals and judges doesn't go into the event log and is not reported in M7 (listed as deferred).
- **F12 Permission check.** `check:plugin-permissions` gains rule `perm-hooks`: the mount in `ctx.hooks.on(mount, …)` must be a literal and declared in `permissions.hooks`. Hooks are still shown as sensitive; the existing display is unchanged.
- **F13 SDK snapshot.**
  - Report file: `packages/plugin-sdk/api/plugin-sdk.api.md`; api-extractor reads `packages/plugin-sdk/dist/index.d.ts`.
  - `pnpm check:sdk-api` first runs `tsc -b packages/plugin-sdk`, then runs in non-local mode; a mismatched report fails, with a hint to run `pnpm gen:sdk-api`.
  - A separate check `check:sdk-api-changeset` (PRs only): relative to base, if `.api.md` changed and no changeset in the diff mentions `"@capybara-hq/plugin-sdk"`, fail.
- **F14 Test container reuse.**
  - Vitest `globalSetup` starts only one PG 17 and one Valkey per run, passing their addresses to workers through the env vars `CAPYBARA_TEST_PG_ADMIN_URL` / `CAPYBARA_TEST_REDIS_URL`.
  - In shared mode, `startTestPostgres()` returns a freshly created random database (`stop()` drops it with `DROP DATABASE … WITH (FORCE)`), transparent to existing callers.
  - Redis is **not** shared by default: bus channels `cap:<namespace>:<topic>` ignore the DB, so multiple test files sharing one instance would cross messages. So in shared mode `startTestRedis()` assigns a DB number per file (the container starts with `--databases 1024`, numbers allocated by `INCR capybara-test:db`), **only** for callers that explicitly pass `{ shared: true }`. T1 first investigates which test files don't use the bus or BullMQ events, then switches those to shared.
  - The dual-replica harness also uses the shared PG when no `pgUrl` is passed.

## Review Focus

1. **The number of gateway replicas changes during rolling upgrades or scaling.** After a new replica joins, old replicas release at most one connection per round, never dropping all at once; each connection has at most one holder at any moment; when a replica is killed, its connections are taken over within one `leaseTtlMs`. Covered by T3's dual-replica test (a third replica joins midway, then is SIGKILLed).
2. **Forged or replayed webhook requests.** A bad signature, a timestamp more than 5 minutes off, or a connection not in webhook mode are never enqueued, replying 401 / 401 / 404 respectively; a redelivered event is processed only once. Covered by the tests in T4 (kernel) and T5 (Slack / Lark signature verification).
3. **A policy hook itself fails.** If the handler throws or times out, `tool.preExecute` counts as denied, the run continues and the model gets an English error; an observe hook failure doesn't affect the run, and its warnings are rate-limited. Hooks stop firing immediately after the plugin is disabled. Covered by the tests in T14 and T15.
4. **`docker compose up` on old data volumes (upgrade).** Running migrate again in init is idempotent and `--if-none` won't create a duplicate admin; when init fails (e.g. PG version < 15), kernel services don't start because they have `depends_on: init: service_completed_successfully`. Covered by T8's smoke script (two consecutive ups, a PG 14 failure case).
5. **Rerunning the release pipeline.** A package whose version is already on npm is skipped without error; rerunning after a partial failure fills in the rest. Plugin tgz sha512s match the CI artifacts. Covered by T9's `publish-plan` unit tests.
