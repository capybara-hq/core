# Permission Policy and Approval Continuation Implementation Plan

## Task 7: Profile-aware policy and pending approval races

**Goal:** Profile-aware discretionary review, exact per-call expansion and stale-card continuation without bypassing fixed policy or duplicating effects.

**Architecture:** Read permission facts before tool start; record exact approved directory/host expansion in a private immutable PG row; bind it to the actual started call and each method's accepted ledger identity. Canonical profile transitions supersede pending cards and owe continuation through existing outbox/run machinery.

**Base:** accepted Task 6b `429e837f8`. Read the accepted [call-grant design](../specs/2026-11-16-permission-call-grants-and-approvals-design.md) for formal types/methods, directory evidence, concrete root/host bounds, existing signatures and controller rulings. Specs: accepted conversation-profile design, permission-operation contract and delivery plan Task 7. Stack: TypeScript/Nest, PG, existing BullMQ maintenance worker, Vitest two-kernel fixtures. Paths beginning `src/` or `test/` below are relative to `packages/kernel/`; all other paths are repository-relative.

## Global constraints and ownership

- No public SDK change, file-only root claim, implicit dirname grant, standing permission product, arbitrary inline-code regex whitelist, profile activation or Linux task. Actual scoped operation enforcement permits ordinary Python/generated scripts; classifiers do not create confinement.
- Fixed denies/asks, current role/owner/connector/git/hook ceilings, scheduled explicit grants and live root inheritance survive. Full skips discretionary sensitive-command review only. Failed/uncertain independent review asks; deny is never allow.
- Final filesystem root union ≤64, final hosts ≤100; paths ≤4096 characters; reject overflow, never truncate. Both human and model reviewer see the exact directory/host object persisted and later emitted for UI.
- New call grants are attended per-call only. Existing `NetworkGrants` and explicit scheduled task grants stay independent. No child/run-tree inheritance of a new call grant. Every method rechecks current scope; admitted work retains starting scope.
- No new-ID effect retry. Existing `pending()` refresh is same-ID only. No tool callback replay after start; typed pre-admission retry is bounded to the same individual method.
- Task 6c alone owns publisher/startup/lifecycle/CLI tests and TransactionHost extensions. Consume `withTransactionFencePrelude`/`runOutsideTransaction` unchanged; ask controller for serialized integration if an extension is needed. Do not edit those files in Task 7.
- One controller integrator owns DB/event schema, migration allocation, module registrations, maintenance/outbox registry, status-reader adjustments and test lists. Task 8a output files, Task 8 background/cutover files and Task 9 replay/context files are not parallel Task 7 ownership.

## Review focus

1. Canonical pipeline event versus fixture-only fake `tool_started`: true pipeline → staged ledger acceptance must pass (7A).
2. Exact directory displayed versus implicit parent or regular-file root: no silent widening (7B).
3. Call-bound hosts versus accidentally run-wide transport grants; native methods cannot inherit another call's grant (7B–C).
4. Approved-click/profile change and creation/supersession races; real inherited execution fence stays live (7D–E).
5. Forced Full reset under ancestor authority obtains rows/events without descendant lock acquisition or cycle (7D–E).
