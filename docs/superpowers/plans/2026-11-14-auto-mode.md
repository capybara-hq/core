# Auto mode: implementation plan

- Spec: `docs/superpowers/specs/2026-11-13-auto-mode-design.md` (reviewed 2026-11-13; §11 holds the
  maintainer's four decisions, all covered below). It amends the sandbox dev tiers spec
  `2026-11-12-sandbox-dev-tiers-design.md` (tiers, unsandboxed mode, §4.1 settings), the network
  ask-to-allow spec `2026-11-12-network-ask-to-allow-design.md`, the environments spec
  `2026-11-07-environments-design.md` (§8.4), and in `capybara-hq/plugins` `sandbox-docker` (egress)
  and `sandbox-e2b` (network policy).
- Issue: open one ("auto mode: capable devices guarded by command review") and put `Refs #<issue>`
  in every PR. The plan is the reviewable artifact; nothing here is implemented yet.
- Phases: **1** core (plugin-sdk, kernel, `@capybara-hq/device`, web) in this repository; **2**
  `capybara-hq/plugins` (sandbox-docker egress, sandbox-e2b network); **3** nothing else. The git
  gateway (core#198) is **not** on the default path (§6 of the spec): local auto mode uses the
  owner's credentials, cloud devices use `gh`'s own login through the device-code card. The gateway
  line is unchanged and remains an option for orgs that manage credentials centrally.
- Execution: one core branch `feat/auto-mode` from `origin/main` (one commit per task, waves
  reviewed together), then two plugin PRs (below). `wave-planned-subagent-development` on top of
  `subagent-driven-development`. Nothing is merged by the implementer.

## Conventions every task follows

- AGENTS.md: English comments and model-facing text; explicit `@Inject` on every constructor
  parameter; `@Transactional()` for writes with `afterCommit` for bus / resume; every Redis key with
  a TTL; no in-process state that another request or replica must read; UI text through i18n (zh:
  平台 / 超级管理员 / 智能体); UI pages from `@capybara-hq/design`, apps/web writes no styles.
- **No compatibility layers** (pre-0.1.0): old settings, keys and commands are removed, not kept
  beside the new ones. Applied migrations stay immutable; the settings migration below is new.
- SDK public API changes: `pnpm gen:sdk-api` + a changeset bumping `@capybara-hq/plugin-sdk`.
  Device changes: a changeset bumping `@capybara-hq/device`. Kernel / web: a changeset on
  `@capybara-hq/capybara`.
- Migration number: **0130** (`origin/main` has 0128). File
  `packages/kernel/src/migrations/0130_auto_mode.sql`; renumber above the base if the number is
  taken by merge time (`check:applied-migrations`).
- Tests run from the repo root: `pnpm exec vitest run <path>`. Before each commit: `pnpm lint`,
  `pnpm typecheck` for the touched packages, the touched tests; `pnpm check` before the PR.
  Implementers stage only their own paths, never `git add -A`.
- Run the zero-drift fixtures before and after every task that touches request building, tool
  results or the log: `pnpm exec vitest run packages/kernel/test/evals/reconstruct.test.ts
  packages/kernel/test/tools/rename-compat.test.ts`.
- The review (§5 of the spec) is a **kernel step, not an extension hook**, and fails closed. It runs
  for `Bash` (foreground and background launches) and for file-tool writes outside the workspace,
  after argument validation and before the device exec. Existing `tool.preExecute` policy hooks run
  **after** it.
- Kernel tests load no official plugin except `model-fake` (`pnpm check:test-plugins`).

## Decisions taken while planning

The spec leaves these to the plan; each is marked so review can overturn it.

- **P-D1 Review position in the pipeline.** Review is a stage of `runCall` (`tools/pipeline.ts`),
  after the tool policy decision and approval and before `tool.preExecute` / `tool_call_started`,
  with an optional `review` dependency. It is not inside each builtin handler because an ask must
  park the run, and the pipeline is the only place that does that. The facts come from the
  conversation's device (bound by the same `ConversationDevices.forTool` call the tool would make).
  Position satisfies §5.1 ("after argument validation and before the device exec").
- **P-D2 "本会话允许同类" is a rule-class grant.** A `session` decision writes
  `conversation_tool_grants` with `tool_key = "command:<ruleId>"`, `connector_id NULL`,
  `spec_hash = "command"`, on the root conversation of the tree. No new table. A **classifier-decided
  ask has no rule hit**, so its card offers `once` only (the spec says the session grant remembers
  the rule hit; there is none to remember). Deny rules are never grantable.
- **P-D3 Unattended asks are a hard deny.** No approval row, no task grant, no `missing_grants`
  entry (there is no `command:` grant class in this design). The model gets the reason and "No one
  can approve this now; do the work another way or leave it for the person." `unattendedAsk: "wait"`
  does **not** apply to command review.
- **P-D4 `remoteGrants` is removed entirely.** The old opt-out ("the cloud may not widen my
  machine") is replaced by the device's mode: auto mode has no local policy to widen, and in
  sandbox mode a host added from the owner's page stays inside the org's allowlist and never gives a
  command the owner's credentials. The device still refuses `mode: "auto"` from the kernel; only
  `capybara-device mode auto` on the machine turns auto on (§4.1). This is a deliberate trust-model
  change against network spec §10.1 and is called out in the release notes.
- **P-D5 The platform keeps a network kill switch.** `sandbox.limits.egress: "none"` survives
  (the spec does not list it as removed): it forces every device's `network` to
  `{ kind: "allowlist", hosts: [] }`, so auto mode's local network (the machine's own) is the only
  thing it cannot cut. `sandbox.limits.allowHosts` becomes the default host list of 白名单 and of
  sandbox mode (§4.4).
- **P-D6 Cloud "sandbox" mode is the allowlist, not an inner sandbox.** §4.2 says there is no
  sandbox inside the container in either mode; §4.3 still labels a cloud device "auto when allowed,
  else sandbox". The plan therefore treats cloud `mode` as a derived label and enforces through
  `network`: `auto` → the org's `cloudNetwork` default `open-public` (or `allowlist`); auto mode off
  → `allowlist` regardless of `cloudNetwork`. Providers never implement an inner sandbox.
- **P-D7 Local Docker-mode machines.** Auto = the container on its default bridge (today's
  behaviour); sandbox = `--network none` (Docker mode has no per-domain filter, as today's
  `dockerNote` says). The device page says so.
- **P-D8 Org `cloudNetwork` replaces `sandboxEgress`.** Old `sandboxEgress: allowlist` →
  `cloudNetwork: { mode: "allowlist", allowHosts }`; `none` → `{ mode: "allowlist", allowHosts: [] }`
  (the org's intent "no network" survives); absent → open (the new default).
- **P-D9 `devices.autoMode` is both a config field and a deployment setting.** The spec calls it a
  deployment config; the super admin also needs to change it in the console like `sandboxTiers`.
  Precedence env > config file / Nacos > `deployment_settings` key `devicesAutoMode` > default
  `allowed`, read live per use. An invalid stored value reads as `off` (fail closed).
- **P-D10 Rules are pure and depend on no new package.** A small quote-aware tokenizer in the rules
  module (`|`, `&&`, `;`, `>`, `bash -c` / `sh -c` / `eval` unwrapped one level); anything it
  cannot read with confidence is `unsure`. No shell parser dependency.
- **P-D11 Network use is not what review restricts.** Auto mode's point is the machine's network, so
  `curl` / `wget` (any method) and `gh api` are **allow** unless they read a secret path (deny) or
  write outside the workspace (ask). The spec's allow list only names GETs; this keeps API work from
  reaching the classifier. Secret-path handling (§5.2) is the restriction that matters.
- **P-D12 Ask texts are fixed English.** Deny: `Command blocked by review: <reason>. Do the work
  another way or ask the user to run it.` Ask text in the card; unattended: `This command needs
  approval (<reason>), and no one can approve it now; do the work another way or leave it for the
  person.` Person-denied: `The user declined to run this command: <reason>. Continue without it or
  ask the user.` File writes speak of "this write".
- **P-D13 Device-code recognition is `gh`-only for v1.** The kernel parses `gh auth login --web`'s
  fixed output (`one-time code: XXXX-XXXX`, `https://github.com/login/device`) from the exec result,
  appends a display-only `device_code` event, and the web draws a card with the URL and a copy
  button. No token ever leaves the container; nothing model-driven is involved. Other CLIs later.
- **P-D14 The device page gets the approved unslop redesign in this work**, not a second polish
  pass: a nameplate head and a two-state 自动 / 沙箱 scale (design package components), one bright
  element and quiet chrome (task T10).

## Review focus

1. Every command and every write outside the workspace passes review before it runs; review errors,
   timeouts and unparseable answers are `ask`, never `allow` (T5–T7).
2. No model path can enable auto mode: only `capybara-device mode auto` on the machine; the policy
   op accepts `sandbox` only; the web never sends it; Platform/PAT operations only narrow (T3, T4,
   T13).
3. The session grant remembers the rule hit, lives on the root conversation, and never covers a
   deny rule or a classifier ask (T7).
4. An unattended run never waits and never gets an `ask`-level command executed; scheduled runs get
   the deny note (T7, T15).
5. Replay is unaffected: the review record is display-only, deny notes are new content in new
   results, and both zero-drift fixtures pass before and after (T7).
6. Multi-replica: grants, approvals, settings and the device summary are in PG / Redis; the
   classifier call runs outside transactions; the approval decision and resume follow
   `@Transactional()` + `afterCommit` (T2, T3, T7).

**`modes.ts`** — one pure function:
```ts
type SandboxMode = "auto" | "sandbox";   // not `DeviceMode`, which is the os|docker run mode
function effectiveDevicePolicy(deployment, org, deviceMode: SandboxMode | null): {
  mode: SandboxMode;           // min(device's choice, the allowed mode)
  allowedMode: SandboxMode;    // auto only when the platform and the org allow it
  modeSource: "device" | "org" | "platform";
  network: { kind: "open-public" | "allowlist"; hosts: string[] };
  localAllowedDomains: string[]; // the org allowlist local sandbox mode intersects with
}
```
- `allowedMode` = `auto` when `devices.autoMode` and the org's `autoMode` are both `allowed`, else
  `sandbox`.
- Cloud network: `open-public` when `mode === "auto"` and the org's `cloudNetwork` is `open` (the
  default), else `allowlist` with the org hosts (default `sandbox.limits.allowHosts`);
  `sandbox.limits.egress: "none"` forces `{ kind: "allowlist", hosts: [] }`.
- Local network: the exec args always carry the sandbox-mode **allowlist** (the org hosts) in
  `network`, even when the ceiling is auto — the device may run stricter than the ceiling, and in
  sandbox mode it intersects that list with its own `allowedDomains`. In auto mode the device ignores
  the list (the machine's own network); `open-public` is a cloud-only kind.

**`SandboxService`** — `deviceLimits` builds `{ cpu, memoryMb, diskMb, mode, network }`;
`instance_limits` records `{ mode, network: { kind, hosts? } }`; the use path compares `mode` and

`limitsApplyAt` semantics unchanged. `sandboxTierRefused` becomes
`sandbox.open_network_refused` (the provider's `openEgress: "off"`), with an actionable text; the

**`@local` provider** — exec args carry `mode: allowedMode` (the device cuts its own choice to it),

unattended `dev` cap, `UNATTENDED_OPEN_TIER_ERROR`, `UNATTENDED_UNSANDBOXED_ERROR` and the
`tier:open` grant. Add the gate: a machine whose summary reports `mode: "auto"` while `allowedMode`

**API**
```ts
type RuleOutcome = "allow" | "ask" | "deny" | "unsure";
interface RuleHit { id: string; outcome: RuleOutcome; reason: string }
interface ReviewFacts { workspace: string; mode: "auto" | "sandbox"; attended: boolean }
/** The parsed command, or null when the tokenizer is not confident. */
function parseCommand(command: string): ParsedCommand | null;
/** The strictest outcome and every hit, in rule order. */
function reviewRules(command: string, facts: ReviewFacts): { outcome: RuleOutcome; hits: RuleHit[] };
/** The same table for a file write outside the workspace (paths, not commands). */
function reviewWrite(path: string, facts: ReviewFacts): { outcome: RuleOutcome; hits: RuleHit[] };
```
Tokenizer: quote-aware split into simple commands over `|`, `&&`, `||`, `;`, newlines, `>`, `>>`,
`<`; `bash -c` / `sh -c` / `eval` unwrapped one level; heredocs, `$( )` that build a script,
`base64`-into-interpreter and `\`-obfuscated text are `unsure`. No new dependency (P-D10).

| Id | Outcome | Covers |
|---|---|---|
| `allow.read` | allow | reading anything except the secret paths below (incl. `Read` / `Glob` / `Grep`) |
| `allow.dev` | allow | builds, tests, linters, formatters, package managers (`npm`, `pnpm`, `pip`, `uv`, `cargo`, `go`, …) |
| `allow.git` | allow | `git` except the ask / deny cases below |
| `allow.gh` | allow | `gh` reads, `gh pr create\|edit\|comment`, `gh api` (P-D11) |
| `allow.network` | allow | `curl` / `wget` / `nc` / `ssh` / `scp` / `rsync` that do not read a secret path or write outside the workspace (P-D11) |
| `allow.serve` | allow | starting servers, browsers |
| `allow.docker` | allow | `docker` / `docker compose` without `--privileged` or a host mount outside the workspace |
| `allow.workspace-write` / `allow.tmp-write` | allow | writes and deletes under the workspace / the device's tmp |
| `allow.own-kill` | allow | `kill $$`, `kill %1`, `kill` of a job |
| `ask.outside-write` | ask | deleting / overwriting outside the workspace and tmp; a file-tool write outside them |
| `ask.force-push` | ask | `git push --force` / `--force-with-lease` (always), a plain push to `main` / `master` / `release/*`, `gh pr merge` |
| `ask.remote-destroy` | ask | `git push --delete`, `git push origin :ref`, `gh repo delete`, `gh release delete` |

## Rollout

- **One switch-over**, no compatibility layer: the device program and the kernel change together;
  the deployed migration 0130 rewrites the stored settings; every config key of the old model is
  removed from the schema (a deployment that still sets it starts, and the release notes say the
  key does nothing).
- **Release notes** (docs/deploy/release.md flow, changeset texts):
  - New local devices start in **auto mode**: commands run as the owner, every command is reviewed
    in the kernel, dangerous ones are blocked or ask a person.
  - `capybara-device mode auto|sandbox`; the web device page can switch to sandbox only.
  - Cloud devices: network **开放（挡内网）** by default; orgs choose 白名单; loopback, private,
    link-local and metadata addresses are always blocked outside the container.
  - Removed: tiers (`strict` / `dev` / `open`), isolation, `localhost`, `remoteGrants`, the device
    domain list in auto mode, `sandboxTier`, `sandboxEgress`, `sandbox.tiers.*`,
    `sandbox.limits.devHosts`; stored settings are migrated (a device whose local policy was
    unsandboxed / open becomes auto; an org or platform at `open` becomes `autoMode: allowed`, lower
    becomes `off`; `sandboxEgress: allowlist` becomes `cloudNetwork: allowlist` with its hosts).
  - The 本会话允许同类 approval and the `gh auth login` device-code card.
  - The git gateway is not on the default path (local credentials; cloud `gh` login).
- **Upgrade steps**: `capybara migrate` (0130) runs with the kernel; device owners upgrade
  `capybara-device` (the page says 设备程序需要升级 for a program without the `mode` feature; it runs
  as sandbox until then); the app review of the first session per device shows the auto risk text
  once.

## Left open by the design (calls this plan takes, flagged for review)

1. **Cloud "sandbox" has no enforcement of its own** (§4.2 vs §4.3): the plan treats the cloud mode
   as a label and enforces the network only (P-D6). If review wants a real cloud sandbox, it is a
   new design.
2. **`sandboxEgress` is not in §4.4's removal list** but `cloudNetwork` replaces it; the plan
   migrates and removes it (P-D8).
3. **A classifier ask has no rule hit**, so 本会话允许同类 is offered only for rule asks (P-D2).
4. **`unattendedAsk: "wait"`** does not apply to command review (P-D3), a deliberate difference
   from tool approvals.
5. **`sandbox.limits.egress: none`** in the new model — kept as the platform kill switch (P-D5);
   the spec does not say what it means once tiers are gone.
6. **`gh api` / `curl -X POST`** are not named by §5.2; the plan allows them unless a secret path is
   involved (P-D11).
7. **The device page redesign** is not in the spec; it comes from the maintainer's unslop direction
   (P-D14, T10).
