# M4 渠道与生态插件 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 先落地扩展模型第一组（插件权限清单、按清单构造 `ctx`、能力取用、权限批准），再让 agent 进入 IM：Slack 与 Lark 插件各自提供登录、通讯录、bot 三种能力；IM 里对话、点卡片审批与回答、流式回复；外部身份登录与绑定；通讯录同步与离职处理。另含 `openai-compatible` 的方舟（Ark）方言。验收：在 Slack / Lark 里与 agent 对话，写操作在 IM 里点卡片审批后继续。

**Architecture:**
- **插件只管 IM 协议，内核管会话**：插件实现 `channel@1`（连上 IM、收事件、发 / 改消息、按内核卡片规范渲染卡片）、`identity-source@1`（外部登录）、`directory@1`（列成员）。内核负责渠道连接（插件 + bot 凭据 + 绑定的 agent）、长连接选主、IM 会话 ↔ 对话的对应、身份映射与绑定、把运行输出与卡片投递回 IM、卡片操作的授权。
- **投递可靠**：入站消息按 IM 消息 id 去重后写入对话；出站由持久化的投递任务完成（BullMQ，按会话与事件序号做幂等 job），worker 中途崩溃时由其他副本接着投递，最终回复与卡片不丢；流式草稿是尽力而为。
- **权限清单先行**：内核按清单为每个插件构造 `ctx`，未声明即不存在；清单（含由配置与迁移推导的部分）形成权限集合，与 PG 中已批准的快照比对，新增权限须企业管理员用 CLI 批准后插件才加载。
- **三段执行**（第三段为 D13，先设计后实现）：第一段（Task 1–14）扩展模型第一组 + 三个契约 + 内核渠道运行时 + 登录 / 绑定 / 通讯录 + 网页，用仓库内的假渠道插件跑通；第二段（Task 15–20）Slack、Lark 插件与真实验收。一个分支，最后一起合并。

**Tech Stack:** 同 M3；新增 `@slack/socket-mode`、`@slack/web-api`（Slack 插件，不用 Bolt）、`@larksuiteoapi/node-sdk`（Lark 插件，长连接 `WSClient`）；zod 4 的 `z.toJSONSchema` 把插件配置 schema 交给网页。

**Spec:** `docs/superpowers/specs/2026-10-17-capybara-architecture-design.md` §2.1–§2.5、§3.1–§3.5、§9；扩展模型设计 `docs/superpowers/specs/2026-10-18-extension-model-design.md`（第 2、3、7 节与第 9 节分期）。设计系统 `docs/design/spec.md`、`skills/writing-web-ui`。

## Global Constraints

- 沿用 M2 / M3 计划的 Global Constraints 全文；重点：插件只 import `@capybara-hq/plugin-sdk` 与第三方包（`pnpm check:deps`）；多副本纪律（状态只在 PG / Redis，Redis 写入带 TTL，内核键前缀 `capk:`，队列名与 job id 不含 `:`，进程内定时器只用于本进程持有的资源——**长连接与其租约续期属于「本进程持有的资源」**）；内核 HTTP 默认拒绝、新公开路由加入 `public-routes.test.ts`、组织写操作 `lockOrgAndAuthorize`、错误码登记在 `errors.ts`；事件日志只追加；模型可见文案英文；界面文案 i18n（zh / en 同步）、页面只用 design 模板与组件；每道新增自动检查先证明会红。
- **身份源键**：`identities.source` = `"<插件名>:<租户 id>"`（Slack 为 team id，Lark 为 tenant key），`external_id` = 平台用户 id（Slack user id、Lark `open_id`）。登录、渠道入站、通讯录三处用同一个键，同一个人只对应一行身份。
- **硬规则**：识别不出发言人身份时绝不借用渠道开通人或连接创建者的身份；匿名访客只在连接显式开启时出现，且只能用可见范围为「全组织」的 agent、不得取用个人凭据。
- **IM 文本与卡片**：机器人在 IM 中说的固定话术（绑定提示、错误提示）走 i18n，语言取组织默认语言（`zh` / `en`，缺省 `en`）；模型回复原样转换为该 IM 的富文本格式，不翻译。
- **密钥**：bot token、app secret、登录 client secret 全部走密钥存储并登记日志打码；渠道连接的 GET 只返回非密钥字段与「已设置」标记。
- **权限清单是治理，不是沙箱**：未声明的平台能力访问抛 `PluginPermissionError`（英文消息写明要在清单哪一项声明）并写审计；`permissions.network` 只展示不拦截。

## Review Focus

1. **两个副本都想接管同一个渠道连接**：任一时刻只有一个副本持有长连接；持有者被杀后另一副本在租约过期后接管；同一条 IM 消息即使被平台重投也只写入一次。→ Task 10 测试（双副本 + 杀副本）。
2. **IM 用户点了不属于他的审批卡片**：卡片操作按点击者映射到的账号走 `ApprovalsService.decide` 的授权，非审批人无效并在 IM 中回一句说明；未绑定的人点卡片得到绑定提示。→ Task 11 测试。
3. **投递中途 worker 崩溃**：最终回复与卡片在其他副本上补发且不重复（按已投递的事件序号续）。→ Task 11 测试。
4. **通讯录同步时有人离职**：只撤销由该通讯录同步加入的成员关系；同一事务内吊销会话与令牌、删除其在该组织的个人连接器凭据、其负责的 agent 转给所有者并标记待重新指派；手动加入的成员不被同步删除。→ Task 12 测试。
5. **插件升级后多要了权限**：未批准前不加载，依赖它的插件同样不加载并给出原因；权限变少或不变直接加载。→ Task 4 测试。

**Interfaces（Produces）:**
```ts
// capability.ts
export interface CapabilityInfo { cardinality: "single" | "multi"; brokered: boolean; orgScoped: boolean }
export const CAPABILITIES: Record<string, CapabilityInfo>;
//  model-provider / connector / sandbox / secret-store / object-store(预留) = brokered；
//  channel / identity-source / directory = 直通且 orgScoped（按组织启用）；config-source 单选；counter（示例）直通。
//  CAPABILITY_CARDINALITY 保留为由 CAPABILITIES 派生的兼容导出。

// permissions.ts
export interface PluginPermissions {
  secrets?: boolean;                                   // ctx.secrets
  http?: { method: "GET" | "POST" | "PUT" | "DELETE"; path: string; public?: boolean }[];
  tools?: string[];                                    // ctx.tools.register 的工具名
  hooks?: string[];                                    // 预留（M6），只校验名字
  models?: { purpose: string; kind: "chat" | "embedding"; label: { zh: string; en: string } }[]; // 预留
  storage?: boolean;                                   // 预留（M5）
  network?: string[];                                  // 域名，只展示
}
export class PluginPermissionError extends Error { constructor(plugin: string, what: string /* e.g. 'permissions.secrets' */) }
export class CapabilityUnavailableError extends Error {}
export function validatePermissions(plugin: string, p: unknown): string[];   // 用途键须 "<插件名>.<名称>"，路由须以 / 开头且不重复，域名格式

// define-plugin.ts：PluginManifest 增加 optional?: CapabilityRef[]; permissions?: PluginPermissions
// 校验：optional 与 requires / provides 不重叠；brokered 能力不得出现在 requires / optional（只能经平台能力使用）——例外：无
// ctx.ts：增加
capabilities: {
  get<T>(ref: CapabilityRef, provider?: string, opts?: { orgId?: string }): T;   // orgScoped 能力传 orgId 时校验该组织已启用，否则抛 CapabilityUnavailableError
  list<T>(ref: CapabilityRef, opts?: { orgId?: string }): { plugin: string; impl: T }[];
};
// secrets / http / tools 的类型不变，但运行时可能是「未声明」的占位（访问即抛 PluginPermissionError）
```

### Task 3: 内核按清单构造 `ctx` 与能力取用

**Files:** `packages/kernel/src/plugins/{resolve,host}.ts`、`packages/kernel/src/ctx/create-ctx.ts`、现有全部插件的清单（`plugins/*/src/index.ts`：按实际使用补 `permissions`，如 `todo` 的 `tools: ["write"]`、`example-counter` 的 `http`）；测试 `packages/kernel/test/plugins/{ctx-permissions,capabilities,resolve}.test.ts`

- `createPluginContext(deps, manifest, config, capabilityAccess)`：

### Task 4: 权限快照、待批准与 CLI

**Files:** `packages/kernel/src/migrations/0016_plugin_permissions.sql`、`packages/kernel/src/plugins/{permission-set,approvals}.ts`、`host.ts`、`config/schema.ts`、`apps/capybara/src/{args,cli}.ts`、`apps/capybara/src/commands/plugins.ts`；测试 kernel + CLI

- 表 `capybara.plugin_permission_snapshots(plugin text pk, version text, permissions jsonb, approved_by text null, approved_at, source text check (cli|auto))`。
- `computePermissionSet(manifest, migrationsDir): PermissionSet`：provides、requires、optional、配置字段（部署级 / 组织级的路径与是否密钥，来自 zod schema 遍历——复用 `config/fields.ts`）、数据表（解析插件迁移 SQL 中的 `CREATE TABLE [IF NOT EXISTS] <name>`）、`permissions` 各项；规范化排序。`diff(prev, next): { added: string[]; removed: string[] }`（每项一个稳定的字符串键，如 `permissions.tools:write`、`table:todos`、`config.org.secret:apiKey`）。
- `PluginHost.load`：每个插件在 `setup` 之前比对快照：无快照或有新增 → 不加载，记入 `host.pending()`（含 diff）并打 warn 日志；依赖它（`requires`）的插件同样不加载（原因写明）；`optional` 依赖它的插件照常加载。配置 `pluginPermissions.autoApprove`（默认 false，非 hot）为 true 时自动写快照（`source: "auto"`，启动日志醒目提示）。
- CLI（直连 PG，同 `admin create` 的方式）：`capybara plugins review` 列出待批准插件与新增项；`capybara plugins approve <name> [--yes]` 写快照并审计（终端交互确认，`--yes` 跳过）；批准后需重启内核生效（命令输出提示）。
- `dual-replica` 测试工具与 e2e、内核测试辅助默认开启 `autoApprove`。

- [ ] **Step 1: 失败测试**：无快照 → 待批准不加载；批准后加载；升级多一项权限 → 待批准且依赖它的插件不加载；权限变少 → 直接加载并更新快照；`autoApprove` 自动写快照；`computePermissionSet` 对迁移解析与配置字段的输出；CLI review / approve。
- [ ] **Step 2–4**；**Step 5: 提交** `feat: 插件权限快照、待批准与 CLI 批准`。

### Task 21: 设计（brainstorming，产出设计文档，用户审）
