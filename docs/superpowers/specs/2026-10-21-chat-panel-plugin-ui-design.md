# 对话页改版与插件扩展界面 设计

日期：2026-10-21。来源：M4 第三段 Task 21，需求见 M4 计划决策 D13。草图在 https://claude.ai/artifact/9RdWjVSiWBkDtL8uoVH2qN，用户选了方案 A（标签页）。

本文里标「（设计者的决定）」的条目是写这份设计的人替用户拿的主意，用户还没有逐条确认。其余条目都是用户在讨论中明确表达过的意见。

## 1. 为什么做

- 现在的对话页把工具调用画成一张张卡片，输入和输出都是原样 JSON，长对话读不下去。用户希望工具调用的显示方式参照 Claude Code 的 VS Code 插件，整体布局参照 Claude Code 网页版：中间是对话，右侧是可以收起的面板。
- 用户最想在右侧看到的是产物、工具的输入输出，以及**实时更新的任务清单**（todo 插件）。
- todo 这类插件需要界面配合才有价值，所以要建立一套机制，让插件可以往界面上加内容。这套机制分两档：
  - **渲染 schema**：插件只返回结构化描述，网页用设计系统的组件把它画出来。
  - **嵌入应用**：用来承载 schema 画不了的复杂应用，例如工作流进度刷新、类似 Jira 的多人协作看板，这类应用本身就有交互。
- 用户决定这次**两档都做**。

## 2. 目标、非目标、反目标

**目标**
1. 对话页改成「中间对话 + 右侧标签面板」，右侧面板可以收起。
2. 对话中的工具调用改成时间线式显示，长输出默认折叠。
3. 插件可以通过渲染 schema 往右侧面板加标签（作用于对话），也可以往主导航加页面（作用于组织）。
4. 插件可以通过嵌入应用往同样两个位置加内容，嵌入应用运行在沙箱 iframe 里。
5. todo 插件作为第一档的参考实现：任务清单在右侧实时刷新。
6. 用一个示例插件演示第二档：一个组织页面加一个对话标签，带实时刷新。

**非目标（这次不做）**
- 产物插件本身。产物插件是独立的插件，以后再做。这次只把「产物」标签和它的接口位置留出来。
- 沙箱里的输出文件（M5）。
- 用渲染 schema 去画 IM 卡片或桌面端界面。schema 设计时要保证以后可以这样复用，但这次不实现。
- `ctx.hooks`（M6）。

**反目标（出现了就算失败，即使功能能用）**
- 插件能在第一档里写样式，或者执行代码。
- 嵌入应用能读到用户的内核会话 Cookie，能调用内核 API 冒充用户，或者能读写外层页面。
- 右侧面板或插件内容拖慢对话流。比如插件接口慢了或挂了，对话照常流式显示，插件那一块单独显示加载失败。
- 改版后的对话页破坏了现有能力：插话、停止、审批 / 提问 / 连接卡片、崩溃续跑、重连。

## 3. 对话页

### 3.1 布局
- 沿用 T7 `PlaygroundPage` 模板，也就是 `Body layout="inspector"`，布局为「内容 + Inspector」。Inspector 宽 400px，按设计规范可以关闭；视口窄于 1280px 时改成右侧的 Sheet。
- Inspector 里放一组 `Tabs`，用作右侧面板的标签栏。标签上带计数，例如「任务 2/4」「产物 1」。
- 记住用户最后选的标签，存在浏览器本地，只是个人便利。（设计者的决定）
- **没有内容的标签不显示**。比如组织没有启用 todo 插件，就没有「任务」标签。（设计者的决定）
- 有待批准的操作时，「运行」标签上显示一个提醒标记。（设计者的决定）

### 3.2 内核自带的标签
- **运行**：本次对话的工具调用列表，内容来自事件日志里的 `tool_call_started` / `tool_result`。
  - 点开一条，在面板里看它的完整输入和输出。如果输出已经存档，就从现有的读取存档接口拿全文。
  - 对话流里对应的那一条保持折叠。
- **上下文**：
  - 已用 token：取最近一次 `usage` 事件。上下文窗口大小取模型声明的值。
  - 当前 agent 和模型。
  - 本对话里接上的应用。
  - 压缩记录：`compaction_summary`。
- **产物**：这次没有产物插件，标签默认隐藏，只定义好它的数据来源，见 §4.6。

### 3.3 对话流里的工具调用显示（D13）
- 用一条时间线串起本轮的各个步骤：
  - 思考显示成「思考了 N 秒」，可以展开。
  - 工具调用显示成一行：圆点 + 工具名 + 一句说明，例如「搜索 #feedback 本周消息 · 42 条」。
- **说明文字的来源（用户已定，方案 b）**：由工具自己给。
  - SDK 的 `ToolResult` 增加一个可选的、只用于显示的摘要，例如 `display: { summary: { zh, en } }`，中英文两份都由插件提供。字段的具体形状由实现者定，但摘要必须是双语。（设计者的决定）
  - 摘要随 `tool_result` 事件写进事件日志，所以刷新页面后照样能还原。
  - 摘要**不进模型的上下文**。不改变模型看到的工具定义和结果，也不影响按日志重建模型请求。
  - 工具没有给摘要时（连接器工具总是这样），网页退回到「工具名 + 输入的前几个字段」。
  - 内核内置工具和 todo 都要补上摘要。`skills/writing-tools` 里写明这个可选字段怎么用。
- 展开后用等宽字体分两块显示 IN 和 OUT，长内容默认折叠，可以「展开全部」。
- 审批 / 提问 / 连接卡片的位置和行为不变。这些卡片要更醒目：用强调色描边。
- 运行中的工具显示「运行中」状态。出错的显示错误摘要，可以展开看详情。

### 3.4 需要新增的设计组件
按 `skills/writing-web-ui` 的流程新增组件：先改规范，再写实现、目录页和截图。组件清单和命名由实现者决定，至少要覆盖这些：
- 时间线容器；
- 工具调用行，带展开 / 折叠和 IN / OUT 块；
- 思考行；
- 渲染 schema 用到的各类积木组件，见 §4.3。

`apps/web` 里只能拼装组件，不写样式。

## 4. 第一档：渲染 schema（插件视图）

### 4.1 插件怎么声明
- 插件清单新增一节 `ui`，列出插件提供的界面贡献。每项包含：
  - `id`；
  - `title {zh, en}`；
  - `place`：`"conversation"` 表示对话页右侧标签，`"page"` 表示主导航里的组织页面；
  - `kind`：`"view"` 表示渲染 schema，`"embed"` 表示嵌入应用，见 §5。
- 同一个插件可以只声明某一个位置，也可以两个都声明。
- 权限清单新增 `permissions.ui`，列出这些贡献的 id。`check:plugin-permissions` 也要检查它。
- **能不能卡住插件加载（用户已定）**：
  - `view`（渲染 schema）记进权限快照，管理员审阅时能看到，但**不卡加载**。升级后多出 `view` 时，插件照常加载，快照自动补上这一项。理由是 `view` 只是把插件已有的数据交给我们的组件来画，没有给插件新的能力。快照比较逻辑要为此新增「不卡加载」这一类。
  - `embed` 和其他新增权限一样**卡加载**，等批准，并且标为**敏感**项，见 §5.4。
- 插件必须在该组织**已启用**，贡献才会出现。

### 4.2 数据怎么流动
- SDK 新增 `ctx.ui`，具体名字由实现者定，形如：
  - `ctx.ui.view(id, render)`：`render({ orgId, accountId, conversationId?, locale, signal }) → Promise<UiView>`。
  - `ctx.ui.action(id, handler)`：插件视图里的按钮和表单提交，回调到这里。返回值可以是一条提示，也可以是一份新的视图。
  - `ctx.ui.invalidate({ orgId, conversationId?, view })`：告诉内核「这个视图变了」。
- 内核新增 HTTP 接口，走正常的会话鉴权：
  - **列出贡献**：列出当前组织已启用插件的界面贡献，供网页决定显示哪些标签、导航里放哪些页面。
  - **取视图**：调用插件的 `render`，带上超时；校验返回的 `UiView`，把结果交给网页。
    - 对话视图要求调用者能访问这个对话，规则和 SSE 流的现有规则一致。
    - 组织视图要求调用者是组织成员。
  - **执行动作**：调用插件的 `action`。内核把身份传给插件；插件拿不到用户的会话凭据。
- **实时刷新**：
  - 插件调用 `invalidate` 后，内核在对话的 bus 主题 `conv.<id>` 上发一条 `ui` 消息。现有 SSE 流把它转发给网页，网页收到后重新取视图。
  - 组织视图在组织级的 bus 主题上发消息，网页通过一个组织级 SSE 流接收。这个流用新接口还是复用现有通道，由实现者定。
  - 消息经 Redis bus 传递，满足多副本纪律。
- 插件的 `render` 慢、出错或者返回非法视图时：只有那个标签显示「加载失败 / 重试」，对话本身不受影响。内核记录告警日志，不写进对话日志，因为这不是模型能看到的内容。

### 4.3 schema 的积木
`UiView` 是一个有上限的块列表，类型和校验函数 `validateUiView` 放在 SDK 里，只含纯函数。至少包括这些块：
- `heading`、`text`。`text` 支持 Markdown：链接只允许 http(s)，不支持原生 HTML。
- `checklist`：每项有 `pending` / `in_progress` / `completed` 三种状态，`in_progress` 那项高亮。
- `keyValue`、`table`（列定义 + 行）、`code`（语言 + 文本）。
- `image`：只允许 http(s) 地址，或者插件自己路由下的资源。
- `chart`：简单的柱状图 / 折线图，复用现有的 `BarChart` / `Sparkline`。
- `actions`：一组按钮，每个按钮对应 `actionId + payload`，可以标成「危险」，危险按钮要二次确认。
- `form`：复用 SDK 现有的 `InputForm`，提交时走 `action`。
- 每个视图可以带一个 `badge`，显示在标签上，例如「2/4」。

上限（块数、表格行数、文本长度等）由实现者定，原则是够用并且能防滥用，校验函数里统一检查。schema 要设计成以后也能拿去渲染 IM 卡片。（设计者的决定）

### 4.4 todo 插件
- 注册一个对话视图 `tasks`：标题「任务」，`badge` 为「已完成 / 总数」，主体是一个 `checklist`。
- `todo__write` 写完之后调用 `invalidate`，右侧面板随之实时刷新。
- 对话流里 `todo__write` 那一行工具调用不再显示原样 JSON，改成一句说明，例如「更新任务清单（4 项）」。

### 4.5 导航里的插件页面
- 现在的主导航在顶栏（`components/shell/nav.tsx` 里的 `NAV`，不在左侧）。用户的要求：顶栏放一个**下拉菜单**，列出所有插件页面；只有当前组织至少有一个已启用插件注册了页面时，这个菜单才出现。
- 下拉菜单不叫「应用」，因为顶栏已有「应用」，指连接器（MCP / OpenAPI）。暂定叫「扩展」。（设计者的决定，待用户确认名字）菜单项按插件分组，显示插件标题和页面标题。
- 插件页面的路由形如 `/p/<plugin>/<id>`，用现有的某个页面模板来承载。用哪个模板、要不要新增一个模板，由实现者定；新增模板要走设计系统的变更流程。

### 4.6 产物（只留接口）
- 「产物」标签显示插件声明为产物的视图或文件。这次只定义数据形状，和插件视图共用 `UiView`；没有来源时标签隐藏。产物插件以后接入。（设计者的决定）

## 5. 第二档：嵌入应用

### 5.1 用在哪里
- 用于渲染 schema 画不了的复杂应用：工作流进度刷新、多人协作看板，以及带复杂交互的界面。
- 能放的位置和第一档一样，可以是对话页右侧标签，也可以是导航里的组织页面。

### 5.2 怎么运行
- 嵌入应用的页面由插件自己的 HTTP 路由提供。今天插件路由 `/plugins/<name>/...` 不经过网页代理，内核也不鉴权（裁定 A2），所以要补两件事：
  1. **入口**：网页新增一条同源代理路径，形如 `/plugin-ui/<plugin>/...`，转发到内核的 `/plugins/<plugin>/ui/...`。只允许插件声明过的 ui 路由，并且剥掉内核会话 Cookie，内核现在已经会剥。
  2. **身份**：内核签发一个**短期嵌入令牌**，有效期几分钟，可以续期。
     - 令牌里的声明有：插件、组织、账号、对话（可选）、贡献 id、过期时间。
     - 令牌只对这个插件有效，不能用来调用内核 API。
     - 插件用 SDK 提供的校验函数验证令牌（如 `ctx.ui.verifyEmbedToken`），拿到可信的调用者身份。
- iframe 加 `sandbox`，不给 `allow-same-origin`，这样它是不透明源，读不到外层页面和 Cookie。只放开运行所需的最小能力：脚本、表单。具体的 CSP 和 `frame-ancestors` 由实现者定，原则是嵌入页面只能被我们自己的网页嵌入。

### 5.3 外层页面与 iframe 怎么通信
外层页面和 iframe 之间用 `postMessage` 通信，协议固定，消息带版本号：
- 外层发给 iframe：
  - 初始化消息：令牌、语言、主题（明 / 暗）、设计 token 的值、对话 / 组织上下文；
  - 令牌续期；
  - 主题切换。
- iframe 发给外层：
  - 请求调整高度，只在页面内嵌时有用；
  - 请求打开某个对话或页面，只能是站内路径；
  - 请求显示一条提示。
- 外层只接受来自这个 iframe 的消息，按 schema 校验；不认识的消息直接忽略。

### 5.4 权限与审批
- 清单里 `kind: "embed"` 的贡献，在权限清单里标为**敏感**项，和密钥、对外路由同一个级别。它在两个地方高亮显示（用户已定）：
  - 部署级审阅：`capybara plugins review`。
  - 组织启用插件时的权限清单页。这个页面已经存在，在网页的组织插件设置里。
- 升级后新增 `embed` 会卡住加载，直到管理员执行 `capybara plugins approve` 批准。
- 实时刷新、多人协作由插件自己实现：插件可以用自己的 `ctx.bus`、`ctx.kv`、`ctx.db`，再通过自己的路由开 SSE 或长轮询。网页代理要支持流式响应。
- iframe 内页面的样式不受我们控制。我们提供设计 token，作为初始化消息的一部分；另外提供一份可选的样式包，建议使用，不强制。（设计者的决定）

### 5.5 示例插件
- 新增 `plugins/example-board`（设计者的决定），一个最小的「工作流进度看板」：
  - 一个组织页面，显示若干任务卡片，可以拖动改状态；
  - 一个对话标签，显示和当前对话关联的卡片；
  - 状态一改，另一个打开的浏览器窗口实时刷新。
- 它是第二档的参考实现，也是双副本测试的对象：令牌签发与校验、代理、刷新消息跨副本到达。

## 6. 约束
- 界面文案走 i18n，提供中文和英文两套。给模型看的文本用英文。
- `apps/web` 只用 `@capybara-hq/design` 的模板和组件，遵守 `check:web-ui`。
- 插件只依赖 SDK。SDK 只放类型和纯函数，不依赖其他包。
- 多副本纪律：刷新消息、令牌状态都放在 Redis 或 PG。BullMQ 的队列名和 job id 不能含 `:`。
- 新增的自动检查都要有用违规样例证明它会报错的测试。
- 设计系统改动要更新规范文档、`/dev/ui` 目录页和截图基线。截图基线只在 CI 的 Linux 环境生成。
