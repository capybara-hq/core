## Controller decisions: directory roots and scope presentation

Accepted native roots are **directories**. SDK `sandbox-native-runtime-source.ts:73–74` requires `S_ISDIR(fstat(fd))`; local `operation-worker.ts:262` opens `O_DIRECTORY|O_NOFOLLOW`; `native-helper-client.ts:101/125` rejects non-directory descriptors. Missing logical directory roots use a pinned ancestor plus trusted components; that ancestor is never a data-access grant. These facts do not establish file-only grants, and passing a regular-file path as a root fails.

Controller ruling: grant only explicitly proposed directory scope. No implicit `dirname(file)` promotion to authority and no fictitious file-only capability; the separately displayed parent-directory proposal below is a request only. An outside file call can be covered only by a separate, explicit directory proposal, showing that entire directory to both reviewer/person before grant; if only file authority is requested, fail with an actionable explanation. Do not stat outside base authority to guess root type. Backend descriptor validation remains the enforcement boundary; a proposed directory that is actually a file fails closed. Symlink aliases cannot silently substitute another directory.

The same immutable object is stored, reviewed and shown in approval events/API: `permissionScope: { readDirectories: string[], writeDirectories: string[], hosts: string[] }`, with `targetPath?` separately for explanatory file context. Task 10 renders those exact fields and labels directory reach, not just the target filename. Approval of a directory authorizes its descendants; sibling directories remain outside. No new public SDK field, standing-grant product or helper/backend source change.

## Trusted candidate construction (I2)

Create pure `sandbox/review/permission-candidate.ts`; the pipeline calls it after validation and mandatory policy, using actual logged raw input, actual resolved validated input, resolved tool key/spec and `previewCall` facts. New private interface:

```ts
type PermissionCandidate = Readonly<{
  binding: PermissionCallBinding;
  permissionScope: PermissionExpansion;
  targetPath?: string; // explanatory file, never the authorized root
  scopeKind: "directories-and-hosts";
  candidateHash: string;
}>;
type PermissionCandidateResult =
  | { kind: "in-scope" }
  | { kind: "proposal"; candidate: PermissionCandidate }
  | { kind: "unsupported"; code: "unbounded-scope";
      message: string };
function buildPermissionCandidate(
  call: {toolKey:string; specHash:string; rawInput:unknown; validatedInput:unknown},
  facts: PermissionReviewSnapshot,
): PermissionCandidateResult;
```

The builder computes the input hashes, binds server identity/revisions from facts, resolves relative operands against the trusted working root, validates/normalizes exact roots and hosts, applies write-implies-read and final 64/100 bounds **before** freezing a candidate/hash. The repository has no structured file-only restriction producer. Do not invent a permission field/event or infer owner authority from prose. Existing human/reviewer refusal of the separately displayed directory proposal is canonical denial/ask evidence and yields no expansion. It performs no provider/stat/realpath I/O outside base scope. Pure extraction proposes access; it never grants it or proves that an arbitrary program is confined.

Controller-selected deterministic extraction policy: bare validated Read/Write/Edit, and GenerateImage with `file_path` (each image path it writes, judged as Write), with an absolute outside `file_path` may produce a **new parent-directory proposal**, never parent authority. Normalize the target lexically, derive its immediate dirname as the explicitly labelled proposed directory, put the original normalized file in separate `targetPath`, and choose read reach for Read or write-implies-read for Write/Edit/GenerateImage. Example Write `/outside/reports/report.txt` proposes **write directory `/outside/reports`**, not file-only access; the entire directory is displayed/reviewed before any grant. An input path is target metadata, not evidence of consent. Reject a catch-all root such as `/`, invalid/unbounded paths; do not stat outside base scope or guess file type. A human/reviewer refusal of directory reach can never become file-only approval or an implicit parent grant. This does not add public arguments or a new intent/standing-grant product. For Bash retain parsed literal explicit `cd <directory>` operands and concrete targets beneath them, and literal HTTP(S) URL operands for exact normalized hosts; opaque strings never invent roots/hosts. Every proposed addition remains subject to live ceilings. Directory requests and unsupported results explain that only directory grants are supported and offer an in-project path; they do not force ordinary outside Write/Edit through a Bash workaround.

Calls needing no known expansion, including ordinary opaque inline Python, return in-scope and run under enforced base scope; this is **not** a claim that parsing predicted every access. Unknown/dynamic targets receive no expansion and any later confinement failure preserves prior effects without auto-replay. Existing fixed-deny/ask checks run before this branch. Never use a regex whitelist to authorize arbitrary inline code.

The pipeline sends the same frozen normalized candidate to `ReviewClassifierInput`/independent review request as delimited untrusted data, retaining server-controlled identity and instructions; the verdict cannot replace it. The human command detail, approval_requested/permission_reviewed evidence and grant row carry exactly its permissionScope, targetPath and candidateHash. Request asks; Approve-for-me reviews then asks on uncertain/error; only a final allow issues the identical expansion. Admission retrieves that stored object and adds it to base scope under current ceilings; no second normalization or inferred parent widening occurs. A current ceiling mismatch invalidates the proposal rather than silently approving a different object. An actual-input staged pipeline test must exercise this entire chain, not hand supply roots to issueLocked.

## Persisted call-grant contract

New private leaf `sandbox/permission-call-grants.ts`, `permission-call-grants.module.ts` and pure `permission-call-types.ts`. One new table **`permission_call_grants`** holds approved grants only; pending proposal lives in the existing command approval `detail`. No second grant state machine.

```ts
type PermissionCallRef = { runId: string; callId: string };
type PermissionExpansion = {
  readDirectories: readonly string[]; writeDirectories: readonly string[];
  hosts: readonly string[];
};
type PermissionCallBinding = {
  orgId: string; rootConversationId: string; conversationId: string;
  deviceId: string; accountId: string; runId: string; callId: string;
  toolKey: string; specHash: string;
  callInputHash: string; resolvedInputHash: string;
  profile: PermissionProfile; profileRevision: number;
  scopeRevision: string; authorityRevision: string;
};
type PermissionGrantDecision =
  | { source: "human"; approvalId: string; decidedBy: string }
  | { source: "review-model"; reviewEventSeq: number; decidedBy: null };
```

`authorityRevision` is the same hash of `{scopeRevision, vector}` used for operation `ceilingRevision`, so restricted-only ceiling changes invalidate new use too; Full consent's `scopeRevision` alone is insufficient. Hashes are `permissionScopeHash` of exact canonical input values: raw logged tool input and resolved validated input separately. Neither is the native method/input digest computed by `describeOperationPayload`.

Table columns: `id` UUID; every binding field in snake_case; `expansion` bounded JSONB; `expansion_hash`; `candidate_hash`; nullable `target_path`; `scope_kind`; `source`; nullable `approval_id`, `review_event_seq`, `decided_by`; `created_at`. FK run/conversation/org/device as existing tables permit. Add `binding_hash = permissionScopeHash(validated full PermissionCallBinding)` with a UNIQUE constraint, plus unique non-null approval ID. The unique identity excludes `expansion_hash`; the latter remains evidence only. Under the existing call/conversation fence, issuance first reads that binding identity and compares every persisted binding field. Exact retry must also match normalized expansion/hash, candidate_hash/target_path/scope_kind, source, evidence locator (`approvalId` or `reviewEventSeq`) and decider; it returns the original row. Any different candidate or incompatible evidence conflicts and leaves the winner unchanged. Never append a competing grant, merge roots, pick newest, or rely on row iteration. Admission looks up binding_hash and verifies all fields; exactly one immutable expansion can match. For automated decisions, append a new display/audit-only `permission_reviewed` event before inserting the grant in the same transaction; `review_event_seq` identifies its real `(conversation_id,seq)`, not an invented event UUID. Record binding, exact permissionScope, outcome/reason and decision source for allow/ask/deny; grant lookup requires an allow event matching all fields. Existing human approval events remain human evidence. Rows are immutable evidence; no consumed bit (a single tool legitimately needs stat/read/write). New revision creates new evidence, never rewrites old approval/grant. Normal run/conversation retention cleans rows; ledger references retain copied starting scope independently. Do not delete grants while any pending/admitted/dispatching/unknown invocation still needs them for execution/reconciliation; deletion may use retained explicit-host provenance only after that reader contract is reviewed. No new expiry timer or premature cascade is assumed.

Validation: normalized absolute lexical directory paths, maximum 4096 chars each, no glob/NUL/relative components; exact normalized hosts passing `validateAllowHost`, no wildcard expansion hosts. Deduplicate/sort; reject overflow, never truncate. **The final union of base+expanded readable/writable directory roots must be ≤64 distinct roots; final network list ≤100 hosts.** Writes imply reads, and the emitted SDK arrays also each satisfy its 64-entry limit. Persist only the exact displayed candidate; a reviewer returns allow/deny/ask and reason, never replacement roots/identity. Existing deny rules, owner restricted reach/denied paths and org network ceiling still intersect it. No roots in `ToolCallContext`, `SandboxUseContext`, SDK `SandboxExecOptions` or model arguments become authority.
