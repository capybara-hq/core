# Capybara 整体架构设计

- 日期：2026-10-17
- 状态：设计已逐节确认，待评审本文档
- 许可证：Apache-2.0

> **Capybara —— 和谁都处得来的企业 Agent 平台。**
> *The calm agent that gets along with everything.*
>
> 「和谁都处得来」= 接入一切（飞书、Slack、各种已有系统）；
> 「情绪稳定」= 企业级（高并发、多副本、故障自愈）。

## 0. 背景与定位

Capybara 是一个**独立的开源项目**：企业级、高并发、连接企业一切的 agent 平台。
先单独发布试水，社区有反响再考虑并入其他产品线。设计上**不为任何特定商业产品定制**，
商业能力（计费、席位等）一律通过插件接缝接入。

参考了两个来源：

- **DeepSeek Harness**：借它的**接缝设计**（接口定义 / 实现方 / 使用方三角色、事件日志即事实源、
  中间件拦截点、loop 可替换、审批失败即拒绝），**不借它的运行时形态**（进程内注册表、
  进程内锁与事件、热重载、单用户本地存储），因为后者与多副本部署根本冲突。
- **一个既有的内部 agent 平台的经验教训**：身份体系多套并存、服务间双向耦合、
  计费门禁多副本、复杂的 per-agent × per-channel 权限矩阵、所有模型压进 OpenAI 兼容网关带来的大量补丁。
  这些都是 Capybara 要在结构上避免的。

### 0.1 命名空间

| 资源 | 值 |
|---|---|
| 域名 | `capybarahq.com`（主）、`capybarahq.cn` |
| GitHub | `github.com/capybara-hq` |
| npm | 组织 `@capybara-hq/*`；裸包 `capybara`（历史版本 0.0.1、0.1.2、1.0.0–1.0.5 不可复用） |

### 0.2 非目标（第一版不做）

- 客户端（桌面端 / 移动端）
- 内置工作流引擎、知识库、记忆（都是外部应用）
- 组织嵌套
- 插件的进程级隔离（插件是受信代码，见 1.6）
- 本地 stdio MCP 直连（见 4.2）

## 1. 总体架构

### 1.0 三层划分

| 层 | 判据 | 形态 | 谁装 |
|---|---|---|---|
| **内核** | 每个部署都需要；定义其他层之间的契约；在每一轮对话的热路径上 | 内核代码 | — |
| **插件** | 需要**参与或拦截 agent 的运行过程**（入口、模型、工具执行、计量、身份、沙箱） | 进程内受信 TS 包，经 `ctx` 接缝扩展 | 企业管理员，**部署时** |
| **外部应用** | 只是**给 agent 提供工具或数据**，有自己的数据与生命周期 | MCP 或 OpenAPI 端点，Capybara 不执行其代码 | 组织管理员 |

常用模式「外部应用 + 薄插件」：数据和逻辑在应用里（比如记忆服务），
需要每轮自动注入时再加一个只挂 hook 的薄插件。

### 1.1 进程与依赖拓扑

```
           ┌──────────── 一个镜像，三种角色 ────────────┐
 浏览器/IM →│ api / gateway / worker                     │
           │  ┌──────── 内核 ────────┐  ┌── 插件 ───┐ │
           │  │ 身份与租户            │←→│ 飞书/Slack │ │
           │  │ Agent 运行时(LangGraph)│  │ 模型供应商 │ │
           │  │ 工具运行时 + 策略      │  │ 沙箱实现   │ │
           │  │ 连接器(MCP/OpenAPI)   │  │ 计量/观测  │ │
           │  │ 插件宿主 + ctx        │  │ ...        │ │
           │  └───────────────────────┘  └───────────┘ │
           └──────┬───────────┬───────────┬─────────────┘
              Postgres   Redis/Valkey  S3 兼容存储 · 沙箱 · 外部应用
```

- `api`：HTTP / WebSocket、管理后台与网页聊天静态资源
- `worker`：执行 agent 运行
- `gateway`：渠道入站（webhook 与长连接）

三种角色同一镜像、按启动参数区分，生产中各自扩缩；试用时一个进程包揽全部。

### 1.2 内核职责（只有五件）

1. 身份与租户：账号、组织、成员、角色
2. Agent 运行时：会话、loop、模型调用、上下文管理、中断续跑、流式推送
3. 工具运行时：注册、执行管线、策略
4. 连接器：MCP / OpenAPI 客户端、认证适配、凭据保管
5. 插件宿主：加载、`ctx`、配置

## 2. 内核与插件契约

### 2.1 能力接口

内核在 `@capybara-hq/plugin-sdk` 里声明**带版本号的能力接口**；插件实现，内核与其他插件使用。

| 基数 | 含义 | 例子 |
|---|---|---|
| 单选 | 整个部署只有一个实现 | `sandbox@1`、`config-source@1`、`secret-store@1` |
| 多选 | 可同时装多个，按名字区分 | `channel@1`、`model-provider@1`、`identity-source@1`、`directory@1` |
| 中间件链 | 按序串联 | hook（见 2.4） |

### 2.2 插件清单与两级配置

```ts
export default definePlugin({
  name: "feishu",
  version: "1.2.0",
  sdk: "^1.0.0",
  provides: ["identity-source@1", "directory@1", "channel@1"],
  requires: [],
  config: {
    deployment: z.object({ region: z.enum(["cn", "global"]) }),   // 企业管理员配
    org: z.object({ appId: z.string(), appSecret: secret() }),      // 组织管理员配
  },
  migrations: "./migrations",        // 只作用于本插件自己的 PG schema
  setup(ctx) {
    ctx.provide("channel@1", (orgConfig) => new FeishuChannel(orgConfig, ctx));
  },
});
```

- **安装在部署级、启用和配置在组织级**：插件向内核提供的是「按组织创建实例的工厂」，
  同一个飞书插件可以服务多个各自有飞书应用的组织。
- 管理后台的配置表单由 Zod schema 生成；`secret()` 字段加密存储、不回显。

### 2.3 `ctx`：插件能拿到的全部能力

| 能力 | 说明 |
|---|---|
| `ctx.db` | 本插件独占的 PG schema |
| `ctx.kv` | 带命名空间的 Redis，**写入必须带 TTL** |
| `ctx.queue` | 带命名空间的 BullMQ 队列，含延迟任务（替代定时器） |
| `ctx.bus` | 跨副本广播（替代进程内事件） |
| `ctx.lock` | 分布式锁（含选主） |
| `ctx.secrets` | 按组织隔离的加密凭据 |
| `ctx.http` | 在 `/plugins/<name>/*` 下注册路由 |
| `ctx.tools` | 注册插件自带的工具 |
| `ctx.hooks` | 挂中间件链 |
| `ctx.log` / `ctx.trace` | 日志与 OpenTelemetry |

**`ctx` 不提供定时器和任何进程内共享对象。** 由于这挡不住插件作者自己写 `new Map()`，
SDK 附带**双副本测试工具**：起两个内核实例共享同一套 PG/Redis、请求轮流落到两边。
插件测试必须在此环境通过；它也是公共市场上架插件的必过检查。

### 2.4 Hook 挂载点

| 挂载点 | 用途 | 出错时 |
|---|---|---|
| `session.start` / `session.end` | 审计、分析 | 放行 + 告警 |
| `agent.preStep` | 注入上下文（如记忆插件） | 放行 + 告警 |
| `model.request` / `model.response` | 计量、观测、内容过滤 | 过滤类拒绝；观测类放行 |
| `tool.preExecute` | 审批、策略、自动评审 | **拒绝** |
| `tool.postExecute` | 脱敏、审计 | 放行 + 告警 |
| `usage.report` | 计量、计费 | 放行 + 告警 |

规则：**策略类出错即拒绝，观测类出错即放行并告警**。

### 2.5 信任与版本

- 插件是受信代码、进程内运行、不做代码沙箱；因此**只有企业管理员能在部署时安装**，
  组织管理员只能启用与配置。不受信的扩展一律做成外部应用。
- 每个能力接口独立版本（`channel@1` → `channel@2`），内核同时支持当前版与上一版。
- 插件即 npm 包，安装列表写在部署配置（`plugins: ["@capybara-hq/plugin-feishu"]`）。

## 3. 身份与组织

### 3.1 数据模型

```
账号 account ─┬─ 外部身份 identity（来源 + 外部 ID：飞书 union_id / Slack user id / OIDC sub）
              ├─ 成员关系 membership ── 组织 org（角色：所有者 / 管理员 / 成员 / 访客）
              └─ 企业管理员标记（部署级）

agent ── 归属 (组织, 负责人账号)；可见范围：仅自己 / 全组织 / 指定成员；
         agent 本身也有一个组织角色（见 3.6）
```

- 一个部署 = 一家企业或集团；组织平铺，对应子公司或团队；账号部署内共享，可加入多个组织，有「当前组织」上下文。
- **身份只按「来源 + 外部 ID」识别，不按邮箱。** 仅当两侧邮箱都已验证、且企业管理员明确信任该身份源时才自动合并；
  其他情况由已登录用户手动绑定。

### 3.2 登录

- 登录方式 = 已安装且被企业管理员启用为登录方式的身份来源插件（飞书、Slack、钉钉、企业微信、OIDC/SAML）+ 内置本地账号密码。
- 首次登录自动建**账号**（不建组织）；入组织靠通讯录映射或邀请。
- 第一个企业管理员：首次启动的初始化向导或 `capybara admin create`。
- Web 会话 Cookie 仅限当前主机，不写根域；短期 access token + PG 中可吊销的 refresh token。
- 程序化访问：个人访问令牌、组织服务令牌。

典型流程：

```
① 首次访问 → 初始化向导 → 成为企业管理员 → 建第一个组织
② 启用 Slack 插件，配映射：Slack 工作区 X ↔ 组织「研发团队」
③ 员工「用 Slack 登录」→ 自动建账号 → 属于工作区 X → 自动加入「研发团队」
④ 不在通讯录里的人 → 邀请链接
```

### 3.3 通讯录同步与离职

通讯录插件把企业通讯录同步为组织成员（组织管理员配置映射）。人员离开时**同一事务内**：
撤销成员关系 → 吊销该组织下的会话与令牌 → 删除其连接器凭据 → 其负责的 agent 转给组织所有者并标记「待重新指派」。
事件在事务提交后发出。

### 3.4 角色

| 能力 | 访客 | 成员 | 管理员 | 所有者 |
|---|---|---|---|---|
| 使用被分享给自己的 agent | ✓ | ✓ | ✓ | ✓ |
| 创建 agent、使用已安装的应用与技能 | | ✓ | ✓ | ✓ |
| 申请安装应用与技能 | | ✓ | ✓ | ✓ |
| 安装应用与技能、配置插件、管理成员 | | | ✓ | ✓ |
| 转让所有权、删除组织 | | | | ✓ |

- **企业管理员**：模型供应商、插件、全局策略、允许安装哪些应用；能看到所有组织，**默认不能读对话内容**
  （合规审计作为显式开启的功能，每次查看都入审计）。
- 任何账号都能创建组织；企业管理员可关掉，改为「仅企业管理员可建」。
- 组织至少保留一个所有者，最后一个所有者须先转让才能退出。
- **管理面只有三个旋钮**：角色、agent 可见范围、工具策略。渠道没有独立权限矩阵：
  谁能用某渠道里的 agent = agent 可见范围 ∩ 渠道本身的受众。

### 3.5 渠道中的身份

- IM 发送者经外部身份映射到账号；映射不上时按渠道策略：引导绑定，或作为匿名访客（仅公开 agent、无个人连接器）。
- **硬规则：识别不出身份，绝不借用渠道开通人的身份。**
- 无人在场的运行（定时任务等）以 agent 负责人身份执行，审计标注触发来源。

### 3.6 Agent 作为组织成员

Agent 和人类员工一样有组织角色（默认「成员」），可以修改自己的运行环境。
**但 agent 无法承担责任，所以它的角色是天花板，不是权力来源；权力永远来自委托链上的人。**

| 规则 | 内容 |
|---|---|
| **R1 权力来自人** | 实际权限 = agent 角色 ∩ 委托链上每个人的角色。委托链：当前发消息的人；定时与自动触发 = 配置该触发的人；agent 调 agent = 上游每一环 |
| **R2 只有人能审批** | 权限不足转为审批，推给持有相应角色的人；agent 不能审批任何请求，更不能批准自己发起的 |
| **R3 有权 ≠ 已确认** | 固定清单上的高影响动作即使有权也必须人工确认，策略只能是「询问」：发布到公共市场、安装应用、提插件申请、改角色与成员、删除、改共享技能、改自己的指令 |
| **R4 共享 agent 改自己要负责人批** | 仅自己可见的 agent 写自己的技能直接生效；共享 agent 写/改技能进入待审，负责人批准后才对他人生效 |
| **R5 执行时实时校验** | 权限在动作执行那一刻判定，运行中被降级立即生效 |
| **R6 审计整条链** | 谁 → 经由哪个 agent → 做了什么 → 谁批准 |

Agent 的环境修改能力都是普通工具：

| 动作 | 需要的角色 | 默认策略 |
|---|---|---|
| 给自己写 / 改 / 试用技能 | 成员 | 允许（共享 agent 受 R4） |
| 从企业目录 / 公共市场下载技能自用 | 成员 | 允许（在企业策略范围内） |
| 发布技能到企业目录 | 管理员或经审批 | 询问 |
| 发布技能到公共市场 | 企业策略允许 | 永远人工审批 + 发布前扫描密钥与内部地址 |
| 为组织安装应用 | 管理员 | 询问 |
| 插件 | — | 只能向企业管理员提申请 |
| 修改自己的指令 | 生成新版本，负责人确认后生效 | 询问 |

审批卡片必须展示**具体改动（差异）**，同类审批可批量处理，防止审批疲劳。

## 4. Agent 运行时

### 4.1 Agent 定义

名字头像、指令、主模型与兜底模型、可用工具（应用 / 技能 / 内置）、工具策略、是否需要沙箱、可见范围、负责人、组织角色。
**每次保存生成新版本**；每轮运行开始时固定所用版本，可追溯、可回滚。

### 4.2 两份记录

| | 会话事件日志 | 执行快照（LangGraph checkpoint） |
|---|---|---|
| 内容 | 只追加：用户消息、模型回复、工具调用与结果、审批、压缩摘要、用量 | 图执行状态 |
| 用途 | **唯一事实记录**：界面历史、审计、回放、分析 | **只用于续跑**：审批后恢复、崩溃后恢复 |
| 保留 | 永久 | 一轮结束后只留最新一份 |

原则：**模型看到的一切都进日志**，压缩摘要也作为事件写入，任何一次模型请求的输入都可从日志还原。

### 4.3 一次运行（多副本、高并发）

```
消息进来（Web / IM / API / 定时）
  → 写入用户消息事件 → 投递 run 任务（BullMQ）
  → 任意 worker 领取 → 加载 agent 版本与执行快照 → 跑 loop
  → 流式增量经 Redis 广播 → 持有连接的 api 副本推给浏览器；渠道插件投递回 IM
```

- 同一会话同一时刻只跑一轮（会话级锁）。
- **插话**：运行中的新消息不打断当前轮，在下一个步骤间隙插入上下文；要彻底改主意就点停止。
- **组织级并发配额**（Redis 计数），防止单个组织占满 worker；企业管理员可按组织调整。
- 崩溃恢复：任务超时后由其他 worker 从最近快照续跑。
- **有副作用的工具不盲目重跑**：调用前写「调用开始」事件；恢复时只有开始没有结果的调用，告诉模型「结果未知」，由模型查证或问用户。
- 中止信号经 Redis 广播，任意副本上的运行都能收到。
- 每轮有最大步数与最长时长兜底。

### 4.4 Loop

- 内核定义 `AgentLoop` 接口，默认用 **LangGraph** 实现（调模型 → 执行工具 → 再调模型）；扩展只依赖接口。
- 第 2.4 节的 hook 挂在 loop 上。
- 内置上下文压缩：接近上限时总结较早内容，摘要入日志，最近几轮保持原文。
- 提示词缓存：内核保证稳定内容（指令、工具定义）在前，具体缓存标记由模型供应商插件负责。

### 4.5 模型

- **各家原生协议**：官方供应商插件 `anthropic`、`openai`、`gemini` 各用原生协议；
  另有一个 `openai-compatible` 插件接 vLLM / DeepSeek / Qwen 等，**各家毛病只在这个插件里打补丁，不进内核**。
- 每个供应商插件必须通过**一致性测试**：工具调用往返、流式、思考模式、缓存、用量统计。
- 插件向内核报告模型能力：工具调用、视觉、推理、上下文长度、缓存。
- 企业管理员添加供应商与模型；组织管理员为 agent 选择；**兜底模型必须是另一家供应商**（后台提示）。
- 每次调用产生带（组织、账号、agent、会话）归属的用量事件，经 `usage.report` 交给计量 / 计费插件；开源默认只记录。

### 4.6 人机交互

- 审批：「询问」策略触发 loop 暂停；用户可在 Web 或 IM 消息卡片中处理（卡片由渠道插件渲染），处理后从快照恢复。
- 附件：存对象存储，需要时挂入沙箱。

## 5. 连接器与工具策略

### 5.1 工具来源

| 来源 | 例子 | 谁装 |
|---|---|---|
| 内置（尽量少） | 问用户与给选项、任务清单、`skill_load`、`tool_search`；沙箱启用时的命令执行与文件读写 | 内核 |
| 应用 | 飞书文档、Jira、公司内部系统 | 组织管理员 |
| 技能 | `SKILL.md` + 脚本与资料 | 组织管理员 / agent 自己（见 3.6） |
| 插件提供的工具 | Slack「读取频道历史」 | 随插件 |

### 5.2 连接器：我们适配对方

**原则：Capybara 去适配对方已有的认证方式，不要求对方信任 Capybara 签发的身份或令牌。**

一个已安装的应用 = 一个端点 + 对方要求的认证方式。

端点类型：

- **MCP**（远程 Streamable HTTP）。只支持 stdio 的 MCP 服务以后放到沙箱里跑再经代理暴露，第一版不做。
- **OpenAPI**：导入对方的 OpenAPI 文档，**每个接口自动生成工具**；可勾选只暴露部分接口；
  GET 默认按只读处理，POST / PUT / PATCH / DELETE 默认询问。

认证方式：

| 对方的认证 | 接法 | 凭据归属 |
|---|---|---|
| API key / Bearer / Basic / 自定义 header | 组织管理员填写，或每人各填 | 组织或个人 |
| OAuth 2.0 授权码（含标准 MCP OAuth） | 每人点「连接」用自己的账号授权 | 个人 |
| OAuth 2.0 客户端凭据 | 组织管理员填 client id / secret | 组织 |

规则：

- 工具调用使用**发起这次对话的人**的凭据；未连接则返回「需要连接」并推送连接卡片（IM 中也可点），连接后继续。
- 匿名访客拿不到个人类凭据的应用；定时任务用 agent 负责人的凭据。
- 凭据信封加密；access token 自动刷新，**刷新加分布式锁**（避免多副本并发刷新使 refresh token 互相作废）。

后续口子（第一版不做）：对方与 Capybara 信任**同一个企业 IdP**（Entra ID、Okta 等）时，
借用该 IdP **自己的** on-behalf-of 换票能力实现免连接——信任锚是企业 IdP，不是 Capybara。

### 5.3 工具策略

- 两层：组织管理员给每个应用 / 工具设默认策略；agent 负责人只能收紧（允许 → 询问 / 拒绝），不能放宽。
- 默认值：`readOnlyHint` → 允许；`destructiveHint` → 询问；**无注解 → 询问**（管理员可批量改为允许）。
- 用户审批选项：仅这一次 / 本次会话内都允许 / 以后都允许（记到「用户 × agent × 工具」，可在设置中撤销）。
- 审批失败即拒绝：超时、渠道未送达、找不到审批人一律按拒绝处理。
- 3.6 的 R3 清单上的动作策略固定为「询问」。

### 5.4 工具执行管线

参数校验 → 策略判定 → 带超时执行 → 结果过大则存对象存储、只回摘要与引用 → 应用连续失败自动熔断 → 写审计事件。

### 5.5 工具规模

工具数超过阈值时，上下文里只放工具目录（名字 + 一句话）；模型用 `tool_search` 加载完整定义。
未加载就直接调用 → 返回明确的校验错误（不自动替模型加载或猜测）。

### 5.6 技能

- 兼容 Anthropic 提出的 Agent Skills 格式（目录 + 带 frontmatter 的 `SKILL.md` + 脚本资料）。
- 上下文只放名字和描述；需要时 `skill_load` 全文；带脚本的技能在沙箱中运行。

## 6. 把事做对（可靠性原则）

| 原则 | 做法 |
|---|---|
| **1. 原生协议** | 见 4.5；模型 / 网关特定补丁只存在于对应供应商插件，内核零补丁 |
| **2. 通用机制是显式管线阶段** | 压缩、超大输出落盘、tool_use/result 配对守卫、超时降级、熔断、轮次收尾等，各自是独立、有测试的阶段 |
| **3. 给事实，不猜** | 不做模糊匹配、自动纠错、「Did you mean」；工具错误必须准确且可执行（附完整 schema / 现有候选）；正确性要求写成工具前置条件（如「先读后改」） |
| **4. 工具面简单** | 只有一种发现机制（目录 + `tool_search`），不设多层加载，相应的提示词规则也不需要 |
| **5. 行为规范短而通用** | 如实报告、做完要验证、不清楚就问、不暴露内部细节；动态信息通过对话中插入的提醒传给模型，不堆进系统提示词 |
| **6. 内置任务清单** | 多步骤任务列步骤、边做边勾，进度在 Web 与 IM 中可见 |
| **7. 验证闭环** | 写操作的工具结果返回可核对之物（id、链接、读回内容）；声称完成须引用证据；通用机制，不按应用写适配器 |
| **8. 评测是一等公民** | 内核内置轨迹记录与回放：从真实会话抽样建评测集，换模型 / 改提示词 / 升版本前跑回放对比；管理后台有轨迹查看器。**第一版就做** |

## 8. 基础设施与部署

### 8.1 依赖

| 组件 | 用途 | 说明 |
|---|---|---|
| **Postgres** | 唯一事实源：账号组织、agent、事件日志、checkpoint、扩展、加密凭据、审计 | 插件各自独立 schema；内核不需要 pgvector |
| **Redis / Valkey** | 队列（BullMQ）、跨副本广播、锁、限流、短时状态、缓存 | 丢了最多导致重试、不丢数据；只用协议层能力，保证 Valkey（BSD）可直接替换 |
| **S3 兼容对象存储** | 附件、超大工具输出、技能包、沙箱工作区 | MinIO / Ceph / SeaweedFS / 各家云 |

- **不用 RabbitMQ**（暂无场景；事件外送 Kafka / RabbitMQ 做成插件）。
- 试用版也要求 PG + Redis 两者（不做「仅 PG」精简模式），保证只有一套实现。

### 8.2 配置

```bash
CAPYBARA_CONFIG_SOURCE=file    # file | nacos
CAPYBARA_CONFIG_FILE=/etc/capybara/config.yaml
# 或
CAPYBARA_NACOS_SERVER=nacos:8848
CAPYBARA_NACOS_NAMESPACE=prod
CAPYBARA_NACOS_DATA_ID=capybara.yaml
```

- 两种来源同一套 schema 校验；**环境变量优先级最高**。
- 密钥类配置推荐只走环境变量 / K8s Secret。
- 热更新仅对标记为「可热更」的项生效；各副本各自监听。
- 新来源（Apollo、Consul）按 `config-source@1` 接口加插件。

### 8.3 沙箱

- **按需懒创建**：只有用到沙箱类工具才拉起。
- 实现由部署配置选定（一个部署一种）：

| 形态 | 实现 | 隔离 |
|---|---|---|
| 试用 | Docker(runc) | 弱 |
| 演示 / 小规模 | Docker(**gVisor/runsc**)，经 socket 代理 | 强，无需 KVM |
| 大规模 | K8s **agent-sandbox + gVisor**（高安全可选 Kata） | 强 / 最强 |
| 可选插件 | E2B 云或自托管 E2B runtime（开源版为单机设计，需 KVM） | 强 |

```yaml
sandbox:
  provider: docker            # docker | k8s | e2b
  limits:
    cpu: 1
    memory: 2Gi
    egress: allowlist         # none | allowlist | open
    suspendAfterIdle: 10m     # 空闲后休眠（不销毁）
    destroyAfterInactive: 30d # 长期不用才销毁（连同文件）
    maxRunning: 2h            # 兜底：连续运行上限，到点强制休眠
  docker:
    runtime: runsc            # runc | runsc
    endpoint: tcp://sandbox-proxy:2375
  k8s:
    namespace: capybara-sandbox
    runtimeClassName: gvisor  # gvisor | kata
    warmPool: 20
  e2b:
    apiUrl: https://api.e2b.dev
    apiKey: ${E2B_API_KEY}
```

- **休眠两级保证**：「文件系统保留」所有实现必须支持（休眠期间零 CPU / 内存）；「内存保留」是可选能力
  （E2B 原生支持；gVisor checkpoint/restore 待验证后接入）。agent 只依赖文件系统保留。
- 沙箱镜像只有一份 Dockerfile，Docker / K8s / E2B 模板共用。
- **单机安全**：应用容器不直接挂 `docker.sock`，经仅放行沙箱生命周期接口的 socket 代理或独立沙箱管理服务。
- 后续：休眠时工作区打包进对象存储，使恢复不绑定节点。

### 8.4 部署形态与前端

| 形态 | 方式 |
|---|---|
| 试用 | `docker compose up` 起全部服务（见下） |
| 演示 / 小规模生产 | 单台云主机 + compose + gVisor |
| 大规模生产 | K8s + 官方 Helm chart |

**前后端分开部署**（2026-10-17 调整）。官方 compose 编排一条命令起全部服务：

```
docker compose up
├── api        后端镜像，角色 api      ┐
├── worker     后端镜像，角色 worker   ├─ 后端始终是一个镜像，按角色拆服务
├── gateway    后端镜像，角色 gateway  ┘
├── web        前端镜像（Next standalone），代理 /api 到 api
├── postgres
├── valkey
├── 对象存储（S3 兼容）
└── sandbox-proxy
```

管理后台与网页聊天是一个 **Next** 应用，独立构建、独立发版；第一版界面支持中文、英文。
官网 / 文档站若需 SEO，另起仓库，与产品前端分开。

### 8.5 升级不停机

- 迁移向前兼容一个版本（扩展 → 收缩两步）；由独立的 `capybara migrate` 任务（K8s Job / compose init 容器）在新 Pod 启动前执行，内核与插件 schema 统一迁移。
- worker 优雅退出：停止领新任务 → 宽限期内跑完 → 跑不完则保存快照、任务回队列。

### 8.6 扩缩容

`api` 按 CPU / 连接数；`worker` 按队列积压（可选 KEDA）；`gateway` 长连接 bot 靠 `ctx.lock` 选主，同一 bot 连接全局只有一个持有者。

### 8.7 观测

OpenTelemetry（trace / 指标 / 结构化 JSON 日志）；内置指标：队列积压、每轮耗时、按供应商的模型错误率、
活跃 / 休眠沙箱数、审批积压；`/healthz`、`/readyz`；管理后台轨迹查看器。Langfuse 等做成插件。

### 8.8 数据安全

- 凭据信封加密：每组织一把数据密钥，由主密钥加密；主密钥可轮换，可经插件接 Vault / 云 KMS。
- 审计日志保留期可配；支持按组织导出与删除数据；文档给出 PG 时间点恢复的备份建议。

### 8.9 发版

语义化版本；插件 SDK 独立版本；发布说明写明破坏性改动与迁移方式。

## 9. 渠道与生态插件

一个生态插件可同时提供身份来源、通讯录、渠道三种能力，三者各自独立开关，可共用同一个平台应用凭据。

- **渠道连接 = (渠道插件, 一组 bot 凭据) → 绑定一个 agent**；一个组织可有多个渠道连接（如「HR 助手」「IT 助手」各是一个 bot）。
- 支持长连接模式（Slack Socket Mode、飞书长连接、钉钉 Stream），**内网部署无需公网地址**；长连接用 `ctx.lock` 选主防重复收消息。
  有公网地址时用 webhook 模式（`ctx.http`）。
- 国内平台的特殊处理（回调加解密、可信 IP、新旧 API、飞书国内版 / Lark）全部封装在插件内。
- 文档、日历、审批等业务能力做成外部应用；市场上以「生态包」形式整体展示。
- 首发官方插件建议 **Slack + 飞书**；钉钉、企业微信第二批或交给社区。

## 10. 技术栈

- TypeScript 全栈，依赖使用最新版本。
- Agent：LangChain / LangGraph（JS）。
- 后端：**NestJS + Fastify 适配器**（2026-10-17 定，与团队现有技术栈一致）。
  **插件契约不暴露框架**：插件只认 `ctx`，不写 Nest controller、不依赖 Nest 的模块与依赖注入；
  插件路由经统一入口 `/plugins/:name/*` 分发到插件注册的处理函数。配置、迁移、`ctx`、插件宿主、
  双副本测试工具与框架无关。选 Nest 看重的是团队熟悉度与内核变大后的结构（模块、校验、守卫、Swagger），
  不是单进程性能——高并发靠多副本横向扩展与无状态设计。
- 前端：**Next**（独立 web 服务，standalone 镜像）。
- 队列：BullMQ；ORM / 迁移工具在实施计划中确定。

## 13. 工程协作约定（贡献者 harness）

社区共建意味着贡献者来自各处、大量使用 AI 编码助手，且都不了解本项目的约定。
这一层与产品架构同等重要。

### 13.1 三层约束

| 层 | 给谁 | 内容 | 约束力 |
|---|---|---|---|
| ① 自动检查 | 所有人 | CI 上的 lint、类型检查、测试、自定义检查 | 合不进去 |
| ② 技能 | AI 编码助手（人也可读） | 「怎么做某件事」的操作手册 | 按需加载 |
| ③ 文档 | 人 | 架构总览、贡献指南、各约定的「为什么」 | 理解 |

- **能写成检查的规则，不只写成文档。**
- **每道检查必须先被证明会红**：故意制造违规确认被拦住，再修绿。读起来对、实际从不拦人的检查比没有更糟。

### 13.2 AI 编码助手入口

- 根目录 `AGENTS.md` 为唯一事实来源（跨工具约定）；`CLAUDE.md` 只写 `@AGENTS.md` 引用，不另写一份。
- 仓库开发技能使用产品本身支持的 Agent Skills 格式（`SKILL.md`），自己用自己的格式。

### 13.3 第一批约定

| 主题 | 自动检查 | 技能 / 文档 |
|---|---|---|
| 架构边界：内核 / 插件 / 应用分层；插件只 import `plugin-sdk` | 依赖方向检查 | 架构文档 |
| 多副本纪律 | 插件代码禁止定时器与模块级可变状态的 lint；插件测试须过双副本测试工具 | 技能：插件怎么存状态 |
| 数据库与迁移：schema 归属、扩展→收缩、幂等、命名 | 迁移检查：同一版本内禁止删列、要求幂等写法 | 技能：怎么写迁移 |
| 配置与密钥：配置项全部在 schema 声明；环境变量统一 `CAPYBARA_` 前缀；标注可热更 / 密钥 | 配置文档由 schema 自动生成，不同步即拦 | 技能：怎么加配置项 |
| 国际化：界面文案走 key；服务端错误走错误码 + 翻译；**给模型看的文案一律英文** | 各语言 key 同步；错误码唯一 | 技能：怎么加文案与错误码 |
| 插件 SDK 兼容性 | 公开 API 快照比对，破坏性改动必须升主版本 | 文档：版本策略 |
| 工具设计规范（第 6 节「给事实」的落地） | 工具描述非空；错误信息须带可执行的修正方式 | 技能：怎么写一个好工具 |
| 测试与评测：单测、契约测试、供应商一致性测试；改提示词或 loop 时跑回放评测 | CI 按改动范围触发 | 文档：测试分层 |
| 提交与发版：Conventional Commits；Changesets 管理各包版本 | 提交信息检查；缺 changeset 即拦 | 贡献指南 |

### 13.4 取舍

- 从既有内部平台带**原则**（多副本纪律、迁移可回滚、错误码 + i18n、模型文案英文、检查须证明会红、给事实不猜），
  **不带绑定特定框架的脚本**；技术选型定后按同样原则重写。
- 控制检查数量与速度：CI 目标 10 分钟以内；报错直接说明怎么改；能本地一条命令复现的不只在 CI 跑。
- CI 使用 GitHub Actions。

### 13.5 贡献授权：CLA

- 采用 **CLA**：贡献者首次提 PR 时由机器人引导签署，授权项目方使用与再授权其贡献，
  保留将来调整许可证或推出商业版的选择权。
- 贡献指南中明确承诺：**代码始终以 Apache-2.0 开源**，降低社区对 CLA 的顾虑。
- CLA 文本与签署工具（如 CLA Assistant）在仓库初始化时确定；文本需公司法务过目。
