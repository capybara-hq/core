# Extensions: install, lifecycle and the admin console

Every deployment gets two required plugins, `openai-compatible` (model) and `object-store-s3` (object storage), and seven optional preinstalls: `anthropic` and `openai` (models), `connector-mcp` and `connector-openapi` (connectors), `jina` (web search and fetch), `sandbox-docker` (sandboxes) and `todo`. The optional ones are installed and enabled on the deployment but off in every organization until an org admin switches them on in Plugins, and a super admin may disable or uninstall them. The required two are bootstrap plugins: `capybara bootstrap` (compose `init`) or a starting kernel downloads them from npm once (or takes them from the offline directory `bootstrap.dir`, `/app/bootstrap` in the image) and installs them as required extensions (source `bootstrap`): approved, enabled in every org, and they can't be uninstalled or disabled; they only need deployment-level config (when it isn't set up, the admin console shows "pending configuration" and the kernel starts normally). Every other extension is installed into the extension directory as a **extension package** (an npm-pack tgz: single-file ESM with third-party dependencies bundled in; only `@capybara-hq/plugin-sdk` and `zod` are provided by the host):

- Pack: `capybara-plugin pack <dir>` (`@capybara-hq/plugin-tools`; in a core checkout `pnpm pack-plugin <dir>`, output in `artifacts/plugins/`). The published official plugins need no packing (`npm:@capybara-hq/plugin-<name>`); a [capybara-hq/plugins](https://github.com/capybara-hq/plugins) checkout packs all of them, the unpublished `example-*` included, with `pnpm pack-plugins`.
- Install: the super admin goes to "Admin → Extensions → Install", uploads a tgz or enters an npm package name and version (`packages.npmRegistry`; the token for a private registry is `packages.npmToken`), reviews the permissions (sensitive items and migration warnings are highlighted), then installs, approves and enables. The CLI works too:

```bash
pnpm capybara extensions install npm:@capybara-hq/plugin-todo   # or a local tgz: ../plugins/artifacts/plugins/capybara-hq-plugin-todo-<version>.tgz
pnpm capybara extensions approve todo
pnpm capybara extensions enable todo
pnpm capybara extensions list            # each extension's desired state and whether the replicas agree
pnpm capybara extensions disable todo    # disable before uninstalling: pnpm capybara extensions uninstall todo
```

- **Install, enable, disable, upgrade and uninstall never restart anything**: the admin console and CLI only write the desired state into PG, and each replica loads / revokes on notification (a maintenance task reconciles as a fallback every `extensionHost.reconcileIntervalSeconds` seconds). When switching versions, the new version loads first and the old one is revoked after; on disable or upgrade, in-flight tool calls are given up to `extensionHost.drainSeconds` (default 30 seconds). If the new version needs more permissions, it stays pending approval while the old version keeps running; extension migrations run on one replica holding a lock and are expand-only; a downgrade can only go back to a version whose migrations have all been run. Uninstalling doesn't delete data (the extension schema, secrets, org config and approval records are all kept). Old version code stays in process memory until restart; when one process has been upgraded many times (> 20), the log suggests restarting that replica.
- **Deployment-level config can be changed in the admin console** ("Admin → Extensions → Config", stored in PG, secrets encrypted): precedence is env vars > config file / Nacos > admin console > defaults, and fields given in the startup config are read-only in the admin console and show their source. When the config is invalid, the extension shows "pending configuration" and isn't loaded while the kernel starts normally; it loads automatically once fixed.
- Packages are stored under `deployment/plugins/blobs/` in object storage (in PG when no object storage is configured), and each replica syncs them by sha256 into the local `extensionHost.dir` (default `.capybara/plugins` under the working directory, `/var/lib/capybara/plugins` in the image; safe to clear at any time). **When you change the object-storage bucket or endpoint, migrate the objects under the `deployment/` prefix too**; otherwise the extension packages and catalog files stored in the old bucket can't be fetched and new replicas fail to sync.
- Packages uploaded through the web app are also limited by the web layer's `CAPYBARA_WEB_MAX_PACKAGE_BYTES` (default 50 MiB); raise it together with the kernel's `packages.maxBytes`, see [docs/config.md](../config.md).

**Migrating from config-declared extensions to install records** (C15): the `extensions` list in the startup config still works (development mode and existing deployments, source `config`), but extensions declared that way are read-only in the admin console: they can't be installed / upgraded / disabled from the web app, changing the list needs a restart, and installing an extension with the same name returns 409 `extension.config_declared`. The kernel doesn't convert automatically; the migration steps are:

1. Prepare an extension package of the same npm package (the version on npm, or `capybara-plugin pack <dir>`): an extension name belongs to the first npm package that used it, and changing the package name is rejected (`extension.name_conflict`).
2. Remove it from the `extensions` list (deployment config in `extensionConfig` can stay and still takes effect; you can also move it to the admin console) and roll-restart the replicas. The extension is then not loaded, extensions that depend on it are unloaded with it (the admin console shows `dependency`), and they reload automatically once the extension is back.
3. Upload / npm-install the package and enable it (admin console, or `capybara extensions install …` + `enable`). The extension schema, secrets, org config and approval records carry over; if the new package's permissions don't exceed what was approved, it loads directly.

**Extension UI** goes into the slots of a versioned catalog (conversation panel, properties section and tool-result card, org page, file preview, agent detail section, org settings section, platform page): [UI slots](ui-slots.md) lists every slot with its scope, accepted kinds, minimum role and arguments (generated from the SDK). A contribution names its slot with `slot` (the old `place` is deprecated); one that names an unknown slot or version is dropped, the extension still loads, and the admin extension detail page lists it under 未生效的界面. Org admins hide and reorder contributions on the 界面位置 page (hidden means not listed; an org page or platform page still opens by its direct link); the super admin sets the platform default.

**Client code** (components, replaceable slots such as the brand and the empty-conversation hero, and decoration with plugin CSS) is the browser half of a plugin's extension. It needs `permissions.client` (sensitive: it blocks loading until approved) and runs with full trust in the page, only where the plugin is on. The super admin can stop it all or per plugin (平台设置 › 插件界面代码, the kill switch); anyone can open a page without it with `?safe-ui=1` (safe mode lasts the browser session; `?safe-ui=0` ends it). An upgrade that is pending approval or failed keeps serving the old build. A plugin that suggests an appearance gets one confirmed step, "Apply this plugin's appearance", for admins. The part names plugin CSS may select are listed in [UI parts](ui-parts.md); the slot catalog in [UI slots](ui-slots.md).

**Trust model**: extensions run with full trust inside the kernel process (an extension's migration SQL also runs on the kernel's database connection). The permission manifest, approval and catalog policy are **governance and audit, not a sandbox**: they control the resources the kernel holds (secrets, storage, tools, conversation content), but can't stop an extension from connecting to the database or the network directly. Install packages only from publishers you trust, and read the migration SQL before approving (writes outside the extension's own schema, permission changes, `DO` blocks and the like are listed as sensitive warnings, and a changed warning needs a new approval); don't run `pnpm pack-plugin` on untrusted source (packing executes extension code). Make untrusted extensions external apps that call the kernel over HTTP. To write an extension, see [.agents/skills/writing-extensions](../../.agents/skills/writing-extensions/SKILL.md).
