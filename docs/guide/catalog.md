# Catalog, marketplaces and plugins

A **plugin** is the install unit: an npm-pack tgz with a `.capybara-plugin/plugin.json` manifest that bundles at most one **extension**, **skills** and **connector templates** (connectors with the endpoint and auth preset, so the org only fills in credentials), and may depend on other plugins by name and version range. The catalog lives inside the deployment ("Admin → Plugins") and holds plugins. Each item has a **scope** set by the super admin: `all` (on in every org, org admins cannot turn it off), `optional` (off until an org admin turns it on; the default for a new item) or `named` (on in the listed orgs, invisible to the others unless it is shown to them so they can request it). Built-in plugins (the required bootstrap ones) are `all` and their scope is fixed. **Disabled** stops a plugin on the whole deployment and keeps its scope. Changing the scope or disabling first shows the orgs and agents that would lose the plugin, and applies only after you confirm; a background job then installs or removes the plugin in the affected orgs. A plugin's skills, agent templates and connector templates are platform components, one version per deployment, that follow the plugin's scope or have their own; an org admin can switch a single component off or on. Org admins turn an `optional` or `named` plugin on or off in "Plugins" (`/plugins`); members ask their org admin for an `optional` plugin that is off, and org admins ask the super admin for a plugin shown to them or for a marketplace entry that has not been imported (the deployment setting `orgMarketplaceBrowse`, default on, controls marketplace browsing and these requests). Requests are answered in the inbox and take effect at once. When the deployment settings `customConnectors` / `customSkills` are set to `deny`, orgs can only install connectors / skills from the catalog (this doesn't affect an agent registering its own skill with `agents.register-skill`, but it does refuse sharing an agent's skill with the org and new versions of shared skills).

- **Item sources**: manual upload (tgz) or npm ("Admin → Plugins → Import", or `capybara plugins import <file.tgz | npm:<name>[@<version>]>`); the **official marketplace** (the `capybara-hq/plugins` repository, configured under `marketplaces.official.*`; on by default, offline deployments set `marketplaces.official.enabled: false`); **custom marketplaces** (added under "Admin → Marketplaces", several allowed, with an optional mirror and token). A marketplace is a static `marketplace.json` (format in `packages/plugin-sdk/schemas/marketplace.v1.schema.json`; one entry per plugin, its current version, with an npm, archive, path or git source; older versions stay importable by direct npm import, and an entry the maintainer marked deprecated is never offered or imported), pulled every `marketplaces.refreshIntervalMinutes` minutes or refreshed manually; its entries are browsed first, and a version is downloaded and built into a catalog item only when you "import" it; when a new version appears you are only notified, and it isn't pulled automatically.
- **Import review**: every plugin goes through one review before anything reaches the catalog: the extension's permissions and migration warnings, each skill's body, each connector template's endpoint and auth, the dependencies and the version each resolves to, the source and license. The staged review stays available for 24 hours at its own link. On confirm the plugin's extension is installed and enabled on the deployment and the admin picks the scope of a new plugin; a version older than the one deployed is added to the catalog only. A plugin whose permissions still need confirming waits in "Pending" (待确认). A dependency not yet in the catalog doesn't block the import, but orgs can't install the plugin until a matching version is imported. A package in the pre-0.1.0 format is refused with a message asking to repack it with `pnpm pack-plugin`.
- **Verification**: downloads are always verified against the integrity in the marketplace (or npm's `dist.integrity` for a direct npm import), and a mismatch is rejected (`marketplace.integrity_mismatch`); the permission summary in the marketplace is used for display only, and the review page warns when it differs from what is computed after download.
- **Network and tokens**: marketplace addresses, mirrors and archive source URLs accept only https (`marketplaces.allowInsecureLoopback` is for tests only), redirects are not followed, and responses have a size limit. A custom marketplace's token is sent only to the origin of the marketplace's main address (not when the mirror is on another origin), and archive downloads don't carry it; npm sources are downloaded from `packages.npmRegistry` with `packages.npmToken`. **Don't put tokens in the query of a marketplace URL** (URLs are stored in PG and shown in the admin console); use the marketplace's "Token" field (stored encrypted, sent as `Authorization: Bearer`). The kernel doesn't block https URLs that resolve to internal-network addresses: marketplace and archive addresses are decided by the super admin (and the marketplace author), so add only marketplaces you trust.
- **Offline deployment**: set `marketplaces.official.enabled` to `false` (the admin console then shows offline mode, and the official marketplace is never contacted); use a custom marketplace hosted on the internal network and manual upload instead; npm sources need access to an npm registry, so point `packages.npmRegistry` at an internal mirror (such as Verdaccio or Nexus), and put the private registry's token in `packages.npmToken`.
- **Org install**: an org admin turning a plugin on first installs its dependencies that aren't in the org yet (each the highest imported version matching its range, whatever their own scope says), then enables its extension in this org and creates connectors from its templates (filling in credentials); its skills and agent templates are platform components and are not copied; on failure everything created by this install is undone, dependencies included. Approval follows the plugin being installed (its dependencies aren't approved separately), but a disabled dependency refuses the install. Uninstall removes only components created by this install that aren't in use elsewhere (a dependency goes with the last install that uses it), and the kept ones are listed with reasons. Installs that were interrupted by a replica crash, that have been "installing" for more than `catalog.staleInstallMinutes` (default 30) minutes, and failed installs can all be cleaned up through uninstall. **Updates**: a plugin moves to a new version only through the super admin's platform update (one per deployment, after a preview of what changes per component), which moves the extension, the platform components and every org install in one step and undoes every step on failure; a template added by the update shows the org as needing config until an org admin creates its connector.
- **Extensions in an org**: extensions are installed to the deployment only by the super admin (importing a plugin installs its extension). An org's "Extensions" page (`/extensions`) lists the extensions its plugins offer; switching one that ships in a catalog plugin is that plugin's switch (turning it off previews what is affected first, and `all` / built-in ones are locked on), while org config is written directly. Extensions not installed through the catalog have no scope.
- **Plugins owned by an org**: an org admin may upload a plugin (`.tgz`) for the org. Without an extension it installs at once, owned by the org and on only there; with an extension it waits as pending until the super admin confirms or rejects that exact package, and every later version carrying an extension is confirmed again. The owner org may mark what it created 可共享 (shareable, off by default); only then can the super admin show it to or turn it on in other orgs. Plugin names stay unique across the deployment. When the owner deletes an item other orgs still use, it is transferred to the platform instead of removed.

To write plugins and connector templates, see [.agents/skills/writing-plugins](../../.agents/skills/writing-plugins/SKILL.md).
