# Catalog, marketplaces and plugins

A **plugin** is the install unit: an npm-pack tgz with a `.capybara-plugin/plugin.json` manifest that bundles at most one **extension**, **skills** and **connector templates** (connectors with the endpoint and auth preset, so the org only fills in credentials), and may depend on other plugins by name and version range. The catalog lives inside the deployment ("Admin → Catalog") and holds plugins. The enterprise admin sets a policy for each item: `allow` (the default for new items), `needs_approval` (when an org admin installs it, it goes to the enterprise admin for approval, and the approval holds for that org across versions), or `disabled` (cannot be newly installed; installed ones are unaffected; a disabled plugin's extension can't be newly enabled in an org by any route). Members browse and request in "Catalog" in the top bar, and requests go to the org admin's inbox. When the deployment settings `customConnectors` / `customSkills` are set to `deny`, orgs can only install connectors / skills from the catalog (this doesn't affect agents writing their own skills with `SkillWrite`).

- **Item sources**: manual upload (tgz) or npm ("Admin → Catalog → Import", or `capybara plugins import <file.tgz | npm:<name>[@<version>]>`); the **official marketplace** (configured under `marketplaces.official.*`; off by default until the official marketplace goes live, then set `marketplaces.official.enabled: true`); **enterprise marketplaces** (added under "Admin → Marketplaces", several allowed, with an optional mirror and token). A marketplace is a static `marketplace.json` (format in `packages/plugin-sdk/schemas/marketplace.v1.schema.json`; one entry per plugin version, with an npm, archive, path or git source; path and git sources are listed but can be imported only once git marketplaces arrive), pulled every `marketplaces.refreshIntervalMinutes` minutes or refreshed manually; its entries are browsed first, and a version is downloaded and built into a catalog item only when you "import" it; when a new version appears you are only notified, and it isn't pulled automatically.
- **Import review**: every plugin goes through one review before anything reaches the catalog: the extension's permissions and migration warnings, each skill's body, each connector template's endpoint and auth, the dependencies and the version each resolves to, the source and license. The staged review stays available for 24 hours at its own link. On confirm the enterprise admin can also install and enable the plugin's extension on the deployment; otherwise the extension is installed later from the item ("Install to deployment"), and until then orgs see the plugin as "not deployed". A dependency not yet in the catalog doesn't block the import, but orgs can't install the plugin until a matching version is imported. A package in the pre-0.1.0 format is refused with a message asking to repack it with `pnpm pack-plugin`.
- **Verification**: downloads are always verified against the integrity in the marketplace (or npm's `dist.integrity` for a direct npm import), and a mismatch is rejected (`marketplace.integrity_mismatch`); the permission summary in the marketplace is used for display only, and the review page warns when it differs from what is computed after download.
- **Network and tokens**: marketplace addresses, mirrors and archive source URLs accept only https (`marketplaces.allowInsecureLoopback` is for tests only), redirects are not followed, and responses have a size limit. An enterprise marketplace's token is sent only to the origin of the marketplace's main address (not when the mirror is on another origin), and archive downloads don't carry it; npm sources are downloaded from `packages.npmRegistry` with `packages.npmToken`. **Don't put tokens in the query of a marketplace URL** (URLs are stored in PG and shown in the admin console); use the marketplace's "Token" field (stored encrypted, sent as `Authorization: Bearer`). The kernel doesn't block https URLs that resolve to internal-network addresses: marketplace and archive addresses are decided by the enterprise admin (and the marketplace author), so add only marketplaces you trust.
- **Offline deployment**: the official marketplace is off by default (`marketplaces.official.enabled` defaults to `false`, the admin console shows offline mode, and the official marketplace is never contacted), so no extra setup is needed; use an enterprise marketplace hosted on the internal network and manual upload instead; npm sources need access to an npm registry, so point `packages.npmRegistry` at an internal mirror (such as Verdaccio or Nexus), and put the private registry's token in `packages.npmToken`.
- **Org install**: an org admin installing a plugin first installs its dependencies that aren't in the org yet (each the highest imported version matching its range), then enables its extension in this org, creates connectors from its templates (filling in credentials) and imports its skills; on failure everything created by this install is undone, dependencies included. Approval follows the plugin being installed (its dependencies aren't approved separately), but a disabled dependency refuses the install. Uninstall removes only components created by this install that aren't in use elsewhere (a dependency goes with the last install that uses it), and the kept ones are listed with reasons. Installs that were interrupted by a replica crash, that have been "installing" for more than `catalog.staleInstallMinutes` (default 30) minutes, and failed installs can all be cleaned up through uninstall. **Org upgrades aren't supported yet**: uninstall first, then install the new version.
- **Extensions enabled directly**: extensions can be installed to the deployment only by the enterprise admin. When an org enables an extension directly ("Settings → Extensions"), the decision is made over all catalog items that brought this extension into the deployment, and **the strictest wins** (any item `disabled` means it can't be enabled, and any `needs_approval` item that this org hasn't been approved for means a request must come first). Extensions not installed through the catalog aren't subject to catalog policy.
