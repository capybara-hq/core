# Connect Slack and Lark (bot, login, directory)

`@capybara-hq/plugin-slack` and `@capybara-hq/plugin-lark` each provide three extension points: an IM bot (`channel@1`: talk to agents in the IM and approve by clicking cards), web login (`identity-source@1`) and directory sync (`directory@1`). All three use the same identity key (`slack:<team id>` / `lark:<tenant_key>` + the platform user id), so one person maps to one account. Both use long connections (Slack Socket Mode, Lark long connection) and **need no public callback address**. Every step on the platform side, the required permissions (scopes) and behavior details are in the extension READMEs; only the order is listed here:

- Slack: [the slack README](https://github.com/capybara-hq/plugins/blob/main/plugins/slack/README.md)
- Lark: [the lark README](https://github.com/capybara-hq/plugins/blob/main/plugins/lark/README.md)

**0. Prerequisite**: configure `http.publicUrl` (the web app's externally reachable origin, as in the OAuth notes of [Tools and connectors](tools-and-connectors.md)). Binding links, the web links in cards and login callbacks are all based on it; when it isn't set, the bot can't recognize unbound people (it only replies "please contact your admin"), approval / question cards degrade to a single line "please handle this on the web", and third-party login is unavailable. Long connections run only on replicas with the `gateway` role (`capybara start` runs all roles by default).

**1. Create the platform app**
- Slack: create the app from a manifest with [`app-manifest.yaml`](https://github.com/capybara-hq/plugins/blob/main/plugins/slack/app-manifest.yaml) (Socket Mode, event subscriptions and bot scopes are all in it), then generate an app-level token `xapp-…` (scope `connections:write`) and install it to the workspace to get `xoxb-…`.
- Lark: create a **custom enterprise app** (long connections support only custom apps), add the bot capability, enable the permissions listed in the README, choose "Use long connection" for both events and callbacks, then publish a version and set its availability scope. **Login, bot and directory must use the same Lark app**: `open_id` is per app, so with a different app the same person no longer matches (the extension checks as best it can and reports an error). Only Lark international (`open.larksuite.com`) is supported for now; the Feishu (`feishu`) region is reserved but not yet available.

**2. Install the extension and approve its permissions**: the super admin installs the extension package of `@capybara-hq/plugin-slack` / `@capybara-hq/plugin-lark` under "Admin → Extensions" (or `pnpm capybara extensions install npm:@capybara-hq/plugin-slack`, during development too). A new extension isn't loaded when it first appears; on the install confirmation page, or with `pnpm capybara extensions review`, check the permissions it asks for (the two extensions declare only `permissions.network`, provide three extension points, and carry deployment-level and org-level config; the channel, login and directory providers are marked sensitive). After approving (in the web app, or `pnpm capybara extensions approve slack` / `approve lark`) and enabling, the replicas load it without a restart. `extensionPermissions.autoApprove` is only for local development and trials.

**3. Enable in the org and create a channel connection** (org admins, web app): "Extensions" enable `slack` / `lark` (you can also fill in the directory's org-level config here, see step 5) → top-level navigation "Channels" → new connection: pick the extension, fill in the bot credentials (Slack `appToken` + `botToken`; Lark `appId` + `appSecret`; all go into the secret store, and the API only returns "set"), then pick the bound agent and how to handle unbound users:
- `bind` (the default): someone unknown who DMs the bot gets a binding card, and confirms the binding after logging in on the web; in a group, they are only told to DM the bot (the binding link is not posted in the group).
- `anonymous`: people in this org's tenant who aren't bound converse as the org's "anonymous guest"; this takes effect only when the bound agent is visible to the whole org, and personal credentials can't be used; people from external tenants can still only bind.

On save, the extension verifies the credentials (`verify`), and then a gateway replica opens the long connection; the connection page shows the status and the latest error (`last_error`). The language of the bot's fixed phrases in IM comes from "Settings → Organization → IM language" (zh / en, default en).

**4. Web login** (super admin, deployment level):
- Register the callback URL `<http.publicUrl>/api/v1/auth/sso/slack/callback` / `.../sso/lark/callback` in the platform app;
- Write the deployment-level config `extensionConfig.slack.clientId` / `clientSecret` and `extensionConfig.lark.appId` / `appSecret` (secret fields are masked in logs);
- Add the extension name to `auth.loginSources` (such as `CAPYBARA_AUTH__LOGIN_SOURCES='["slack","lark"]'`, hot-reloaded), and the login page shows "Sign in with Slack / Lark".

Third-party login only creates accounts and doesn't add anyone to any org (membership comes from invitations or directory sync). To have third-party login merge into an existing local account by **verified email**, put the tenants your enterprise controls into `auth.trustedIdentitySources`; each entry is a full key `<plugin>:<tenant id>` (such as `"slack:T0123ABCD"`; a bare extension name is rejected). List only your own workspaces / tenants, otherwise anyone in that tenant could claim your users' emails. For now only Slack login reports "email verified"; Lark login and both platforms' directories always report unverified, so Lark login never merges accounts.

**5. Directory** (org admins): under "Extensions", in that extension's org-level config, fill in the Slack `teamId` (`T…`) + `botToken`, or the Lark `appId` + `appSecret` (for Lark, also set the directory permission scope to all members). Leaving them empty counts as "not configured": no sync and no error. Once configured, the kernel syncs every hour, and also when the platform pushes a personnel change; "Sync now" on the same page triggers it manually (`POST /api/v1/orgs/:orgId/extensions/:extension/directory/sync`). Sync only adds people (role member) and revokes memberships **that were added by the directory**; people who joined manually / by invitation are never removed by sync.

**Behavior notes**
- **The sessions and tokens revoked on offboarding are account-level**: when the directory decides someone has left, an admin removes them, or they leave an org themselves, all of that person's web sessions and personal tokens are revoked (not only those of that org), and they must log in again (Ruling A8). Their personal connector credentials in that org are also deleted, and their in-progress runs in that org are aborted.
- **Anonymous guests in one group thread share one conversation** (when the connection is `anonymous`): everyone unbound in the thread shares one conversation context, and any of them can give a "this once" approval on that conversation's approval cards (Ruling A16).
- **A local account with no bound external identity gets a second account created by directory sync**: directory sync doesn't merge by email. To avoid this, first have the person DM the bot in IM with their local account to complete binding, or merge by verified email through third-party login under a trusted tenant (currently only Slack login can), and then turn on directory sync (a consequence of Ruling A9).
- **An identity bound through IM can't be used directly for web login**: an identity created by clicking a binding card in IM can only represent the person inside IM; to use it to log in to the web app, first log in to the bound account, and then complete one third-party login of that platform while logged in ("Verify" on that identity under "Settings → IM identities"). Identities created by directory sync are not subject to this (Ruling A18 / A23).
- **Following up in a group thread requires @-mentioning the bot again**: in group chats only messages that @-mention the bot are handled, and replies in a thread without an @ are ignored (D4).
- **Mass-removal protection**: for syncs triggered by the schedule or by personnel changes, when the planned removals exceed `max(5, 20% of existing directory members)`, or when the directory has no active member at all, that round removes nobody and records the audit entry `org.directory.removal_blocked`. When you've confirmed it is a real mass departure, trigger "Sync now" manually; a manual sync isn't subject to this limit. But if another sync round happens to be running during a manual sync, it is instead completed by the catch-up run after that round ends; the catch-up run is handled as a `changed` trigger and is still protected (Ruling A17).
- **Removals are postponed while personnel changes keep coming**: if a personnel change arrives during a sync round, that round only adds people and doesn't remove, leaving removals to the catch-up run that follows (Ruling A32). If changes never stop, removals are postponed indefinitely.
- **Slack Enterprise Grid**: the tenant is the workspace (team), not the enterprise. People from other workspaces of the same enterprise who speak in a shared channel are treated as an external tenant, and can only bind, not be anonymous; the directory syncs only the full members of the workspace given by `teamId`, and guests (single- / multi-channel) are not synced (Ruling A26 / A27 / A29).
- **Other limits**: Sign in with Slack doesn't use PKCE (Slack OIDC doesn't declare it), and Slack users from any workspace can complete login (it only creates an account); Lark login serves only the tenant where the deployment-level login app lives, while orgs in other tenants can still use the bot and bind in IM; Slack sending has no idempotency parameter, so when an over-long reply is split into several messages, a failure midway followed by a retry may duplicate the first parts; replies visible only to yourself (ephemeral) are not supported in IM yet.
- **Still awaiting integration testing on the real platforms** (so far verified only against fake servers): whether a Lark card callback is re-pushed after a failure response like events are (if not, that click is lost and needs another click); Lark card callbacks arriving as event frames, and how multi-select forms and button layouts render in JSON 2.0 cards; the Lark long-connection WSS hostname; the return-code type of the Lark v2 token endpoint and the stability of recursive department pagination when the structure is unchanged; how Slack Socket Mode reconnection and rate limiting behave in a real workspace.

To write channel, login and directory extensions, see [.agents/skills/writing-channels](../../.agents/skills/writing-channels/SKILL.md).
