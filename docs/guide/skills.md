# Skills

Skills are compatible with the Anthropic Agent Skills format: a directory with a `SKILL.md` at its root that has `name` / `description` frontmatter, and it can carry scripts and other files. Metadata is in PG and files are in object storage (so install an object-store extension first).

- **Skill library** ("Skills" in the top bar): an org admin uploads a zip (≤ 50MB, each file ≤ 10MB, total after unzipping ≤ 50MB; `SKILL.md` sits at the root or in the single top-level folder), and uploading the same name again creates a new version; members can browse. When editing an agent, tick the org skills to use in the "Skills" group. The skills of builtin plugins (today `skill-guide` from `skills-core`) need no ticking: every agent has them in its skills list (listed, not pinned; loaded with `Skill` when needed), shown ticked and greyed out with a "Built-in" tag. An agent's own skill of the same name takes their place; an org skill of the same name hides them in the whole org (the org's own skill wins), and the org's pinned copy of one is always included instead.
- **At runtime**: when a conversation starts a run, the kernel writes the list of skills available to that agent (name + description) into the conversation log and tells the model; the model reads the body by name with the builtin tool `Skill`. Skills that carry scripts are copied into the device's `/skills/<name>@<digest>/` (one directory per skill version; read-only, run with `sh` / `python3`), and the agent needs sandbox tools. When skills change, the model gets a reminder at the **start of the next run**.
- **Agents writing their own skills**: there is no dedicated tool. The agent writes a skill directory in its sandbox (a `SKILL.md` with `name` / `description` frontmatter, plus scripts or references), zips it, and calls the Platform operation `agents.register-skill` with `{ filePath }`. Only the agent's owner can register (never from a sub-agent conversation, and not when the Platform tool is off or read-only or no person is present). On a private agent the person confirms a card in the conversation, and the confirmation can be remembered; on a shared agent, or when the agent's `skills.writePolicy` is `ask`, it is confirmed every time. Registering the same name again is a complete new version. The new version applies to every conversation with the agent from its next run, and the agent can use it with `Skill` in the same run. Owners can also upload a zip on the agent page. The builtin skill `skill-guide` (from the builtin `skills-core` plugin in `capybara-hq/plugins`, pinned in `bootstrap.json`) teaches agents the package format; it is in every agent's skills list.
- **No text form**: skills enter only as zip packages. The org "Skills" page has only "Upload skill", `POST /orgs/:orgId/skills` accepts only an upload, and the Platform operation `skills.create` no longer exists.
- **Sharing an agent's skill with the org**: the owner shares it with `agents.share-skill` or the agent page's Share action. Org admins approve in the inbox (it is immediate when the owner is an org admin). A shared skill is an org skill owned by the org, with the owner recorded as its maintainer; the original agent keeps using it. When `customSkills` is `deny`, sharing and new versions of shared skills are refused. When the maintainer's agents register a skill of the same name, an org admin maintainer's version applies at once (confirmed every time, never remembered); another maintainer's becomes a version proposal for the org admins, and only the proposing conversation can try it until it is approved. An agent cannot register a name that belongs to an org skill it uses and does not maintain. Sharing across orgs is unchanged (mark an org skill shareable and use the super admin scope).
