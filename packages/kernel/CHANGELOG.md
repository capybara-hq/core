# @capybara-hq/kernel

## 0.2.0

### Minor Changes

- 9493b97: Add `GET /conversations/groups` (the caller's conversations grouped by agent, per-group and group paging) and an `agentId` filter on `GET /conversations`, for the sidebar.
- 21b1385: Tool presentation for the conversation page: `GET /conversations/:id/tools?keys=…` returns each tool's title, kind (command, read, edit, search, connector, meta, tool), key arguments and source. `title` and `keyArgs` are left out of the tool definition fingerprint, so they never trigger drift review; a connector refresh that changes only them updates the stored definition silently and logs `connector.tool_display_updated`. Remote titles are cleaned of control, bidi and invisible characters (ZWNJ and ZWJ are kept) before they are kept. Builtin tools declare their key arguments.
  
  An extension written without the SDK types that already passed a top-level `title` on a tool gets a new fingerprint for that tool: its remembered grants no longer match and older eval cases report the tool definition as changed.
  
  A NUL byte in a tool result (a file read, command output) no longer fails the run: the event log stores every NUL in a payload as U+FFFD, since PostgreSQL jsonb rejects `\u0000`. Approval denials can carry a reason the model sees ("An approver denied this tool call. Reason: …") (at most 500 characters, no control characters except newline and tab, no format characters except ZWNJ and ZWJ), and `approval_requested.policy` names the rule that asked (`role`, `agent`, `connector`, `fixed`, `org` or `default`).
  
  Conversations are created on first send: `POST /conversations` takes an optional `message` (with a required `clientMessageId`) and writes the conversation and its first message in one transaction; a retry with the same `clientMessageId` returns the same conversation and event (200 instead of 201), and the same id with another agent is 409 `conflict`. `PATCH /conversations/:id` renames (1–120 characters, counted in code points, no control or format characters except ZWNJ and ZWJ) and stops title generation; `ConversationView` gains `titleSource`. Titles are generated by a model after the first completed run through the queue `cap-kernel-titles` and the new kernel model purpose `title` (unmapped → the conversation's current chat model), at most 3 attempts; the call's tokens are a `usage` event with `purpose: "title"` (no run), reported through `usage.report` (an estimate when the call failed after sending). The title model sees only the first message's typed text and the first reply, never `@` resource bodies. Title calls fire the `model.request` and `model.response` hooks with `purpose: "title"`; a policy denial skips the title for good (no retry) and writes one `hook.denied` audit row. The conversation stream sends `event: changed` with `{ "what": "title" }` when the title changes.
  
  Model and effort can be switched mid-conversation: `POST …/messages` and the first message of `POST /conversations` take `model` and `effort`; a change is logged as a `model_switched` event before the message and applies from the next run that starts (`ConversationView.selection`, `event: changed` with `selection`). An unknown model is 400 `agent.model_unavailable`, an effort the model does not declare 400 `validation_failed`. A switched-to model that disappears falls back to the agent's model with a `model_switched` notice (`reason: "unavailable"`). Step and full-run replays use the switched model; a candidate model that replaces it reports the new drift reason `model_switched`.
  
  Queued messages: `GET|POST /conversations/:id/queue`, `PATCH|DELETE …/queue/:itemId`, `POST …/queue/:itemId/send` and `POST …/queue/resume` (owner only). A queued message is kept in PG (`conversation_queue`, at most 20 per conversation, 409 `conversation.queue_full`) and is not in the event log until it is sent: after each run ends the head item goes out as its own `user_message`, one per run, never ahead of an unconsumed message; a run that fails or is stopped pauses the queue until `resume`; "send now" posts an item as an interjection. `@` resources are read with the sender's credentials when the message is queued (a full queue answers 409 before reading them). A queued message goes out only while its author can still use the conversation (active, a member, the agent visible to them); otherwise the queue pauses. Removing a member deletes their queued messages. A queued message can carry `model` and `effort`, checked when queued like a direct send's and written as a `model_switched` before the message when it goes out (`0061_queue_selection`). Every change sends `event: changed` with `{ "what": "queue" }`.
  
  File outputs: `GET /conversations/:id/files?after=&limit=` lists the files the agent delivered, newest first by first delivery (a new version keeps the file's place, so the cursor is stable), grouped by source path into versions (`version`, `versions` newest first, at most 20), with `status: "removed"` when the stored object is gone and `previewable: "image" | "text" | null`. `GET …/files/:fileId/content?limit=` returns the first bytes (at most 1 MiB) of a text file version, with `X-Content-Truncated: true` when cut; every type is served as `text/plain; charset=utf-8` with the stored type in `X-Content-Original-Type`, the response is sandboxed and never sniffed; a removed object is 410 `conversation.artifact_removed`. Delivering a file sends `event: changed` with `{ "what": "files" }`.
  
  File previewers (`file-preview@1`): `GET /conversations/:id/files/:fileId/previewers` lists the extension previewers that take a file in the org's order, `GET …/files/:fileId/previews/:plugin/:previewerId` renders a view previewer (10 s → 504 `ui.timeout`, a throw → 502 `ui.render_failed`, an invalid view → 502 `ui.invalid_view`), and the embed-token route takes `fileId` for a `file-preview` embed (the token is for that one file and conversation). Admins order and disable previewers with `GET|PUT /orgs/:orgId/file-previewers` (`capybara.file_previewers`).
  
  Extension UI places: `GET /orgs/:orgId/ui/contributions` lists the new places `panel`, `section` and `inline` with an `icon` (default `puzzle`); a contribution declared with the old `place: "conversation"` is listed as `place: "panel"` with `legacyPlace: "conversation"`, aliases (`aliasOf`) and `file-preview` embeds are not listed. Section and inline views follow the conversation access rule. `GET …/ui/views/:plugin/:id` takes `item` (passed as `args.item`) and `callId` / `key` (passed as `args.card`); fetching an alias renders the contribution it names. A plugin tool's `ToolResult.card` is recorded as `tool_result.card: { plugin, view, key? }` when it names an inline view of that extension, otherwise dropped with a warning; it is never part of a model request or compaction.
  
  A retry after a failed run can say which message it repeats: `POST …/messages` takes `retryOf` (the seq of that message), recorded on the `user_message` for display only (the web folds it into the failed run's divider).
  
  A denied approval's IM card shows the reason the person gave (redacted like the input), also for a sub-agent's approval once its card is brought up to date.
  
  A sub-agent's conversation is read-only for the new writes too (rename, queued messages, a model switch with a message, extension UI actions: 409 `conversation.read_only`; its extension views still render); its queue and files read through its parent's access. The builtin `agent` tool declares `description` and `subagent_type` as its key arguments. A `general-purpose` sub-agent, and a tier that falls back to the parent's model, use the parent run's model after a model switch (recorded in `subagent_started`).

  imports with files) may now be an enabled, approved install record such as the bootstrap
  object-store-s3, and `capybara extensions list` shows bootstrap plugins with source `bootstrap` and

  The org extensions page shows required plugins as "Required" with a read-only switch.

- 452b6e4: Sub-agents (package ecosystem phase C): agents can dispatch sub-agents with the builtin `agent` tool,
  plugins can ship agent templates, and a conversation's sandbox runs the commands of parallel
  sub-agents concurrently. The Claude Code plugin import also brings in `agents/*.md`, and with
  superpowers' `subagent-driven-development` a small plan runs end to end.
  
  The kernel shares a conversation's sandbox between up to `sandbox.maxConcurrentCommands` holders
  (new, hot, default 6) under shared leases, keeps lifecycle changes exclusive, and kills only a
  crashed holder's commands by their tag.
  
  Rolling upgrade: finish it before anyone uses sub-agents. A replica of an older version re-enqueues
  the sub-agents it resumes (an approval decided there, its sweeps) on the ordinary run queue and runs
  them with the parent's definition and a sandbox of their own, and it resumes parents waiting on
  sub-agents early; the new wait sweep repairs the unpaired `agent` calls this can leave. Older
  replicas also don't read the per-holder sandbox records; new holders
  write the old busy marker (value `v2`) as well, so an older replica that takes a sandbox after a new
  holder crashed still kills the leftover commands. Anything that marker misses runs until the
  in-sandbox time limit (`sandbox.limits.maxCommandSeconds`).
  
  Agent definitions gain an optional `subagents` block (general-purpose, plugin and inline templates,
  allowlisted org agents, `dispatchable`), checked on save (`agent.subagents_invalid`), and the
  kernel declares the model purposes `subagent_fast`, `subagent_standard` and `subagent_capable`.
  
  The builtin tool `agent` (always loaded under `tool_search`, default policy `allow`) lists the
  agent's sub-agent roster in its description, with owner and plugin text made inert (one line per
  entry, `<` / `>` shown as `‹` / `›`).
  
  An `agent` call dispatches its sub-agent as a run of a read-only child conversation (messages to
  it are refused with `conversation.read_only`, 409) on the new queue `cap-kernel-subagent-runs`;
  the parent waits and gets the child's final reply as the tool result. Every dispatch is audited
  `subagent.dispatched`. An empty roster offers no `agent` tool.
  
  The wait sweep repairs sub-agent runs: a child whose enqueue was lost is enqueued again, a running
  child without job or lock fails `run.orphaned`, the children of a finished parent are stopped, and
  a parent whose resume was lost resumes once. A sub-agents wait timeout stops that step's children.
  A child stopped outside its worker reports to its parent at once.
  
  Sub-agent limits per parent run: `subagents.maxConcurrentPerRun` (4), `subagents.maxDispatchesPerRun`
  (50) and `subagents.maxTokensPerRun` (5 000 000), all hot, with per-organization values in the
  deployment setting `subagentLimitOverrides`; calls beyond them are refused with an actionable text,
  and the `agent` tool description shows the organization's concurrency limit. Every child model
  call (compaction included) adds its tokens to the parent run's counter; at the cap a running child
  ends with `run_finished { reason: "budget" }`. A child stopped by its parent's sub-agents wait
  timeout reports `timed out`, and a lost timeout job is recovered by the wait sweep through the new
  `runs.wait_expires_at` (migration 0054). Migration 0055 indexes the parent links, so deleting a
  conversation never scans every child or dispatch row.
  
  Sub-agents' permissions and approvals: a child's policy is the parent agent's current version with
  the frozen template overlay on top; its approvals and questions go to the person who started the
  parent run, appear in the parent conversation as `subagent_waiting` (and as the usual cards in the
  IM thread of a channel conversation, updated once the child is done), and link from the inbox to
  the parent (`ApprovalView.parentConversationId`). "Approve for this conversation" on a child is
  stored on the parent conversation. Hooks fire in sub-agents with `parent` set, `usage.report`
  payloads of a sub-agent carry `parent`, and the parent's `agent` result is audited `tool.called`
  and fires `tool.postExecute`.
  
  Other org agents can be dispatched as sub-agents when the parent's owner allowlists them, they opt
  in with `subagents.dispatchable`, and the person who started the conversation can use them; the
  gates are checked at every dispatch and follow-up (a refusal is audited `subagent.refused`). Such
  a sub-agent runs the agent's version frozen at its first dispatch, with the starter's personal
  credentials, approvals and grants for that agent, and the parent's policies on top of its own.
  
  Stopping a run stops its sub-agents: a parent stopped while it waits gets the stop text in its open
  `agent` calls (audited and passed to `tool.postExecute`), every terminal state of a parent (its
  deadline included) stops its active children, and removing a member stops their sub-agent runs too.
  
  `GET /conversations/:id/subagents` lists a conversation's sub-agents (status, tool calls, usage,
  pending approvals and questions), `GET /conversations/:id/usage` sums a conversation's usage with its
  sub-agents', the conversation view gains `parentConversationId` and `subagentType`, a sub-agent's
  sandbox status is its parent's, a child is opened through its parent conversation, and the parent's
  stream carries an ephemeral `subagent_progress` message after each sub-agent step.
  
  Plugins ship agent templates as `agents/<name>.md` (listed in `plugin.json` `agents` or scanned):
  the packer ships and checks them, the import review lists them (`agentTemplates`, part of
  `reviewHash` when there are any), and an org install creates one org template per plugin and name
  (component `agent_template`, action `agents.manage`). Upgrades add a version to changed templates
  and list them in the diff, rollbacks write the previous definition back, and uninstalling keeps a
  template an agent selects (`used_by_agents`).
  
  Claude Code plugins' `agents/*.md` are imported as agent templates (`<plugin>:<name>`): tools go
  through the Claude tool-name table, model aliases map to tiers, and the report says what was
  dropped or ignored (`agent_imported`, `agent_invalid`, `agent_tools_unmapped`,
  `agent_model_mapped`, `agent_skills_truncated`, `agent_field_ignored`). The Claude Code tool-name
  map now points `Task` / `Agent` at the `agent` tool when the agent has it; conversations get the
  new map with their next skills snapshot. `capybara plugins import` prints agent templates.
  
  Replay and evals cover sub-agents: a parent's full-run replay returns the recorded `agent` results
  and starts no child; a sub-agent's run can be added as an eval case (under the parent's agent, or
  the dispatched org agent), replays from its logged definition and preamble, and reports the new
  drift reason `subagent_changed` when a candidate's effective definition differs; the trajectory
  links each `agent` call to its sub-agent and back.
  
  A translated Claude plugin whose agents all fail translation now imports with `agent_invalid`
