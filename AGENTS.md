# AGENTS.md

Capybara: an open-source enterprise agent platform (TypeScript, pnpm monorepo, Apache-2.0). The kernel only does config, database, extension hosting and HTTP; every capability is provided by an extension.

Terms (renamed 2026-10-24, see `docs/superpowers/specs/2026-10-22-package-ecosystem-design.md` §1): a **plugin** is the install and distribution unit (a bundle of an extension, connector templates and skills; the packages under `plugins/*`, npm `@capybara-hq/plugin-*`); an **extension** is the in-process code inside a plugin (`defineExtension`, `ctx`, the permission manifest, approval); an **extension point** is a versioned contract an extension provides or consumes (`channel@1`); the **catalog** is what a deployment has imported for orgs to install; a **marketplace** is a manifest listing importable plugins; "app" means only an external app calling the kernel over HTTP. Data locations keep their old names (`plugin_<name>` schemas, `plugins/<plugin>/<orgId>/` storage keys, `/plugin-ui`, `/plugins/<name>/…` routes).

## Three layers and dependency direction

Kernel / extensions / external apps. Dependencies only point downward:

- External apps -> the kernel HTTP API; never import kernel internals.
- Extensions -> only `@capybara-hq/plugin-sdk` and third-party npm packages; **never** `@capybara-hq/kernel`.
- Kernel -> implements the interfaces declared in the SDK.

The full package dependency chain (only these directions are allowed):

- `plugins/*` -> `@capybara-hq/plugin-sdk` (tests may also use the devDependencies `@capybara-hq/testing` and `@capybara-hq/plugin-model-fake`, the scripted model provider that drives agent runs in a plugin's kernel-level tests)
- `@capybara-hq/kernel` -> `@capybara-hq/plugin-sdk`
- `@capybara-hq/testing` -> `@capybara-hq/kernel` (`@capybara-hq/plugin-sdk` is a peerDependency; `@capybara-hq/plugin-tools` is an optional peerDependency that `packFixture` imports lazily: a peer, not a devDependency, because plugin-tools depends on the kernel, which tests with testing; the root `package.json` installs it for the workspace)
- `@capybara-hq/plugin-tools` (published) -> `@capybara-hq/plugin-sdk`, `@capybara-hq/kernel` (the package readers and SQL helpers its checks validate with); `@capybara-hq/testing` as a devDependency (tests only: the fake npm registry)
- `@capybara-hq/capybara` (CLI, assembles the core image) -> `@capybara-hq/kernel` only. The plugins `packages/kernel/bootstrap.json` pins (`openai-compatible`, `object-store-s3`) are not dependencies of any package: the kernel image packs them with `packages/plugin-tools` (`pnpm pack-bootstrap`, checked against the pinned sha512) into `/app/bootstrap`, and `capybara bootstrap` (compose init) or a starting kernel installs them as install records with source `bootstrap`
- `@capybara-hq/design` depends on no `@capybara-hq/*`
- `@capybara-hq/web` depends only on `@capybara-hq/design`, never on the kernel or other packages; it talks to the kernel only over HTTP (the "external app" layer)
- `tools/checks` -> `@capybara-hq/kernel` (devDependency: reads the config schema to generate docs, validates extension packages); `tools/checks` -> `@capybara-hq/design` (devDependency, tests only: checks the template list); `tools/checks` -> `@capybara-hq/plugin-tools`, `@capybara-hq/plugin-sdk` (devDependency: the plugin-scoped checks, the source scanner, the packer and the npm fetcher); `tools/checks` -> `@capybara-hq/testing` (devDependency, tests only: the fake npm registry and git server for `check:bootstrap --network`); the kernel's exported `readGitTree` reads the official marketplace for `check:bootstrap --network`
- `@capybara-hq/release` (`tools/release`, private) -> `@capybara-hq/plugin-tools` (devDependency: the semver helpers and the npm lookups of the image plan)
- `@capybara-hq/plugin-sdk` depends on no `@capybara-hq/*` (its public API snapshot `api/plugin-sdk.api.md` is produced by the third-party devDependency `@microsoft/api-extractor`, run by `tools/checks`)
- `@capybara-hq/ci` (`tools/ci`, private) depends on no `@capybara-hq/*` (CI runs it with plain `node`, before `pnpm install`)
- `@capybara-hq/dev` (`tools/dev`, private) -> `@capybara-hq/ci` (`pnpm verify` reuses the CI plan)
- `@capybara-hq/worktree` (`tools/worktree`, private) -> `@capybara-hq/dev` (remote detection)

Kernel, CLI and plugin tests use `@capybara-hq/testing` as a devDependency, in tests only. Core tests load no official plugin except `model-fake` (it stays in core): the kernel side of a contract is tested on the fake extensions of `@capybara-hq/testing` (`packages/testing/fixtures/extensions/*`), and a real plugin's behaviour, including through a real kernel (`startTestKernel`, `createDualReplicaHarness`), is tested in `plugins/<name>/test`, which imports only the SDK, `@capybara-hq/testing`, model-fake and the plugin itself (both enforced by `pnpm check:test-plugins`). Tests outside a plugin that load an official plugin by path (e.g. kernel tests loading `plugins/model-fake/src/index.ts`) do **not** declare it as a devDependency; they list it in `tools/ci/test-plugins.json` instead (enforced by `pnpm check:test-plugins`). A devDependency would make pnpm treat the kernel as depending on the plugin: every plugin change would then pull in everything that depends on the kernel, it would add kernel -> plugin -> testing -> kernel cycles, and apps/web may depend only on design. `pnpm check:deps` only checks the plugin/SDK boundary; dependency direction for the kernel, CLI and web is not checked automatically yet and relies on review.

Package names are always `@capybara-hq/<name>`.

## Multi-replica discipline (production runs multiple replicas)

- `ctx` provides no timers and no in-process shared objects; periodic and delayed work goes through queues.
- Every `ctx.kv` write must have a TTL.
- State whose writer and reader may be in different requests or processes must not live in process memory (no in-process Maps, timers, local events); use Redis / PG.
- BullMQ queue names and job ids must not contain `:`.

## Rules at a glance

- Migrations: plain SQL files named `NNNN_<snake_desc>.sql`; creating or dropping objects must use `IF NOT EXISTS` / `IF EXISTS`; the kernel schema is `capybara`, an extension's is `plugin_<name>` (`-` becomes `_`). See [.agents/skills/writing-migrations](.agents/skills/writing-migrations/SKILL.md).
- Config: env var prefix `CAPYBARA_`, nesting with double underscores (`CAPYBARA_DB__URL` -> `db.url`), env vars win; the source is chosen by `CAPYBARA_CONFIG_SOURCE` (`file` / `nacos`). See [.agents/skills/adding-config](.agents/skills/adding-config/SKILL.md). Extension deployment config can also be stored in PG by an enterprise admin from the admin console (precedence: env > file / Nacos > PG > default; fields present in the startup config are read-only; invalid config = extension pending configuration, never a kernel startup failure); see "two-level config" in [.agents/skills/writing-extensions](.agents/skills/writing-extensions/SKILL.md).
- Language: English is preferred for docs, code comments, identifiers and commit messages; Chinese is not required. Existing Chinese docs are migrated gradually. Code comments and test titles are not bulk-translated. When you touch a file, write new comments in English and translate the comments and test titles you edit. Model-facing text (prompts, tool descriptions, model-visible errors) is always English; UI text goes through i18n (zh and en).
- UI: page = template + design components; apps/web writes no styles (no className / style / .css / color literals). See [.agents/skills/writing-web-ui](.agents/skills/writing-web-ui/SKILL.md); enforced by `pnpm check:web-ui`.
- Extensions: see [.agents/skills/writing-extensions](.agents/skills/writing-extensions/SKILL.md); reference implementation `plugins/example-counter`. An extension ships inside a plugin package, an npm-pack tgz whose `.capybara-plugin/plugin.json` carries the `extension` section (`capybara-plugin pack`, in core `pnpm pack-plugin` / `pack-plugins`; single-file ESM; only the SDK and zod are provided by the host; dynamic imports must be literals); read by `packages/kernel/src/catalog/plugin-package.ts` and `packages/kernel/src/extensions/package.ts`; a tgz in the pre-0.1.0 format is refused (`extension.legacy_format` / `catalog.legacy_format`), never read.
- Kernel HTTP uses NestJS + Fastify: domain classes don't depend on Nest, constructor params use explicit `@Inject`; extensions don't depend on Nest. See [.agents/skills/writing-kernel-api](.agents/skills/writing-kernel-api/SKILL.md).
- Runtime: the conversation event log is the single source of truth; everything the model sees goes into the log (any model request can be reconstructed from the log plus the agent version), and the history sent to the model is append-only. Code lives in `packages/kernel/src/runtime`.
- Model provider extensions (including media blocks image / document: model capability declarations, limits and placeholders are owned by the kernel; extensions never receive `ref`): see [.agents/skills/writing-model-providers](.agents/skills/writing-model-providers/SKILL.md).
- Tools (`ctx.tools`, descriptions and error text, default policy, output archiving, `tool_search`, drift review; the builtin `sandbox_*` tools and the skill tools `skill_load` / `skill_write`; keys contain no dots; `skill_write` always asks on shared agents, private agents don't ask by default and may set `skills.writePolicy: "ask"`; `skill_load` also accepts `<plugin>:<name>`; an agent pins at most 3 skills (`skills.pinned`, SKILL.md total ≤ 32 KB) whose bodies the run start writes into the `skills_catalog` snapshot with the Claude Code tool-name map, and requests render them only from the log): see [.agents/skills/writing-tools](.agents/skills/writing-tools/SKILL.md); reference implementation `plugins/todo`.
- Sandboxes (`sandbox@1`: abort must kill the command; throw `SandboxGoneError` only when certain the sandbox is gone; auto-start stopped instances; commands have a time limit inside the sandbox too; `killAll`; same-name replacement; `/skills` is read-only; `open` egress requires `allowOpenEgress`; locking, suspension and destruction are owned by the kernel `SandboxService`; never publish the socket proxy on a host address): see [.agents/skills/writing-sandbox-providers](.agents/skills/writing-sandbox-providers/SKILL.md); reference implementations `plugins/sandbox-docker`, `plugins/sandbox-e2b`.
- Object storage (`object-store@1` / `ctx.storage`: the key prefixes `plugins/<plugin>/<orgId>/` and `kernel/<orgId>/` are added by the kernel; presigned upload size must be enforced by the store; keys may not contain `${`; using `ctx.storage` requires declaring `permissions.storage`): see [.agents/skills/writing-object-store-providers](.agents/skills/writing-object-store-providers/SKILL.md); reference implementation `plugins/object-store-s3`.
- Connectors (remote service instances, formerly called "apps"; protocols are implemented by **connector extensions** providing `connector@1`, e.g. MCP / OpenAPI; stdio MCP is not supported): see [.agents/skills/writing-connectors](.agents/skills/writing-connectors/SKILL.md); reference implementations `plugins/connector-mcp`, `plugins/connector-openapi`.
- Channels, third-party login, directory sync (`channel@1` / `identity-source@1` / `directory@1`: identity key `<plugin>:<tenant>`, ack only after onEvent resolves, the card spec, no @everyone; inbound is a long connection by default, held only by the `gateway` role, spread across gateway replicas by share (`channels.shareSlack`), with optional webhook inbound (`Channel.webhook`: the extension verifies signatures and answers the challenge, the kernel dedupes, enqueues and acks only after every event is accepted); leader election, sharing and durable queues are owned by the kernel): see [.agents/skills/writing-channels](.agents/skills/writing-channels/SKILL.md); reference implementations `plugins/slack`, `plugins/lark`.
- Extension UI (`ctx.ui`: right-panel tabs on the conversation page and "Extensions" pages; schema-rendered views don't gate loading, embeds require approval and are sensitive, tokens are valid only for their own extension and never for `/api`): see [.agents/skills/writing-extension-ui](.agents/skills/writing-extension-ui/SKILL.md); reference implementations `plugins/todo` (views), `plugins/example-board` (embed).
- Extension hooks (`ctx.hooks`: `model.request` / `model.response` / `tool.preExecute` / `tool.postExecute` / `usage.report`; observe or deny only, never rewrite; registered only during `setup`; declared in `permissions.hooks`, and a `mode: "policy"` hook also in `permissions.policyHooks`, which makes it fail closed on a replica where the extension is not loaded; every denial is logged (`hook.denied` audit row, `hook_denied` event); payloads carry no media bytes; `usage.report` goes through the queue `cap-kernel-usage-report`, at least once, so handlers are idempotent by `eventId`; hooks never fire in eval replays): see "Hooks" in [.agents/skills/writing-extensions](.agents/skills/writing-extensions/SKILL.md).
- SDK public API: `@capybara-hq/plugin-sdk` has a committed API snapshot (`packages/plugin-sdk/api/plugin-sdk.api.md`); changing the public API means regenerating it (`pnpm gen:sdk-api`) and adding a changeset that bumps `@capybara-hq/plugin-sdk` (`check:sdk-api`, `check:sdk-api-changeset`).
- Evals and replay (trajectories, eval sets, step / full-run replay, judge): the event log is the single source of truth; run the zero-drift fixture tests before and after changing request building (`runtime/context/build.ts`, `model-call.ts`); any new model-visible input must go into the log with a matching `DriftReason` (today `system_hash`, `tools_changed`, `tool_spec_missing`, `definition_missing`, `pinned_changed`, `legacy_event`, `params_changed`, `media_missing`, `media_changed`, `tool_unmatched`); full-run replay only uses recorded tool results and never executes tools; evals run on queue `cap-kernel-evals` with per-org concurrency and token caps. See [.agents/skills/replay-evals](.agents/skills/replay-evals/SKILL.md).
- Extension packages and lifecycle: an extension is installed on the deployment from a plugin tgz; install / enable / disable / upgrade / uninstall never restart (desired state in PG + per-replica reconcile, per-instance ledger revocation, optional `dispose` and `ctx.signal`, in-flight calls drained within `extensionHost.drainSeconds`); extension migrations are expand-only; extensions run in-process with full trust, so permission approval is governance, not a sandbox. There are no built-in extensions: the plugins every deployment needs are bootstrap plugins, pinned by version and sha512 in `packages/kernel/bootstrap.json` (`source: "workspace"` until phase A3b, then `source: "npm"`, downloaded and verified at image build time, the only time they need the network), baked into the image and installed offline by `capybara bootstrap` (compose init) or a starting kernel, once per manifest (`bootstrap_runs`, advisory lock); `required` ones are enabled in every org without config rows (`extensions/enabled.ts` is the one enabled-set query) and cannot be disabled or uninstalled (409 `extension.required`); a stale pin fails `pnpm check:bootstrap` (`--write` rewrites it). See [.agents/skills/writing-extensions](.agents/skills/writing-extensions/SKILL.md).
- Catalog and marketplaces: one item kind, the plugin; policy allow / needs approval / disabled; sources = the official marketplace, enterprise marketplaces (http: a `marketplace.json` URL; git: a repository with `.capybara-plugin/marketplace.json`, a Claude Code `.claude-plugin/marketplace.json` or a single-plugin repo; npm, archive, path and git sources all import), npm, a direct git import, manual upload; the JSON Schemas for `plugin.json`, connector template files and `marketplace.json` live in `packages/plugin-sdk/schemas/` (generated by `pnpm gen:package-schemas`, drift-checked by `check:package-schemas`); downloads are always verified against the marketplace's integrity (or npm `dist.integrity` for a direct npm import), never other npm metadata, and git sources are pinned by the commit recorded at import; every download from a marketplace- or admin-supplied URL goes through `packages/kernel/src/net` (https, no redirects, public addresses only except `marketplaces.allowPrivateHosts`, whose IP / CIDR entries match IP-literal URLs only, and the `packages.npmRegistry` origin; connection pinned to the checked address; with `net.httpsProxy` set, https downloads tunnel through the proxy with `CONNECT` and the proxy resolves DNS names, so SSRF protection for names is then the proxy's job, while IP-literal and hostname rules still apply and `net.noProxy` hosts go direct; npm registry downloads don't use the proxy); every import records a content digest, and other content at an imported version becomes `<version>+git.<sha12>` / `+sha256.<12>`; npm provenance is display only.
- Plugins (bundles: `.capybara-plugin/plugin.json` with at most one extension, skills under `skills/`, connector templates as `connectors/<id>.json`, dependencies on other plugins by name + semver range; one import review (prepare -> confirm with `reviewHash`); an org install installs missing dependencies first and refuses a skill name another source already owns (`plugin.skill_conflict`), and only removes, on uninstall, components it created that nothing else uses; org in-place upgrade and rollback (preview -> confirm with `diffHash`; an extension-bearing plugin only to the catalog version carrying the deployment's extension) undoes every step on failure; Claude Code plugins are read from git only (a marketplace entry, a single-plugin repo or a direct git import), translated by allowlist into skills and `connector-mcp` templates with a five-group translation report inside the same review, never with an extension; confirm takes `pinnedSuggestions`): see [.agents/skills/writing-plugins](.agents/skills/writing-plugins/SKILL.md). Plugin authors use `capybara-plugin pack | check | sync-versions | release` (`@capybara-hq/plugin-tools`); the official marketplace is the git repository `https://github.com/capybara-hq/plugins.git`, off by default until phase A3b publishes it.
- **When a rule can be checked automatically, the check is the authority**: `pnpm check` gathers the custom checks; every check has a test where a violating fixture makes it fail. A new check must be proven red first.

## Common commands

```bash
pnpm install
pnpm lint        # biome check
pnpm typecheck   # tsc -b
pnpm test        # vitest run
pnpm exec vitest run <path>   # a single test: run from the repo root (the root config adds the @capybara-hq/source condition dual-replica tests need); don't use pnpm --filter <pkg> exec vitest
pnpm check       # custom checks
pnpm wt:new <branch>   # start a task worktree (see "Branches and worktrees")
pnpm doctor:env  # check your environment (--json for machines; use pnpm -s for clean JSON)
pnpm verify      # run the required checks locally for the current branch (--json, pnpm -s)
docker compose -f docker/compose.dev.yaml up -d   # local postgres + valkey
```

## How work is done

- **Design before code for larger changes.** A new feature, a cross-package change, a new contract or a behavior change starts with a design doc in `docs/superpowers/specs/`, reviewed by a maintainer; then an implementation plan in `docs/superpowers/plans/` (tasks with files, interfaces, tests), also reviewed; then implementation against the plan. Small fixes skip this.
- Changes reach `main` only through pull requests; a maintainer merges.
- The contribution workflow (issues, claiming, PRs, review) is in the `contributing` skill (`.agents/skills/contributing/SKILL.md`) and the [org guide](https://github.com/capybara-hq/.github/blob/main/CONTRIBUTING.md).

## Branches and worktrees

- The Claude session runs in the main checkout, not in a separate window; the main checkout's HEAD stays on `main` so it is always a clean baseline.
- All task work happens in a worktree: `pnpm wt:new <branch> [--from origin/main] [--no-install]` creates `.claude/worktrees/<dir>` (gitignored; checks out the remote branch if it exists, otherwise creates it from `--from` (default `<upstream>/main`: `origin/main` in clones of capybara-hq/core, the upstream remote's main in fork clones) with `--no-track`; runs its own `pnpm install`). Work in that directory (cd into it or use absolute paths); after merge, `pnpm wt:rm <branch>` cleans up (the branch is kept). The branch name must be the first argument.
- `.claude/hooks/branch-safety.sh` (PreToolUse, wired in `.claude/settings.json`) enforces this: no pushes to `main`; no switching the main checkout to `feat/` `fix/` `docs/` `chore/` `test/` `refactor/` branches (worktrees are not restricted).
- Don't run the dev stack in two worktrees at once (`docker/compose.dev.yaml`, the kernel, `pnpm dev:web`): the ports collide; stop one before starting the other.

## CI and checks

- The required statuses are `ci-ok` and `issue-linked`. `ci-ok` aggregates every job in `.github/workflows/ci.yml`, which must all feed into it. `issue-linked` is set by `.github/workflows/community.yml` (the shared gate from `capybara-hq/.github`) and is not part of `ci-ok`.
- **PRs run what the diff affects; pushes to `main` run everything.** Cheap checks or checks that inherently look at the whole repo run in full on PRs too; expensive checks that can be scoped run only when affected. The plan is computed by `tools/ci/src/affected.ts` (rules unit-tested in `tools/ci/test`); keep this list, that file and the comments in `ci.yml` in sync:

  | Job | On PRs | Runs when |
  |---|---|---|
  | `ci`: `pnpm lint`, `pnpm typecheck`, `pnpm check` (all custom checks), plugin packing, commitlint; `pnpm check:bootstrap --network` when the plan's `bootstrap-network` output is true (see below) | full | always |
  | `test` (vitest) | by diff | the changed workspace packages, everything that depends on them (any dependency kind, transitively), every package whose tests load an affected plugin per `tools/ci/test-plugins.json`, and `apps/capybara` when a bootstrap plugin or `packages/plugin-tools` is affected (its tests pack the bootstrap plugins with `pnpm pack-bootstrap` and run `capybara bootstrap` on them); `tools/checks` tests join every run (they read across the repo and take seconds). A plugin change runs that plugin's tests (its kernel-level tests included) and `tools/checks`, not the kernel's; a `model-fake` change also reruns the plugins that devDepend on it; a `packages/testing` change runs everything. Passed to vitest as directory filters; 4 shards when `packages/kernel` is in the set, else 1 |
  | `web` (Next build) | by diff | `apps/web/**`, `packages/design/**` |
  | `visual` | by diff | `apps/web/**`, `packages/design/**` |
  | `e2e` | by diff | anything in the dependency closure of `apps/web`, `apps/capybara` (kernel, plugin-sdk, testing), the plugins `apps/web/e2e` loads (`"apps/web/e2e"` in `test-plugins.json`), the bootstrap plugins (the kernel installs them at start) and `packages/plugin-tools` (the e2e setup packs them with `pnpm pack-bootstrap`) |
  | `docker`: builds the four images for linux/amd64 (loaded, never pushed), then `docker/test/compose-smoke.sh` | by diff (~15 min) | anything in the dependency closure of `apps/capybara` and `apps/web` (kernel, plugin-sdk, design, testing), the bootstrap plugins (the workspace entries of `packages/kernel/bootstrap.json`, read by `affected.ts`: the image packs them) and `plugins/model-fake` / `packages/plugin-tools` (the image packs the bootstrap plugins with it; the smoke test packs and installs model-fake); `docker/**`, the Dockerfiles and `.dockerignore` belong to no package, so they run everything. Layer cache: GitHub Actions cache, written only on `main` |

  - **Run everything** when the diff touches root `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `vitest.config.*`, `tsconfig*.json`, `biome.json`, `.github/**`, `tools/ci/**`, `packages/testing/**`, any file that is neither a doc nor inside a workspace package (e.g. `docker/**`, `tools/fixtures/**`, `commitlint.config.ts`), or when the diff can't be computed.
  - **Docs-only** diffs (`docs/**` except `docs/config.md`, `*.md` outside packages, `.gitignore`, `.agents/**`, `.claude/**` except hooks and `settings.json`) skip test / web / e2e / visual / docker.
  - Files outside packages that tests read are mapped in `EXTRA_INPUTS` in `affected.ts` (`.claude/hooks/**`, `.claude/settings.json` -> `tools/worktree`; `docs/config.md` -> `tools/checks`); add an entry when a new test reads such a file.
  - `check:synced-skills` (full: cheap, part of `pnpm check`): the synced skills under `.agents/skills/` must match the versions and hashes recorded from `capybara-hq/.github`.
  - `check:skills-frontmatter` (full: cheap, part of `pnpm check`; reads the 17 small `SKILL.md` files): the frontmatter (`name`, `description`) of every skill under `.agents/skills/` decides when a skill loads, so it must contain no CJK characters, must be valid YAML (quote a value that contains `: `; strict loaders skip the skill otherwise) and its `description` must be at most 1024 characters (the Agent Skills limit; rule `skills-frontmatter-length`); a `SKILL.md` without frontmatter is also reported. The body is not checked.
  - `check:i18n` (full: cheap, part of `pnpm check`; reads the two message files): the zh and en UI messages have the same keys, and every message parses as ICU MessageFormat the way next-intl reads it (rule `i18n-invalid-message`: an unescaped `<word>` is an unclosed tag; write examples without angle brackets or quote them `'<'x'>'`).
  - `perm-hooks` (full: cheap, part of `pnpm check` via `check:extension-permissions`): an extension that calls `ctx.hooks.on(mount, …)` must list the mount point in `permissions.hooks`, and a `mode: "policy"` registration must also list it in `permissions.policyHooks`; a mount point that is not a literal (or same-file const) is reported as "cannot be confirmed statically".
  - `check:sdk-api` (full: cheap, part of `pnpm check`; ~2 s): emits the plugin SDK's declarations from `src` and runs api-extractor on them; the result must equal the committed `packages/plugin-sdk/api/plugin-sdk.api.md` (regenerate with `pnpm gen:sdk-api`; doc comments and `(undocumented)` markers don't count).
  - `check:sdk-api-changeset` (full on every PR: a cheap diff inspection; skipped on pushes to `main`, where there is no base to compare): a step in the `ci` job, `pnpm check:sdk-api-changeset --base "$(git rev-parse HEAD^1)"`, where `HEAD^1` is the first parent of the PR merge commit the job checks out (the base branch as merged), not `pull_request.base.sha`, which goes stale once `main` moves on. When the diff changes `plugin-sdk.api.md`, a changeset added in the same diff must bump `@capybara-hq/plugin-sdk` in its frontmatter. Skipped when the report does not exist at the base (the PR that introduces it).
  - `check:applied-migrations` (full on every PR: a cheap diff inspection, `git diff --name-status` against the base, no checkout of other commits; skipped on pushes to `main`, where there is no base, and when no `--base` is given): a step in the `ci` job next to `check:sdk-api-changeset`, with the same `--base "$(git rev-parse HEAD^1)"`. Fails when the diff modifies, deletes or renames an existing migration file (`packages/kernel/src/migrations/*.sql`, `plugins/*/migrations/*.sql`; rule `applied-migration-edited`); adding files is fine. The migrator rejects an applied file whose checksum changed, but only on databases that already ran it, so fresh test databases never catch it.
  - `check:test-plugins` (full: cheap): a test outside a plugin that loads an official plugin by path or package name must have it as a dependency of its package or listed under its test root (`<package>/test`, `<package>/e2e`) in `tools/ci/test-plugins.json`, written as a literal path (no interpolated plugin names); stale entries fail too. Rule `test-plugins-official`: a test root outside `plugins/` loads no official plugin except `model-fake`, and the exceptions listed with their reasons in `tools/checks/src/test-plugins.ts` (`tools/checks/test/bootstrap.test.ts`: the `bootstrap.json` workspace entries; `apps/web/e2e/global-setup.ts`: connector-openapi and example-board for `connector-openapi-wizard.spec.ts` and `embed-board.spec.ts` until phase A3b). Rule `plugin-test-imports`: a file under `plugins/<name>/test` imports no `@capybara-hq/*` package other than `plugin-sdk`, `testing`, `plugin-model-fake` and the plugin itself, and has no relative import or path string leaving the plugin directory and no repo-root path into `packages/` or `apps/` (a missing kernel facility is exported by `@capybara-hq/testing`), so the tests keep working once the plugin lives in its own repository.
  - `check:compose-haproxy` (full: cheap, reads three files): the sandbox-proxy haproxy config inlined in `docker/compose.yaml` (`configs.sandbox-proxy-haproxy.content`, so the compose file works on a clean host) must match `docker/sandbox-proxy/haproxy.cfg` line for line, comments and blank lines aside, with every literal `$` written `$$`; and `plugins/sandbox-docker/test/sandbox-proxy/haproxy.cfg`, the copy the plugin's tests start the socket proxy from, must equal that file byte for byte (rule `compose-haproxy-copy`).
  - `check:release-metadata` (full: cheap, reads the workspace `package.json` files): every package that would be published (not `"private": true`) has a `description`, a `license`, an https `homepage` and `repository` `{ type: "git", url: "git+https://github.com/capybara-hq/core.git", directory: <its dir> }` (npm provenance rejects a mismatch), and published packages outside `plugins/` have a `files` allowlist, a `README.md` and, while the repository has a `NOTICE`, an identical copy listed in `files` (`release-readme`, `release-notice`; plugins get `NOTICE` from the packer; the published libraries are `plugin-sdk`, `kernel`, `testing` and `plugin-tools`); `packages/design`, `plugins/example-*`, `apps/*` and `tools/*` must be private; `apps/capybara` (the image tag) and `apps/web` have the same version and are one changesets `fixed` group in `.changeset/config.json`; and the default image tag in `docker/compose.yaml` (`${CAPYBARA_VERSION:-X}`) and `docker/.env.example` equals the `apps/capybara` version (rule `release-image-tag`, `tools/checks/src/image-tag.ts`; `pnpm version-packages` rewrites it).
  - `check:terms` (full: cheap, part of `pnpm check`; a text scan of the tracked files and of untracked files that are not gitignored, under a second): the phase-0a terminology guard (`tools/checks/src/terms.ts`, which lists every old name). The plugin SDK API report declares no `Plugin*` / `Capabilit*` identifier except the names plan 0b removes (`terms-sdk-api`); `ERROR_CODES` has no `directory.*` key (except the directory sync code) or `app.*` key (`terms-error-code`); the config schema has none of the old top-level keys (`terms-config-key`); no kernel route uses an old admin or org path (`terms-route`); the CLI help names no `capybara plugins` (`terms-cli`); and no tracked file uses a code-shaped old name (SDK and kernel identifiers, tables, env vars, config keys, routes, CLI commands, check names, skill folders; `terms-reference`), outside the exemptions listed with their reasons in the check (applied migrations, the rename migrations and their tests, historical plans, the phase-0a plan and the ecosystem spec, synced skills, rename-mapping lines). Frozen names (`plugin_<name>` schemas, `/plugin-ui`, `directory@1`, `skills_catalog`, model `capabilities`, ...) are never matched.
  - `check:bootstrap` (full: a few seconds, part of `pnpm check`; packs two plugins): `packages/kernel/bootstrap.json` (the plugins init installs, SDK `parseBootstrapManifest`, JSON Schema `bootstrap.v1.schema.json`) must parse (`bootstrap-invalid`); every `source: "workspace"` entry's `path` is packed with `packages/plugin-tools` (byte-reproducible) into a temp dir and its version and sha512 must equal the entry's (`bootstrap-stale`, with the expected value; `pnpm check:bootstrap --write` updates them), its plugin name the entry's (`bootstrap-name`), and it must pack (`bootstrap-pack`). Full rather than by diff because a change to a pinned plugin, `packages/plugin-tools` or the lockfile stales the pin without touching the manifest. `source: "npm"` entries need the network and are skipped here.
  - `check:bootstrap --network` (by diff on PRs: only when `packages/kernel/bootstrap.json` changes, plan output `bootstrap-network` of `affected.ts`, a conditional step in the `ci` job; always on `main`; and in `release.yml`'s `publish` job before publishing): the network half, needing GitHub and npm. Each `source: "npm"` entry must be published on the registry (`--registry`, default `CAPYBARA_PACKAGES__NPM_REGISTRY` or the public one) at its version, with the packument's `dist.integrity` and the tarball's sha512 equal to the pin (`bootstrap-npm`: unpublished, tampered, or mislabelled); and `.capybara-plugin/marketplace.json` of the official marketplace at `marketplace.commit` (read with the kernel's git reader; `--marketplace-url` reads a mirror) must list each npm entry under its name at the same version as an npm source of the same package and integrity (`bootstrap-marketplace`). By diff because the pins are the only input of the diff that changes its answer, and it needs the network.
- **npm release** (`.github/workflows/release.yml`, `pnpm release`): never on PRs; runs on push to `main` and on `workflow_dispatch`, in two jobs that share nothing: `version-pr` (push only, changesets/action, no npm token or id-token) opens / updates the "Version Packages" PR, using the optional `RELEASE_PR_TOKEN` so the PR's CI runs; its version command `pnpm version-packages` runs `changeset version`, then `sync:plugin-versions` (`capybara-plugin sync-versions`: copies each plugin's `package.json` version into its `plugin.json` and extension manifest, which the packer requires equal), `sync:image-tag` and `check:bootstrap --write` (the bootstrap pins in `packages/kernel/bootstrap.json` are a release artifact; `tools/release/test/workflow.test.ts` pins this order); `publish` (fresh checkout of `github.sha`, `contents: read` + `id-token`) publishes, on every push (`pnpm release --auto`), the versions of the committed main tree that are not on npm yet (they only change when the reviewed Version Packages PR merges; no per-push bump check, so a cancelled queued run is caught up by the next), refusing while nothing is on npm yet. `tools/release/test/workflow.test.ts` pins this layout. The first release (0.1.0) is published only by a manual `workflow_dispatch`. Publishes the SDK, kernel, testing and plugin-tools, in that order (`pnpm pack` then `npm publish`; `pnpm build` runs first), and every `plugins/*` except `example-*` as its plugin tgz, with `--provenance`, skipping versions already on npm. `pnpm release` is `capybara-plugin release` of `packages/plugin-tools` (the npm half; the plugins repository reuses it), run from source.
- **Image release** (same workflow, jobs `images-plan` -> `images-build` -> `images-publish`, after `publish` succeeds): never on PRs. Pushes `ghcr.io/capybara-hq/capybara-{api,worker,gateway,web}` for linux/amd64 + arm64 (native `ubuntu-24.04` / `ubuntu-24.04-arm` runners, pushed by digest, then joined with `docker buildx imagetools create`), tagged with the `apps/capybara` version plus `latest` (only for a version without a prerelease part and not lower than any stable semver tag already in ghcr.io, so re-running an old release never moves it back; not for an image whose tag lookup was denied after the first release), with provenance (mode=max), SBOM and the `org.opencontainers.image.source` label. `pnpm release:images` (`tools/release/src/images.ts`) plans it: on push nothing until the first npm release exists (the first release, npm and images, is the manual run), then every image whose version tag is missing in ghcr.io (self-healing like npm; a run builds only the `apps/capybara` version of its own commit, so re-running an old failed run rebuilds that version from that commit); a manual run builds the missing tags; a dry run builds all four and pushes nothing. If the first manual run published npm but no digest of some image (its builds all failed), that package doesn't exist yet, ghcr.io answers "denied" and push runs fail until a manual run publishes it; once every package exists, push runs catch up. Uses only `GITHUB_TOKEN` (`packages`). **A change that only affects the images** (Dockerfiles, `.dockerignore`, runtime files baked into an image) **needs a changeset on `@capybara-hq/capybara`**, otherwise no new tag is ever built; `@capybara-hq/web` is in the same `fixed` group, so web changes bump the tag by themselves.
- **Every new check must state whether it runs in full or by diff on PRs**, with the reasoning in the PR description, and update this section and the comments in `ci.yml`; on `main` everything always runs.
- **Flaky tests get fixed, not hidden behind retries.** Reproduce locally first by injecting a delay or adding load (`pnpm exec vitest run --maxWorkers=2`), then decide whether it's a test timing issue (wait for the full convergence condition instead of betting on one moment's state) or a product bug (fix the code and add a test). One "flaky" test once turned out to be a real lost-message bug.
- Visual baselines are generated only in the Playwright Docker image, via the `visual-update` workflow (see [.agents/skills/writing-web-ui](.agents/skills/writing-web-ui/SKILL.md)). The bot's baseline commit does not trigger PR checks; push an empty commit afterwards to rerun CI.

## Live API tests

- Tests that hit real services (model providers, E2B, MCP servers, Slack / Lark) run only when their `CAPYBARA_TEST_*` env vars are set; each skill lists the variables.
- Keep keys in a local env file outside the repo, load it only inside the test command, and never print it, paste it into a chat or commit it.
- Run the live tests after changing request mapping, protocol handling or upgrading a vendor SDK.
- A transient network error (e.g. `ECONNRESET`) is rerun once for that case before it is treated as a bug.
