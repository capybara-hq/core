# AGENTS.md

Capybara: an open-source enterprise agent platform (TypeScript, pnpm monorepo, Apache-2.0). The kernel only does config, database, extension hosting and HTTP; every capability is provided by an extension.

Terms (renamed 2026-10-24, see `docs/superpowers/specs/2026-10-22-package-ecosystem-design.md` §1): a **plugin** is the install and distribution unit (a bundle of an extension, connector templates and skills; the packages under `plugins/*` of `capybara-hq/plugins` and core's `plugins/model-fake`, npm `@capybara-hq/plugin-*`); an **extension** is the in-process code inside a plugin (`defineExtension`, `ctx`, the permission manifest, approval); an **extension point** is a versioned contract an extension provides or consumes (`channel@1`); the **catalog** is what a deployment has imported for orgs to install; a **marketplace** is a manifest listing importable plugins; "app" means only an external app calling the kernel over HTTP. Data locations keep their old names (`plugin_<name>` schemas, `plugins/<plugin>/<orgId>/` storage keys, `/plugin-ui`, `/plugins/<name>/…` routes).

## Three layers and dependency direction

Kernel / extensions / external apps. Dependencies only point downward:

- External apps -> the kernel HTTP API; never import kernel internals.
- Extensions -> only `@capybara-hq/plugin-sdk` and third-party npm packages; **never** `@capybara-hq/kernel`.
- Kernel -> implements the interfaces declared in the SDK. It is a standard Nest application, but Nest stops at the extension boundary: an extension sees only the SDK `ctx`, which the extension host (a provider) builds from injected services.

The full package dependency chain (only these directions are allowed):

- `plugins/model-fake` -> `@capybara-hq/plugin-sdk` (tests may also use the devDependency `@capybara-hq/testing`); the plugins in `capybara-hq/plugins` follow the same rule against the published packages
- `@capybara-hq/kernel` -> `@capybara-hq/plugin-sdk`
- `@capybara-hq/testing` -> `@capybara-hq/kernel` (`@capybara-hq/plugin-sdk` is a peerDependency; `@capybara-hq/plugin-tools` is an optional peerDependency that `packFixture` imports lazily: a peer, not a devDependency, because plugin-tools depends on the kernel, which tests with testing; the root `package.json` installs it for the workspace)
- `@capybara-hq/plugin-tools` (published) -> `@capybara-hq/plugin-sdk`, `@capybara-hq/kernel` (the package readers and SQL helpers its checks validate with); `@capybara-hq/testing` as a devDependency (tests only: the fake npm registry)
- `@capybara-hq/capybara` (CLI, assembles the core image) -> `@capybara-hq/kernel` only. The plugins `packages/kernel/bootstrap.json` pins (`openai-compatible`, `object-store-s3`, npm packages of `capybara-hq/plugins`) are not dependencies of any package: the bootstrap step of `capybara bootstrap` (compose init) or a starting kernel takes each from the offline directory (`bootstrap.dir`, matched by sha512) or downloads it from `packages.npmRegistry` (checked against the pinned sha512), once per manifest, and installs them as install records with source `bootstrap`
- `@capybara-hq/design` depends on no `@capybara-hq/*`
- `@capybara-hq/web` depends only on `@capybara-hq/design`, never on the kernel or other packages; it talks to the kernel only over HTTP (the "external app" layer)
- `tools/checks` -> `@capybara-hq/kernel` (devDependency: reads the config schema to generate docs, validates extension packages); `tools/checks` -> `@capybara-hq/design` (devDependency, tests only: checks the template list); `tools/checks` -> `@capybara-hq/plugin-tools`, `@capybara-hq/plugin-sdk` (devDependency: the plugin-scoped checks, the source scanner, the packer and the npm fetcher); `tools/checks` -> `@capybara-hq/testing` (devDependency, tests only: the fake npm registry and git server for `check:bootstrap --network`); the kernel's exported `readGitTree` reads the official marketplace for `check:bootstrap --network`
- `@capybara-hq/release` (`tools/release`, private) -> `@capybara-hq/plugin-tools` (devDependency: the semver helpers and the npm lookups of the image plan)
- `@capybara-hq/plugin-sdk` depends on no `@capybara-hq/*` (its public API snapshot `api/plugin-sdk.api.md` is produced by the third-party devDependency `@microsoft/api-extractor`, run by `tools/checks`)
- `@capybara-hq/ci` (`tools/ci`, private) depends on no `@capybara-hq/*` (CI runs it with plain `node`, before `pnpm install`)
- `@capybara-hq/dev` (`tools/dev`, private) -> `@capybara-hq/ci` (`pnpm verify` reuses the CI plan)
- `@capybara-hq/worktree` (`tools/worktree`, private) -> `@capybara-hq/dev` (remote detection)

Kernel, CLI and plugin tests use `@capybara-hq/testing` as a devDependency, in tests only. Core tests load no official plugin except `model-fake` (the others live in `capybara-hq/plugins`) and never download published plugins: the kernel side of a contract is tested on the fake extensions of `@capybara-hq/testing` (`packages/testing/fixtures/extensions/*`; the CLI's bootstrap tests pin packed fakes), and a real plugin's behaviour, including through a real kernel (`startTestKernel`, `createDualReplicaHarness`), is tested in its own repository's `plugins/<name>/test`, which imports only the SDK, `@capybara-hq/testing`, model-fake and the plugin itself (`plugin-test-imports` of `capybara-plugin check`; in core it applies to model-fake). Only the web e2e setup and the docker smoke tests download the bootstrap plugins (their kernels' bootstrap step, the way production installs them). Tests outside a plugin that load an official plugin by path (e.g. kernel tests loading `plugins/model-fake/src/index.ts`) do **not** declare it as a devDependency; they list it in `tools/ci/test-plugins.json` instead (enforced by `pnpm check:test-plugins`). A devDependency would make pnpm treat the kernel as depending on the plugin: every plugin change would then pull in everything that depends on the kernel, it would add kernel -> plugin -> testing -> kernel cycles, and apps/web may depend only on design. `pnpm check:deps` only checks the plugin/SDK boundary; dependency direction for the kernel, CLI and web is not checked automatically yet and relies on review.

Package names are always `@capybara-hq/<name>`.

## Multi-replica discipline (production runs multiple replicas)

- `ctx` provides no timers and no in-process shared objects; periodic and delayed work goes through queues.
- Every `ctx.kv` write must have a TTL.
- State whose writer and reader may be in different requests or processes must not live in process memory (no in-process Maps, timers, local events); use Redis / PG.
- BullMQ queue names and job ids must not contain `:`.
- Kernel fixed-period jobs are `@LockedCron` (cron expression) or `@LockedInterval` (a config-driven period, optional `runOnStart`): once per tick across replicas (a per-tick Redis marker plus a renewed run lock; another replica's tick logs INFO), in a fresh async context. They and the kernel's queue consumers (`@Processor`, each job inside `runJob`) are provided only under `WorkerModule` (`kc-worker-only`): an `api`- or `gateway`-only process runs no cron and no BullMQ worker. No tick runs before the worker's start sequence (migrations, bootstrap, extension load, consumers started) opened the schedule gate; an earlier tick is skipped with INFO `cron skipped: the scheduler is not started` (decision R21), and the stop closes the gate first. A periodic job's name enqueued on `cap-kernel-maintenance` runs that job's body once (`ScheduledRuns.runNow`: no tick marker, no run lock; decision R23); a body's `signal` aborts at the stop or when its run lock is lost, but only bodies that read it stop. One-off and delayed work is a BullMQ job with a deterministic id.
- Writes run in `@Transactional()` methods on the injected `KernelDb` (the async context's transaction, else the pool); enqueues, bus publishes and Redis calls happen after the commit (`afterCommit`), never inside the transaction; `afterCommit` hooks run outside any transaction (also those of a `requires_new` nested in an outer one), and outside a transaction `afterCommit` runs the hook at once. Jobs, bus handlers (no transaction, no log context of the subscriber) and timers start a fresh context. `@CacheEvict` evicts after the COMMIT inside a transaction (nothing on rollback); `@Cacheable` is bypassed inside one (no read, no write). Distributed mutual exclusion is `LockService` / `@WithLock` (Redis, renewed every TTL/3; `acquire` / `run` / `hold` / `lease` / `tryShared` / `tryExclusive` throw inside a transaction); a holder whose renewals keep failing gives up at the send time of its last successful renewal + TTL − TTL/3 (decision R19: the run of a lost conversation lease is re-queued, a lost channel lease reconnects) and `LockService` logs one `lock lost: <key>`. `pg_advisory_xact_lock` is transaction semantics (decision R9): only through `XactLock` inside a `@Transactional({ propagation: "mandatory" })` method of one small `*Lock` provider per lock; session-level advisory locks only in the two migration runners.
- A parent never waits in process for its sub-agents: it suspends with a `subagents` wait (PG), children run on the queue `cap-kernel-subagent-runs`, and the last child to finish resumes the parent through `Waits.resume`; the wait sweep repairs lost enqueues, orphaned children, children of finished parents and overdue waits (`runs.wait_expires_at`).
- A conversation's sandbox is shared by its sub-agents under Redis leases (`sandbox/leases.ts`): commands take shared leases (up to `sandbox.maxConcurrentCommands`, `1` = serialized), lifecycle changes the exclusive one, and a takeover kills only a crashed holder's tagged commands.

## Rules at a glance

- Migrations: plain SQL files named `NNNN_<snake_desc>.sql`; creating or dropping objects must use `IF NOT EXISTS` / `IF EXISTS`; the kernel schema is `capybara`, an extension's is `plugin_<name>` (`-` becomes `_`). See [.agents/skills/writing-migrations](.agents/skills/writing-migrations/SKILL.md).
- Config: env var prefix `CAPYBARA_`, nesting with double underscores (`CAPYBARA_DB__URL` -> `db.url`), env vars win; the source is chosen by `CAPYBARA_CONFIG_SOURCE` (`file` / `nacos`). See [.agents/skills/adding-config](.agents/skills/adding-config/SKILL.md). Extension deployment config can also be stored in PG by an enterprise admin from the admin console (precedence: env > file / Nacos > PG > default; fields present in the startup config are read-only; invalid config = extension pending configuration, never a kernel startup failure); see "two-level config" in [.agents/skills/writing-extensions](.agents/skills/writing-extensions/SKILL.md).
- Language: English is preferred for docs, code comments, identifiers and commit messages; Chinese is not required. Existing Chinese docs are migrated gradually. Code comments and test titles are not bulk-translated. When you touch a file, write new comments in English and translate the comments and test titles you edit. Model-facing text (prompts, tool descriptions, model-visible errors) is always English; UI text goes through i18n (zh and en).
- UI: page = template + design components; apps/web writes no styles (no className / style / .css / color literals); no characters as icons (`design-char-icon`). The conversation page (`/chat`, `/chat/<id>`) is the `ConversationPage` template: pages never group tool calls themselves (`apps/web/src/lib/timeline.ts` is the one builder), the right area (properties panel or one right panel) lives in the URL hash, and nothing is created before the first send. See [.agents/skills/writing-web-ui](.agents/skills/writing-web-ui/SKILL.md); enforced by `pnpm check:web-ui`.
- Extensions: see [.agents/skills/writing-extensions](.agents/skills/writing-extensions/SKILL.md); author guide and reference implementation [`example-counter`](https://github.com/capybara-hq/plugins/tree/main/plugins/example-counter) in `capybara-hq/plugins`. An extension ships inside a plugin package, an npm-pack tgz whose `.capybara-plugin/plugin.json` carries the `extension` section (`capybara-plugin pack`, in core `pnpm pack-plugin` / `pack-plugins`; single-file ESM; only the SDK and zod are provided by the host; dynamic imports must be literals); read by `packages/kernel/src/catalog/plugin-package.ts` and `packages/kernel/src/extensions/package.ts`; a tgz in the pre-0.1.0 format is refused (`extension.legacy_format` / `catalog.legacy_format`), never read.
- Kernel: one standard NestJS + Fastify application (spec `docs/superpowers/specs/2026-10-28-nest-kernel-design.md`, status implemented), one convention per concern, enforced by `pnpm check:kernel-conventions`: domain services are `@Injectable` providers, each provided by one module (one instance), every constructor parameter with an explicit `@Inject` (no decorator metadata); no `useFactory` / `useValue` for domain classes, no late-bound closures, no facade; config through `KernelConfigService`; DTOs are `createZodDto` classes with `@ZBody` / `@ZQuery` / `@ZParam` (route parameters too, decision R20); `roles` imports `ApiModule` / `WorkerModule` / `GatewayModule`; `KernelLifecycle` owns the start order and the stop phases, and `listen()` waits for the start. `startKernelApp` installs its own `handleShutdownSignals` instead of `enableShutdownHooks()`: a signal flips readiness to 503 and stops at once (a start in progress aborts), the stop phases and `QueueShutdown` (queues and workers, abandoned when they cannot close, e.g. Redis down) share the 30 s budget before Redis and the pool close, and a second signal exits 1 at once. `KernelAppOptions.overrides` takes only the named seam tokens of `KernelOverride`, for the kernel's own tests (decision R22: not exported, `startTestKernel` takes none). Extensions don't depend on Nest. Decisions made during the implementation are the spec's appendix "Decisions made during implementation" (R1–R26, N1–N10; code and docs cite them as "decision R<n>"). See [.agents/skills/writing-kernel-api](.agents/skills/writing-kernel-api/SKILL.md).
- Runtime: the conversation event log is the single source of truth; everything the model sees goes into the log (any model request can be reconstructed from the log plus the agent version), and the history sent to the model is append-only. A person's skill invocation is logged as its rendered text (`content[0]`) with the non-model-visible `user_message.skill` record; a forked skill's report is the model-visible `skill_fork_result`, rendered in the invocation's user turn unless a model call already sent that turn. Code lives in `packages/kernel/src/runtime`. Queued messages (`POST …/queue`, `capybara.conversation_queue`) are not in the log until sent: one per run, after the turn, as an ordinary `user_message`. A model / effort switch comes with a message and is logged as `model_switched` just before it (not model-visible; replays honor it through `selectionAt`, DriftReason `model_switched`); a run in progress keeps its model. Titles are generated after a completed run on queue `cap-kernel-titles` (model purpose `title`, its own `usage` event, no run, never in replays); a rename always wins; titles reject control, bidi and other format characters (ZWJ / ZWNJ allowed). See [.agents/skills/replay-evals](.agents/skills/replay-evals/SKILL.md).
- Model provider extensions (including media blocks image / document: model capability declarations, limits and placeholders are owned by the kernel; extensions never receive `ref`): see [.agents/skills/writing-model-providers](.agents/skills/writing-model-providers/SKILL.md).
- Tools (`ctx.tools`, descriptions and error text, default policy, output archiving, `tool_search`, drift review; display-only `title` / `keyArgs` (validated by `validateToolPresentation`, excluded from `specHash`, read live by `GET …/conversations/:id/tools`, never sent to the model) and tool kinds; `sandbox_bash` requires a `description` the row shows instead of the command; display-only `tool_result.view` (exit code, diff, read range); the builtin `sandbox_*` tools and the skill tools `skill_load` / `skill_write`; manual-only skills (`disable-model-invocation: true`) never enter the model's catalog or the pinned skills, and `skill_load` is also offered, and loads the recorded version, once a person invoked a skill; keys contain no dots; `skill_write` always asks on shared agents, private agents don't ask by default and may set `skills.writePolicy: "ask"`; `skill_load` also accepts `<plugin>:<name>`; an agent pins at most 3 skills (`skills.pinned`, SKILL.md total ≤ 32 KB) whose bodies the run start writes into the `skills_catalog` snapshot with the Claude Code tool-name map, and requests render them only from the log): see [.agents/skills/writing-tools](.agents/skills/writing-tools/SKILL.md); reference implementation [`todo`](https://github.com/capybara-hq/plugins/tree/main/plugins/todo) in `capybara-hq/plugins`.
- Sub-agents (the builtin `agent` tool; depth 1; children run in read-only child conversations with their definition frozen in `subagent_started`, never get `agent` / `ask_user` / `sandbox_deliver` / `skill_write`, and share the parent conversation's sandbox; per-run limits `subagents.*` with org overrides `subagentLimitOverrides`, the children's tokens count against the parent run; approvals go to the person who started the parent run and show in the parent as `subagent_waiting`; org agents only behind the allowlist, `dispatchable` and visibility gates, checked at every dispatch and follow-up; stopping a parent stops its children; replays never start a child): see "The `agent` builtin tool" in [.agents/skills/writing-tools](.agents/skills/writing-tools/SKILL.md) and "Sub-agents" in [.agents/skills/replay-evals](.agents/skills/replay-evals/SKILL.md); spec `docs/superpowers/specs/2026-10-26-subagents-design.md`.
- Sandboxes (`sandbox@1`: abort must kill the command; throw `SandboxGoneError` only when certain the sandbox is gone; auto-start stopped instances; commands have a time limit inside the sandbox too; `killAll`; providers that declare `concurrentExec` run several holders' commands at once and must implement `killTagged`; same-name replacement; `/skills` is read-only; `open` egress requires `allowOpenEgress`; locking, suspension and destruction are owned by the kernel `SandboxService`; never publish the socket proxy on a host address): see [.agents/skills/writing-sandbox-providers](.agents/skills/writing-sandbox-providers/SKILL.md); reference implementations [`sandbox-docker`](https://github.com/capybara-hq/plugins/tree/main/plugins/sandbox-docker), [`sandbox-e2b`](https://github.com/capybara-hq/plugins/tree/main/plugins/sandbox-e2b) in `capybara-hq/plugins` (core keeps the socket proxy config `docker/sandbox-proxy/haproxy.cfg`, whose copy in the plugin's tests `check:bootstrap --network` compares, and builds the sandbox images in compose from git contexts at `marketplace.commit`).
- Object storage (`object-store@1` / `ctx.storage`: the key prefixes `plugins/<plugin>/<orgId>/` and `kernel/<orgId>/` are added by the kernel; presigned upload size must be enforced by the store; keys may not contain `${`; using `ctx.storage` requires declaring `permissions.storage`): see [.agents/skills/writing-object-store-providers](.agents/skills/writing-object-store-providers/SKILL.md); reference implementation [`object-store-s3`](https://github.com/capybara-hq/plugins/tree/main/plugins/object-store-s3) in `capybara-hq/plugins`.
- Connectors (remote service instances, formerly called "apps"; protocols are implemented by **connector extensions** providing `connector@1`, e.g. MCP / OpenAPI; stdio MCP is not supported): see [.agents/skills/writing-connectors](.agents/skills/writing-connectors/SKILL.md); reference implementations [`connector-mcp`](https://github.com/capybara-hq/plugins/tree/main/plugins/connector-mcp), [`connector-openapi`](https://github.com/capybara-hq/plugins/tree/main/plugins/connector-openapi) in `capybara-hq/plugins`.
- Manual skill invocation (phase D, spec `docs/superpowers/specs/2026-10-27-phase-d-manual-skills-design.md`): a person runs a skill of the conversation's agent with `/name args` (`POST …/messages` / `…/queue` `skill: { name }`, a bare or `<plugin>:<name>`; the `/` menu reads `GET …/agents/:id/invocable-skills`); the kernel resolves it at send time, renders it with the SDK's `renderSkillInvocation` (nothing executed, arguments ≤ 10 000 and the result ≤ 200 000 characters) and refuses with 400 `skill.not_invocable` / `validation_failed` or 503 without writing anything. A `context: fork` skill starts its own run that dispatches a sub-agent before any model call and waits for its report; replay never dispatches. Claude Code commands import as ordinary skills. IM channels post `/name args` (bot mention stripped) as an invocation when it names an invocable skill, else as text; `/new` stays reserved in direct messages. See [.agents/skills/writing-tools](.agents/skills/writing-tools/SKILL.md), [.agents/skills/writing-plugins](.agents/skills/writing-plugins/SKILL.md), [.agents/skills/replay-evals](.agents/skills/replay-evals/SKILL.md) and [.agents/skills/writing-channels](.agents/skills/writing-channels/SKILL.md).
- Channels, third-party login, directory sync (`channel@1` / `identity-source@1` / `directory@1`: identity key `<plugin>:<tenant>`, ack only after onEvent resolves, the card spec, no @everyone; inbound is a long connection by default, held only by the `gateway` role, spread across gateway replicas by share (`channels.shareSlack`), with optional webhook inbound (`Channel.webhook`: the extension verifies signatures and answers the challenge, the kernel dedupes, enqueues and acks only after every event is accepted); leader election, sharing and durable queues are owned by the kernel): see [.agents/skills/writing-channels](.agents/skills/writing-channels/SKILL.md); reference implementations [`slack`](https://github.com/capybara-hq/plugins/tree/main/plugins/slack), [`lark`](https://github.com/capybara-hq/plugins/tree/main/plugins/lark) in `capybara-hq/plugins`.
- Extension UI (`ctx.ui`: on the conversation page the places `panel` (a right panel from a title-bar icon; the old `conversation` means `panel`), `section` (the properties panel) and `inline` (a card under the tool result that names it with `ToolResult.card`), each block failing alone; `place: "page"` for "Extensions" pages; file previewers are the extension point `file-preview@1` (`render` with a one-file read grant, or an embed fed over the bridge; an accepting extension previewer wins over the built-ins); schema-rendered views don't gate loading, embeds require approval and are sensitive, tokens are valid only for their own extension and never for `/api`): see [.agents/skills/writing-extension-ui](.agents/skills/writing-extension-ui/SKILL.md); reference implementations [`todo`](https://github.com/capybara-hq/plugins/tree/main/plugins/todo) (views), [`example-board`](https://github.com/capybara-hq/plugins/tree/main/plugins/example-board) (embed) in `capybara-hq/plugins`.

- Evals and replay (trajectories, eval sets, step / full-run replay, judge): the event log is the single source of truth; run the zero-drift fixture tests before and after changing request building (`runtime/context/build.ts`, `model-call.ts`); any new model-visible input must go into the log with a matching `DriftReason` (today `system_hash`, `tools_changed`, `tool_spec_missing`, `definition_missing`, `pinned_changed`, `legacy_event`, `params_changed`, `media_missing`, `media_changed`, `tool_unmatched`); full-run replay only uses recorded tool results and never executes tools; evals run on queue `cap-kernel-evals` with per-org concurrency and token caps. See [.agents/skills/replay-evals](.agents/skills/replay-evals/SKILL.md).
- Extension packages and lifecycle: an extension is installed on the deployment from a plugin tgz; install / enable / disable / upgrade / uninstall never restart (desired state in PG + per-replica reconcile, per-instance ledger revocation, optional `dispose` and `ctx.signal`, in-flight calls drained within `extensionHost.drainSeconds`); extension migrations are expand-only; extensions run in-process with full trust, so permission approval is governance, not a sandbox. There are no built-in extensions: the plugins every deployment needs are bootstrap plugins, pinned by version and sha512 in `packages/kernel/bootstrap.json` (`source: "npm"` packages of `capybara-hq/plugins`, with `marketplace.commit` the plugins repository commit that lists them; obtained by the bootstrap step of `capybara bootstrap` (compose init) or a starting kernel, `capybara start` always running it: when not done for the manifest (a done run reads nothing and needs no network), inside the Redis lock `lock:bootstrap` (`LockService`, renewed; so `capybara bootstrap` needs Redis) and before writing anything, each entry is a `*.tgz` of the offline directory `bootstrap.dir` (`./bootstrap`, `/app/bootstrap` in the image) whose sha512 equals the pin, else downloaded from `packages.npmRegistry` and verified against the pin only (`bootstrap.missing_file` / `bootstrap.download_failed` / `bootstrap.integrity_mismatch`), once per manifest (`bootstrap_runs`); the image carries no packages; `required` ones are enabled in every org without config rows (`extensions/enabled.ts` is the one enabled-set query) and cannot be disabled or uninstalled (409 `extension.required`); moving a pin is a core PR (version, integrity and `marketplace.commit`, plus the compose build contexts at that commit), checked by `pnpm check:bootstrap --network`. See [.agents/skills/writing-extensions](.agents/skills/writing-extensions/SKILL.md).
- Catalog and marketplaces: one item kind, the plugin; policy allow / needs approval / disabled; sources = the official marketplace, enterprise marketplaces (http: a `marketplace.json` URL; git: a repository with `.capybara-plugin/marketplace.json`, a Claude Code `.claude-plugin/marketplace.json` or a single-plugin repo; npm, archive, path and git sources all import), npm, a direct git import, manual upload; the JSON Schemas for `plugin.json`, connector template files and `marketplace.json` live in `packages/plugin-sdk/schemas/` (generated by `pnpm gen:package-schemas`, drift-checked by `check:package-schemas`); downloads are always verified against the marketplace's integrity (or npm `dist.integrity` for a direct npm import), never other npm metadata, and git sources are pinned by the commit recorded at import; every download from a marketplace- or admin-supplied URL goes through `packages/kernel/src/net` (https, no redirects, public addresses only except `marketplaces.allowPrivateHosts`, whose IP / CIDR entries match IP-literal URLs only, and the `packages.npmRegistry` origin; connection pinned to the checked address; with `net.httpsProxy` set, https downloads tunnel through the proxy with `CONNECT` and the proxy resolves DNS names, so SSRF protection for names is then the proxy's job, while IP-literal and hostname rules still apply and `net.noProxy` hosts go direct; npm registry downloads don't use the proxy); every import records a content digest, and other content at an imported version becomes `<version>+git.<sha12>` / `+sha256.<12>`; npm provenance is display only.
- Plugins (bundles: `.capybara-plugin/plugin.json` with at most one extension, skills under `skills/`, connector templates as `connectors/<id>.json`, agent templates as `agents/<name>.md` (org templates `<plugin>:<name>`; Claude `agents/*.md` are translated), dependencies on other plugins by name + semver range; one import review (prepare -> confirm with `reviewHash`); an org install installs missing dependencies first and refuses a skill name another source already owns (`plugin.skill_conflict`), and only removes, on uninstall, components it created that nothing else uses; org in-place upgrade and rollback (preview -> confirm with `diffHash`; an extension-bearing plugin only to the catalog version carrying the deployment's extension) undoes every step on failure; Claude Code plugins are read from git only (a marketplace entry, a single-plugin repo or a direct git import), translated by allowlist into skills and `connector-mcp` templates with a five-group translation report inside the same review, never with an extension; confirm takes `pinnedSuggestions`): see [.agents/skills/writing-plugins](.agents/skills/writing-plugins/SKILL.md). Plugin authors use `capybara-plugin pack | check | sync-versions | marketplace | release` (`@capybara-hq/plugin-tools`); the official plugins and their author skills live in `capybara-hq/plugins` (core's writing skills cover the kernel side; a contract change needs a PR in core first); the official marketplace is the git repository `https://github.com/capybara-hq/plugins.git`, on by default (`marketplaces.official.enabled`; offline deployments set it to `false`, and every test kernel config, the e2e stack and the docker smoke tests turn it off unless the test is about it, checked by `packages/kernel/test/offline-configs.test.ts`).
- **When a rule can be checked automatically, the check is the authority**: `pnpm check` gathers the custom checks; every check has a test where a violating fixture makes it fail. A new check must be proven red first.

## How work is done

- **Design before code for larger changes.** A new feature, a cross-package change, a new contract or a behavior change starts with a design doc in `docs/superpowers/specs/`, reviewed by a maintainer; then an implementation plan in `docs/superpowers/plans/` (tasks with files, interfaces, tests), also reviewed; then implementation against the plan. Small fixes skip this.
- Changes reach `main` only through pull requests; a maintainer merges.
- The contribution workflow (issues, claiming, PRs, review) is in the `contributing` skill (`.agents/skills/contributing/SKILL.md`) and the [org guide](https://github.com/capybara-hq/.github/blob/main/CONTRIBUTING.md).

## Branches and worktrees

- The Claude session runs in the main checkout, not in a separate window; the main checkout's HEAD stays on `main` so it is always a clean baseline.
- All task work happens in a worktree: `pnpm wt:new <branch> [--from origin/main] [--no-install]` creates `.claude/worktrees/<dir>` (gitignored; checks out the remote branch if it exists, otherwise creates it from `--from` (default `<upstream>/main`: `origin/main` in clones of capybara-hq/core, the upstream remote's main in fork clones) with `--no-track`; runs its own `pnpm install`). Work in that directory (cd into it or use absolute paths); after merge, `pnpm wt:rm <branch>` cleans up (the branch is kept). The branch name must be the first argument.
- `.claude/hooks/branch-safety.sh` (PreToolUse, wired in `.claude/settings.json`) enforces this: no pushes to `main`; no switching the main checkout to `feat/` `fix/` `docs/` `chore/` `test/` `refactor/` branches (worktrees are not restricted).
- Don't run the dev stack in two worktrees at once (`docker/compose.dev.yaml`, the kernel, `pnpm dev:web`): the ports collide; stop one before starting the other.

import, re-export and namespace aliases are resolved, and what cannot be resolved statically (a default export of a module or job, `export * as`, a renamed destructuring of a dynamic import) is reported as unconfirmable). Every rule reads names through one resolver (import, re-export and namespace aliases, same-file aliases, decorators held in variables, string consts, provider lists held in consts, spreads, conditionals and casts); an entry it cannot follow is reported as unconfirmable. Permanent exceptions (`KC_EXCEPTIONS`, `KC_ALLOWED_FACTORY_TOKENS`) carry their reason, and an exception may carry a `what` (the start of the finding's message) to cover one entry only; `KC_PENDING` (paths not converted yet, each with the number of violations it may still hide, `{ path, max }`, a ratchet) is empty since the refactor finished, and new code adds no entry; the mechanism stays: more than `max` fails with the violations listed, fewer fails as "lower max", and an entry or exception with nothing left fails (`kc-stale-pending`, `kc-stale-exception`), so both only shrink. Every rule has a red fixture under `tools/checks/fixtures/kernel-conventions/`.
  - `check:bootstrap` (full: cheap, part of `pnpm check`; reads the manifest and the two compose files): `packages/kernel/bootstrap.json` (the plugins init installs, SDK `parseBootstrapManifest`, JSON Schema `bootstrap.v1.schema.json`) must parse (`bootstrap-invalid`); every remote build context in `docker/compose.yaml` and `docker/compose.dev.yaml` (anything that is not a local path: a URL, `git@…`, `github.com/…`, block or flow form) must be exactly `https://github.com/capybara-hq/plugins.git#<marketplace.commit>:<dir>` (rule `bootstrap-compose-ref`; a fork, another URL form, a branch, `?ref=` or a missing directory fails). `source: "npm"` entries need the network and are left to `--network`. A `source: "workspace"` entry (core has none since the plugins moved out; the format still allows one) is packed with `packages/plugin-tools` and must equal its pin (`bootstrap-stale`, `--write` updates it; `bootstrap-name`, `bootstrap-pack`).
  - `check:bootstrap --network` (by diff on PRs: only when one of its inputs changes: `packages/kernel/bootstrap.json`, the check's own code (`tools/checks/src/bootstrap*.ts`, `tools/checks/src/cli/bootstrap.ts`), the npm fetcher `packages/plugin-tools/src/pack/npm.ts` or the SDK parser `packages/plugin-sdk/src/bootstrap.ts`; `docker/**` (the socket proxy config, the compose files) runs everything anyway; plan output `bootstrap-network` of `affected.ts`, a conditional step in the `ci` job; always on `main`; and in `release.yml`'s `publish` job before publishing): the network half, needing GitHub and npm. Each `source: "npm"` entry must be published on the registry (`--registry`, default `CAPYBARA_PACKAGES__NPM_REGISTRY` or the public one) at its version, with the packument's `dist.integrity` and the tarball's sha512 equal to the pin (`bootstrap-npm`: unpublished, tampered, or mislabelled); and `.capybara-plugin/marketplace.json` of the official marketplace at `marketplace.commit` (read with the kernel's git reader; `--marketplace-url` reads a mirror) must list each npm entry under its name at the same version as an npm source of the same package and integrity (`bootstrap-marketplace`); `marketplace.url` must be the official `https://github.com/capybara-hq/plugins.git` (`bootstrap-marketplace-url`; a mirror is read with `--marketplace-url`, the manifest keeps the official URL); at that commit, `plugins/sandbox-docker/test/sandbox-proxy/haproxy.cfg` (the copy the plugin's tests start the socket proxy from) must equal core's `docker/sandbox-proxy/haproxy.cfg` byte for byte (`bootstrap-haproxy`: change both in step), and every pinned compose build context must have its `Dockerfile` (`bootstrap-compose-ref`). By diff because those files are the only inputs of the diff that change its answer, and it needs the network. Required on a PR that moves a pin. **One `marketplace.commit` pins three things**: the bootstrap entries (listed in that commit's `marketplace.json`), the compose sandbox build contexts, and the plugin's copy of the socket proxy config; moving it moves all three, and the PR must pass `--network`. A change to `docker/sandbox-proxy/haproxy.cfg` alone needs the same file in `capybara-hq/plugins` first (`plugins/sandbox-docker/test/sandbox-proxy/haproxy.cfg`, merged), then a core PR that changes the file and moves `marketplace.commit` (and the compose contexts) to a plugins commit carrying it; the pins may stay at their versions as long as that commit's `marketplace.json` still lists them (it keeps every published version).
- **npm release** (`.github/workflows/release.yml`, `pnpm release`): never on PRs; runs on push to `main` and on `workflow_dispatch`, in two jobs that share nothing: `version-pr` (push only, changesets/action, no npm token or id-token) opens / updates the "Version Packages" PR, using the optional `RELEASE_PR_TOKEN` so the PR's CI runs; its version command `pnpm version-packages` runs `changeset version`, then `sync:plugin-versions` (`capybara-plugin sync-versions`: copies each plugin's `package.json` version into its `plugin.json` and extension manifest, which the packer requires equal), `sync:sdk-version` (`SDK_VERSION` from the SDK's `package.json`, then `gen:sdk-api`), `sync:image-tag` and `check:bootstrap --write` (the bootstrap pins in `packages/kernel/bootstrap.json` are a release artifact; `tools/release/test/workflow.test.ts` pins this order); `publish` (fresh checkout of `github.sha`, `contents: read` + `id-token`) publishes, on every push (`pnpm release --auto`), the versions of the committed main tree that are not on npm yet (they only change when the reviewed Version Packages PR merges; no per-push bump check, so a cancelled queued run is caught up by the next), refusing while nothing is on npm yet, and refusing (publishing nothing) when a package would be promoted from a release candidate (a stable version whose highest npm version is a prerelease of it): the first release and each promotion are manual. While the release is a candidate, changesets run in pre mode with the tag `rc` (`.changeset/pre.json`), so a changeset versions `0.1.0-rc.N` to `-rc.N+1`; promotion is a reviewed PR running `changeset pre exit` and `pnpm version-packages` (see `docs/deploy/release.md`). `tools/release/test/workflow.test.ts` pins this layout. The first release (the release candidate `0.1.0-rc.0`; acceptance, then further rcs and the final 0.1.0 follow as ordinary releases) is published only by a manual `workflow_dispatch`. Publishes the SDK, kernel, testing and plugin-tools, in that order (`pnpm pack` then `npm publish`; `pnpm build` runs first), then `model-fake` as its plugin tgz (the root `release` script passes `--plugins plugins/model-fake`: every other official plugin is published by `capybara-hq/plugins`), with `--provenance`, skipping versions already on npm; a prerelease goes to the dist-tag `next`, a backport to `release-<major>.<minor>`, anything else to `latest` (`distTagFor`). `pnpm release` is `capybara-plugin release` of `packages/plugin-tools` (the npm half; the plugins repository reuses it), run from source.
- **Image release** (same workflow, jobs `images-plan` -> `images-build` -> `images-publish`, after `publish` succeeds): never on PRs. Pushes `ghcr.io/capybara-hq/capybara-{api,worker,gateway,web}` for linux/amd64 + arm64 (native `ubuntu-24.04` / `ubuntu-24.04-arm` runners, pushed by digest, then joined with `docker buildx imagetools create`), tagged with the `apps/capybara` version plus `latest` (only for a version without a prerelease part and not lower than any stable semver tag already in ghcr.io, so re-running an old release never moves it back; not for an image whose tag lookup was denied after the first release), with provenance (mode=max), SBOM and the `org.opencontainers.image.source` label. `pnpm release:images` (`tools/release/src/images.ts`) plans it: nothing at all (a run notice says why; a dry run still builds) while `packages/kernel/bootstrap.json` has a `"source": "workspace"` entry, because a released kernel downloads its bootstrap plugins from npm and could not obtain a workspace entry, or when a stable `apps/capybara` version would pin a prerelease npm package; on push also nothing for a stable version whose highest image tag is a prerelease of it (promotion is manual); on push nothing until the first npm release exists (the first release, npm and images, is the manual run), then every image whose version tag is missing in ghcr.io (self-healing like npm; a run builds only the `apps/capybara` version of its own commit, so re-running an old failed run rebuilds that version from that commit); a manual run builds the missing tags; a dry run builds all four and pushes nothing. If the first manual run published npm but no digest of some image (its builds all failed, or, as in the first rc round, the workspace gate held them back), that package doesn't exist yet, ghcr.io answers "denied" and push runs fail until a manual run publishes it; once every package exists, push runs catch up. Uses only `GITHUB_TOKEN` (`packages`). **A change that only affects the images** (Dockerfiles, `.dockerignore`, runtime files baked into an image) **needs a changeset on `@capybara-hq/capybara`**, otherwise no new tag is ever built; `@capybara-hq/web` is in the same `fixed` group, so web changes bump the tag by themselves.
- **Every new check must state whether it runs in full or by diff on PRs**, with the reasoning in the PR description, and update this section and the comments in `ci.yml`; on `main` everything always runs.
- **Flaky tests get fixed, not hidden behind retries.** Reproduce locally first by injecting a delay or adding load (`pnpm exec vitest run --maxWorkers=2`), then decide whether it's a test timing issue (wait for the full convergence condition instead of betting on one moment's state) or a product bug (fix the code and add a test). One "flaky" test once turned out to be a real lost-message bug.
- Visual baselines are generated only in the Playwright Docker image, via the `visual-update` workflow (see [.agents/skills/writing-web-ui](.agents/skills/writing-web-ui/SKILL.md)). The bot's baseline commit does not trigger PR checks; push an empty commit afterwards to rerun CI.
- The design reference set (`docs/design/reference/*.png` and its review page `index.html`, rendered from `docs/design/reference/src` by `apps/web/reference`) is likewise rendered only by a manual workflow, `reference-update` (`workflow_dispatch` with the branch; never on PRs, not part of `ci-ok`), in the same Playwright image; see `docs/design/reference/README.md`.

## Logs

- Dev logs: `pnpm dev:kernel` and `pnpm dev:web` copy their output to `/tmp/capybara-dev-kernel.log`
  and `/tmp/capybara-dev-web.log` (pretty, one line per record, no colors). When a dev kernel or the
  web app misbehaves, read those first (`tail -n 200`, `grep reqId=<id>`) before guessing.
- The kernel logger is pino (`packages/kernel/src/log.ts`): records are `{ level, time, role, msg,
  ...fields }`, redacted before any output; `log.format` picks pretty or JSON (auto: pretty on a
  TTY), `log.loki.url` also pushes to Loki. Request records carry `reqId` (echoed in
  `x-request-id`), queue jobs `queue` / `jobId` / `runId` (`log-context.ts`); a new `@Processor`
  runs each job in `runJob` (`infra/queue/run-job.ts`: a fresh async context plus `withJobContext`).
- Tracing is OpenTelemetry, on only when `OTEL_EXPORTER_OTLP_ENDPOINT` (or `..._TRACES_ENDPOINT`) is
  set: `apps/capybara/src/main.ts` starts it (`tracing.ts`) for `capybara start` before the kernel
  is imported, and imports no OpenTelemetry module otherwise (`apps/capybara/test/tracing.test.ts`).
  Records logged inside a span carry `traceId` / `spanId`.

## Live API tests

- Tests that hit real services (model providers, E2B, MCP servers, Slack / Lark) run only when their `CAPYBARA_TEST_*` env vars are set; each skill lists the variables.
- Keep keys in a local env file outside the repo, load it only inside the test command, and never print it, paste it into a chat or commit it.
- Run the live tests after changing request mapping, protocol handling or upgrading a vendor SDK.
- A transient network error (e.g. `ECONNRESET`) is rerun once for that case before it is treated as a bug.
