# Custom checks

`pnpm check` runs every custom check; each also runs alone as `pnpm check:<name>`. When a rule can be
checked automatically, the check is the authority, and every check has a test where a violating
fixture makes it fail (a new check is proven red first). Each entry says whether CI runs it in full
or by diff on pull requests ([tools/ci/README.md](../ci/README.md)); on `main` everything runs.
The plugin-scoped checks are `packages/plugin-tools`' (`capybara-plugin check`), run here on core's
scope (`src/cli/dirs.ts`).

- `check:synced-skills` (full: cheap, part of `pnpm check`): the synced skills under `.agents/skills/` must match the versions and hashes recorded from `capybara-hq/.github`.
- `check:skills-frontmatter` (full: cheap, part of `pnpm check`; reads the 18 small `SKILL.md` files): the frontmatter (`name`, `description`) of every skill under `.agents/skills/` decides when a skill loads, so it must contain no CJK characters, must be valid YAML (quote a value that contains `: `; strict loaders skip the skill otherwise) and its `description` must be at most 1024 characters (the Agent Skills limit; rule `skills-frontmatter-length`); a `SKILL.md` without frontmatter is also reported. The body is not checked.
- `check:tokens` (full: cheap, part of `pnpm check`; reads one JSON and three generated files): `packages/design/src/styles/tokens.css`, `packages/design/src/tokens.ts` and the SDK file `packages/plugin-sdk/src/theme-tokens.generated.ts` must equal what `pnpm gen:tokens` renders from `docs/design/tokens.json` (`tokens-stale`); the JSON must be well-formed (`tokens-invalid`); every pair in `contrast` must meet its floor in both themes (`tokens-contrast`; an rgba value is composited over `bg`, or over the surface a pair names as its fourth element); and every `separation` entry `[ground, surface, minDeltaL]` must, composited over its surface, differ from it by at least `minDeltaL` in OKLab lightness ×100 in both themes (`tokens-separation`), with `selected` further from a surface than `hover` on the same surface (`tokens-separation-order`).
- `check:ui-parts` (full on PRs: cheap, part of `pnpm check`; renders the SDK catalog in memory and reads three generated files): `packages/design/src/ui-parts.generated.ts`, `packages/plugin-client/src/ui-parts.generated.ts` and `docs/guide/ui-parts.md` must equal what `pnpm gen:ui-parts` renders from `UI_PARTS` in `@capybara-hq/plugin-sdk` (`ui-parts-stale`). It also parses every `.tsx` under `packages/design/src` and `apps/web/src` (not `dev/`) for the `data-cap-part` JSX attribute: `ui-part-literal` (the value is not a string literal or a conditional of literals), `ui-part-undeclared` (a token that is no catalog part), `ui-part-owner` (a token rendered outside the files of its `owner` list) and `ui-part-unrendered` (a catalog part with no literal in any of its owner files). `owner` is a list because one part can be drawn by several components (`sidebar.item`, `section`, `card`, `input`, `dialog`). Red fixtures in `tools/checks/fixtures/ui-parts/` (`stale`, `unrendered`, `undeclared`, `owner`, `dynamic`, each checked with a small catalog override; `ok` is the green one). Not the plugin-tools rule `ui-part-unknown`.
- `check:ui-slots` (full: cheap, part of `pnpm check`; renders the SDK catalog in memory and reads two generated files): `apps/web/src/lib/ui-slots.generated.ts`, `packages/plugin-client/src/slots.generated.ts` (the slots that accept `component`) and `docs/guide/ui-slots.md` must equal what `pnpm gen:ui-slots` renders from `UI_SLOTS` in `@capybara-hq/plugin-sdk` (`ui-slots-stale`). It also parses every `.tsx` under `apps/web/src` (not `dev/`) for `<ExtensionSlot slot=…>`: `ui-slot-literal` (the `slot` is not a string literal), `ui-slot-undeclared` (a literal that is no catalog id), `ui-slot-unrendered` (a catalog slot nothing renders), `ui-slot-owner` (rendered outside the file its `owner` names) and `ui-slot-twice` (rendered more than once; several `anchor` renders of one list slot count as one). Runs in full on PRs because it is cheap (one SDK file plus a parse of apps/web/src). Red fixtures in `tools/checks/fixtures/ui-slots/` (`unrendered`, `undeclared`, `owner`, `twice`, `dynamic`, each checked with a small catalog override). Not the plugin-tools rule `ui-slot-unknown`.
- `web-ui-extension-slot` (full: cheap, a rule of `check:web-ui`, part of `pnpm check`, same scan as its siblings): a JSX element `ExtensionPanel`, `ExtensionSection`, `ExtensionCard`, `ExtensionViewTab`, `EmbedTab`, `ClientComponentBlock`, `ReplaceableSlot` or `ReplaceableFrame` outside `apps/web/src/components/extension-ui/` (and `dev/`) fails: extension UI is drawn through `<ExtensionSlot>` (UI slots spec §7). A name the file declares itself is a local component, not the block. Red fixtures `extension-slot-outside` and `extension-slot-client` (green `extension-slot-ok`) in `tools/checks/fixtures/web-ui/`.
- `design-char-icon` (full: cheap, a rule of `check:web-ui`, part of `pnpm check`; a text scan of `apps/web/src`, `packages/design/src` and the web message files): a character used as an icon (`▾ ✓ ✕ ⋯ ●`…) in non-test code or a message value fails, naming the `Icon` to use; box-drawing, `⌘`, `↵`, `→`, `·` and `…` are text.
- `web-ui-page-path` (full: cheap, a rule of `check:web-ui`, part of `pnpm check`; parses the `page.tsx` files under `apps/web/src/app/(app)`): the `header` of a design page template (all but `ConversationPage`, `AuthPage`, `OnboardingPage`, `StatusPage`, `TracePage`, `InboxPage`) must be an object literal (inline or a same-file const) with a `path` property, so every page keeps the shared page head with its breadcrumb; a header the rule cannot follow (no literal `path` beside a spread, an imported or called value, a spread element without an explicit `header`) is reported as "cannot be confirmed statically". Red fixtures `page-path-missing` / `page-path-spread` in `tools/checks/fixtures/web-ui/`.
- `web-ssr-loading-file`, `web-ssr-client-page`, `web-ssr-location`, `web-ssr-view-value-import`, `web-ssr-stale-pending` and the changed `web-ui-template` (full: cheap, rules of `check:web-ui`, part of `pnpm check`; text and AST scans of `apps/web/src/app`; spec `docs/superpowers/specs/2026-11-01-web-ssr-design.md` §9): no `loading.tsx`; a `page.tsx` under `(app)` / `(auth)` is a server component (no `"use client"`); no `location.search` / `location.pathname` read during render or in a `useState` initializer; `// ssr-exempt: <reason>` on the line or the line above exempts a location finding (an empty reason fails); a server `page.tsx` imports from `./view` only its default export and types (`web-ssr-view-value-import`: any other value of a `"use client"` module is a client reference on the server); a server page that imports `./view` passes `web-ui-template` when that view uses a page template. `SSR_PENDING` in `tools/checks/src/web-ui.ts` lists the pages not migrated yet (empty since the migration finished; exempt from the `web-ssr-*` rules, a ratchet: an entry whose file no longer violates, or no longer exists, fails as `web-ssr-stale-pending`; new pages are never added).
- `web-query-no-direct-read`, `web-query-keys`, `web-query-freshness`, `web-query-page-read`, `web-query-route-table` and `web-query-stale-pending` (full: cheap, rules of `check:web-ui`, part of `pnpm check`; AST scans of the non-test files of `apps/web/src`, a second or two; spec `docs/superpowers/specs/2026-11-03-web-query-cache-design.md` §8, which replaces the removed `web-ssr-first-paint`): every network read is a `defineQuery` and every write a `useAppMutation` (`lib/query/define.ts`). A `"use client"` file under `app/` and any file under `components/` calls no `src/lib` export that reaches the kernel (a function whose body, or a same-file function it calls, calls `apiFetch`; found by scanning `src/lib`, not `lib/server` or `lib/query`) outside the `fn` of `defineQuery` / `useAppMutation`, and no `useLoad` / `useServerState` / `apiFetch` (pure helpers and the SSE stream opener are fine); an array literal is never a `queryKey` or a `defineQuery` `key` outside `lib/query/keys.ts`; an object literal with `queryKey` / `queryFn` appears only in `lib/query/define.ts` (the filter argument of `invalidateQueries` and the like is exempt, and `useQuery({ ...defined, enabled })` passes); a server `page.tsx` under `(app)` / `(auth)` calls no kernel read, `read` / `section` / `optional` / `workspace` / `admin` or other `lib/server` helper that reads; every such page has an entry in `ROUTES` (`lib/query/routes.ts`, whose `pattern:` literals are parsed statically) and an entry with `none` gives a reason. `// query-exempt: <reason>` on the line or the line above exempts a read finding (an empty reason fails). `QUERY_PENDING` in `tools/checks/src/web-ui.ts` lists the files not converted yet with the migration task that removes each (empty since the migration finished; a ratchet like `SSR_PENDING`: an entry whose file no longer violates, or no longer exists, fails as `web-query-stale-pending`; new files are never added).
- `web-ui-extension-label` (full: cheap, a rule of `check:web-ui`, part of `pnpm check`; a parse of the non-test files of `apps/web/src`, under a second): a template literal that puts a `provider` value before ` / ` (`${x.provider} / ${…}`), or that holds a `provider` value and is the value of a `label` property or JSX `label=` attribute (spaced or not; `value:` and encode helpers stay allowed), outside `apps/web/src/lib/extension-label.ts` fails; a provider label is built by `modelLabel` / `extensionLabel`, which show the extension's display name (the id when it has none). Option values stay `provider/model`.
- `web-ui-form-method` (full: cheap, a rule of `check:web-ui`, part of `pnpm check`; rides on the parse of the non-test files of `apps/web/src` and `packages/design/src` the other rules already do; whole-tree like its siblings, since a component that draws a password input may live in another file): every `<form>` (JSX, or `createElement("form", …)`) says `method="post"` as a literal. When the client JS does not load (a dev origin `next dev` blocks, a script error, JS off) the browser submits natively, and a form without a method is a GET that puts every field, passwords included, in the URL (history, logs, Referer); which component inside a form draws a password input cannot be followed statically, so every form posts. The POST is answered by the proxy (`apps/web/src/lib/form-post.ts`: sign-in and setup server side, a 303 back for other pages). Red fixture `form-method` in `tools/checks/fixtures/web-ui/` (a form without a method, `method="get"`, `createElement("form")` without one, a design form).
- `web-lib-client-hook` (full: cheap, a rule of `check:web-ui`, part of `pnpm check`; reads the import lines of `apps/web/src/lib/**`): a `lib/**` module that imports a `use*` hook must start with `"use client"`, so the modules server layouts and pages import (`lib/query/define.ts`, loaders, the route table) stay hook-free; `next build` rejects a server component reaching a client hook, vitest and tsc do not.
- `web-ui-box-in-box` and `web-ui-box-stale-pending` (full: cheap, rules of `check:web-ui`, part of `pnpm check`; an oxc parse of the non-test `.tsx` files of `apps/web/src`, well under a second; whole-tree because a component's boxes are followed across files and the ratchet needs every entry's file; spec `docs/design/spec.md` §1 principle 7, §9.1): a boxed design component (`Card`, `FormSection`, `LoadingFormSection`, `DangerZone`, `ObjectList`, `LinkCard`, `StatCards`, `InlineCard`, `FilePicker`) drawn inside a box (`Card`, `FormSection`, `Dialog`, `DangerConfirm`, `Sheet`, `Popover`, `AgentMapDialog`, `InlineCard`, `PropertySection`, `Callout`, `DangerZone`, `ObjectList`) fails: directly, in an attribute (`title`, `actions`, a render prop such as a table cell), through an apps/web component whose JSX draws one (same-file components, relative and `@/` imports, re-exports), through a same-function `const` holding JSX (a `.map(...)` result too), a same-file helper returning JSX (`renderCard()`), or a render function a hook returns (`const { editor } = useX(); editor(v)`, the hook in the same file or imported); a local wrapper that draws a prop inside its box (`children`, renamed `{ children: body }`, `props.footer`, or a slot such as `aside`) counts as that box for what is passed there. So does a `DataTable` in a FormSection that is not `flush`, and a `framed` CodeBlock / EmbedFrame / DataTable inside a box. A `Callout` is a box for what it holds but never an inner one: inside a box it draws its warn / fail line by itself (spec §6.19). Portals reset the outer box: an overlay that is a box (`Dialog`, `Sheet`, `Popover`, `AgentMapDialog`) is the box of what it holds, the others (`Menu`, `ConvMenu`, `CommandPalette`, `Tooltip`) start on no box; full-height panes (`RightPanel`, `FilePreviewFrame`, `TranscriptFrame`) hold content like a page. A FilePicker in a Dialog is allowed. `BOX_PENDING` in `tools/checks/src/box-in-box.ts` has been empty since AB wave 2 and new code adds no entry; the mechanism stays, bounded like `KC_PENDING` (`{ path, inner, max }`: more findings than `max` are all reported, fewer fail as "lower max", none or a missing file as stale, `web-ui-box-stale-pending`). Red fixture `box-in-box` in `tools/checks/fixtures/web-ui/` (`boxes.tsx`: direct, components, imports, attributes; `follow.tsx` and `use-editor.tsx`: identifiers, calls, hooks, slots, and the portals that are not reported). Its rendered half is the jsdom guard `findNestedBoxes` (`@capybara-hq/design/reference`: the boxes the design package draws by markup, full-height panes, and the reasoned exceptions: option cards, a FilePicker in a Dialog), which runs by diff with vitest: `packages/design/test/box-in-box.test.tsx` (red fixtures: a Card in a Card, Cards in a form card, a DangerZone in a form card, a forced framed CodeBlock, a FilePicker in a Card; a Callout in a form card draws its line form and nests nothing; every box holding every piece with an unboxed form; the template loading shapes) and `apps/web/test/box-in-box.test.tsx` (every `/dev/ui` route).
- `check:i18n` (full: cheap, part of `pnpm check`; reads the two message files): the zh and en UI messages have the same keys, and every message parses as ICU MessageFormat the way next-intl reads it (rule `i18n-invalid-message`: an unescaped `<word>` is an unclosed tag; write examples without angle brackets or quote them `'<'x'>'`); and a message whose key names a label (the last segment, or the last camelCase word of it, is `title` / `label` / `action` / `confirm` / `cancel` / `submit` / `button` / `name` / `tab` / `heading` / `item` / `menu` / `placeholder`, case-insensitive) does not end with `。` or `.` (rule `i18n-label-period`; full sentences end with a period, labels don't, `docs/design/spec.md` §7 "Copy"); no message contains `...` (rule `i18n-ellipsis`: write the single character `…`); and no zh message has a half-width `?` `!` `:` `;` right after a Chinese character (rule `i18n-cjk-halfwidth`).
- `i18n-zh-enterprise` (full: cheap, a rule of `check:i18n`, part of `pnpm check`; red fixture `tools/checks/fixtures/i18n/zh-enterprise`): no zh message contains 企业 (the deployment layer is 平台, its admin 超级管理员, a non-official marketplace 自定义市场源; spec `2026-11-05-plugin-component-management-design.md` §13.4b, §13.4c).
- `i18n-zh-agent` (full: cheap, a rule of `check:i18n`, part of `pnpm check`; red fixture `tools/checks/fixtures/i18n/zh-agent`): no zh message has the Latin word `agent` / `agents` (case-insensitive, word boundary) in its text: the zh UI says 智能体 (§13.4); argument names and select keys (`{agent}`, `{kind, select, agent {…}}`) are not text, branch bodies are.
- `i18n-design-unreadable` and the two zh word rules on the design system (full: cheap, part of `check:i18n` / `pnpm check`; reads one file; red fixtures `tools/checks/fixtures/i18n/design-zh` and `design-unreadable`): the zh strings of `packages/design/src/i18n.ts` follow `i18n-zh-enterprise` and `i18n-zh-agent` too; every line of its `const zh = { … }` object is one `"key": "text"` entry, and anything else (a concatenation, a template literal, a value over several lines) is `i18n-design-unreadable` (cannot be confirmed statically).
- `i18n-zh-subagent` (full: cheap, a rule of `check:i18n`, part of `pnpm check`; red fixture `tools/checks/fixtures/i18n/source-zh`, plus a test on a zh.json): no zh text has 子代理 (the UI says 子智能体). It applies to every zh source below too.
- `checkSourceZh`, the zh word rules on source (full: cheap, part of `check:i18n` / `pnpm check`; parses the non-test files of `packages/kernel/src` and `packages/plugin-sdk/src` with oxc, so it runs in full: a label added anywhere in the kernel can break it): every `zh:` property whose value is a string or template literal (the `{ zh, en }` labels the web shows directly: model purposes, tool display summaries, channel phrases) follows `i18n-zh-enterprise`, `i18n-zh-agent` and `i18n-zh-subagent`; a template's interpolations are not text, a non-literal value is skipped. Red fixture `tools/checks/fixtures/i18n/source-zh`.
- `perm-hooks` (full: cheap, part of `pnpm check` via `check:extension-permissions`): an extension that calls `ctx.hooks.on(mount, …)` must list the mount point in `permissions.hooks`, and a `mode: "policy"` registration must also list it in `permissions.policyHooks`; a mount point that is not a literal (or same-file const) is reported as "cannot be confirmed statically".
- `check:sdk-api` (full: cheap, part of `pnpm check`; ~2 s): emits the plugin SDK's declarations from `src` and runs api-extractor on them; the result must equal the committed `packages/plugin-sdk/api/plugin-sdk.api.md` (regenerate with `pnpm gen:sdk-api`; doc comments and `(undocumented)` markers don't count).
- `check:plugin-client-api` (full: cheap, part of `pnpm check`; ~2 s): `apps/web/src/lib/client-host/api.generated.ts` (`CLIENT_API_VERSION`, the sorted runtime export list of `@capybara-hq/plugin-client`, the design subset, the component slot ids) must equal what `pnpm gen:plugin-client` renders from the package, and the package's api-extractor report `packages/plugin-client/api/plugin-client.api.md` must equal the committed one (both `plugin-client-api-stale`; `gen:plugin-client` rewrites both; a change to the API also needs a changeset for `@capybara-hq/plugin-client`). The web app never imports the package, so the host module of the import map is built from this copy. Runs in full on PRs because it is cheap.
- `check:sdk-api-changeset` (full on every PR: a cheap diff inspection; skipped on pushes to `main`, where there is no base to compare): a step in the `ci` job, `pnpm check:sdk-api-changeset --base "$(git rev-parse HEAD^1)"`, where `HEAD^1` is the first parent of the PR merge commit the job checks out (the base branch as merged), not `pull_request.base.sha`, which goes stale once `main` moves on. When the diff changes `plugin-sdk.api.md`, a changeset added in the same diff must bump `@capybara-hq/plugin-sdk` in its frontmatter, unless the diff itself changes the SDK's `package.json` version (a version set by hand in a reviewed PR, like the first release `0.1.0-rc.0`, is the bump). Skipped when the report does not exist at the base (the PR that introduces it).
- `check:applied-migrations` (full on every PR: a cheap diff inspection, `git diff --name-status` against the base, no checkout of other commits; skipped on pushes to `main`, where there is no base, and when no `--base` is given): a step in the `ci` job next to `check:sdk-api-changeset`, with the same `--base "$(git rev-parse HEAD^1)"`. Fails when the diff modifies, deletes or renames an existing migration file (`packages/kernel/src/migrations/*.sql`, `plugins/*/migrations/*.sql`; rule `applied-migration-edited`); adding files is fine, and so is deleting a whole plugin (its `.capybara-plugin/plugin.json` deleted or renamed away in the same diff, as when the official plugins moved to `capybara-hq/plugins` with their migrations), while a migration deleted from a plugin that stays is still reported. The migrator rejects an applied file whose checksum changed, but only on databases that already ran it, so fresh test databases never catch it. The same step runs rule `migration-number-behind-base` (by diff, for the same reason: only a base tells which numbers are taken): every migration file the diff adds (also a rename's or copy's destination) must be numbered above the highest `NNNN` of its directory at the base itself (`git ls-tree <base>`, not the merge base, so a number the base released after the branch started counts; a file the base already has under the same name is skipped); it is skipped where the step is (pushes to `main`, no `--base`). Nothing caught the rc2 collision before merge, when a branch's `0063..0068` met main's released `0063` and a shared database ended up numbered differently; run it locally with `--base origin/main`. Both rules are plugin-tools' (`checkAppliedMigrations`, `checkMigrationNumbers`), so `capybara-plugin check --base` runs them on a plugin repository too.
- `migration-duplicate-number` (full: cheap, part of `pnpm check` via `check:migrations`, which already reads every migration directory: the kernel's, `plugins/*/migrations` and the fake extensions' under `packages/testing/fixtures/extensions/*/migrations`): no two files of one directory share a `NNNN` (the second and later files of a number are reported, naming the first). It needs no base: a duplicate is wrong in any tree, including the merge commit a PR is tested as. It is a rule of plugin-tools' `checkMigrations`, red fixture `packages/plugin-tools/fixtures/migrations/duplicate-number`.
- `check:test-plugins` (full: cheap): a test outside a plugin that loads an official plugin by path or package name must have it as a dependency of its package or listed under its test root (`<package>/test`, `<package>/e2e`) in `tools/ci/test-plugins.json`, written as a literal path (no interpolated plugin names); stale entries fail too. Rule `test-plugins-official`: a test root outside `plugins/` loads no official plugin except `model-fake`, plus the exceptions listed with their reasons in `OFFICIAL_EXCEPTIONS` (`tools/checks/src/test-plugins.ts`; empty since the plugins moved to `capybara-hq/plugins`); rule `test-plugins-stale-exception`: an exception whose file is gone or no longer loads one of its plugins fails, so the list only shrinks. Rule `plugin-test-imports` (a plugin-scoped check of `packages/plugin-tools`, `capybara-plugin check`; core runs it in `pnpm check` and `check:test-plugins`; full: cheap, scans the plugin tests): a file under `plugins/<name>/test` imports no `@capybara-hq/*` package other than `plugin-sdk`, `testing`, `plugin-model-fake` and the plugin itself, names no other such package in a string, and has no relative import or path string leaving the plugin directory, no `join` / `resolve` whose bare `..` arguments leave it, and no repo-root path into `packages/` or `apps/` (a missing kernel facility is exported by `@capybara-hq/testing`); `capybara-hq/plugins` runs the same rule on its plugins.
- `plugin-config-ui` and `plugin-config-labels` (plugin-scoped checks of `packages/plugin-tools`, "Config forms" of `capybara-plugin check`; core runs them in `pnpm check` and `check:config-forms` on model-fake and the fake extensions; full: cheap, one bundle and import per plugin with an extension, like "Plugin pack"; red fixtures `packages/plugin-tools/fixtures/plugin-config-ui` and `plugin-config-labels`): the deployment and org config schemas as form JSON Schemas (`configJsonSchema`) must have no `validateConfigUi` problem and no `options` / `presets` on or under a secret (the JSON Schema drops them silently; the packer refuses both, spec `docs/superpowers/specs/2026-11-03-extension-config-forms-design.md` §10); and a published plugin (not `"private": true`) gives every rendered field (every property node, in nested objects, array items and record values) an `x-ui.label` with zh and en, except a secret record named by an `x-ui.secrets[].path` (drawn per item with that hint's label). An error from the start, not a warning.
- `release-display-name` (part of `plugin-release-metadata` of `packages/plugin-tools`, in `pnpm check`; full: cheap, reads each plugin's `plugin.json`; red fixture `packages/plugin-tools/fixtures/release-metadata/violations/plugins/no-display-name`): a published plugin's `.capybara-plugin/plugin.json` has a `displayName` (`{ zh, en }`); private ones (`plugins/example-*`) need none.
